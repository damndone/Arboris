## 2. 暂停：F2 / F3（核心，最高风险）—— 计划与现实不符

### 计划怎么写的（错的）
`docs/v1.5.3-plan.md` §2-F2 说："`useTabs()` 只有一个消费方 `useSelectedNode`，而 `useSelectedNode` 零生产消费方，都是 V1.5.0/1.5.1 死代码，直接删。"

### 真实代码（读出来的，推翻计划）
- `useSelectedNode` **是生产代码**，在 `WorkbenchRouteContainer.tsx:67` 被调用：
  ```
  const { selectedKey, select, tabs, activeTabId, setActiveTab, closeTab, lastEvictedTabId }
    = useSelectedNode(model?.nodes ?? null, model?.runId ?? null);
  ```
- 它内部用 `useTabs()`，而 `useTabs` 有**自己的 `setParams` writer**（`writeUrl`），写 `tabs`/`active`。
- 这个 `useSelectedNode` 调用发生在 `WorkbenchStateProvider`（`WorkbenchRouteContainer.tsx:105` 才 mount）**之外**；LineageContext 的 `{selectedKey, select, tabs...}`（line 106）全部来自 `useSelectedNode`，**不是** Provider。

### 结论：§3-① 是**真实存在的活 bug**，不是理论风险
production 里**确实有两个 URL writer 同时写 `tabs`/`active`**：
1. `useTabs.writeUrl`（经 useSelectedNode，喂 LineageContext）
2. `WorkbenchStateProvider.commit()`（经 dispatch.*）

它们同 tick 触发会互相覆盖。**F2 和 F3 因此是同一次重构**，不是两件事：
> 把选择源（selectedKey/select/tabs/activeTabId/closeTab）从 `useSelectedNode` 搬进 `WorkbenchStateProvider`，让 LineageContext 读 Provider，删掉 `useTabs` + `useSelectedNode`。

### 对接时必须保留的两个行为细节（坑）
1. **auto-select**：`useSelectedNode` 有首屏自动选中逻辑——`nodes` 加载后，若当前无选中，自动 openTab 第一个 `trust==="review"`（其次 `"caution"`）的节点。`useSelectedNode.test.tsx`（15 个测试）覆盖它。重构后必须等价保留。
2. **focus 语义差异**：旧 `useTabs.openTab(key)` 只设 tabs/active，**不碰 focus**；而 Provider 的 `selectByCanvasClick(key)` 在 `!pinned` 时**会顺带设 focus=key**。所以把 auto-select / select() 直接换成 `selectByCanvasClick` 会**改变 focus 行为**。需要确认期望语义：要么接受 focus 跟随，要么给 Provider 加一个"只开 tab 不设 focus"的路径。

### 受影响的测试（blast radius）
mount 容器或直接测这些 hook 的文件：
- `frontend/src/workbench/WorkbenchRouteContainer.test.tsx`（容器集成）
- `frontend/src/lineage/hooks/useSelectedNode.test.tsx`（15，删 hook 后要迁移到容器级或 Provider 级）
- `frontend/src/lineage/hooks/useTabs.test.tsx`（删 hook 后处理）
- `frontend/src/lineage/detail/DetailDrawerTabs.test.tsx`、`DetailDrawer.test.tsx`（只 import `TabState` 类型）
- `frontend/src/workbench/state/tabsSchema.test.ts`、`urlSchema.test.ts`（只 import `TabState` 类型，且注释里提到 useTabs）

### TabState 类型迁移（F2 的子任务）
`TabState` 当前定义在 `lineage/hooks/useTabs.ts`，被 6 处 import。删 useTabs 前，先把 `TabState` 定义搬到 `workbench/state/tabsSchema.ts`（它已是 tab parse/write/reduce 的纯 reducer，是类型的自然归属），再把 6 处 import 重定向：
- `workbench/state/tabsSchema.ts`（自身定义）
- `lineage/LineageContext.tsx`
- `lineage/detail/DetailDrawer.tsx`、`DetailDrawerTabs.tsx`、`DetailDrawerTabs.test.tsx`、`DetailDrawer.test.tsx`
- `workbench/WorkbenchStateProvider.tsx`

### 建议的安全步骤（给对接工程师）
1. 先把 `TabState` 搬到 tabsSchema + 重定向 import（纯类型移动，零行为变化），跑全量绿，单独 commit。
2. 在 Provider 里实现/确认 selected 单一源（F3），并加 lock-in 测试：selectedKey 严格 = active tab 的 nodeKey；无 active 时为 null；focus-only dispatch 不动 selected。
3. 在容器里加一个 bridge：LineageContext 的 `{selectedKey, select, tabs, activeTabId, setActiveTab, closeTab, lastEvictedTabId}` 全部从 `useWorkbench()` 派生；`select(null)` 对齐现有 deselect = closeTab(active) 语义。
4. 把 auto-select 逻辑搬到容器（消费 Provider dispatch），保留 review/caution 首屏选中 + focus 语义决策。
5. 删 `useTabs.ts/.test.tsx` + `useSelectedNode.ts/.test.tsx`，迁移其测试断言。
6. 每步全量 `cd frontend && npx vitest run`，绿了再下一步。F1→F2→F3 顺序里 F1 已完成，可直接做。

## 5. 流程教训（给所有对接者，也是给我自己）

1. **不要过度并行批处理工具调用**：我两次在一个回合里塞了几十个有依赖关系的调用（读→改→测→提交混在一起），结果中间一个失败触发整批 cancellation，造成 commit message 与实际落地不符（F1 的 wiring 和测试都掉了，事后才补）。**改代码—测试—提交要分回合、串行确认。**
2. **commit message 不能 overclaim**：F1 那条 message 写了"524 passed""改了三处 wiring""3 个测试"，但其中两件没真正落地。对接时**以代码和 `git show` 为准，不信 message**。
3. **Read 跨 worktree 副本会失配**：本机有 ~25 个 worktree，路径相似。编辑前确认 Read 的是 `workbench-v1.5.3` 那份。
