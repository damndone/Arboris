# V1.5.3 实施计划 — 地基版（架构硬化，纯前端）

> 状态：草案 / 待审。
> 分支：`workbench-v1.5.3`（基于 `workbench-v1.5.2`，HEAD `3dbaa78`）。
> 隔离：本版所有代码与文档只写入 `.worktrees/workbench-v1.5.3`，不回写 v1.5.2。

---

## 0. 这一版的定位

V1.5.2 把整套工作台的骨架、URL 三层契约、§7 transition 表、三个 Registry、5 级高亮全部立起来了，单元测试 FE 518 / BE 621 全绿。但交接文档列了 6 个**脆弱点**和一批"路线图占位"，其中相当一部分是**状态机没收敛**留下的债：

- `commit()`（Provider 唯一 URL writer）与 `useTabs`（旧 writer）**并存**，同 tick 触发会重演 setParams 覆盖 bug。
- `selectedKey` 有三条派生路径（Provider / useTabs / LineageContext），靠 `LineageContext.Provider` 在中间桥接才"理论上一致"。
- `focusUpstream` action 复用 `selectByCanvasClick`，导致"只设 focus 不动 selected"在语义上**做不到**。
- ⌘K 全局监听不判断焦点是否在输入框，抽屉里打字会被吞。

**结论**：在堆 AI / 可编辑 / 重跑这些重功能之前，必须先把状态机收敛成单一源。V1.5.3 = 一次把这些地基债还清，**零新后端**，为 V1.5.4（AI）/ V1.5.5（编辑+重跑）扫清障碍。

## 2. 逐项实施规格

### F1 — `setFocusOnly` 独立 dispatch

**问题**：`actionRegistry.focusUpstream` 经 GraphView 菜单 wiring 走 `wb.dispatch.selectByCanvasClick(k)`，会同时改 tabs/active/selected。脆弱点 §3-②。

**改动**：
1. `WorkbenchStateProvider.tsx`
   - `WorkbenchDispatch` 新增 `setFocusOnly(nodeKey: string): void`。
   - 实现：`commit({ slice: { ...urlRef.current, focusKey: nodeKey, pinned: false } })` —— **只动 focus/pinned，不碰 tabs、不碰 active**。
   - 加进 `value.dispatch` 与 `useMemo` 依赖数组。
2. GraphView / ContextMenu 菜单 wiring：把 `focusUpstream: (k) => wb.dispatch.selectByCanvasClick(k)` 改为 `focusUpstream: (k) => wb.dispatch.setFocusOnly(k)`。
3. `ActionDispatch.focusUpstream` 的文档注释（`actionRegistry.ts:42-43`）已经写明语义，无需改签名，只改实现。

**§7 transition 表**：新增 1 行
| 触发 | tabs | active | selected | focus | pinned |
|---|---|---|---|---|---|
| `setFocusOnly(k)` | 不变 | 不变 | 不变 | = k | 0 |

**测试**（`WorkbenchStateProvider.test.tsx`）：
- `setFocusOnly` 设置 focus 且 pinned=0；**断言 tabs / activeTabId / selectedKey 不变**（这是和 `selectByCanvasClick` 的关键区别）。
- 已 pinned 时调用 `setFocusOnly` → 覆盖为新 focus、pinned 回 0。
- focusUpstream action 经 `actionsForSurface("graph-context-menu")` invoke 后只改 focus（actionRegistry.test.ts 加断言）。

**验收**：右键"Focus upstream path"后，中间抽屉仍停在原 selected 节点，graph 高亮上游；URL 只多 `?focus=`，`tabs/active` 不变。

### F2 — `useTabs` 退役

**问题**：`useTabs` 仍被 `useSelectedNode` 消费，并自带 `setParams`（`writeUrl`）。它和 Provider 的 `commit` 是两个 URL writer，同 tick 触发会重演覆盖 bug。脆弱点 §3-①。

**前置**：先确认 `useTabs` 的全部消费方（计划执行时用 `grep -rln useTabs frontend/src`，已知至少 `useSelectedNode.ts`）。

**改动**：
1. `useSelectedNode.ts` 改为消费 Provider，而非 `useTabs`：
   - `activeNodeKey` → `useWorkbench().state.selectedKey`
   - `openTab` → `dispatch.selectByCanvasClick`
   - `setActive` → `dispatch.selectByTabSwitch`
   - `closeTab` → `dispatch.closeTab`
   - `lastEvictedTabId` → `state.lastEvictedTabId`
   - 保持 `useSelectedNode` 的**对外签名不变**（它是抽屉/旧测试的稳定接口），内部换源。
2. 删除 `useTabs.ts` 的 `writeUrl` / `setParams` 路径。`useTabs` 已被 `tabsSchema.ts` 的纯 reducer 覆盖（parse/write/reduce 都在那），所以可以：
   - **方案 A（推荐）**：直接删 `useTabs.ts`，把仍依赖它的引用全部迁到 Provider / `tabsSchema`。
   - **方案 B（保守）**：把 `useTabs` 改成 Provider 的薄 shim（内部 `useWorkbench`），保留导出但不再自己写 URL。若有第三方/测试还在 mount 裸 `useTabs`，先用 B 过渡，下一版删。
   - 决策点：取决于 grep 出的消费方数量与旧测试是否裸 mount `useTabs`。计划执行时确认后选 A 或 B，并在 progress 里记原因。
3. `TabState` 类型现在被 `tabsSchema.ts` 从 `useTabs.ts` import（`tabsSchema.ts:19`）。若删 `useTabs.ts`，把 `TabState` 定义迁到 `tabsSchema.ts`，`useTabs`（若保留为 shim）反过来 re-export。

**测试**：
- `useSelectedNode.test.tsx` 改为在 `WorkbenchStateProvider` 下 mount，断言行为等价（open/close/setActive/evict）。
- 删除或迁移 `useTabs.test.tsx`：若走方案 A，其覆盖的语义已由 `tabsSchema.test.ts` + `WorkbenchStateProvider.test.tsx` 覆盖，确认无遗漏后删；若走 B，保留并改为断言 shim 转发。
- **回归重点**：跑全量 FE 测试，确认没有任何测试还依赖 `useTabs` 自己写 URL。

**验收**：全局只剩 `commit()` 一个 URL writer；`grep -rn "setParams" frontend/src/lineage/hooks` 无结果（除非保留 shim 且 shim 不写 URL）。

### F3 — `selectedKey` 单一源

**问题**：GraphView 用 `useLineage().selectedKey`，WorkbenchShell 也用，Provider 又自己派生，三者靠 `LineageContext.Provider` 桥接才一致。脆弱点 §3-④。

**改动**：
1. `LineageContext` 的 `{ selectedKey, select }` 改为**由 Provider 驱动**：
   - 在 `WorkbenchRouteContainer` 里，`LineageContext.Provider` 的 `value.selectedKey` 直接取 `useWorkbench().state.selectedKey`；
   - `value.select` 包装为 `dispatch.selectByCanvasClick`（select(null) 走 `closeTab` 或保持现有 deselect 语义——执行时对齐现有 select(null) 行为）。
2. Provider 成为 selected 的**唯一持有者**；`LineageContext` 退化为"读 Provider 的视图"，自己不再独立派生。
3. GraphView 继续用 `useLineage().selectedKey`（无需改），因为它现在间接读 Provider —— 保持 GraphView 对 `useWorkbenchOptional()` 的软依赖不变（裸测试仍可用 LineageContext 直接喂 selectedKey）。

**测试**：
- `WorkbenchRouteContainer.test.tsx`：点击 canvas → Provider selectedKey 变 → LineageContext.selectedKey 同步变 → 抽屉切换。一条链断言三处一致。
- 保留 GraphView 裸 mount 测试（只有 LineageContext 无 Provider）仍绿——验证软依赖降级。

**验收**：`selectedKey` 只有 Provider 一处真正派生；其余都是读取。

> ⚠️ F2 + F3 是本版风险最高的两项（动核心状态机 + 一堆旧测试）。务必 F1 → F2 → F3 顺序做，每步跑全量测试再进下一步。

### F4 — ⌘K input/textarea focus guard

**问题**：`SearchPalette` 的 `window keydown` 不判断焦点，抽屉里打字按 ⌘K 被吞。脆弱点 §3-⑤。

**改动**（`SearchPalette.tsx:78-93`）：
- 在 `onKey` 里，命中 `k + meta/ctrl` 之前先判断 `document.activeElement`：若是 `INPUT` / `TEXTAREA` / `[contenteditable]` 且 palette 当前未开，则**不**拦截（让浏览器/输入框正常处理）。
- 抽离一个共享工具 `isEditableTarget(el: Element | null): boolean`（放 `workbench/state/` 或新建 `workbench/keyboard.ts`），F6 的全局 dispatcher 复用。
- 例外：palette 已经打开时，⌘K 仍允许 toggle 关闭（此时焦点本就在 palette input，属于预期内）。

**测试**（`SearchPalette.test.tsx`）：
- 焦点在普通页面 → ⌘K 开 palette。
- 焦点在 `<textarea>` → ⌘K **不**开 palette，事件不被 preventDefault。
- palette 已开（焦点在其 input）→ ⌘K 关闭。

**验收**：抽屉里编辑文字时 ⌘K 不再被吞。

### F5 — search cursor 专属高亮（第 6 级）

**问题**：cursor 已进 Tier 3（`state.searchCursor`），但 GraphView 只用 `searchHitKeys` 高亮"所有命中"，cursor 没专属态。路线图。

**改动**：
1. `SearchPalette` 已 `dispatch.setSearchCursor(index)`；但 cursor 是**结果列表下标**，graph 需要的是 nodeKey。需要把"当前 cursor 的 nodeKey"暴露给 graph。两种做法：
   - **方案 A（推荐）**：新增 Tier 3 字段 `searchCursorKey: string | null`，SearchPalette 在 cursor 变化时 `dispatch.setSearchCursorKey(results[cursor]?.nodeKey ?? null)`。graph 直接消费 nodeKey，无需知道列表语义。
   - 方案 B：保留 index，graph 自己重建 searchIndex 再按 index 取——耦合且重复计算，不推荐。
2. `GraphView.tsx`：把 `searchCursorKey` 透给 `GraphCanvas`，作为第 6 级高亮（优先级最高，盖过普通命中）。高亮层级更新为：`selected > focus > focus-upstream > search-cursor > search-hit(related) > dim`。
3. `GraphCanvas` 增加 `searchCursorKey?: string` prop 与对应样式 token。

**测试**：
- `SearchPalette.test.tsx`：↑/↓ 改 cursor → 派发的 cursorKey 跟随。
- GraphView/GraphCanvas 测试：传入 searchCursorKey → 该节点拿到 cursor 高亮 class，其余命中拿普通 hit class。

**验收**：⌘K 输入后用 ↑/↓ 在结果间移动，graph 上"当前项"有区别于其他命中的高亮。

### F6 — shortcut 全局 dispatcher

**问题**：`actionRegistry` 的 `shortcut` 字段只显示不触发。路线图。

**改动**：
1. 新建 `workbench/keyboard.ts`（或 `useGlobalShortcuts.ts` hook）：
   - 解析 `actionRegistry` 中带 `shortcut` 且 surface 含 `"shortcut"` 的条目，建 `shortcut → actionId` 映射。
   - 全局 `window keydown`，复用 F4 的 `isEditableTarget` guard（输入框内不触发）。
   - 命中后用**当前 selected 节点**构造 `ActionContext` 并 invoke；若 action `disabled` 则不触发（disabled action 此版仍占位，所以实际可触发的是 read-only 那批）。
2. 把 dispatcher 挂在 `WorkbenchRouteContainer`（与 SearchPalette 同层）。
3. 给现有 read-only action 补 `shortcut` 字段（如 `openDetail`、`pinTab`、`copyNodeId`）——具体快捷键执行时与现有 ⌘J / ⌘K 不冲突，列一张表评审。

**注意**：`shortcut` 字段需把"显示用字符串"和"匹配用键组合"对齐。若现字段是显示文案（如 `"⌘P"`），需定义解析规则或增加结构化字段 `keys: { key, meta?, ctrl?, shift? }`。决策点：执行时定字段形状，写进 registryTypes。

**测试**：
- dispatcher 单测：按下注册的组合 → 对应 action invoke（mock dispatch）。
- 输入框内按下 → 不触发（共用 F4 guard）。
- disabled action 的快捷键 → 不触发。

**验收**：至少一个 read-only action（如 pin tab）可由键盘触发；输入框内安全。

### F7 — Command Palette 组件

**问题**：`ActionSurface` 已留 `"command-palette"`，但无组件。路线图。

**改动**：
1. 新建 `workbench/CommandPalette.tsx`，结构复用 SearchPalette 的 portal + ↑/↓ + Enter 模式，但**列的是 action 而非节点**：
   - 数据源 = `actionsForSurface("command-palette", ctx)`（ctx 用当前 selected 节点）。
   - disabled action 灰显且带 reason tooltip，不可 invoke。
2. 触发键：与 ⌘K 区分（如 ⌘⇧P）；复用 F4 guard。
3. 给应出现在命令面板的 action 在 `surfaces` 里加 `"command-palette"`。

**测试**（`CommandPalette.test.tsx`）：
- 打开 → 列出 command-palette surface 的 action。
- Enter 选中 read-only action → invoke。
- disabled action 灰显且不可触发。

**验收**：⌘⇧P 打开命令面板，可执行 read-only action。

> F7 体量可裁剪：若本版时间紧，F7 可降级为"留 surface + 最小可用面板"，把丰富度推到 V1.5.4。F6 是 F7 的前置（共享 ctx 构造 + guard）。

### F8 — legacy-hint key 命名空间统一

**问题**：sessionStorage 有 `lineage:`（V1.5.0）和 `workbench:`（V1.5.2）双前缀，切版本留遗留 key。脆弱点 §3-③。

**改动**：
1. 统一前缀为 `workbench:`（codebase 已全量用 workbench 命名）。
2. `GraphView.tsx:60` 的 `lineage:legacy-hint-dismissed:${runId}` → `workbench:legacy-hint-dismissed:${runId}`。
3. 加一次性迁移读取：读新 key；若不存在但旧 `lineage:` key 存在，迁移其值并删旧 key（避免用户已 dismiss 的提示重新冒出来）。
4. 审计其余 sessionStorage key（Tier 2 的 viewport/expandedGroups/splitter/layout 在 `useSessionByRunId`），统一确认前缀一致。

**测试**：
- 旧 `lineage:` key 存在 → 迁移后新 key 有值、旧 key 删除、提示保持 dismissed。
- 无旧 key → 走默认。

**验收**：`grep -rn "lineage:" frontend/src` 在 sessionStorage key 上无残留。

## 3. 执行顺序（建议）

按"先低风险隔离项暖身 → 再啃核心状态机 → 最后交互增强"：

1. **F9 venv** —— 先把测试环境立干净（否则后面跑 BE 测试都不可信）。
2. **F8 key 统一** —— 独立小改，暖身，验证 worktree + 测试链路通。
3. **F4 ⌘K guard** —— 独立，且产出 `isEditableTarget` 给 F6 复用。
4. **F1 setFocusOnly** —— 状态机加法，纯增量、低回归。
5. **F2 useTabs 退役** —— 高风险，动核心 + 旧测试。做完跑全量。
6. **F3 selectedKey 单一源** —— 紧接 F2，收敛派生。做完跑全量。
7. **F5 cursor 高亮** —— 交互增强，依赖 graph 高亮层。
8. **F6 shortcut dispatcher** —— 复用 F4 guard。
9. **F7 Command Palette** —— 依赖 F6；可按时间裁剪。

每个 phase 遵循记忆里的三级评审：Implementer → Test & QA → Reviewer，然后 commit；commit 后立即 push 分支。
