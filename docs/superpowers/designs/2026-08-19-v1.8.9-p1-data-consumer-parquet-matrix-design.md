# Design: Truthful Parquet Engine Admission

## Evidence and root cause

At baseline `ace99dcc4d6e16c1cd790297d0de581b8c3ebe81`, a controlled probe
simulating fastparquet-only reported:

```text
_parquet_engine() -> fastparquet
interchange_capability("parquet") -> available
read_frame_bounded(...) -> optional_dependency: pyarrow is required for bounded Parquet ingestion.
```

The mismatch is in the engine-admission boundary, not in the typed error
itself: `data_interchange.py` admits two pandas Parquet engines, but
`ingestion.py` directly imports the pyarrow batch API. The current environment
has `pyarrow=True`, `fastparquet=False`, `pyreadstat=False`, and
`openpyxl=True`; no dependency will be installed for this remediation.

## Decision

Use a conservative single-engine admission contract. `_parquet_engine()` will
admit `pyarrow` only, because the existing bounded reader's safety contract is
implemented and locally verifiable with pyarrow's batch iterator. A
fastparquet-only bounded adapter cannot be verified in this environment and
would need an explicit implementation and tests for row-cap sentinel behavior,
filter semantics, and boundary handling before it can be admitted. Therefore,
fastparquet-only is deliberately typed unavailable everywhere in this line.

This is not a claim that fastparquet can never be supported. It is a fail-closed
package-local capability decision: no caller can plan Parquet as available when
bounded ingestion cannot execute the same contract.

## Contract matrix

| simulated modules | `_parquet_engine()` | capability | writer/read-back | bounded ingestion |
| --- | --- | --- | --- | --- |
| pyarrow only | `pyarrow` | available | available / verified | available |
| fastparquet only | `None` | unavailable / `optional_dependency` | unavailable / typed | unavailable / typed |
| both | `pyarrow` | available | available / verified | available |
| neither | `None` | unavailable / `optional_dependency` | unavailable / typed | unavailable / typed |

The matrix is tested by monkeypatching module discovery, without importing or
installing the optional dependency. The real environment separately exercises
the pyarrow Parquet write/read-back and bounded row-cap path.

## Code boundaries

- `backend/workbench/data_interchange.py` owns engine admission and the stable
  Parquet optional-dependency capability message. Public capability, writer,
  and round-trip functions continue to consult that boundary.
- `backend/workbench/ingestion.py` consults the same module-level engine
  admission before importing pyarrow's bounded batch reader. It never advertises
  a different engine contract.
- Existing CSV/XLSX behavior, metadata-loss reporting, canonical
  `DataOperationsRegistrySection` preview/confirm/lineage code, and
  pyreadstat-unavailable behavior are regression boundaries only.
