**Goal:** Make one workflow capability declaration automatically appear in the operation registry, proposal schema, vocabulary, planning-agent contracts, context inspection, route rendering, and unified capability inventory without adding a new orchestrator dispatch branch.

Use the real P7 operation ID and input shape in a registration test, but do not import or modify the unmerged P7 worktree and do not implement its runtime executor in P3.

## Design decisions

1. **Single live source:** WORKFLOW_STEP_SPEC_CONTRACTS becomes a small validated registry that refreshes its compatibility projections when a declaration is added or removed. Production code uses a dynamic workflow_step_operations() accessor where a current value matters; the exported tuple remains for compatibility with existing imports.
2. **Closed declarations:** Add field_enums to StepSpecContract, publish it into both the contract payload and JSON schema, and validate that enum keys are declared fields. Do not change proposal_schema to accept arbitrary objects; additionalProperties remains false.
3. **Capability identity:** Add capability_kind to StepSpecContract, defaulting to the existing data_operation, and project it into CapabilityContract. A pack can therefore be registered through the same operation path without a second inventory list.
4. **Exposure versus reachability:** Add top_level_exposure_note as an informational field. It is allowed when composable_as is nonempty and reachability_exempt_reason is None; no code may infer an exemption from it.
5. **Real P7 seam test:** Register a test-only declaration with the exact repeated-measures operation ID and field vocabulary verified above. The test exercises all current hookup points. It proves that a future P7 pack needs one declaration; it does not claim that the P7 numerical executor is implemented.
