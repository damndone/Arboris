## 1. How to read this plan

### 1.1 Task ID convention

`T<step>.<n>` where `<step>` is the §14 step in the spec (2–10). T1 is pre-flight. Example: `T6.4` = §14 step 6, task 4.

### 1.2 Effort sizing

| Size | Wall-clock budget |
|---|---|
| **S** | < 30 min |
| **M** | 30–90 min |
| **L** | 90–180 min |

If a task overruns 2× its budget, **stop**. Escalate per §17 risk register; do not push through with thrashing.

### 1.3 Per-task fields

- **Owner**: FE-A / FE-B / BE / shared (see §15)
- **Effort**: S / M / L
- **Touched files**: exact paths
- **UIUX ref**: path:line citations into `/Users/jiayuanren/项目规划/uiux/` when visuals/interactions matter
- **Steps**: sequential bullets; no decision points (those are in the spec)
- **DoD**: observable test or behavior; no "looks good"
- **Depends on**: upstream task IDs that must be green first

### 1.4 Per-step Git hygiene

Each step ends with one commit on `workbench-v1.5.0` and `git push origin`. Commit message format:

```
<type>(lineage|backend|tokens): <step summary>

T<step>.<n>: <task>
T<step>.<n>: <task>
...

Tests: FE +<n> (<total>), BE +<n> (<total>)

Co-Authored-By: Claude Opus 4.7 <noreply@anthropic.com>
```

A step's commit is created only after its tests are green. Per spec §14 revert policy: one focused fix; if still red, revert the step's working changes and re-plan.

### 1.5 Test count tracking

Every step's commit message ends with `Tests: FE +N (M total), BE +K (L total)` where N/K is the delta vs previous step and M/L is the absolute count after the step. `git log --grep="Tests:" workbench-v1.5.0` is the audit trail.

If the actual delta differs from this plan's expected delta by more than ±2 tests, document the reason in the commit body. Larger drift means the spec or the plan needs amending.
