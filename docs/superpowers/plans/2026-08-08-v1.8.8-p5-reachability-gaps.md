## Statistical semantics and multiplicity policy

Automatic and named execution are two evidence modes and must coexist:

1. The existing automatic statistical stage stays in the pipeline at its current position and continues to run the same dtype-driven eight-family matrix on the cleaned input. No family, row, or automatic stage is removed; no automatic choice is changed into a named choice. Its packet gains explicit mode/provenance metadata only: `execution_mode="automatic_pipeline"`, the existing core FDR scope, and the existing independent `advanced_evidence_family` scope.
2. A named `test.<family>` workflow step requires explicit source columns and runs only the selected family. It does not infer a different family from dtype, expand to all eight families, or become a model-selection decision. `test.evidence` requires its declared reference means and/or paired columns when those evidence forms are requested and preserves the existing evidence packet meaning.
3. Named results apply Benjamini-Hochberg (`correction_method="fdr_bh"`) only across p-values returned by that selected family and record `correction_scope="named:<family>"`. A family with no p-values records an explicit not-applicable scope rather than silently dropping metadata. Automatic core rows retain their existing all-core scope; evidence remains corrected separately as `advanced_evidence_family`. This keeps automatic multiplicity broad and transparent while preventing a named request from borrowing multiplicity from unrelated families.
4. Artifact identity and lineage distinguish `automatic_pipeline` from `named:<family>`; the underlying test functions and result fields remain unchanged. Tests must assert both modes and prove that a named correlation request cannot create t-test/ANOVA rows, while automatic execution still emits its historical family set.
