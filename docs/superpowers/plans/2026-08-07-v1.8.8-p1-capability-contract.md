## 0. 一个必须先讲清的区分：能力 ≠ 操作

设计文档 §决策一 的字段表隐含「能力≈操作」，**那是错的**，而同一份文档的守卫要求写对了：

> 必须按**能力**枚举，不是按操作——`model.genesis` 一个操作覆盖 23 个模型族，
> 按操作写的守卫在新增第 24 个族时照样是绿的。

今天的真实结构：

| 注册表 | 数量 | 是什么 |
|---|---|---|
| `MODEL_FAMILY_CONTRACTS` | 23 | 模型族。**全部**由 `model.genesis` 一个操作提议 |
| `OperationDefinition` | 16 | agent 提议面（其中 8 条是 workflow step 身份） |
| `WORKFLOW_STEP_SPEC_CONTRACTS` | 10 | 可组合的 step |
| `TEST_FAMILIES` | 8 | **只是一个 `{族名: 文件名}` 字典**，没有契约 |
| P7 pack operation ids | 29 | frozenset，尚未接入 |

**所以 `CapabilityContract` 不是「又一种 OperationDefinition」。** 它是一层**索引**：
能力声明自己是谁，以及**通过哪条路能被够到**。一个 operation 可以承载多个能力
（`model.genesis` 承载 23 个），一个能力也可能有两条可达路径（顶层提议 + step 组合）。

**衡量标准（来自设计文档，不放宽）**：接入第 N+1 个能力应只需实现契约 + 写能力本身，
**不需要改 orchestrator 的四处分发**。做不到就说明契约没抽对。

## 1. 契约形状

```python
@dataclass(frozen=True)
class CapabilityContract:
    capability_id: str          # "model.ols" / "multivariate.pca" / "data.merge"
    kind: str                   # "model_family" | "data_operation" | "statistical_test" | "pack"
    summary: str                # 一句话，人和模型都读

    # 可达路径。两条都为空 = 这个能力够不着，P2 的守卫就是断言这件事。
    proposed_by: tuple[str, ...] = ()   # 能提议它的 operation_id
    composable_as: tuple[str, ...] = () # 能组合它的 workflow step operation_id

    # 有意关闭的能力必须显式说明，不得靠「不在清单里」来表达
    reachability_exempt_reason: str | None = None
```

**为什么 `proposed_by` / `composable_as` 是元组而不是布尔**：守卫要能说出
「这个能力**通过谁**可达」，而不只是「可达」。第 24 个模型族接错到一个不存在的
operation 上时，布尔值看不出来，元组配合交叉校验看得出来。

**为什么豁免要写理由**：`code.execute` / `model.custom` 是用户既定关闭的。
「不在清单里」和「在清单里但显式豁免」的区别，就是「静默排除」和「如实记录」的区别——
这是本版反复强调的那条。

```python
"""One capability's identity and the paths by which it can be asked for.

A capability is not an operation. `model.genesis` is a single operation that
carries twenty-three model families, so a guard written over operations stays
green when the twenty-fourth family is unreachable -- which is exactly how the
previous version's reachability check missed the data-operation family. This
contract is the layer that makes "every capability" enumerable, and reach a
property each capability states about itself rather than one a human re-checks.
"""

from __future__ import annotations

from dataclasses import dataclass


CAPABILITY_KINDS = frozenset(
    {"model_family", "data_operation", "statistical_test", "pack"}
)


@dataclass(frozen=True)
class CapabilityContract:
    capability_id: str
    kind: str
    summary: str
    #: operation_ids that can propose this capability at the top level.
    proposed_by: tuple[str, ...] = ()
    #: workflow step operation_ids that can compose this capability in a plan.
    composable_as: tuple[str, ...] = ()
    #: Deliberately closed capabilities say so here. Absence from the inventory
    #: and presence with a stated reason are different claims, and only the
    #: second one survives someone asking "was this an oversight?".
    reachability_exempt_reason: str | None = None

    def __post_init__(self) -> None:
        if not self.capability_id.strip():
            raise ValueError("capability_id must be a non-empty string")
        if self.kind not in CAPABILITY_KINDS:
            raise ValueError(
                f"capability {self.capability_id} kind must be one of: "
                + ", ".join(sorted(CAPABILITY_KINDS))
            )
        if not self.summary.strip():
            raise ValueError(
                f"capability {self.capability_id} needs a summary: it is what a "
                "reader and a model both see first"
            )

    @property
    def is_reachable(self) -> bool:
        return bool(self.proposed_by or self.composable_as)


__all__ = ["CAPABILITY_KINDS", "CapabilityContract"]
```

## Task 4: 清单要暴露「够不着」这个状态

**Files:**

- Test: `tests/test_capability_inventory.py`

P2 的守卫会断言「全部可达」。但 P1 的清单必须先能**如实报告不可达**——
否则守卫无从判断。

### ⚠️ 计划初稿的错误（Task 3 完成后发现，已改正）

初稿的测试写的是「**不可达的都必须有豁免理由**」：

```python
for item in unreachable:
    assert item.reachability_exempt_reason   # ← 错的
```

**这个假设不成立。** Task 3 完成后清单有 54 条、**15 条不可达**，而它们
`reachability_exempt_reason` 全是 `None`——因为它们是**真缺口**，不是有意关的门。

照初稿做，实现者会被逼着给 15 个缺口编造豁免理由——**那正好是把缺口粉饰掉**，
与本任务的目的相反。

**不可达有两种，必须分开**：

| 状态 | 含义 | 例子 |
|---|---|---|
| **有意关闭** | 产品决定不开放，有陈述的理由 | 用户既定关闭的能力 |
| **真缺口** | 没人接线，应该开放却够不着 | 8 个检验族、3 个预测模型、4 个数据准备 |

「够不着」和「有意不给」是两个不同的事实。把后者当成前者会掩盖缺口；
把前者当成后者会让有意的决定看起来像疏忽。

- [ ] **Step 1: 写失败测试**

