**Goal:** 在同一候选提交上证明 Workflow、Evidence、Agent Compiler、Data Consumer、Classification ML、Consumer Projection 与 Agent/Notebook Cutover 能被发现、编译、确认、执行、持久化和消费，并将 deterministic、independent evaluation、browser、provider、formal、host gate 和 release 状态分开记录。

**Architecture:** 本 plan 包含两个 formal lines。Integration Conductor 在 P0 + Harness 后启动，生成 C1/C2/C3，并在 C3 前完成所有 acceptance harness/tests；独立 E1/E2/E3 精确评测各 candidate。E3 后另启 Final Acceptance line，在独立 control worktree 对 read-only C3 运行 product-path、browser、provider boundary 和 final gate，只写 sidecar evidence/handoff，绝不回写 candidate。产品缺陷退回 owner line；两条线都不修产品行为。

## Preconditions and non-negotiable boundaries

- 启动输入必须命名 exact Contract Lock、P0 dependency SHAs 和已完成的 Evaluation Harness tip；E1 尚不存在，必须在 C1 candidate commit 产生后运行。
- 每个 integration phase 开始前，对应 wave writers 必须停止写入并提交 Completion Reports；后续 wave 可以在已冻结的 C1/C2 上并行。Integration 始终只有一个 merge queue 和一个 active candidate SHA。
- Evaluator did not author the product code it scores; its manifests are immutable and tied to candidate/dependency SHAs.
- A merge, contract/provider/catalog change, fixture change or product fix invalidates all downstream evidence whose inputs changed.
- Push/PR/merge to protected branch/tag/release remain separately approval-gated.

## Task 1: deterministic C1/C2/C3 merge queue

- [ ] Record pre-merge candidate SHA, clean/dirty state, branch/worktree identity and dependency head SHAs.
- [ ] 在每次获得明确 merge approval 后按 C0 → Wave A/C1 → Wave B/C2 → Cutover/C3 合流；禁止用 blanket “ours/theirs” 解决冲突，也不把批准 C1 自动解释为批准 C2/C3。
- [ ] After each merge, run the changed line’s focused tests plus contract/provider catalog verification before accepting the next head.
- [ ] Compare changed paths against each Work Order; reject unowned changes, stale Contract Lock refs or hand-edited formal records.
- [ ] 每一阶段先生成不自引用的 `c1-p0.yaml`、`c2-p1.yaml`、`c3-cutover.yaml`，只包含 merge inputs、contract/provider/catalog/coverage digests、tests 和 invalidated evidence；它不包含自己的 future commit SHA 或尚未运行的 evaluation digest。将产品合流 + lock yaml 形成 candidate commit 后，才得到 C1/C2/C3 exact SHA。
- [ ] 对每个 exact candidate SHA 启动独立 E1/E2/E3 formal run line；run 在 Evaluation worktree 写唯一 manifest/sidecar admission，不修改或合并进 candidate。只有 admission 绑定 candidate SHA、harness/fixture digests 且通过后，下一 wave Work Order 才可从该 exact candidate SHA 启动。
- [ ] 如果 owner 修复、merge conflict resolution、lock 内容或任何 candidate 文件变化，旧 evaluation admission 失效；生成新 candidate revision 并重新运行对应 evaluation。
- [ ] 在形成 C3 candidate commit 前完成本线所有 backend/frontend acceptance harness、tests、runner 和 conductor handoff；关闭 Integration Conductor 后不得再改变 candidate。E3 只评测这个 clean C3。
