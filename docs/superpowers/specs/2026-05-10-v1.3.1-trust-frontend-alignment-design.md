# V1.3.1: Trust Frontend Alignment — Design Spec

Date: 2026-05-10

## 1. Goal

V1.3.1 aligns the browser experience with the V1.3.0 trustworthiness model. V1.3.0 introduced `diagnostic_summary.json`, four-level severity, structured narrative constraints, variable-role inference, and a ReportViewModel adapter. V1.3.1 makes those trust artifacts visible and actionable in Run detail and Report without adding new statistical methods.

The primary user outcome is: after opening a run, the user can quickly tell whether the result is interpretable, why caution is needed, which variables or coefficients carry interpretation risk, which statements are forbidden, what the next recommended action is, and whether the report can be treated as formal output.

## 2. Scope

### P0 Must Have

1. `GET /runs/{run_id}` returns `diagnostic_summary_preview`.
2. Run detail shows a progressive Trust Summary at the top.
3. Trust Summary uses backend canonical status; the frontend does not infer trust state from counts.
4. Frontend supports four severity levels: `BLOCKER`, `WARNING`, `CAUTION`, `INFO`.
5. Coefficient Risk defaults to the primary model and groups by original variable.
6. Coefficient Risk can expand to show coefficient terms and dummy levels; P0 includes `role_summary`, while full evidence browsing is P1.
7. Categorical/code/dummy misleading interpretation is fixed in Run detail and Report.
8. Report shows `CAUTION` and causal/treatment/categorical interpretation restrictions.
9. Legacy fallback and contract fallback are explicit.
10. `errors.json` is only fallback/debug, not the primary display contract.
11. Run detail minimally shows interpretation restrictions.
12. Run detail minimally shows the top 1-3 recommended actions.

### P1 Should Have

1. Full recommended-action display, grouping, and issue/variable jump links.
2. Full interpretation-restriction section in Run detail.
3. Report top lightweight Trust Summary.
4. Report primary-model risk badges.
5. Full Run detail and Report copy/key consistency with snapshot tests.
6. Raw `diagnostic_summary.json` download entry.
7. Secondary-model collapsed visual polish.
8. Full coefficient-risk evidence expansion: name hints, data hints, unique count, source IDs, linked issue details.

## 3. Non-Goals

V1.3.1 does not add new model families, new statistical tests, cancellation UI, full export governance, full i18n, or a new artifact browser. `cancelled` is reserved in the lifecycle contract but V1.3.1 does not implement user-initiated cancellation.

Categorical integrity work is limited to P0 cases that can mislead users: category codes interpreted as continuous values, dummy-coded terms losing traceability to original variables, or reports describing categorical candidates as one-unit numeric changes.

## 4. API Contract

`GET /runs/{run_id}` returns the existing run detail fields plus `diagnostic_summary_preview`. The preview is the frontend's primary trust contract.

```json
{
  "diagnostic_summary_preview": {
    "available": true,
    "preview_contract_version": "1.0",
    "source_schema_version": "diagnostic_summary.v1",
    "preview_status": "complete",
    "contract_warnings": [],
    "run_lifecycle_status": "completed",
    "run_status": {
      "status": "usable_with_caution",
      "status_scope": "primary_model",
      "safe_to_generate_report": true,
      "safe_to_interpret": "partial",
      "has_blockers": false,
      "has_warnings": true,
      "has_cautions": true,
      "model_results_available": true
    },
    "trust_label": "interpret_with_caution",
    "trust_counts": {
      "blockers": 0,
      "warnings": 1,
      "cautions": 2,
      "info": 3
    },
    "primary_reasons": [],
    "model_identity": {
      "primary_model_id": "model_ols_1",
      "model_label": "OLS regression",
      "model_type": "ols",
      "y_variable": "wage",
      "x_variables": ["education", "region_code", "treatment"],
      "x_variable_count": 3,
      "n_observations": 700,
      "standard_error_type": "unavailable"
    },
    "artifact_manifest": {},
    "diagnostic_highlights": [],
    "coefficient_risk": null,
    "interpretation_restrictions": [],
    "recommended_actions": []
  }
}
```

### Required Canonical Fields

These fields are required for rendering the V1.3.1 Trust Summary when `available=true`:

- `available`
- `preview_contract_version`
- `preview_status`
- `run_lifecycle_status`
- `run_status.status`
- `run_status.status_scope`
- `run_status.safe_to_generate_report`
- `run_status.safe_to_interpret`
- `run_status.model_results_available`
- `trust_label`
- `trust_counts.blockers`
- `trust_counts.warnings`
- `trust_counts.cautions`
- `trust_counts.info`
- `primary_reasons`

`primary_reasons` may be an empty array, but the field must exist.

`coefficient_risk` is a P0 display feature but not a preview-availability gate. If it is missing or incomplete, the preview may remain available with `preview_status=partial`, and the Coefficient Risk section displays unavailable. If `coefficient_risk` is present, it must include `primary_model_id` and `models`.

### Model Identity

`model_identity` is required when `run_status.model_results_available=true`, but only the following inner fields are required:

- `primary_model_id`
- `model_label`
- `model_type`
- `y_variable`
- `n_observations`

Recommended fields:

- `x_variables`
- `x_variable_count`
- `standard_error_type`

If `standard_error_type` is missing, `unavailable`, or `unknown`, the frontend must not show a Standard errors line outside debug/details.

## 5. State Model

### Run Lifecycle Status

The outer lifecycle status controls whether analysis output exists:

```text
queued | running | completed | failed | interrupted | cancelled
```

`cancelled` is reserved for future cancellation support. V1.3.1 must handle it in UI without implementing cancellation.

When `run_lifecycle_status` is `queued` or `running`:

- `diagnostic_summary_preview.available=false`
- `preview_status=pending`
- `trust_label=analysis_running`
- Do not enter legacy fallback.
- Do not enter contract fallback.
- Show analysis-running state and existing progress/SSE UI.

When `run_lifecycle_status` is `interrupted` or `cancelled`, use `trust_label=lifecycle_unavailable`.

### Diagnostic Trust Status

`run_status.status` is the canonical diagnostic trust status and is meaningful only after diagnostic output exists:

```text
ok | usable_with_caution | blocked | failed
```

Running, queued, cancelled, and interrupted states do not belong in `run_status.status`.

### Trust Labels

`trust_label` is a backend-provided display key. The frontend maps it to copy but does not infer it.

```text
analysis_running
ready_to_interpret
interpret_with_caution
not_ready_to_interpret
run_failed
lifecycle_unavailable
legacy_unavailable
contract_unavailable
```

Mapping:

- `analysis_running`: queued/running, no diagnostic result yet
- `ready_to_interpret`: completed + `ok`
- `interpret_with_caution`: completed + `usable_with_caution`
- `not_ready_to_interpret`: completed + `blocked`
- `run_failed`: execution failed
- `lifecycle_unavailable`: interrupted/cancelled
- `legacy_unavailable`: old run or missing V1.3.1 preview
- `contract_unavailable`: malformed, unsupported, or inconsistent preview contract

### Safe-To-Interpret Consistency

`safe_to_interpret` is fixed to:

```text
yes | partial | no | unavailable
```

Backend consistency rules:

- `status=ok` requires `safe_to_interpret=yes`.
- `status=usable_with_caution` requires `safe_to_interpret=partial`.
- `status=blocked` requires `safe_to_interpret=no`.
- `status=failed` requires `safe_to_interpret=unavailable`.
- `safe_to_interpret=yes` requires `safe_to_generate_report=true`.
- `safe_to_interpret=unavailable` requires `safe_to_generate_report=false`.
- `safe_to_interpret=partial` usually has `safe_to_generate_report=true`.
- `safe_to_interpret=no` usually has `safe_to_generate_report=false`.

If canonical fields conflict, the frontend shows a contract warning and does not repair or reinterpret the status.

### Status Scope

`run_status.status_scope` is required:

```text
primary_model | all_models | run_level
```

Rules:

- Single-model run: `primary_model`.
- Multi-model run, secondary models have no blockers: `primary_model`.
- Multi-model run, secondary blocker does not affect the primary model: `primary_model`, but the secondary issue must appear in `primary_reasons` or `diagnostic_highlights`.
- Multi-model run, secondary blocker affects overall report trust: `all_models`.
- Pipeline/artifact/report failure: `run_level`.

The frontend displays the scope and must not guess it.

## 6. Preview Availability and Contract Policy

Preview statuses:

```text
pending
complete
partial
unavailable
malformed
unsupported_contract
contract_inconsistent
lifecycle_unavailable
```

Rules:

- Missing `diagnostic_summary.json`: `available=false`, `preview_status=unavailable`, legacy fallback.
- Malformed artifact: `available=false`, `preview_status=malformed`, contract warning.
- Unsupported major `preview_contract_version`: `available=false`, `preview_status=unsupported_contract`.
- Valid artifact with missing optional fields: `available=true`, `preview_status=partial`.
- Valid and complete preview: `available=true`, `preview_status=complete`.
- Required canonical field missing or unparsable: hard fallback to `contract_unavailable`.
- Semantic conflicts between canonical fields: `contract_inconsistent`; do not display potentially misleading trust labels.

Frontend compatibility policy:

- Same major preview contract: best-effort render known fields.
- Higher minor preview contract: show contract warning; keep Trust Summary if required canonical fields are present.
- Different major preview contract: do not render the V1.3.1 Trust Summary.
- `available=true` without `preview_contract_version` is a contract error.

## 7. Artifact Manifest

`artifact_manifest` covers only trust-critical artifacts for Run detail, Trust Summary, Report entry, and fallback. It is not a replacement for artifact groups.

```json
{
  "artifact_manifest": {
    "report_html": {
      "expected": true,
      "available": true,
      "readable": true,
      "artifact_id": "report_html",
      "filename": "report.html"
    },
    "diagnostic_summary_json": {
      "expected": true,
      "available": true,
      "readable": true,
      "schema_valid": true,
      "artifact_id": "diagnostic_summary_json",
      "filename": "diagnostic_summary.json"
    },
    "primary_model_results": {
      "expected": true,
      "available": true,
      "readable": true,
      "model_id": "model_ols_1"
    },
    "secondary_model_results": {
      "expected": false,
      "available_count": 2
    },
    "errors_json": {
      "expected": true,
      "available": true,
      "readable": true,
      "legacy_debug_only": true
    }
  }
}
```

Formal UI uses backend explicit fields such as `artifact_manifest.report_html.available`. Artifact groups remain the full artifact browsing and download source. In legacy fallback only, the frontend may scan artifact groups for an old report and label it as legacy/debug.

## 8. Primary Reasons and Diagnostic Highlights

### Primary Reasons

`primary_reasons` explain `run_status` and `trust_label` in the first screen. The backend returns at most four, already sorted. The frontend displays all of them in order and does not promote other diagnostics into this list.

```json
{
  "reason_id": "reason_001",
  "reason_key": "TREATMENT_PROXY_CORRELATION",
  "severity": "CAUTION",
  "message": "x8_treatment and x10_interaction_proxy are highly correlated.",
  "message_params": {
    "var_1": "x8_treatment",
    "var_2": "x10_interaction_proxy",
    "correlation": 0.791
  },
  "affected_variables": ["x8_treatment", "x10_interaction_proxy"],
  "linked_issue_ids": ["diag_003"]
}
```

### Diagnostic Highlights

`diagnostic_highlights` are second-layer diagnostic summaries. They include both display fields and issue-style audit fields.

```json
{
  "highlight_id": "highlight_001",
  "highlight_key": "TREATMENT_PROXY_CORRELATION",
  "category": "coefficient_interpretation",
  "affected_stage": "diagnostics",
  "severity": "CAUTION",
  "message": "x8_treatment and x10_interaction_proxy are highly correlated.",
  "message_params": {
    "var_1": "x8_treatment",
    "var_2": "x10_interaction_proxy",
    "correlation": 0.791,
    "threshold": 0.7
  },
  "code": "TREATMENT_PROXY_CORRELATION",
  "variables": ["x8_treatment", "x10_interaction_proxy"],
  "metric": "correlation",
  "value": 0.791,
  "threshold": 0.7,
  "linked_issue_ids": ["diag_003"],
  "user_action_required": true,
  "recommended_action_keys": ["INTERPRET_TREATMENT_PROXY_JOINTLY"]
}
```

UI may filter, fold, and group highlights by severity, category, or stage, but cannot change severity or meaning.

## 9. Run Detail Design

Run detail uses a progressive Trust Summary:

1. **Trust Status Bar**: always at the top; shows trust label, status scope, and severity counts.
2. **Lightweight Summary**: default visible; shows up to four `primary_reasons` plus model identity.
3. **Expandable Details**: diagnostic highlights, coefficient risk, minimal restrictions/actions, artifact manifest, and debug information.

Severity labels:

- `BLOCKER`: Blocking issues
- `WARNING`: Warnings
- `CAUTION`: Interpretation cautions
- `INFO`: System notes

Default UI copy is English. API records include stable keys and `message_params` for future localization. V1.3.1 does not implement bilingual UI or full i18n.

## 10. Coefficient Risk

`coefficient_risk` supports model grouping and marks the primary model explicitly.

```json
{
  "coefficient_risk": {
    "primary_model_id": "model_ols_1",
    "models": [
      {
        "model_id": "model_ols_1",
        "model_label": "Primary model",
        "is_primary": true,
        "model_type": "ols",
        "outcome": "wage",
        "risk_groups": [
          {
            "variable": "region_code",
            "display_name": "region_code",
            "variable_kind": "dummy_coded",
            "risk_level": "WARNING",
            "interpretation_guide": "categorical_levels_vs_reference",
            "summary": "region_code was dummy-coded. Coefficients compare each level to the reference level.",
            "linked_issue_ids": ["diag_003"],
            "role_summary": {
              "role": "categorical",
              "status": "confirmed_by_rules",
              "confidence": 0.85,
              "needs_user_confirmation": false
            },
            "terms": [
              {
                "term": "C(Q('region_code'))[T.2]",
                "display_term": "region_code = 2",
                "level": "2",
                "reference_level": "1",
                "estimate": 1.23,
                "p_value": 0.04,
                "source_id": "model_results.model_ols_1.coefficients.C(Q('region_code'))[T.2]"
              }
            ]
          }
        ]
      }
    ]
  }
}
```

Rules:

- Frontend must use `primary_model_id` and `is_primary`; it cannot infer primary model.
- Primary model is shown by default.
- Secondary models are collapsed by default.
- Secondary model blockers that affect overall trust must be lifted into `primary_reasons` or `diagnostic_highlights`.
- `risk_level` is the highest linked severity for that original variable using `BLOCKER > WARNING > CAUTION > INFO`.
- `term` and `source_id` are debug/raw details. Default UI uses `display_term`.
- Dummy terms require `level` and `reference_level`.

Supported `variable_kind` values:

```text
continuous
binary
categorical_confirmed
categorical_candidate
dummy_coded
treatment
proxy
exposure
id_like
time_like
unknown
```

P0 displays `role_summary` and coefficient terms. Full evidence fields such as name hints, data hints, unique count, source IDs, and linked issue details are P1.

## 11. Categorical Interpretation Guardrails

V1.3.1 must prevent misleading categorical/code/dummy interpretation in Run detail and Report.

Rules:

- `categorical_confirmed` and `dummy_coded` variables are interpreted as level-vs-reference, never as continuous one-unit changes.
- `categorical_candidate` variables modeled numerically must not use continuous templates.
- If a dummy term cannot be reliably traced back to the original variable, display review-required text instead of a continuous interpretation.
- Categorical/code variables must not appear in descriptive or importance areas as continuous numeric effects unless explicitly marked as categorical/code.
- The following phrasing is forbidden for categorical candidates or code variables unless `ordinal_confirmed=true`: "one-unit increase", "per unit", "numeric increase", "linear increase", and Chinese equivalents such as "每增加 1 个单位", "数值上升", "线性增加".

## 12. Restrictions and Actions

Backend contract keeps `interpretation_restrictions` and `recommended_actions` separate. Frontend may show them in a combined Interpretation Guidance area, but it must visually separate "Do not" from "Recommended next steps".

P0 structured restriction types:

```text
causal
treatment_proxy
categorical
generic
```

Only `causal`, `treatment_proxy`, and `categorical` drive automatic interpretation guardrails. `generic` is display-only fallback.

```json
{
  "restriction_id": "restriction_001",
  "restriction_type": "treatment_proxy",
  "scope": "variable",
  "severity": "CAUTION",
  "message": "Do not interpret treatment as a standalone effect.",
  "forbidden_language": ["causes", "causal effect"],
  "affected_variables": ["x8_treatment"],
  "affected_terms": [],
  "linked_issue_ids": ["diag_003"],
  "source": "narrative_contract"
}
```

Recommended actions are backend-generated. The frontend displays, sorts, folds, and optionally links them, but does not generate action text from issue codes.

```json
{
  "action_id": "action_issue_003",
  "scope": "issue",
  "severity": "CAUTION",
  "action_key": "INTERPRET_TREATMENT_PROXY_JOINTLY",
  "message": "Interpret treatment and proxy variables jointly rather than as independent effects.",
  "linked_issue_ids": ["diag_003"],
  "linked_variables": ["x8_treatment", "x10_interaction_proxy"]
}
```

P0 Run detail shows the top 1-3 recommended actions. Jump links and complete grouping are P1.

## 13. Report Behavior

Report entry behavior separates artifact availability from formal interpretability:

- `report artifact exists`: whether there is a file to open.
- `safe_to_generate_report`: whether the report is safe as formal output.
- `safe_to_interpret`: whether model conclusions are interpretable.

Rules:

- `failed` or no report artifact: disable the report entry and show Report unavailable.
- `failed` with report artifact: default to disabled or debug-only with failed/debug warning.
- `blocked` with report artifact: allow opening for review/debug, show a blocking warning, fold coefficient interpretation by default, and do not allow formal use.
- `usable_with_caution`: allow normal opening with a caution banner.
- `ok`: allow normal opening.
- preview unavailable with report artifact: allow opening as legacy report with legacy/debug banner.

If formal export or copy-conclusion controls already exist, they must be disabled for `blocked`. V1.3.1 does not build full export governance; a future version should define policies for `ok`, `usable_with_caution`, `blocked`, and `failed`.

Report P0 must:

- Show CAUTION separately from WARNING.
- Show causal/treatment/categorical restrictions.
- Avoid categorical/code/dummy misleading interpretations.
- Use review-required text when interpretation cannot be made safely.

Report top Trust Summary and primary-model risk badges are P1 unless implementation cost is low after P0 is complete.

## 14. Fallback Behavior

### Legacy Fallback

Legacy fallback is used for old runs or missing preview artifacts. It may show:

- run lifecycle status
- legacy `errors.json` issues
- model results summary
- artifact counts and links
- report artifact availability
- raw diagnostic/debug links

It must not derive or display:

- V1.3.1 trust labels
- `safe_to_interpret`
- `safe_to_generate_report`
- `primary_reasons`
- `coefficient_risk`
- `interpretation_restrictions`
- `recommended_actions`

Reports opened from legacy fallback are labeled "Open legacy report".

### Contract Fallback

Required canonical field missing, unsupported major version, malformed JSON, or semantic inconsistency means the V1.3.1 Trust Summary is not rendered. The UI shows a contract warning and debug/fallback information instead.

Optional section missing produces partial preview, not hard failure.

## 15. Testing Strategy

Backend tests:

- `GET /runs/{run_id}` returns `diagnostic_summary_preview` with required canonical fields.
- Missing diagnostic summary returns `available=false` legacy fallback state.
- Malformed or unsupported preview returns contract-unavailable state without a generic 500.
- Running/queued runs return `preview_status=pending` and `trust_label=analysis_running`.
- `run_status.status`, `safe_to_interpret`, and `trust_label` consistency is enforced.
- `artifact_manifest` reports trust-critical artifacts and does not replace artifact groups.
- `primary_reasons` is capped at four and preserves backend order.
- `coefficient_risk` groups by original variable and computes highest linked severity.
- Dummy-coded terms include `display_term`, `level`, and `reference_level`.
- Categorical candidates do not receive continuous interpretation guides.

Frontend tests:

- Trust Status Bar and Summary render before legacy artifacts.
- Four severity levels render with correct labels, including CAUTION as Interpretation cautions.
- Running uses analysis-running state, not legacy fallback.
- Contract version policy handles same-major, higher-minor, and different-major cases.
- Report entry follows failed/blocked/caution/ok split.
- Coefficient Risk defaults to primary model and groups by original variable.
- Term/source IDs are hidden by default.
- Minimal restrictions and top recommended actions are visible in Run detail.
- Legacy fallback does not fake trust labels or safe-to-interpret state.

Report tests:

- CAUTION section is visible.
- Causal/treatment/categorical restrictions are visible.
- Dummy-coded variables render as level-vs-reference.
- Categorical candidates do not produce one-unit-increase language.
- Blocked reports show blocking banner and do not present output as formally interpretable.

## 16. Acceptance Criteria

V1.3.1 P0 is complete when:

1. A V1.3.0-style run with diagnostic summary renders a Trust Status Bar and Summary from `diagnostic_summary_preview`.
2. The frontend does not infer trust status from artifact groups, `errors.json`, or severity counts.
3. A run with CAUTION displays Interpretation cautions in Run detail and Report.
4. A categorical code variable cannot be presented as a continuous one-unit effect.
5. A dummy-coded variable is presented as level-vs-reference and traceable to its original variable.
6. Blocked, failed, running, legacy, and contract-unavailable states are distinct.
7. Report entry behavior separates "can open artifact" from "safe as formal report output".
8. Old runs remain inspectable through legacy/debug fallback without pretending to have V1.3.1 trust state.
