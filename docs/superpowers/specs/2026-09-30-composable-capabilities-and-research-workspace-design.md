## 0. 摘要

1. **能力按“性质”声明，行为由性质推出。** 模型族、检查、后估计、标准误、组合子都声明自己需要什么、提供什么；适用关系由匹配得出，共享代码里不再出现模型族名字。加一个模型族，只写一份声明和对照数据，检查和后估计会自动适用。
2. **结果信封加上“推断核心”。** 每个结果都带系数向量、协方差矩阵、参考分布与自由度、对数似然、估计样本指纹。后估计直接读这些，不再重新拟合。
3. **组合子让能力像函数一样套用。** 按组执行、多重插补、bootstrap 都是接受“能力 + 参数”、产出新能力的组合子。Agent 用目录里的积木拼出带类型的计划，验证通过后执行。
4. **检查库。** 前提检查只写一次，按性质适用；每项检查标明它看不看结局变量。选方案时只能用“不看效应”的检查，这一点由结构保证，不靠提示词。
5. **研究规划重做。** 方案比较只显示前提检查；判断标准在任何估计值出现之前固定并记入台账；看过结果之后才提出的分析自动标为探索性。
6. **四层分工。** 谱系图记录计算关系，Agent 对话负责操作，时间线记录探索顺序，报告负责叙述。三种顺序各有归属，研究因此可以不是线性的。
7. **界面。**
   - 只有一个 Agent，占一整列；现在分散的 4 个 AI 入口合并到这里。
   - 两种布局都保留，用户可以随时切换（⌘\），功能完全一致：
     - **结果主导**：结果在中间，谱系图收成左侧一列；
     - **谱系主导**：谱系图在中间，结果在右侧检查栏。
   - 两种布局其实是同一个网格，只是“宽的那一列”换了位置。
   - 现有的运行记录、版本、图的各种布局工具、右侧多标签、改参数重跑、下方面板，全部保留并找到新位置（§8.3）。
8. **版本安排。** v1.8.10 做地基（§10）；界面外壳和研究规划分两版做，在 v1.8.10 结束时再确认。
9. **报告借鉴 nature-skills。** 吸收它的统计报告规范和图表规范，按 Workbench 的方式落地：能由代码检查的做成确定性检查，写作规范做成可选的规范包，图表规范做成期刊图表配置。不整包接入（§13）。
   - Workbench 比它多一样东西：分析的真实记录。它只能审读文字，我们可以拿台账和结果逐条核对。

## 1. 目标与原则

### 1.1 用户的要求

- AI native：凡是能发挥 LLM 和 Agent 能力的地方，要尽量超过 SPSS 和 Stata。
- 准确与安全是工具的基石，不能让步。
- 一切以给后期扩展打地基为前提，按模块化来做：能力像编程一样可以自由组合，不写死公式和流程，防止“过拟合”。
- 充分考虑 Agent 接入，愿景是用自然语言调用 Workbench 的全部能力。
- 界面要成熟、美观、有设计哲学。参照对象是 Claude Code、Codex 和 iOS，谱系图受 Obsidian 启发。
- 用户主要在 14 寸 MacBook Pro 上使用，要求各种尺寸都适配好。

### 1.2 设计原则

| # | 原则 | 含义 |
|---|---|---|
| P1 | 准确与安全优先 | 统计数字只由确定性代码产生。不适用的方法明确拒绝，不静默降级。每个数字都能追溯到节点和数据。 |
| P2 | 声明而非分支 | 共享代码不写模型族名字。能力声明性质，检查、后估计、标准误、组合子声明需求，适用关系由匹配得出。 |
| P3 | 可组合 | 组合子可以套在任何声明了相应性质的能力上。Agent 组合积木的方式和写一段小程序一样。 |
| P4 | 自然语言可达 | 目录里的每一项都能被 Agent 调用，由可达性守卫测试保证。例外必须写明理由，例如 `code.execute`。 |
| P5 | 结构性防止挑结果 | 选方案时 Agent 看不到结果；判断标准先固定；检验次数和披露由系统计算。 |
| P6 | Agent 负责理解、组合、提醒、解释 | Agent 不负责计算。沿用 `design_precheck.py` 的红线：可以提醒，不可以命令，也不替用户下结论。 |
| P7 | 结果优先、一个 Agent、图是地图 | 研究者的注意力只给数字和判断；来源随手可查，但不占位置。 |
| P8 | 渐进发布 | 每一版都能单独发布和回退。新界面在功能上追平旧界面之前，旧界面不删。 |

**这里说的“过拟合”有两层意思：**

- **统计上的过拟合**：挑出看起来显著的设定，或者因子挖掘里试了很多次没人计数。由 P5 处理（§5.5）。
- **设计上的过拟合**：为个别模型族或个别情形写死分支，后面每加一样东西都要改好几处。由 P2 和 P3 处理（§3）。

## 3. 可组合能力架构

### 3.1 积木的种类

| 积木 | 是什么 | 例子 | 现状 |
|---|---|---|---|
| 能力 Capability | 一次可执行的分析或数据操作 | OLS、t 检验、recode、Moran's I | 已有 `CapabilityContract`，共 131 项 |
| 性质 Trait | 能力声明的“我是什么” | 结局类型（连续 / 二元 / 计数 / 有序 / 生存 / 时间序列）；估计方法（最小二乘 / 最大似然 / GMM / 半参数）；需要的角色（工具变量、聚类、时间、个体）；是否依赖行序；子集语义 | 部分散在 `ModelFamilyContract` 的布尔字段里 |
| 接口 Interface | 结果能提供的读取能力 | `coef_vcov`、`loglik`、`predict`、`residuals`、`df` | 无（本版新增，§3.2） |
| 后估计 Post-estimation | 读接口的操作 | Wald、LR、lincom、nlcom、margins | 只有 OLS，而且要重拟合 |
| 标准误插件 VCE | 协方差估计器 | 普通、HC、聚类、HAC、复杂抽样、bootstrap | 写在各族的运行代码里 |
| 组合子 Combinator | 接受能力和参数，产出新能力 | 按组执行、多重插补、bootstrap、置换 | P7 合同已有，没有接通到端 |
| 检查 Check | 前提检查（§4） | 共线性、分离、工具强度、重叠 | 散落在各处 |
| 目录 Catalog | 以上全部登记于此，Agent 从这里发现可用的积木 | — | 已有 131 项，本版扩展到新积木 |

**适用规则只有一条：需要的性质和接口 ⊆ 声明的性质和接口。**

举例：logit 声明结局为二元、估计方法为最大似然、提供 `coef_vcov`、`loglik`、`predict(probability)`。它因此自动获得：

- 后估计：Wald χ²、LR（仅限模型协方差时）、平均边际效应、lincom；
- 检查：分离、每个自变量对应的事件数、共线性（GVIF）、每个参数的行数；
- 标准误：HC、聚类、复杂抽样；
- 组合子：按组执行（子集或域估计）、多重插补。

以后加一个 complementary log-log 模型，声明同样的性质就能继承上面全部内容。它唯一要补的是对照数据：每一对“族 × 操作”只有在对照数据通过后才开放（§3.3）。

### 3.2 结果信封与推断核心

结果信封 = v1.8.7 的 8 个字段（`contract_version`、`schema_version`、`model_id`、`model_type`、`engine`、`nobs`、`coefficients`、`validation`）+ 以下内容：

- **身份与来源**：节点、数据指纹、估计样本指纹（已有）、使用的标准误插件及其参数。
- **推断核心**：
  - 带名字的参数向量；
  - 完整协方差矩阵：k ≤ 500 时保存全部；k 更大时只保存关注参数，并明确写“其余参数不能做联合检验”；
  - 参考分布与自由度：t 或 F 的 df，或者 z 或 χ²；
  - 对数似然：最大似然族才有；
  - `predict` 声明：能预测什么尺度（线性预测、概率、计数），需要哪些输入。
- **检查结果**：§4 的输出。
- **图、警告、不可用原因**：不可用原因必须写明，不能静默省略。
- **消费者投影**：Agent、报告、表格、Notebook 都从同一份声明读取。合并现有的 `result_shapes` 和 `FAMILY_EVIDENCE_PROJECTIONS`。

**集合信封**（组合子的输出）：

- 按键组织的成员结果，键是组值或插补序号；
- 每个成员的状态：成功 / 无法估计 + 原因；
- 合并结果：多重插补才有；
- 组合子的参数与随机种子。

**漂移测试**：

- 每个已登记能力都必须有信封声明；
- 消费者不得绕开信封直接按路径读取数据包；
- 两条都由测试遍历目录检查。

**外发**：协方差矩阵是汇总统计量，不含原始行，按现有外发管控的“结果”类别处理。

### 3.3 后估计：对接口编程，不对模型族编程

| 操作 | 需要的接口与条件 | 推断规则 | 对照 |
|---|---|---|---|
| Wald（线性假设 Rβ = r） | `coef_vcov` | 核心声明 t/F 时用 F(q, df)，其中聚类 df = G − 1，复杂抽样用设计自由度；最大似然用 χ²(q) | Stata `test`；R `car::linearHypothesis` |
| lincom | `coef_vcov` | 按核心声明用 t(df) 或 z | Stata `lincom` |
| nlcom | `coef_vcov` | delta 方法，数值梯度；高度非线性时给出提示 | Stata `nlcom` |
| LR | `loglik`，且嵌套、同一估计样本、模型协方差 | χ²(Δk)。以下情况拒绝：稳健或聚类标准误、pweight、复杂抽样、样本不同（与 Stata `lrtest` 一致） | Stata `lrtest` |
| 边际效应（AME 或在均值处） | `predict` + `coef_vcov` + 血缘里的估计数据 | delta 方法；明确区分“平均边际效应”和“在均值处的边际效应” | Stata `margins, dydx()` |
| 预测 | `predict` | 按声明的尺度 | Stata `predict` |

- **开放规则**：一对“族 × 操作”要有至少一条 Stata 或 R 对照数据通过才开放，否则明确拒绝，并说明缺的是对照，不是能力。所以覆盖面靠补对照数据扩大，不靠写代码。
- **与组合子的组合规则**：
  - 按组执行的结果可以对每个组分别做后估计。
  - 多重插补合并后的结果暂时拒绝做联合检验。多重插补后的联合检验需要 D1 统计量（Li, Raghunathan & Rubin, 1991），不能拿单份数据的协方差去做 Wald。
- **清理**：去掉 `workflow_runtime.py` 里的 `"ols_1"`，以及 `diagnostics.py` 里按名字写死的族列表。加一条 lint 测试：共享路径里不允许出现模型族名字的字面量。

### 3.4 标准误插件

每个插件声明以下内容：

- 适用性质，例如 HAC 需要已声明的时间顺序、聚类需要聚类角色、复杂抽样需要抽样设计；
- 自由度规则与小样本校正；
- 和其他插件能否组合；
- 对照数据。

**HAC（Newey–West）**：

- 核函数用 Bartlett。
- 滞后阶数可以由用户指定；默认用 ⌊4(T/100)^{2/9}⌋（Newey & West, 1994），并在结果里显示所用的规则和值。
- 以下情况拒绝：数据没有声明时间顺序、有时间缺口、与聚类同时使用。Driscoll–Kraay 以后再做。
- **对照要对齐三方的默认值差异**：
  - Stata `newey` 不做预白化，做小样本校正；
  - R `sandwich::NeweyWest` 默认 `prewhite = TRUE`，所以要设 `prewhite = FALSE, adjust = TRUE`；
  - statsmodels 的 `use_correction` 需要单独确认。
  
  这正是为什么每个插件都要有对照数据：同名方法在不同软件里的默认值并不相同。

### 3.5 组合子

#### 按组分别执行（`by_group`，替代 SPSS SPLIT FILE / Stata `by:`）

- **显式**：每个分析自己写“按 X 分组”，不做隐藏的全局开关，因为 SPLIT FILE 忘了关是常见的错误来源。
- **子集语义**：能力要声明自己的子集语义。
  - `subset`：先筛选再分析。
  - `domain`：复杂抽样用域估计。按组先切数据会破坏方差估计，这是 Stata 专门警告过的错误。
  - `unsupported`：拒绝。
- **缺失的组值**：自成一组“(missing)”，并在结果里写明，不静默丢掉。
- **小组**：最低样本量取自检查库（例如每个参数的行数、每个自变量对应的事件数），不够就把这一组标为“无法估计”并写明原因。
- **输出**：集合信封，各组结果并排显示。
- **自动不变性测试**：每个开放按组执行的能力，组 g 的结果都必须等于“先筛选 group == g 再单独运行”的结果。这是一条通用测试，不需要为每个能力单独写。
- **多重比较**：各组的检验计入台账，并提供跨组的 Holm 或 Benjamini–Hochberg 校正。
- **组间差异**：各组分别估计的系数并排放着，不等于检验了它们的差异。
  - 差异检验的做法是：合并样本、加入与组的完全交互项、再做 Wald。这里直接复用 §3.3。
  - Agent 在说出“两组不同”“某组更大”这类话之前，必须引用差异检验的结果。这条规则由数字核对扩展来执行。
- **上限**：默认最多 50 组。组更多时，建议改用多层模型或交互项，因为那已经是多层结构的问题。
- **性能**：只切分一次；各组复用同一套设计矩阵构造。预算见 objective。

#### 多重插补（`multiple_imputation`）

- 沿用 `replicate_combine.plan` 合同。
- 流程：生成 m 份数据并记录 manifest → 每份分别拟合 → 按 Rubin 规则合并。
- 小样本自由度用 Barnard–Rubin（1999）调整；同时报告缺失信息比例（FMI）和相对方差增量（RVI）。
- 不显示单份数据的残差和 R²。如果以后要合并 R²，用 Harel（2009）的 Fisher z 方法，并写明方法。
- 只有提供推断核心的模型族才能参加。不支持的组合明确拒绝，包括与复杂抽样同时使用、插补不完整。
- 对照：R `mice::pool`。
- 合并结果上的后估计按 §3.3 拒绝。

#### 其他组合子

P7 已有的 bootstrap、置换、抽样复制权重，以后统一输出集合信封，不在本版范围。

### 3.6 Agent 怎样组合积木

```text
自然语言
  → Agent 从目录挑选积木，写出一个带类型的计划（积木 + 参数，按顺序或有向无环图组织）
  → 验证器检查性质、接口、角色、输出类型是否匹配
  → 生成提案；会改动数据、元数据或模型的需要用户确认
  → 执行
  → 核对声明的预期效果
  → 写入台账
```

- **拒绝要讲原因**：用性质来解释，而不是笼统地说不支持。例如“logit 的这个节点没有声明时间顺序，HAC 需要先设定时间变量”。
- **Recipe**：保存下来的带类型计划，可以带参数、可以分享。它本身是数据，不是代码；运行时照样经过验证器。
- **步骤输出类型**：重新评估 `V189-TYPED-STEP-BINDING`。最小做法是让每个步骤的输出声明信封种类（数据集、模型结果、集合、检验），组合子声明自己接受哪些种类。**不**引入 BACKLOG 中已否决的 Plan IR（`V189-AGENT-COMPILER-IR`），除非真机评测复现了组合错误。
- **可达性守卫**：扩展到检查、后估计、标准误插件和组合子。
- **边界**：`code.execute` 对自然语言继续关闭。生成器见 §9.1。

### 3.7 准入套件

一个能力要合入，必须具备以下五项：

1. **声明**：性质、接口、角色、子集语义。
2. **对照**，二选一：
   - R 或 Stata 的对照数据；
   - 没有现成实现时，用**模拟数据验证参数找回**：从已知参数生成数据，重复 R 次（例如 500 次），检查偏差接近 0，95% 置信区间的覆盖率落在 95% ± 2×√(0.95×0.05/R) 以内（R = 500 时约为 ±1.95 个百分点）。
3. **信封声明**。
4. **台账分类**。
5. **一条真机 Agent 评测用例**。

另外两项由系统自动推导并列出，不需要手写：

- 适用的检查（§4）；
- 它开放的组合子要跑的不变性测试。

缺少任何一项都不能合入。现有的模型族生成缺口清单，每项写明计划补齐的版本。

这套检查同时也是以后“Agent 生成的能力”转为正式能力的关口（§9.1）。

## 4. 检查库

### 4.1 一项检查的声明

| 字段 | 说明 |
|---|---|
| `id` | 例如 `collinearity.gvif`、`iv.first_stage_strength` |
| `requires` | 需要的性质、角色、接口，用来匹配适用对象 |
| 盲化等级 | `design`：只用自变量、工具、角色；`outcome_distribution`：只看结局变量本身的分布；`pre_period`：只看处理前的结局；`post_fit`：用到拟合出的关系。详见 §4.3 |
| 成本与预算 | 超出预算时标为“未检查”并写明原因，不静默跳过 |
| 阈值 | 作为数据声明，附文献出处。项目可以调整，但每次调整都记入台账，防止事后放宽 |
| 状态 | Holds（成立）/ Caution（注意）/ Fails（不成立）/ Not applicable（不适用）/ Needs your reason（需要你给理由）/ Not checked（未检查，附原因） |
| 证据 | 具体数字，例如 F = 100.5、VIF = 75.7 |
| 来源标签 | Computed（计算得出）/ Judgment（Agent 的判断）/ Your reason（用户给出的理由）。界面上必须区分 |
| 补救提议 | 只作为提议，从不自动执行 |

### 4.2 首批检查

多数已有实现，要做的是收拢到检查库，并修正前面发现的缺陷。

| 检查 | 适用于（性质） | 盲化等级 | 阈值与出处 | 现状 |
|---|---|---|---|---|
| 每个参数的行数 | 有参数的估计 | design | 少于 10 行为 Caution（Harrell） | 新增 |
| 共线性（GVIF） | 设计矩阵至少 2 项 | design | 用 GVIF^{1/(2·df)} 处理多列的因子项（Fox & Monette, 1992），对应 VIF > 10 | **修正缺陷 1、3** |
| 完全拟合 | 最小二乘 | post_fit | 残差方差约为 0 时判为 Fails，并隐藏推断统计量 | **新增，修正缺陷 2** |
| 分离 | 二元、有序、多项结局，最大似然 | post_fit | 用线性规划判定（Konis, 2007）；补救提议为 Firth 惩罚 | **修正缺陷 4，并扩展到 probit** |
| 每个自变量对应的事件数 | 二元结局 | outcome_distribution | 少于 10 为 Caution（Peduzzi, 1996），同时注明 van Smeden 等人指出这只是粗略指引 | 新增 |
| 过度离散 | 计数结局 | post_fit | Cameron–Trivedi 检验 | 已有（仅 Poisson），扩展到所有计数结局 |
| 工具强度 | 用到工具变量 | design | F < 10 判为 Fails（Staiger & Stock）；F < 104.7 判为 Caution，并自动附上 Anderson–Rubin 区间（Lee, McCrary, Moreira & Porter, 2022） | 已有 `iv.weak_instruments`，加上后一条门槛 |
| 排除限制 | 用到工具变量 | — | 只有一个工具时无法检验，状态为 Needs your reason；工具多于一个时另做过度识别检验（post_fit） | 新增 |
| 重叠 | 处理变量加协变量 | design | 倾向得分落在 [0.1, 0.9] 之外的比例（Crump 等, 2009） | 已有 `matching.balance` |
| 事前趋势 | DID、事件研究 | pre_period | 显示事前系数，附上 Roth（2022）的提醒，并链接到已实现的 HonestDiD 敏感性分析 | 已有 |
| 聚类数 | 聚类标准误 | design | 少于 40 为 Caution，补救提议为 wild cluster bootstrap（Cameron, Gelbach & Miller, 2008） | 新增 |
| 平稳性与序列长度 | 时间序列结局 | outcome_distribution | ADF 与 KPSS 一起判断 | 已有，作为检查接入 |
| 时间顺序与缺口 | HAC、滞后项 | design | 必须先 tsset，且不能有缺口 | 已有 `data.tsset`，作为检查接入 |
| 缺失 | 任何分析 | design | 缺失比例、完整个案数、缺失模式；补救提议为多重插补 | 已有 `missingness.profile` |
| 抽样设计是否声明 | 有抽样权重 | design | 沿用 `design_precheck` 的红线（可以提醒，不可以命令） | 已有 |
| 异方差 | 最小二乘 | post_fit | Breusch–Pagan、White；结果用来选择标准误 | 已有 |

### 4.3 盲化等级决定一项检查能用在哪里

| 等级 | 用到什么 | 能否用于选方案 | 例子 |
|---|---|---|---|
| design | 自变量、工具、角色 | 能 | 共线性、工具强度、重叠、聚类数 |
| outcome_distribution | 结局变量本身（类型、零值比例、偏度、长度） | 能：选择模型族本来就要依据它 | 每个自变量对应的事件数、平稳性 |
| pre_period | 处理前的结局 | 可以显示，但判断规则必须事先固定（Roth 的提醒） | 事前趋势 |
| post_fit | 拟合出来的关系 | **不能用于选实质设定**，只能用于选推断方法（标准误、Firth 惩罚、Anderson–Rubin 区间） | 分离、异方差、内生性检验 |

- 方案比较时传给 Agent 的上下文只包含前三级。这由上下文编译器执行，并有测试检查（§5.3）。
- 这张表同时回答了“判断标准会不会太多、太冗余”：
  - 标准挂在前提假设上，不挂在模型族上。
  - 前提假设只有十几种，模型族只需要声明性质。

## 5. 研究规划的重新设计

### 5.1 什么时候规划，什么时候直接执行

- **请求具体时**（例如“用 logit 跑 y 对 x”）：直接生成带类型的提案。
- **请求开放时**（例如“不知道怎么分析”“教育对工资有多大影响”）：进入方案比较。
- **目标驱动（从结尾反推）**：用户先给出终点，例如一张表的骨架、一个假设、一张图。Agent 反推需要哪些数据和步骤，并在图上标出哪些已经做过、哪些还缺。

### 5.2 方案与试水

- **一个方案包含**：
  - 带类型的计划（§3.6）；
  - 对“是否回答了所问的问题”的说明；
  - 适用的检查；
  - 成本估计。
- **三级试水**：
  - L0：看数据画像，毫秒级，不调用 LLM。沿用 Notebook 的数据证据包。
  - L1：跑前提检查，秒级，由确定性代码完成。
  - L2：做简化估计。只在用户要求时做，结果标“初步”，并计入台账。
- **Token 固定**：每一轮规划只调用 LLM 两次，第一次列出候选方案，第二次读对比表并写说明。不按方案数循环调用。
- **成本如实说**：做不了便宜试水的方案，就直接说明，例如“只能直接跑，预计 3 分钟”。
- **不浪费**：试水的产出本身就是谱系节点，选定方案后正式运行直接复用。

### 5.3 比较与推荐

- **比较维度是固定的**：
  1. 是否回答了所问的问题。这一项排第一：用户问因果，给出相关就不对。
  2. 数据是否支持，也就是检查结果。
  3. 假设强弱：能否检验。
  4. 成本。
  5. 领域惯例：以后从记忆读取。
- **不看的东西**：显著性、R²。预测任务例外，但测试集必须封存。
- **Agent 看不到结果**：方案比较时，Agent 的上下文里不包含候选方案的估计值和 p 值。
  - 由上下文编译器剥离，和外发管控拦住原始行是同一种做法。
  - 有测试断言这一点。
- **标准先固定**：判断标准写入台账事件 `criteria_fixed` 并带时间戳，时间早于任何估计值。
- **推荐结果**：推荐 / 打平 / 证据不足，沿用 Notebook 的合同。
- **来源标签**：每条检查结果都标明它是计算得出、Agent 的判断，还是用户给的理由。

**设计图里的例子**（`Plans.dc.html`）：

- 方案 C 的第一阶段更强（F = 229.4），但母亲的教育很可能直接影响工资，所以不推荐。
- 工具变量如果本身就影响结局，工具越强，得到的错误答案反而越精确。
- 这正是“以数据好看为目标”会选错的典型情形。

### 5.4 用户的自主权

- 任何方案都可以运行，包括不推荐的（“Run anyway”），运行会被记录。
- 如果先运行了几个方案，看过结果再选定其中一个，这个选择会记为“看过结果后选定”，被选中的方案标为探索性。

### 5.5 共线性与 Quant 的过拟合

**共线性**：

- 如实说明“这份数据分不开 x1 和 x2”，并提供联合检验或联合效应。
- 删掉一个混杂变量属于设定变更，必须在看到它对结果的影响之前给出理由。

**Quant 因子挖掘**：

- 按数据集和假设族自动计数试验次数，计数不能重置，写在台账里。
- 显著性门槛随试验次数提高：Harvey, Liu & Zhu（2016）建议 t > 3；另有 deflated Sharpe ratio（Bailey & López de Prado, 2014）。
- 样本外区间封存，一个因子只能用一次。
- 在多个策略之间挑选时，用 White's Reality Check 或 Hansen SPA。
- 这部分与 `V189-GRAPH-SCALE` 的“trial 晋升制”一起做。

## 6. 四层分工与三种顺序

| 层 | 回答什么 | 顺序 | 界面位置 |
|---|---|---|---|
| 谱系图 | 什么由什么算出 | 计算顺序（有向无环图） | 地图列，可全屏 |
| Agent 对话 | 怎么操作 | 对话顺序 | 右侧整列 |
| 时间线（台账） | 什么时候做了什么、为什么 | 探索顺序（按时间） | 下方时间线条，可展开到中间 |
| 报告 | 怎么讲给别人听 | 叙述顺序（可重排，可倒叙） | 中间的报告视图 |

**三层之间的链接**：

- 每个结果节点都链接到对应的时间线事件；
- 报告里的每个数字都链接到节点；
- 报告的披露部分由时间线生成，不由 LLM 写。

**研究不是线性的，由以下机制支持**：

- 可以从任何中间节点分叉；
- 改了中间节点后，下游标为过期并重算（已有）；
- 转折点记为 `question_change` 事件；
- 方案以未执行的虚线分支出现在图上；
- 支持从结尾反推的规划（§5.1）。

## 7. 验证性分析与探索性分析

### 7.1 判定规则

一个分析记为**预先设定（pre-specified）**的条件是：它的计划和判断标准，在本项目里任何与同一问题相关的结果被用户或 Agent 看到之前，就已经记入台账。

其余情况都记为**探索性（exploratory）**，包括：

- 看到相关估计之后才提出的分析；
- 问题变更之后的分析；
- 运行了几个方案、看过结果再选定；
- 看过结果之后才提议的数据改动。

### 7.2 台账的新增内容

- 事件类型：`criteria_fixed`、`decision`（例如用户给出的排除限制理由）、`question_change`。
- 每个分析新增 `specification_status`（预先设定 / 探索性）及判定理由。
- 按问题编号分组。

### 7.3 报告

- 预先设定的分析与探索性分析分成两节。
- 多重比较校正在同一问题之内进行。
- 披露文字由 Workbench 根据台账生成。

### 7.4 边界

- 系统只能判断它自己观察到的情况。用户在软件之外看过数据，系统无从知道，所以标签描述的是“系统观察到的顺序”。
- 以后可以支持导入预注册文件，把对应分析标为验证性（不在近期范围）。
- 看到结果之后修改判断标准：之后的分析一律记为探索性。

## 8. 界面与交互

### 8.1 设计依据

参照 Apple 的设计原则（Purpose、Agency、Responsibility、Familiarity、Flexibility、Simplicity、Craft、Delight），以及 Claude Code、Codex 的对话式工作方式。以下是原创设计，不复制任何产品的界面。

- **Purpose**：研究者的注意力只给数字和判断。内部结构（合同版本、哈希值）折叠进“来源”里。
- **Agency**：用户始终可以运行任何方案。写操作需要确认；读操作直接运行，但会被记录。
- **Responsibility**：检查结果区分“计算得出”和“Agent 的判断”；Agent 核对过的数字带核对标记。
- **Simplicity**：一个 Agent，一个中间区域。常用路径放在第一层，高级选项放第二层。
- **Craft**：间距、字号、颜色都作为设计 token 定义；支持深色模式；动效用弹簧曲线。

### 8.2 两种布局都保留，随时切换（设计图第一行）

用户在 2026-10-01 决定：A（结果在中间）为主，同时保留 B（图在中间），由用户自己切换，两者功能一致。设计如下。

**同一个网格，宽的那一列换位置。**

| | 结果主导（Results first） | 谱系主导（Lineage first） |
|---|---|---|
| 左 | 地图列 280px | 地图（占剩余宽度） |
| 中 | 舞台（占剩余宽度）：当前焦点的完整视图 | 舞台收为 360px 的检查栏：同一份内容的紧凑排版 |
| 右 | Agent 列 380px | Agent 列 380px（位置和宽度不变） |
| 下 | 下方面板：Timeline · Runs · Logs · Activity | 同左 |
| 设计图 | `ModeResults.dc.html` | `ModeGraph.dc.html` |

**切换方式**：

- 顶栏的分段开关（Results first / Lineage first），快捷键 ⌘\；
- 地图列右上角的“展开”按钮，以及检查栏底部的“Open wide”按钮；
- 也可以直接拖动地图与舞台之间的分隔线。拖动有两个停靠点，就是这两种布局。松手时按速度推算落点并吸附到较近的停靠点（Apple 的动量投影），弹簧动画，临界阻尼。

**为什么能保证功能一致**：

- 两种布局用的是同一组组件：地图、舞台、Agent、下方面板。
- 舞台按自身宽度切换排版（container query）：宽时显示完整结果，窄时显示紧凑版。内容和顺序相同，紧凑版把次要部分折叠成可展开的行。
- 选中的节点、打开的标签、Agent 的对话在切换时都不变。

**规则**：

- 每个项目记住上次使用的布局。
- Data、Tables、Report、Plans 这几个视图需要宽度（表格和文档），在谱系主导时打开它们会临时用宽舞台；回到 Analysis 视图时恢复原来的布局，并有过渡动画说明变化。
- 不加模态遮罩，不打断操作；动画从当前位置开始，可以中途打断（Apple 的可打断原则）。
- 谱系主导相当于现在的界面（中间是图，右边是详情）再加上 Agent 列；结果主导是新的默认布局。习惯现有界面的用户切过去就能找到熟悉的排布。

### 8.3.1 区域职责（以结果主导为例）

- **顶栏**（半透明材质）：
  - 左：显示或隐藏地图、项目切换；
  - 中：视图切换 Analysis · Data · Tables · Report · Plans；
  - 右：布局开关、搜索或命令（⌘K）、New analysis、Rerun、设置。
- **地图列**：
  - 按谱系画成树，节点显示关键数字和所属运行，例如“educ 0.466 · run 53e2”；
  - 虚线表示未执行的方案，实心点表示预先设定，空心圆表示探索性；
  - 右上角按钮切到谱系主导。
- **舞台**：
  - 顶部是标签栏，可以开多个对象并排切换；
  - 下面一行是本页目录（Result · Checks · Coefficients · Rerun with changes · Compare · Roles · Lineage · Info）；
  - 结果视图：主要估计值、区间图、来源行（含估计方程）、检查（分为估计前和估计后）、系数表、改参数重跑、比较、角色、谱系路径、基本信息。
- **Agent 列**：
  - 占整列高度；
  - 输入框上方的焦点标签表示这次对话作用于哪个对象；
  - 回复附带“N 个数字已核对”；
  - 下方一行说明“只读分析直接运行，改动需要你确认”。
- **下方面板**：
  - 收起时是一行：最近几个事件、预先设定或探索性标记、当前披露计数；
  - 展开后有 Timeline、Runs、Logs、Activity 四个标签，可以拖高。

### 8.4 关键交互

- **焦点上下文**（替代 Data 页 Agent 的只读作用域，即 `V189-DATA-TAB-AGENT-SCOPE`）：
  - Agent 的作用范围由当前焦点决定。焦点可以是数据集、节点、方案、报告或时间线。
  - 用 `FocusRef`（类型 + id）表示焦点，由上下文提供者注册表解析，不为每个页面各配一个 Agent。
- **选中即问**：
  - 在 Agent 回复、结果、报告里选中文字，会弹出 Ask / Explain / Add to message / Show source。
  - 选中的内容作为带来源链接的引文进入输入框（设计图 `Report.dc.html`）。
- **方案对比**：
  - 三张方案卡片并排，每张列出按比较维度的检查结果；
  - 状态标签同时有文字和图标，不只靠颜色区分；
  - 推荐的卡片用描边强调，不用左侧色条。
- **来源随手可查**：每个数字都能一键看到节点、数据、估计方法和对照状态。
- **写操作的确认**沿用现有的提案卡片，改用新的视觉语言。

### 8.5 视觉语言（设计 token）

- **字体**：
  - 界面用系统字体（Mac 上是 SF Pro 和苹方）；
  - 数字一律等宽数字（`tabular-nums`）；
  - 报告正文用系统衬线体（New York 或宋体），把“阅读”和“操作”区分开；
  - 等宽字体只用于标识符。
- **字号**：界面 13px，Agent 和阅读 14–16px，区块标题 15px，页面标题 22px，关键数字 44px（字距 −0.02em）。
- **颜色**（浅色模式；深色模式在同一组 token 下重新定义）：

  | token | 值 |
  |---|---|
  | 窗口 | `#F4F4F1` |
  | 内容面 | `#FFFFFF` |
  | 细线 | `#E3E2DE` |
  | 正文 | `#1C1C1E` |
  | 次要文字 | `#48484D` / `#5B5B60` |
  | 说明文字 | `#6E6E73`（对白底对比度 ≥ 4.5:1） |
  | 强调 | `#0A66D8`（对白底 5.4:1） |
  | 状态：成立 | 字 `#1B6B43` / 底 `#E5F2EA` |
  | 状态：注意 | 字 `#8A5300` / 底 `#FAF0DB` |
  | 状态：不成立 | 字 `#A1281F` / 底 `#FBE8E6` |
  | 状态：需要理由 | 字 `#48484D` / 底 `#EEEEF0` |
  | 预先设定 | 实底标签 |
  | 探索性 | 虚线描边标签 |

- **材质**：顶栏和浮层半透明（`backdrop-filter`）；遇到 `prefers-reduced-transparency` 时改为实底。
- **动效**：
  - 默认用临界阻尼弹簧（damping 1.0，response 约 0.35 s）；
  - 只有带动量的手势（拖动、甩动）才加回弹；
  - 面板从哪里出现就回到哪里；
  - 遇到 `prefers-reduced-motion` 时改为淡入淡出。
- **图标**：1.5px 描边的线性图标，不用 emoji。

### 8.8 迁移顺序

每个功能的新位置见 §8.3。迁移按以下顺序进行，保证任何时候都不丢功能：

1. 新外壳放在功能开关后面，和旧界面并存。
2. 依次搬入：地图与布局开关 → 舞台标签与结果视图 → Agent 列（先合并下方 Agent 和节点 Ask AI）→ 下方面板（Timeline、Runs）→ Data、Tables、Report 视图（Report 写作 Agent 并入）。
3. Plans 视图先原样承载现有的 Notebook 界面；v1.9.1 的方案对比视图可用之后，再下线 Notebook 页。Notebook 的后端（证据包、可行性协议、推荐决定、方案生命周期）继续复用。
4. 两种布局下各走一遍完整的验收场景，与旧界面逐项对照，确认没有丢功能后，才把新外壳设为默认。

### 8.9 可访问性

- 所有控件用真实的 `button`、`input`、`label`，只有图标的按钮都带 `aria-label`。
- 文字对比度 ≥ 4.5:1。
- 状态同时用文字、图标、颜色表达。
- 键盘能完成全部操作。
- 字号跟随系统设置，间距使用 rem。

## 11. 风险与待定问题

| 风险 | 缓解 |
|---|---|
| 推荐时看不到结果，用户会觉得受限 | 任何方案都可以直接运行；运行后结果照常显示，只是会被记录和标注 |
| 协方差矩阵的存储量 | k ≤ 500 时约 2 MB；超出的部分只保存关注参数，并明确写出限制 |
| 大数据上的检查性能 | 每项检查有预算；超出预算时标为“未检查”并写明原因 |
| Agent 的判断可能错 | 界面上标明“判断”；用户可以覆盖，覆盖记入台账 |
| 界面迁移成本 | 新界面放在开关后面，功能追平后再切换 |
| 设定分类过严，挡住正常的探索 | 探索性本身是正当的；标注只是让路径可见，不阻止分析 |
| 两种布局加倍维护和测试成本 | 同一组组件、同一个网格；舞台用 container query 做宽窄两种排版；视觉回归测试在两种布局下各截一次 |
| 借鉴外部规范时引入许可或质量问题 | 只取 Apache-2.0 部分，固定到具体提交，保留许可与修改说明；第三方素材（figures4papers）不用；规则进入我们的格式并有测试（§13） |

## 12. 验收与度量

- **AI 入口数量为 1**：界面上只有一个 Agent 输入框。
- **两种布局功能一致**：同一组验收场景在结果主导和谱系主导下各走一遍；§8.3 表中的每个现有功能在两种布局下都能用到。
- **三个场景**：“导入数据 → 得到第一个可信结果”分别在因果、描述、时间序列三个场景下，在浏览器里按真实操作走通，并记录交互次数和耗时。
- **测试守住的规则**：
  - 规划上下文不包含任何估计值；
  - 披露计数等于台账计数；
  - 界面字符串中没有内部标识符；
  - 共享代码中没有模型族名字的字面量；
  - 可达性守卫覆盖全部新积木。
- **可访问性检查**：对比度、键盘操作、减少动效。
- **性能**：沿用各版 objective 的预算。

| `nature-reviewer` | Draft | 模拟三份互不知情的审稿意见 | 投稿前检查 |
| `nature-data` | Draft | Data Availability 声明与 FAIR 检查 | 数据可得性声明 |
| `nature-ref-verifier` | Stable | 多来源核对参考文献 | 以后可考虑 |

其余（文献检索与下载、论文转 PPT、专利、实验日志等）与报告无关。

### 13.2 不整包接入的原因

1. **运行方式不同。** 这些 skill 假设 Agent 能读写本地文件、执行任意脚本。Workbench 的 Agent 只能调用带类型的工具，`code.execute` 对自然语言关闭；整包接入等于为它打开任意执行。
2. **外部服务。** 示意图生成要调用 OpenRouter，文献下载要用图书馆账号或浏览器登录状态，都与外发管控冲突。
3. **许可。** 主体是 Apache-2.0，但 `nature-figure` 里的第三方素材 `figures4papers` 另有条款，它的 README 明确说仓库许可不自动适用于这部分。
4. **成熟度。** 与我们最相关的 `nature-statistics`、`nature-writing`、`nature-reviewer` 都还标为 Draft。
5. **变化快。** 直接依赖会让报告行为随上游变化。
6. **体量。** 完整说明加参考文档很长，每次都放进上下文成本高，也会冲淡我们自己的规则。

### 13.3 吸收方式：分三层

| 层 | 做法 | 例子 |
|---|---|---|
| 确定性检查 | 能由代码判断的规则，进入检查库（§4），新增“报告检查”一类 | ① **伪重复**：数据声明了个体编号且每个个体有多行，模型却没有聚类或多层结构时提醒（对应它的 pseudoreplication）。② **“一组显著、一组不显著”不等于两组有差异**：与 §3.5 的组间差异规则一致。③ 报告里每个 p 值都附效应量和置信区间；p 值写成 p < 0.001 而不是 0。④ 每个结果写明 n。⑤ 图中误差线写明是 SD、SE 还是置信区间。⑥ 识别策略只支持相关的，不得写成因果 |
| 写作规范包 | 声明式数据：规则、章节模板、图注模板；写报告时加载，按项目选择 | 英文期刊（Nature 系）、中文经济学期刊、APA。信息不全时写“需要你补充”，对应它的 `AUTHOR_INPUT_NEEDED`，绝不编造。报告里的数字仍然只能来自结果，由数字核对把关 |
| 期刊图表配置 | 由我们的作图代码执行的配置 | 单栏、双栏宽度；字体与字号；矢量格式；色盲友好配色；面板标号 a、b、c；导出后做面板对齐和文字碰撞检查，可以参考它的脚本思路 |

### 13.4 我们多出的一层：拿事实核对

- `nature-statistics` 审查的是文字：它只能根据稿件里写了什么来推断。
- Workbench 有真实的记录：台账、谱系、结果。所以同一份检查清单，我们可以逐条核对事实：
  - 文中的 n 是否等于模型的估计样本；
  - 文中每个数字是否来自某个结果（数字核对已经在做）；
  - 披露的检验次数是否与台账一致；
  - 预先设定与探索性是否标对。
- 这正是 AI native 超过 SPSS 和 Stata 的地方：投稿前检查由系统根据事实生成，审稿人可能质疑的地方提前标出。

### 13.5 许可与来源

- 只取 Apache-2.0 的部分，固定到具体提交，保留其许可与署名，并标明我们的修改。
- 不使用 `figures4papers` 等第三方素材，不接入它用到的外部服务。
- 期刊名称只用来描述风格（例如“Nature 系期刊风格”），不暗示官方认可。
- 吸收进来的每条规则都转成我们的格式，并有测试。
