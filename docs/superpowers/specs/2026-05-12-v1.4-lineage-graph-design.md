# V1.4: Lineage Graph — Design Spec

Date: 2026-05-12

**Prerequisite**: V1.3.2 (Foundation Refactor) must ship first. V1.4 assumes the `diagnostic_preview` package layout, the `term_parser` module, and the frontend `validateDiagnosticPreview` validator are in place.

## 1. Goal

V1.4 introduces a first-class **artifact lineage graph** as the foundation for Workbench's next phase. The graph records every transformation between raw data and model output as nodes and edges, persists alongside each run, and surfaces in a new Lineage tab where users can browse, fork, archive, and rewind any step.

The primary user outcome is: after a run finishes, the user can see exactly how each variable was derived, follow forward and backward dependency chains between original columns and model coefficients, branch off from any node to try alternative transformations or models, and revisit any prior decision without losing earlier attempts.

V1.4 is also a deliberate architectural foundation. Most items on the broader roadmap (multiverse / specification curve analysis, AI annotation and suggestion hooks, multi-format reports with export governance, process-level rollback history, smart variable detection) all depend on having an artifact graph as a shared substrate. V1.4 builds that substrate end-to-end through one user-visible feature; later versions plug into it without redesigning the underlying model.

## 2. Scope

### 2.1 P0 Must Have

1. New `graph_model.py` defining `Node`, `Edge`, `Graph`, `DecisionPoint`, `BranchRef`, with stable schema versioning.
2. New `graph_store.py` persisting one graph per run as a single JSON document, with append-friendly mutation API.
3. `orchestrator.py` is modified to emit graph nodes and edges as it runs, in addition to existing artifacts. Existing artifact outputs and contracts are unchanged.
4. New API endpoints:
   - `GET /runs/{run_id}/graph` returns the full graph (with optional `?include_archived=true`).
   - `POST /runs/{run_id}/graph/fork` creates a new branch from a specified node.
   - `POST /runs/{run_id}/graph/nodes/{node_id}/archive` and `/unarchive` toggle the archived flag.
   - `POST /runs/{run_id}/graph/rerun` re-executes the pipeline starting from a chosen node with overridden parameters.
5. Each node carries:
   - `id`, `kind` (`dataset_stage`, `variable`, `operation`, `model`, `report`), `display_label`, `created_at`.
   - `trust` reusing the V1.3 four-level enum (`OK / CAUTION / WARNING / BLOCKER`).
   - `auto_chosen: bool` flag for "the system picked a default here, user/AI may want to review".
   - `auto_chosen_reason`: short structured explanation when `auto_chosen=true`.
   - `archived: bool` (soft delete).
   - `payload_ref` pointing to the materialized artifact on disk.
   - `decision_point` (optional): records the candidate set the system chose from, so V1.5 multiverse analysis can enumerate alternatives.
6. Each edge carries `source_id`, `target_id`, `op`, `params`, `reversible: bool`, `inverse_op` (when reversible).
7. Frontend new Lineage tab in Run detail with:
   - Multi-resolution rendering: stage-level nodes by default; double-click expands to variable-level subgraph.
   - Cross-layer edges: when a stage is expanded, its internal variable nodes preserve edges to upstream and downstream nodes (folded or expanded), not enclosed in a sealed box.
   - Selected-node detail panel with two breadcrumbs:
     - Containment path (`run_42 › 变换 › log_income`) — Finder-style nesting.
     - Lineage path (`income → income_cleaned → log_income → 模型A.β`) — data provenance.
   - Each breadcrumb segment is clickable and navigates the selection.
   - Copy-path button on both breadcrumbs.
   - Archived branches shown as dashed/faded with a "Show archived (N)" toggle.
   - "Collapse all" button.
   - Double-click on any node toggles fold / expand (analogous to macOS Stage Manager's stack toggle).
   - Right-click menu: Fork, Archive, Restore, Rerun from here, Copy lineage path.
8. Forking semantics: forking from node X creates a new branch in the **same** run, sharing all upstream nodes with the original branch. The user may then add new operations on this branch. The data model supports arbitrary branching (any node may be forked any number of times). V1.4 UI is optimized for the common case of 1–5 active branches per run; larger graphs still render correctly but the layout algorithm and panning controls may feel less polished — this is a known V1.5+ improvement target, not a V1.4 blocker.

   "Rollback" is not a separate primitive. The user-visible "rollback to here" action is implemented as the composition: fork from the chosen node + archive the original branch + rerun on the new branch. This keeps the data model strictly append-only and consistent with the soft-delete-only rule (§2.1 #9).
9. Soft delete is the only deletion the UI offers. Archived branches persist on disk and remain restorable. Physical deletion is gated behind a separate Run-level "Purge" action with double-confirmation; not in the V1.4 UI by default.
10. Existing `GET /runs/{run_id}` is unchanged. The graph is fetched separately by the new endpoint to keep the existing payload size stable for callers that do not need it.
11. Backwards compatibility: runs created before V1.4 expose an empty graph (`{nodes: [], edges: []}`) with a `legacy: true` marker. The Lineage tab shows a friendly empty state for such runs.

### 2.2 P1 Should Have

1. "Compare branches" view: select two leaf nodes (e.g., model results from two branches) and show side-by-side coefficient and diagnostic comparison.
2. Graph minimap for large graphs.
3. Branch naming and renaming (V1.4 uses auto-generated names like `branch_2`, `branch_3`).
4. Search box: filter nodes by variable name or operation name.
5. Export the graph as a portable JSON for offline inspection.
6. Auto-layout improvements: deterministic, stable across mutations.

### 2.3 Non-Goals (V1.4)

The following items are intentionally deferred to keep V1.4 focused:

1. **Multiverse / specification curve UI.** V1.4 stores the `decision_point` metadata that V1.5 needs, but does not enumerate combinations or batch-generate branches.
2. **Real AI integration.** No live AI calls. Node-annotation and suggested-fork data structures are reserved (see §6) but no producer is wired up.
3. **Multi-format reports** (Word / PDF / LaTeX) and export governance.
4. **i18n / language switching.**
5. **New statistical methods** beyond what V1.3.1 supports.
6. **Adjustable confidence intervals.**
7. **Multi-format data ingestion** beyond CSV / XLSX.
8. **Native local folder picker** for parent directory.
9. **Auto-detection of dependent vs regressor variables.**
10. **Promote-branch-to-new-run** ("Hybrid C" from brainstorming). Not built until a real user need surfaces.
11. **Unlimited nested forks.** V1.4 caps at "linear path + one rollback + one fork per node".
12. **Interactive step-by-step pipeline mode.** The pipeline remains end-to-end (see §4.1).

## 3. Architecture

### 3.1 Data Model (`backend/workbench/graph_model.py`)

```python
class NodeKind(str, Enum):
    DATASET_STAGE = "dataset_stage"   # raw, cleaned, transformed (folded view)
    VARIABLE      = "variable"        # single column at a stage (expanded view)
    OPERATION     = "operation"       # an applied transform (rare; usually edge metadata)
    MODEL         = "model"           # a fitted model
    REPORT        = "report"          # a generated report artifact

class Trust(str, Enum):
    OK = "ok"; CAUTION = "caution"; WARNING = "warning"; BLOCKER = "blocker"

@dataclass
class DecisionPoint:
    """Records the candidate set the system selected from at this node.
    V1.4 stores it; V1.5 multiverse UI consumes it."""
    candidates: list[str]            # e.g. ["log", "sqrt", "raw", "winsorize"]
    chosen: str
    chooser: Literal["user", "system_default", "ai_suggestion"]

@dataclass
class Node:
    id: str                          # stable across mutations
    kind: NodeKind
    display_label: str
    created_at: str                  # ISO 8601
    parent_stage_id: str | None      # for VARIABLE nodes, the containing stage
    branch_id: str                   # which branch this node belongs to
    trust: Trust = Trust.OK
    trust_reason: str | None = None
    auto_chosen: bool = False
    auto_chosen_reason: str | None = None
    archived: bool = False
    payload_ref: str | None = None   # path to artifact on disk
    decision_point: DecisionPoint | None = None
    annotations: list[Annotation] = field(default_factory=list)  # reserved for V1.6 AI

@dataclass
class Edge:
    id: str
    source_id: str
    target_id: str
    op: str                          # e.g. "np.log(x+1)", "drop_na", "OLS.fit"
    params: dict
    reversible: bool = False
    inverse_op: str | None = None

@dataclass
class BranchRef:
    id: str                          # e.g. "main", "branch_2"
    forked_from_node_id: str | None  # None for "main"
    head_node_ids: list[str]         # current leaf nodes of this branch
    archived: bool = False

@dataclass
class Graph:
    schema_version: int = 1
    run_id: str
    nodes: dict[str, Node]
    edges: dict[str, Edge]
    branches: dict[str, BranchRef]
    legacy: bool = False             # True for pre-V1.4 runs
```

### 3.2 Storage (`backend/workbench/graph_store.py`)

- One JSON file per run: `runs/{run_id}/graph.json`.
- All mutations go through `GraphStore.mutate(run_id, fn)` which:
  - Acquires a per-run file lock.
  - Loads, applies `fn(graph)`, writes atomically (temp + rename).
  - Returns the post-mutation graph.
- Graphs are bounded in V1.4 (linear path + one rollback + one fork per node), so a single JSON file is acceptable. If V1.5+ allows unlimited nesting, this becomes a candidate for SQLite migration; the public `GraphStore` API is designed to make that swap mechanical.
- `payload_ref` strings are paths relative to the run directory, so graphs stay portable when runs are moved.

### 3.3 Orchestrator Integration

`orchestrator.py` today writes artifacts at known stages (raw, cleaned, transformed, per-model results, report). V1.4 adds:

- A thin helper `GraphRecorder` (constructed once per run) with methods `record_stage`, `record_variable`, `record_operation`, `record_model`, `record_report`. Each method takes the artifact reference and any `auto_chosen` info and produces the correct node/edge.
- Where the orchestrator currently makes a system default choice (e.g., "user did not specify variance assumption, using robust SE"), the call site sets `auto_chosen=True` and provides `auto_chosen_reason`.
- Existing artifact emission and existing contracts are unchanged. The graph is **additive** — if the recorder is removed, the run still produces the same artifacts and `diagnostic_summary.json`.

### 3.4 API

Endpoint conventions match existing `/runs/{id}/...` style.

| Method | Path | Purpose |
|---|---|---|
| GET  | `/runs/{id}/graph` | Full graph. Query: `?include_archived=true`, `?branch=main` |
| POST | `/runs/{id}/graph/fork` | Body: `{from_node_id, branch_name?}`. Returns new `BranchRef` |
| POST | `/runs/{id}/graph/nodes/{node_id}/archive` | Soft delete |
| POST | `/runs/{id}/graph/nodes/{node_id}/unarchive` | Restore |
| POST | `/runs/{id}/graph/rerun` | Body: `{from_node_id, overrides: {...}, branch_id}`. Re-runs the pipeline starting at `from_node_id`, writing new graph entries on `branch_id`. `branch_id` is required — to "rollback" the user first calls `fork`, then `archive` on the original branch, then `rerun` on the new one (composition, not a primitive) |

`/runs/{id}/graph/rerun` is the bridge between graph and orchestrator: it constructs the resumable pipeline state from the chosen ancestor node and continues execution, writing new graph entries on the specified branch. The operation is strictly additive — it never modifies or deletes existing nodes.

### 3.5 Frontend (`frontend/src/`)

New module `frontend/src/lineage/`:

- `LineageTab.tsx` — top-level layout of graph + detail panel.
- `LineageGraphView.tsx` — D3-based or react-flow-based renderer (decision in §7); handles fold/expand, selection, cross-layer edge routing, archived dimming, double-click toggle, right-click menu.
- `NodeDetailPanel.tsx` — selected node info, both breadcrumbs, copy buttons, action buttons.
- `Breadcrumbs.tsx` — reusable for both containment and lineage paths.
- `useLineageGraph.ts` — hook wrapping API calls and local mutation optimism.

`api.ts` adds typed clients for the four new endpoints.

`runResult.tsx` adds a Lineage tab next to existing tabs. Existing tabs are unchanged.

## 4. Key Design Decisions and Rationale

### 4.1 Pipeline stays end-to-end (with auto-decision flagging)

The V1.4 user model is **best-effort end-to-end pipeline plus post-hoc graph navigation**, not an interactive Jupyter-style step-by-step editor.

For simple cases (basic OLS with common derivations), the pipeline produces a finished, directly-usable result — the user clicks "Run" once and is done. For complex cases, the pipeline still attempts to run end-to-end but its target is downgraded from "best result" to "a working starting point": where the system has to make a default choice (variance assumption, transformation, dummy reference level, etc.), the resulting node carries `auto_chosen=true` with a short reason. The user (and, in V1.6+, AI) uses these flagged nodes as the entry points for optimization and forking.

This decision keeps the existing UX for simple users while enabling power-user / AI iteration on the same backbone — without forcing every user through a Jupyter-style click-by-click interaction.

### 4.2 Why granularity is multi-resolution (C+) rather than coarse or variable-only

Coarse stage-level nodes hide variable-level lineage that the user explicitly wants ("income → log_income → 模型A.β"). Variable-only graphs explode visually for medium-sized datasets. Multi-resolution lets the user start at a clean stage view and zoom in only where needed, while AI annotations (V1.6+) attach at the variable level where they have the most explanatory value.

The "true expansion" requirement (variable nodes preserve cross-layer edges, not sealed in a box) is what makes the granularity useful: zooming into one stage does not break visibility into how its internal variables relate to neighbors.

### 4.3 Why one-run-with-branches (topology B)

Each-fork-as-new-run minimizes implementation cost today but punishes the user with a fragmented experience: comparing branches means juggling Run list entries, and any future AI feature that reasons across branches must repeatedly cross run boundaries. One-run-with-branches keeps all attempts in a single graph and a single view, at the cost of upgrading the run model to a graph.

The data model supports arbitrary branching from the start because users explicitly need to explore non-linear paths: the same starting node can yield A, B, C, and D branches, and any of these can themselves be forked further. The V1.4 *implementation* is optimized for the common case (≤5 active branches per run) — larger graphs render but layout polish is a V1.5+ improvement target.

### 4.4 Why soft delete is the only deletion in V1.4 UI

User feedback during brainstorming (paraphrased): "I might prefer branch A over branch B today, delete B, then later realize that B + new step C would have been better than A + C — and I can't get back." Statistical exploration is non-monotone; a path discarded today may matter when combined with a path discovered tomorrow. V1.4 therefore never destroys nodes through normal UI flows; archive is the only "delete".

## 5. Auto-Decision Flagging Protocol

The `auto_chosen` flag is a contract between the orchestrator and downstream consumers (Trust UI, future AI). Rules:

1. `auto_chosen=true` is set whenever the system picks a non-trivial default that a user might reasonably want to override. Examples: variance assumption, transformation, reference level for dummy variables, drop-vs-impute for missing data, dropping a perfectly collinear column.
2. `auto_chosen=true` does **not** imply trust degradation. A node can be `(trust=OK, auto_chosen=true)` — meaning the default is fine, just made on the user's behalf.
3. `auto_chosen_reason` is a short structured string with the chosen value and the trigger condition. Example: `chose=robust_se trigger=levene_p<0.05`.
4. The Lineage UI surfaces `auto_chosen` nodes with a small badge (e.g., "🤖 auto"), distinct from trust badges.
5. Future AI integration (V1.6+) uses `auto_chosen=true` nodes as a primary set of candidate intervention points.

## 6. Reserved Hooks for Future Versions

V1.4 ships these data structures unused in production but ready to consume:

- `Node.annotations: list[Annotation]` where `Annotation` includes `author` (`user` / `ai_<model>`), `body`, `created_at`, `pinned`. V1.6 AI integration writes here.
- `DecisionPoint.candidates` records the alternative options the system chose between. V1.5 multiverse analysis enumerates these to materialize alternative branches.
- "Suggested fork" representation: a `BranchRef` with `branch_id` prefixed by `suggestion__` is treated as a non-materialized proposal (not run, shown as ghost). V1.6 AI suggestion engine creates these for the user to accept or dismiss.

These are reserved fields only — no producer is wired up in V1.4.

## 7. Open Implementation Questions (Engineer's Call)

These are not blocking for the spec; they are decisions the implementer makes during build with default recommendations:

1. **Graph rendering library.** Default: react-flow (mature, supports custom node renderers, handles pan/zoom). Alternative: D3 directly (more flexible, more work).
2. **Layout algorithm.** Default: dagre for the initial implementation, deterministic layout. Custom layout for fold/expand transitions.
3. **JSON file format on disk.** Default: human-readable indented JSON. Acceptable for V1.4 graph sizes.

## 8. Migration

- Pre-V1.4 runs: graph endpoint returns `{schema_version: 1, legacy: true, nodes: {}, edges: {}, branches: {}}`. Lineage tab renders a friendly empty state explaining that the run was created before V1.4 and lineage is unavailable.
- No data migration is required. New runs after V1.4 deployment automatically get graphs.
- Schema versioning (`schema_version` on `Graph`) lets future versions safely evolve the format. V1.4 ships version `1`.

## 9. Testing Strategy

1. **Unit tests** for `graph_model` (node/edge/branch invariants), `graph_store` (atomic write, lock, restore from disk).
2. **Orchestrator integration tests**: run a fixture pipeline end-to-end, assert the resulting graph has expected nodes, edges, `auto_chosen` flags, and trust states.
3. **API tests**: contract tests for all four new endpoints, including archived/unarchived round-trip and fork semantics.
4. **Backwards compat tests**: load a pre-V1.4 run fixture, confirm the graph endpoint returns the legacy empty payload and Lineage tab renders the empty state.
5. **Three-level review per task** per project convention (Implementer → Test/QA → Reviewer) before commit.
6. **Frontend tests**: snapshot tests for breadcrumbs, fold/expand state machine, archived visibility toggle.

## 10. Out of Scope (Repeated for Clarity)

The following are explicitly NOT in V1.4 — they are documented in the broader roadmap and will land in V1.5 or later:

- Multiverse / specification curve UI
- Real AI integration (annotations, suggested forks, auto-find significance, test-selection helper, artifact commentary)
- Multi-format reports (Word, PDF, LaTeX), export governance, copy/share policy
- i18n
- Multi-format data ingestion beyond CSV/XLSX
- Native folder picker
- Auto y/x detection
- Adjustable confidence intervals
- New statistical methods
- Promote-branch-to-new-run
- Polished layout for very-large graphs (10+ active branches). Renders correctly but auto-layout, panning, and minimap polish are V1.5+
- Interactive step-by-step pipeline mode

## 11. Success Criteria

V1.4 is complete when, on the user's primary working dataset:

1. A fresh run creates a graph with stage-level + variable-level nodes, all expected edges, and trust states matching V1.3.1's diagnostic summary.
2. The user can open the Lineage tab, see the run as a folded stage chain, double-click "变换" to expand to variable nodes, see cross-layer edges intact, click `log_income` and see both breadcrumbs populated correctly.
3. The user can right-click `log_income`, choose "Fork", add a new transformation step, run it, and see both branches in one graph view.
4. The user can archive the original branch, see it dim, toggle "Show archived" off and on, and restore it.
5. A pre-V1.4 run shows the friendly empty Lineage state without errors.
6. All existing V1.3.2 tests still pass; new V1.4 tests pass; full suite remains green.
