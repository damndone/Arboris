# Econometrics Workbench v1.7 Agent Navigation Projection

**Date:** 2026-07-14  
**Status:** Approved direction; awaiting written-spec review before implementation  
**Scope:** Main/Chain/fork bidirectional navigation for the existing Agent Harness

## 1. Problem and goal

The current Agent Harness has durable sessions, event replay, proposals,
operation records, child chains, forks, and child runs. The records are linked
in backend primitives, but the user cannot reliably move between them from the
visible Workbench:

- an Agent message does not expose its source graph node or resulting run;
- a graph node does not expose the Chain Agent session that inspected or
  mutated it;
- an operation status can show a child run id, but the run/fork/session
  relationship is not navigable;
- Main and Chain scope exists in backend metadata, but is not presented as a
  recoverable status tree.

The goal is a read-only, typed navigation projection so every visible Agent,
graph, fork, child-run, and operation reference can open the corresponding
Workbench surface without guessing from message text or duplicating state.

The projection must preserve the existing ownership rule: Agent state records
what happened and points to Workbench state; it does not become a second graph,
run, or execution database.

## 2. Design principles

1. **Backend facts first.** Links are derived from durable session, chain, fork,
   proposal, and operation records. The frontend never infers lineage from
   prose, display labels, or a model-generated id.
2. **One typed link shape.** Agent messages, proposals, operation records,
   graph-node responses, and fork summaries use the same navigation reference
   contract.
3. **Existing URL contract.** Graph navigation uses the current Workbench URL
   fields (`run`, `focus`, `panel`) and preserves unrelated query parameters.
   Agent-specific session/entry/operation focus is added only where necessary.
4. **Fail closed.** Missing, stale, cross-project, or ambiguous references are
   returned as unavailable links or omitted; the UI must not construct a link
   that points at a different project or an unknown run.
5. **Durable recovery.** After reload, the projection is rebuilt from files and
   record status. It must not depend on an event that happened to be received
   in the current browser session.
6. **Small vertical slice.** This work adds navigation and projection only. It
   does not introduce new automatic execution, arbitrary tools, or a new
   Main/Chain orchestration engine.

## 3. Canonical navigation contract

The backend exposes a normalized `AgentNavigationRef` for every navigable
relationship:

```json
{
  "kind": "graph_node | agent_session | agent_entry | chain | fork | run | operation | proposal",
  "id": "stable-id",
  "label": "human-readable label",
  "relation": "source | parent | child | result | audit | context",
  "available": true,
  "href": {
    "view": "graph | agent",
    "run_id": "run-child",
    "node_ref": "model:ols_1",
    "forest_node_key": "run-child::model:ols_1",
    "node_hash": "hash-child",
    "session_id": "agent_chain_…",
    "chain_id": "chain_…",
    "entry_id": "entry_…",
    "fork_id": "fork_…",
    "operation_record_id": "oprec_…",
    "proposal_id": "proposal_…"
  }
}
```

`href` is a typed target object, not an arbitrary URL supplied by the model.
The backend may omit fields that do not apply to the target kind. The
frontend's URL builder is the only place that turns a target into a browser
URL.

The projection uses these relations:

| Origin | Navigable targets |
| --- | --- |
| Main session | Chain sessions, dispatched commands, aggregate status |
| Chain session | Main session, source graph node, fork, proposal, operation |
| Agent message/entry | source node, proposal, operation, child run, child session |
| Graph node | owning Chain session, source/child fork, related operation |
| Proposal | revision, confirmation, operation record |
| Operation record | proposal, source node, child run, child chain/session, fork |
| Child run/fork | parent node, operation record, child Agent session |

No link is considered valid merely because an id is syntactically present. The
resolver must verify the record exists under the current project root and that
the relationship matches the source record's stored scope.

## 4. Backend architecture

### 4.1 Pure navigation module

Add a provider-owned module under `backend/workbench/agent/` (recommended
name: `navigation.py`) containing:

- immutable `AgentNavigationRef` and projection dataclasses;
- deterministic builders for session, entry, proposal, operation, chain, fork,
  and graph-node targets;
- a resolver that reads existing `JsonlSessionRepository`, `ChainStore`,
  `ForkStore`, `ProposalStore`, and `OperationRecordStore` records;
- scope checks and unavailable-target handling.

The module must not write files, execute a run, call an LLM, or parse natural
language. It may use the existing graph/node context provider for authoritative
node/run validation, but only in read-only mode.

### 4.2 HTTP projection seams

Extend the existing session response with typed `navigation` data on messages,
proposals, and operation status entries. Add read-only seams for projections
that cannot be reconstructed from one session response:

```text
GET /agent/sessions/{session_id}/projection
GET /agent/navigation/graph
GET /agent/sessions/{session_id}/operations/{record_id}
```

All endpoints remain project-scoped through `project_root` and use the existing
404/409 error conventions. The graph resolver accepts authoritative selectors
such as `run_id`, `node_ref`, and `forest_node_key`; it must reject ambiguous
or cross-project selectors rather than choosing a candidate.

The projection response contains:

- current Main/Chain identity and status;
- parent/child chain and fork relationships;
- message entry refs with their related refs;
- proposal and operation refs with current durable status;
- child run and graph-node refs when they exist;
- `last_event_seq` so the frontend can reconcile projection refreshes with the
  existing event cursor.

The existing event stream remains the live update channel. Events may carry a
typed `navigation` payload, but event payloads are hints for immediate UI
updates; reload/recovery always calls the projection seam and reads durable
status.

### 4.3 Record-to-record relationship rules

- The `source_node_ref`, `source_run_id`, `forest_node_key`, `fork_id`, child
  chain/session, and child run in a confirmed `model.rerun` operation are the
  authoritative path from operation to graph.
- A fork's `source_session_entry_id` is the authoritative path from graph
  mutation context back to the Agent message branch.
- A proposal's `command_id`, `session_id`, and `chain_id` provide the path to
  the Chain session and Main dispatch context.
- If a legacy record lacks one of these fields, show the remaining verified
  links and mark the missing relationship unavailable; do not backfill by
  searching message text.

## 5. Frontend architecture

### 5.1 URL and navigation adapter

Extend the Workbench URL slice with optional Agent focus fields while retaining
unknown query parameters:

- `agent_session` — the visible session;
- `agent_entry` — optional message/entry focus;
- `operation` — optional operation-record focus.

Graph targets continue to use `run` and `focus`; opening a graph target also
sets `panel=agent` only when the source action explicitly requests the Agent
panel. Existing graph, table, pipeline, and report links remain unchanged.

Create one frontend navigation adapter, owned by the Workbench route container,
that accepts an `AgentNavigationRef` and performs one of:

- focus an existing graph run/node;
- open an Agent session/entry;
- focus an operation record in the Agent panel;
- keep the current surface and show a bounded unavailable state when the target
  is no longer resolvable.

AgentPanel and graph node actions call this adapter instead of constructing
URLs independently.

### 5.2 AgentPanel projection

Add a compact Main/Chain status header and typed link chips to the existing
terminal-style panel:

- Main/Chain role and current chain id;
- parent Main or source Chain link;
- source node link;
- proposal and operation status links;
- child run, fork, and child Agent links when available.

The terminal transcript remains the primary content. Links are secondary
actions and must not push the input box out of view. Operation status continues
to be durable-record driven; link labels must not claim completion when the
record is pending, running, verifying, failed, or stale.

### 5.3 Graph projection

Add a node action or detail affordance labelled according to the verified
relationship, for example `Open Agent context` or `Open child Agent`. It is
shown only when the graph navigation resolver returns an available target.

For a child run or fork node, the detail view exposes the related operation and
Agent session links. Clicking a link updates the shared URL state and keeps the
current project root intact.

## 6. Error and recovery semantics

- Unknown session, entry, operation, fork, chain, run, or node: 404 from the
  read-only seam; existing surface remains usable.
- Cross-session or cross-chain mismatch: 404 or a bounded unavailable ref; no
  silent fallback to a similarly named record.
- Stale active head or stale proposal: show the durable status and preserve a
  link to the source context; do not retry or execute.
- Reload after a child run completes: projection endpoint must reconstruct
  operation status, child run, fork, active head, and Agent session links from
  files without event replay being necessary.
- Partial legacy records: render verified links only and include a concise
  unavailable reason for debugging; do not fail the entire session response.

## 7. Testing and acceptance

### Backend

- unit tests for deterministic ref serialization and URL target construction;
- session projection tests covering Main → Chain → message → proposal →
  operation → child run → fork → child session;
- cross-project and cross-scope rejection tests;
- missing/legacy-field tests proving partial links are safe;
- route tests for all read-only projection seams;
- reload/recovery test proving the same projection is rebuilt without events.

### Frontend

- URL parse/write round trips for Agent session, entry, and operation focus;
- AgentPanel renders typed links and invokes the shared adapter;
- graph node actions render only for available refs;
- operation status links preserve truthful status and target ids;
- unavailable and stale refs render safely;
- reload/deep-link tests for graph ↔ Agent navigation.

### Browser smoke

Using the existing fake-data project and the already available browser smoke
workflow, verify:

1. open a source graph node and open its Chain Agent context;
2. from the Agent proposal/status, open operation and source node;
3. after a completed child run, open the child run and fork node;
4. from the fork node, return to the child Agent session;
5. reload each destination and confirm the same link/status projection remains.

This slice does not require a new DeepSeek mutation call; the earlier
DeepSeek-confirmed execution loop remains the mutation acceptance evidence.

## 8. Non-goals

- no new automatic Main → Chain dispatch engine;
- no arbitrary shell, Python, network, or free-form mutation tool;
- no second graph/run/operation database;
- no redesign of the existing proposal confirmation or rerun executor;
- no broad Graph schema rewrite;
- no push, PR, merge, tag, or worktree creation.

## 9. Completion definition

The slice is complete only when the typed projection is available after reload,
all four core relationships are browser-navigable in both directions, the
backend/frontend focused suites and quick gate pass, the stage-close full gate
passes, and the two protected adversarial review files remain untouched.
