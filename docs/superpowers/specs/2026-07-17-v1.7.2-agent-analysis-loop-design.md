# v1.7.2 Agent Analysis Loop：OLS covariance-only golden flow

**日期：** 2026-07-17
**状态：** 设计规格，待用户审阅
**版本：** v1.7.2
**主线：** Deterministic Analysis Semantics + Thin Agent Driver

## 1. 目标

v1.7.2 首个 golden flow 固定为：从一个成功完成的 OLS source run 出发，将
`conventional` standard errors 改为按用户指定变量聚类的 `clustered` standard
errors，创建一个 child run，并完成确定性的验证、source/child 比较和受约束解释。

产品语义与当前执行器 wire contract 的映射必须保持明确：

```text
产品语义 conventional  → wire covariance=unadjusted
产品语义 clustered     → wire covariance=clustered
cluster variable        → 当前 OLS wire entity_col
```

v1.7.2 不做全局字段重命名。`PlanDiff`、ValidationPacket 和 ComparePacket 可以使用
面向分析语义的 `covariance` / `cluster_variable` 字段，但 canonicalization 到现有
`model.rerun` 执行 payload 时必须显式产生 `covariance` 和 `entity_col`，并记录该映射。

目标不是让 Agent 自己计算统计差异，而是让 Workbench 先产生可验证的分析语义对象，
再由 Agent 解释和编排这些对象。

完整闭环：

```text
inspect
→ diagnose
→ plan
→ validate_proposal
→ await_confirmation
→ execute
→ reconcile
→ validate_result
→ compare
→ explain
→ complete
```

## 2. 范围边界

### 2.1 本版本包含

- OLS source run；
- source 必须已成功完成；
- source 必须使用 conventional covariance；
- 用户明确指定一个合法的 cluster variable；
- covariance-only 的 `model.rerun`；
- 一个新的 child run；
- `PlanDiff`；
- `ValidationPacket`；
- `ComparePacket`；
- 版本化的 OLS conclusion classification；
- Thin Agent Driver 对上述对象的受约束解释；
- 基础设施恢复与分析语义修复的明确分流。

### 2.2 本版本不包含

- Logit、Poisson、Panel、IV、DID 或其他模型的统一 clustered covariance 语义；
- 更换模型族；
- 修改模型公式；
- 自动增删控制变量；
- 数据清洗或静默删除缺失行；
- custom code；
- 多 child 自动分支；
- 多节点 Graph 自动重写；
- LLM 自由编造模型 patch；
- 用户未确认时的连续执行；
- 全面性能重构；
- 新算法族。

`graph.fork` 保留现有底层能力，但不作为本 golden flow 的必要操作。`model.rerun`
创建的 child 已经是本流程需要的分析分支。

## 3. 术语与事实来源

- **source run**：用户当前选择、且满足前置条件的已完成 OLS run。
- **child run**：由确认后的 covariance-only rerun 产生的新 run；不得覆盖 source。
- **PlanDiff**：执行前对计划变化和不变量的确定性描述；不包含新结果数值。
- **ValidationPacket**：执行完整性、模型有效性、golden-flow 不变量和结果完整性的确定性验证。
- **ComparePacket**：source 与 child 的确定性四层比较对象。
- **ComparisonTarget / primary estimand**：本次结论比较所针对的稳定 result identifier；
  首版至少需要一个 primary target。
- **ConclusionClassification**：基于显式、版本化策略对结果变化进行的规则分类。
- **基础设施恢复**：同一个已确认 operation 的 reconcile；沿用 execution key。
- **分析语义修复**：改变分析意义的新 proposal；必须使用新的 execution key 和新的 child。

Agent event stream 只用于观察、重放和 UI 投影，不是分析事实的最终来源。事实必须来自
Operation Record、执行产物、ValidationPacket、ComparePacket 和持久化 lineage。

### 3.1 Packet 统一 envelope 与生命周期

PlanDiff、ValidationPacket 和 ComparePacket 都使用统一的不可变 packet envelope：

```json
{
  "packet_id": "packet_123",
  "packet_type": "compare",
  "schema_version": "compare_packet_v1",
  "status": "pending",
  "source_run_id": "run_source",
  "child_run_id": "run_child",
  "operation_id": "op_123",
  "execution_key": "exec_123",
  "logical_key": "sha256:...",
  "input_fingerprints": {},
  "policy_versions": {
    "validation": "ols_validation_v1",
    "classification": "ols_clustered_v1",
    "covariance": "ols_cluster_policy_v1"
  },
  "generated_at": null,
  "reason_codes": [],
  "payload": null
}
```

envelope 的 `status` 只有：

```text
pending
complete
blocked
failed
```

`partial`、`not_comparable` 和 `blocked_by_integrity` 是 ComparePacket payload 内的
`compare_status`，不是 envelope 状态；ComparePacket 不使用 `compare_status=pending`。
`UNKNOWN` 是 target 级结果状态，也不是 packet 状态。

packet 在生成后是 immutable snapshot。不同 packet 类型使用不同的逻辑唯一键：

```text
PlanDiff:
  source_run_id + source_context_fingerprint + action_id
  + canonical_patch_hash + comparison_target_hash + schema_version

ValidationPacket:
  child_run_id + executed_payload_hash + artifact_manifest_hash
  + validation_policy_version + schema_version

ComparePacket:
  source_run_id + child_run_id + comparison_target_set_hash
  + strategy_version + schema_version
```

相同逻辑键只能有一个逻辑 packet；重复请求必须返回同一 packet。生成、持久化和 crash recovery
必须使用原子写入或等价的幂等机制。软件或策略升级不得原地改变旧 packet，而应生成新的
schema/policy version packet。

`pending` build record 可以由原执行推进到 terminal 状态；`complete` 和 `blocked` packet
不可修改。业务上的最终 `failed` packet 也不可原地覆盖；如果失败是 transient storage/build
failure，使用独立的 build attempt/reconcile 记录后重新生成同一 logical key 的 terminal packet，
不得把临时失败与业务上的 blocked 混为一谈。

build attempt 至少记录 `attempt_id`、logical key、lease/owner、attempt number、started/finished
 timestamps 和 last error。它是可变的协调记录；terminal packet 是不可变的事实快照。

### 3.2 比较目标与指纹

比较可以对全部系数做完整性检查，但结论只能针对明确的 ComparisonTarget。目标选择优先级为：

1. source model contract 中持久化的 primary estimand；
2. 用户明确指定的 coefficient result ID；
3. 注册 Analysis Pack 指定的核心结果。

v1.7.2 首版启用前两种来源，不允许 Agent 根据变量显示名称猜测。没有 primary target 时，
系统可以展示结果表和完整性事实，但不得生成整体结论，返回：

```text
COMPARISON_TARGET_REQUIRED
```

source 和 child 必须分别持久化以下指纹：

```json
{
  "dataset_snapshot_fingerprint": "...",
  "analysis_sample_fingerprint": {
    "row_set": "...",
    "row_order": "..."
  },
  "point_estimation_fingerprint": "...",
  "coefficient_schema_fingerprint": "...",
  "inference_config_fingerprint": "..."
}
```

- `dataset_snapshot_fingerprint` 标识实际输入数据快照；
- `analysis_sample_fingerprint.row_set` 基于实际进入模型的稳定 row identity；
- `analysis_sample_fingerprint.row_order` 区分相同样本但顺序变化；
- `point_estimation_fingerprint` 覆盖 y、X、weights、intercept、categorical encoding、
  missing policy、analysis row set/order 和 point-estimation solver options；明确排除
  covariance、cluster variable、group vector、small-sample correction、degrees of freedom、
  `use_t` 和 confidence level；
- `coefficient_schema_fingerprint` 覆盖 result IDs、canonical term、term order、
  reference levels、interaction 和变换项。
- `inference_config_fingerprint` 覆盖 covariance type、cluster variable、group vector
  fingerprint、cluster count、correction flags、inference distribution、effective degrees
  of freedom、`use_t`、confidence level、engine 和版本；它在本 golden flow 中预期发生
  受控变化。

## 4. Source 前置条件

进入 proposal 生成前，后端必须验证：

1. source run 已处于成功的合法 terminal state；
2. source 的模型类型明确为 `ols`；
3. source 的 covariance 类型明确为产品语义 `conventional`，且 wire 值为显式
   `covariance=unadjusted`；系统默认 robust/HC1 不能隐式满足该条件；
4. source 有冻结且可重放的 executable payload；
5. dataset snapshot fingerprint、point-estimation/inference 指纹、draft hash 和 result
   artifact 均存在且可验证；
6. 产品语义的 covariance 和 cluster variable 能映射到当前 OLS editable schema 的
   `covariance` 与 `entity_col` 字段；
7. source 的 lineage 能确定性建立 child 关系；
8. 所有可比较的候选系数具有稳定的 result identifier；不得仅按显示名称或表格位置匹配；
9. source contract version 满足 `ols_result_contract_v1`。

任一条件不满足，系统不得降级为猜测或普通 rerun。v1.7.2 不做隐式旧 artifact 回填：
不满足 `ols_result_contract_v1` 的旧 run 返回：

```text
SOURCE_CONTRACT_UNSUPPORTED
```

用户可以用现有路径重新运行一次，产生符合新 contract 的 source；旧 artifact 不通过猜测
补写 result ID、analysis sample 或 point-estimation/inference fingerprint。

### 4.1 Target Resolution

在 preflight 通过后、PlanDiff 生成前，后端按以下顺序解析恰好一个 primary target：

1. 如果 source model contract 已持久化 primary estimand，使用它；
2. 否则，如果用户提供 exact coefficient result ID，验证该 ID 存在、稳定且属于 source；
3. 否则返回 `COMPARISON_TARGET_REQUIRED`，不创建 PlanDiff 或 proposal。

其他系数可以作为 secondary results 参与完整性和结果展示，但不改变 primary target。
Agent 不得推断、选择或替换 target；它只能原样转交用户明确提供的 exact result ID。

## 5. Cluster variable 确定性校验

proposal 生成前，后端必须在当前分析样本上校验：

- 字段存在；
- 字段类型符合 OLS clustered covariance 的允许类型；
- 字段不是常量；
- cluster 数量满足当前版本化 covariance policy；
- 每一条实际进入模型的分析观测必须且只能映射到一个 cluster；
- 缺失数量和缺失位置可审计；
- cluster 值与实际分析行严格对齐；
- 不允许根据相似字段名自动猜测变量。

source 必须是显式的 conventional/unadjusted 设定；系统默认的 robust/HC1 不能被当作
conventional source。最低 cluster 数量不是由 Agent 决定的。它必须来自一个可追踪的
`covariance_policy_version`；若策略缺失、无法解析或判定为不满足，proposal 必须 fail closed。
执行结果需要持久化实际 cluster 数量、策略版本和校验结果。

### 5.1 缺失值规则

如果 cluster variable 在当前分析样本中存在缺失，直接阻塞 proposal：

```text
CLUSTER_VARIABLE_MISSING_VALUES
```

返回缺失数量和影响范围，但 v1.7.2 不自动删除行、不自动插补、不自动创建数据清洗操作。
原因是静默删行会把 covariance-only flow 变成同时修改分析样本的 flow，破坏预期的不变量。

### 5.2 OLS wire runner contract

对于本 golden flow，`entity_col` 只作为 clustered covariance estimator 的 group vector
使用，必须满足：

- 不进入 OLS formula；
- 不增加 fixed effects 或其他 explanatory term；
- 不改变分析样本、排序或 missing-value 过滤；
- 不改变 y、X、intercept、weights 或 coefficient schema；
- 只传给 covariance estimator，并将实际使用的 group vector fingerprint 写入结果证据。

cluster covariance 的实际执行配置必须显式记录，至少包括 covariance engine、library
及版本、small-sample correction、degrees-of-freedom correction、`use_t` 和实际生效的
cluster policy；不能依赖第三方库默认值而不写入 result contract。

### 5.3 `ols_cluster_policy_v1`

v1.7.2 使用一个明确、保守且可复现的 one-way cluster policy：

```json
{
  "policy_version": "ols_cluster_policy_v1",
  "allowed_model": "ols",
  "allowed_covariance": "clustered",
  "allowed_cluster_types": ["integer", "string", "category"],
  "reject_boolean": true,
  "reject_float": true,
  "reject_mixed_object": true,
  "reject_null_or_nan": true,
  "hard_min_cluster_count": 2,
  "warning_cluster_count_below": 30,
  "one_way_only": true,
  "allow_singleton_clusters": true,
  "all_singleton_clusters": "warning",
  "small_sample_correction": true,
  "degrees_of_freedom_correction": true,
  "use_t": false,
  "confidence_level": 0.95,
  "alpha": 0.05,
  "inference_distribution": "normal",
  "p_value_method": "normal_z",
  "confidence_interval_method": "normal_z",
  "effective_degrees_of_freedom": "record_per_target",
  "engine": "statsmodels",
  "minimum_engine_version": "0.14"
}
```

规则：

- 少于 2 个非空 cluster 是 hard failure；2–29 个 cluster 允许执行但产生 warning；
- boolean、float、混合类型 object、null/NaN cluster 值 fail closed；字符串按 UTF-8
  canonical value 处理，integer 和 category 必须先转换为稳定的非空 canonical value；
- 只允许 one-way clustering；不允许 Agent 或用户意图隐式增加第二个 cluster 维度；
- singleton cluster 不自动删除，数量被记录；如果所有 cluster 都是 singleton，产生 warning；
- correction、自由度、`use_t`、alpha、confidence level、p-value 和 CI 方法都必须按上面
  的 policy 显式传给 runner 或从实际生效值中记录，不依赖第三方默认值；
- warning 允许进入 Compare，但必须保留在 ValidationPacket 和 Agent 解释中；hard failure
  在 PlanDiff 之前拒绝 intent；
- 实际安装的 statsmodels 版本必须满足最低版本并写入 inference evidence。

该 policy 的 `inference_config_fingerprint` 包含实际生效值和稳定的 row-aligned group vector
fingerprint，确保相同 canonical patch 在不同 source、policy 或 engine 版本下不会被错误复用。

## 6. PlanDiff 契约

PlanDiff 由后端根据冻结 source payload、OLS contract 和不可信的用户意图生成。Agent 只
提交 intent，不直接生成 canonical `model.rerun` payload，也不自行计算或补充具体结果。

生成顺序固定为：

```text
untrusted intent received
→ resolve source
→ resolve exactly one ComparisonTarget
→ preflight source contract
→ preflight cluster variable and covariance policy
→ canonicalize intent
→ generate and persist PlanDiff
→ generate proposal
→ await confirmation
→ revalidate stale/context/hash conditions
→ execute
```

任何 preflight 失败都只产生结构化 `IntentValidationResult` / `ProposalRejection`，不创建
可确认的 PlanDiff 或 proposal。UI 如需展示“为什么不能执行”，读取该独立结果，不把被拒绝
的 intent 伪装成正式 PlanDiff。

PlanDiff 必须与 proposal、用户确认和最终执行 payload 绑定为同一个不可变计划。至少包含：

```json
{
  "plan_id": "plan_123",
  "schema_version": "plan_diff_v1",
  "source_run_id": "run_123",
  "source_context_fingerprint": "...",
  "action_id": "ols.use_clustered_covariance_v1",
  "comparison_target": {
    "result_id": "coef:treatment",
    "role": "primary",
    "selection_source": "model_contract"
  },
  "canonical_patch": {
    "covariance": "clustered",
    "entity_col": "company_id"
  },
  "canonical_patch_hash": "...",
  "plan_hash": "..."
}
```

用户确认必须绑定 `proposal_id`、`plan_id`、`plan_hash`、`canonical_patch_hash` 和
`source_context_fingerprint`。确认后、执行前必须重新校验 source、editable schema、
context fingerprint、cluster 校验结果和 confirmed/executed payload hash；失败时返回：

```text
STALE_PLAN
CONTEXT_FINGERPRINT_MISMATCH
CONFIRMED_PAYLOAD_MISMATCH
```

下面的对象是同一个 PlanDiff 的 payload，不是第二个 PlanDiff；持久化形状是统一 packet
envelope 加上该 payload。

首版 payload 形状：

```json
{
  "change_scope": "covariance_only",
  "source": {
    "model_type": "ols",
    "covariance": "conventional",
    "cluster_variable": null,
    "wire": {
      "covariance": "unadjusted",
      "entity_col": null
    }
  },
  "proposed": {
    "model_type": "ols",
    "covariance": "clustered",
    "cluster_variable": "company_id",
    "wire": {
      "covariance": "clustered",
      "entity_col": "company_id"
    }
  },
  "invariants": {
    "dataset_expected_unchanged": true,
    "analysis_sample_expected_unchanged": true,
    "point_estimation_expected_unchanged": true,
    "coefficient_schema_expected_unchanged": true,
    "inference_config_expected_changed_as_confirmed": true,
    "analysis_rows_expected_unchanged": true,
    "formula_expected_unchanged": true,
    "point_estimates_expected_unchanged": true
  },
  "expected_impacts": [
    "standard_errors_may_change",
    "confidence_intervals_may_change",
    "p_values_may_change"
  ]
}
```

PlanDiff 的语言只能表达预期范围，例如“点估计预计不变，标准误、置信区间和 p 值可能变化”。
它不得填入尚不存在的 p 值、置信区间或显著性结论。

`canonical_patch` 是唯一允许进入执行的 patch；UI 展示的产品语义映射必须与该字段一致，
不得出现 UI 显示 `company_id` 而执行 `subject_id` 的情况。

### 6.1 Hash 与数值规范

所有 plan、patch、target set、fingerprint 和 logical key hash 使用：

```text
algorithm: SHA-256
canonicalization_version: canonical_json_v1
encoding: UTF-8
object keys: lexicographically sorted
strings: Unicode NFC normalized before encoding
numbers: finite canonical JSON numbers; no NaN/Infinity
null vs omitted/default: determined by the versioned schema before hashing
-0.0: normalized to 0
```

`plan_hash` 至少覆盖 source run ID、source context fingerprint、action ID、ComparisonTarget、
canonical patch、covariance policy version 和 schema version。后端先完成 schema defaults 和
产品语义到 wire 字段的 canonicalization，再计算 hash；前端不得自行重算另一种 hash。

所有标量数值比较使用同一公式：

```text
equal(a, b) := abs(a - b) <= atol + rtol * max(abs(a), abs(b))
```

estimate 和 CI width 可以使用不同的 `atol`/`rtol`。`NaN != NaN`；Infinity 不参与普通
容差比较；`-0.0` 与 `0.0` 在 canonicalization 后相同。无法满足这些规则的值进入
target `unknown` 或 integrity finding，不得被 Agent 解释成相等。

## 7. ValidationPacket 契约

ValidationPacket 必须在 child lifecycle 到达可验证状态后由后端生成，至少包含四层。
child 执行失败时也必须生成一个 envelope `status=complete` 的失败型 ValidationPacket，
其中模型执行检查为 `fail`；这样 UI 可以确定性解释为什么没有进入 Compare。
如果 projection 仍 pending，则 ValidationPacket envelope 保持 `pending`，不得伪装成 fail。

每一项检查使用统一结构：

```json
{
  "check_id": "analysis_sample_unchanged",
  "status": "pass",
  "severity": "blocking",
  "expected": "fingerprint_source",
  "observed": "fingerprint_child",
  "evidence_refs": [],
  "reason_code": null
}
```

检查状态为 `pass`、`warning`、`fail`、`unknown`、`not_applicable`；ValidationPacket
另行给出 `overall_status` 和 `blocking_checks`。`overall_status` 只能是
`passed`、`warning`、`failed` 或 `unknown`，与 packet envelope 的 `status` 分离。warning
是否允许 Compare、unknown 是否阻塞结论，必须由本节规则决定，不交给 Agent 判断。

例如：

```json
{
  "overall_status": "failed",
  "blocking_checks": ["analysis_sample_unchanged"],
  "checks": []
}
```

`overall_status=warning` 允许进入 Compare，但不能隐藏 warning；`unknown` 会阻塞相关
ConclusionClassification；`projection pending` 保持 packet `status=pending`；child 已失败
但执行事实完整时，packet `status=complete` 且模型执行 check 为 `fail`。

### 7.1 操作完整性

- 确认 payload 与 executed payload 一致；
- `plan_hash` 与 `canonical_patch_hash` 一致；
- `executed_draft_hash` 匹配；
- effect 已 committed；
- projection 已 complete；
- child 与 source lineage 正确；
- 所需 artifact 完整；
- run 处于合法 terminal state。

### 7.2 Golden-flow 不变量

- dataset snapshot fingerprint 不变；
- analysis sample fingerprint 的 row set 和 row order 不变；
- point-estimation fingerprint 不变；
- coefficient schema fingerprint 不变；
- inference config fingerprint 按确认的 covariance/cluster policy 发生受控变化；
- 模型公式不变；
- 分析行数不变；
- 因变量和自变量集合不变；
- coefficient schema 与点估计的预期分别为不变；
- 唯一允许的模型设定变化是 covariance 配置。

任一不变量失败，必须返回：

```text
UNEXPECTED_ANALYSIS_CHANGE
```

不得继续把该 child 当作普通 clustered covariance 结果解释。

### 7.3 Clustered covariance 有效性

- 实际 wire covariance 为 `clustered`，并在语义层映射为 `clustered`；
- 实际 cluster 字段等于用户确认的字段；
- 实际 cluster 数量已持久化；
- 实际 covariance engine、library version、small-sample correction、degrees-of-freedom
  correction、`use_t`、inference distribution、effective inference degrees of freedom、
  p-value method 和 confidence interval method 已持久化；
- 标准误、置信区间可计算；
- 没有数值失败；
- covariance policy 的 warning 被记录。

### 7.4 结果完整性

- source 与 child 的所有候选系数可按稳定 result identifier 匹配，且 primary target 存在；
- estimate、standard error、confidence interval 和 p-value 各自有明确状态；
- 缺失或不可计算的值不能被解释为“没有变化”。

如果模型执行事实可验证但 child 拟合失败，则 ValidationPacket 为 complete，
`model_execution` check 为 fail，ComparePacket 必须为 `not_comparable`；不得因 child 失败
而完全省略 ValidationPacket。

## 8. ComparePacket 契约

ComparePacket envelope 按统一 packet 生命周期生成；其 payload 使用独立的
`compare_status`：

```text
complete
partial
not_comparable
blocked_by_integrity
```

只有 envelope `status=complete` 且 `compare_status=complete` 或满足本节限定的 `partial`，
并且 primary target 完整时，
才允许生成对应的 semantic classification。比较状态、完整性 findings 和 semantic labels
不得混在同一个标签数组中。

### 8.1 参数层

```text
covariance: conventional/unadjusted → clustered
cluster_variable: null → company_id
wire entity_col: null → company_id
```

### 8.2 目标层

ComparePacket 必须保存：

```json
{
  "comparison_targets": [
    {
      "result_id": "coef:treatment",
      "role": "primary",
      "selection_source": "model_contract"
    }
  ],
  "by_target": []
}
```

全部系数可以参与完整性检查，但 Agent 的“结论变化”只能围绕 primary target。目标缺失
返回 `COMPARISON_TARGET_REQUIRED`，不生成整体结论。

### 8.3 数据层

首个 golden flow 预期：

```text
dataset unchanged
analysis row count unchanged
formula unchanged
analysis sample fingerprint unchanged
point-estimation fingerprint unchanged
coefficient schema fingerprint unchanged
inference config changed exactly as confirmed
```

行数和公式只作为可读诊断，不能单独证明同一样本或同一设计矩阵。fingerprint 不一致时，
ComparePacket 必须标记 integrity finding，不得继续作普通 covariance-only 结果解释。

### 8.4 结果层

针对稳定匹配的系数生成：

- `estimate_before` / `estimate_after`；
- `standard_error_before` / `standard_error_after`；
- `confidence_interval_before` / `confidence_interval_after`；
- `p_value_before` / `p_value_after`。

OLS covariance-only rerun 的 estimate 应在数值容差内保持一致。比较使用数值容差，不能
要求序列化字符串完全一致；超出容差时分类为 `UNEXPECTED_ESTIMATE_CHANGE`，而不是普通结果变化。

结果必须按 target 归属，例如：

```json
{
  "by_target": [
    {
      "result_id": "coef:treatment",
      "role": "primary",
      "status": "complete",
      "labels": ["UNCERTAINTY_INCREASED", "SIGNIFICANCE_LOST"]
    }
  ]
}
```

不同 coefficient 可以分别扩大或缩小不确定性；同一 coefficient 不得同时出现两种相反标签。

### 8.5 结论层

首版至少支持：

- 方向是否变化这一事实字段；若完整性失败，不把它升级为 semantic label；
- 显著性是否变化；
- 不确定性扩大或缩小；
- primary target 的语义标签；
- target 级 status 是否为 `complete` 或 `unknown`。

### 8.6 Partial 规则

允许 `compare_status=partial` 的情况：

- 一部分非 primary coefficient result ID 可以匹配；
- 某个次要指标缺失；
- source 和 child 的部分结果字段可比较，但 primary target 的必需字段完整。

不得标记为 partial 的情况：

- primary target 无法匹配；
- point-estimation、analysis sample 或 dataset snapshot fingerprint 不一致；
- inference config fingerprint 与确认的 canonical patch 不一致；
- covariance-only invariant 失败；
- child effective covariance 不等于 confirmed covariance。

partial 状态下可以展示已确认的事实，但不生成整体模型结论；primary target 完整时只解释
primary target，并列出缺失范围。

## 9. ConclusionClassification

首版策略必须显式、版本化并随 ComparePacket 持久化：

```json
{
  "strategy_version": "ols_clustered_v1",
  "alpha": 0.05,
  "significant_rule": "finite(p) AND p < alpha",
  "confidence_level": 0.95,
  "estimate_zero_tolerance": 1e-10,
  "estimate_match_tolerance": {
    "absolute": 1e-10,
    "relative": 1e-8
  },
  "ci_width_match_tolerance": {
    "absolute": 1e-12,
    "relative": 1e-8
  },
  "sample_count_rule": "must_equal",
  "formula_rule": "must_equal",
  "dataset_rule": "must_equal",
  "analysis_sample_rule": "must_equal",
  "point_estimation_rule": "must_equal",
  "inference_config_rule": "must_match_confirmed_patch",
  "coefficient_schema_rule": "must_equal",
  "covariance_engine": "statsmodels",
  "small_sample_correction": true,
  "degrees_of_freedom_correction": true,
  "use_t": false,
  "inference_distribution": "normal",
  "p_value_method": "normal_z",
  "confidence_interval_method": "normal_z"
}
```

semantic classification 只能在 ComparePacket 的 integrity status 通过后生成，且必须按
`result_id` 绑定到 ComparisonTarget。分类结果是 target 级标签数组，而不是强制互斥的
单一模型级枚举。首版 semantic labels：

```text
NO_MATERIAL_CHANGE
UNCERTAINTY_INCREASED
UNCERTAINTY_DECREASED
SIGNIFICANCE_LOST
SIGNIFICANCE_GAINED
```

以下属于其他层，不属于 semantic labels：

```text
UNKNOWN                  # target status
NOT_COMPARABLE           # ComparePacket compare_status
UNEXPECTED_ESTIMATE_CHANGE
UNEXPECTED_ANALYSIS_CHANGE
DATASET_SNAPSHOT_FINGERPRINT_MISMATCH
POINT_ESTIMATION_FINGERPRINT_MISMATCH
INFERENCE_CONFIG_FINGERPRINT_MISMATCH
COEFFICIENT_SCHEMA_MISMATCH
                         # Validation/Compare integrity findings
```

规则：

- 显著性固定为 `finite(p) AND p < alpha`；`p == alpha` 不算显著，且必须有测试；
- source 和 child 必须使用相同的 `confidence_level`，不确定性由该置信水平的 confidence
  interval width 比较；
- 方向使用 `estimate_zero_tolerance` 将估计值分为 negative、zero、positive；
- confidence interval width 在 `ci_width_match_tolerance` 内视为 unchanged，超过上限才
  产生 `UNCERTAINTY_INCREASED`，低于下限才产生 `UNCERTAINTY_DECREASED`；
- estimate 超出绝对或相对容差时只产生 integrity finding
  `UNEXPECTED_ESTIMATE_CHANGE`，并阻塞 semantic classification；
- 任一 primary target 必需指标缺失时，该 target status 为 `unknown`，不得补出结论；
- `NO_MATERIAL_CHANGE` 只在该 target 没有其他 semantic label 且完整性检查通过时产生；
- 首个 covariance-only flow 不做一般性的“实质效应大小改变”判断；点估计方向变化首先
  视为完整性异常，不作为正常结论标签。

例如同一个 primary target 可以同时产生：

```text
UNCERTAINTY_INCREASED
SIGNIFICANCE_LOST
```

不同 target 可以分别产生 `UNCERTAINTY_INCREASED` 和 `UNCERTAINTY_DECREASED`，但同一
target 不得同时产生两者。

## 10. Recovery Action Registry

恢复动作必须是注册对象，而不是 Agent 自由生成的建议：

```text
diagnostic code
→ applicable conditions
→ allowed operation
→ patch template
→ required fields
→ risk level
→ validation rule
```

v1.7.2 首个 flow 只注册一个 action：

```json
{
  "action_id": "ols.use_clustered_covariance_v1",
  "allowed_model": "ols",
  "source_covariance": "conventional",
  "target_covariance": "clustered",
  "required_fields": ["cluster_variable"],
  "operation": "model.rerun",
  "change_scope": "covariance_only"
}
```

recommended action 只能引用该 action ID，不能动态产生新的 patch template。v1.7.2 首个
flow 只允许两种 proposal 来源：

1. 用户明确请求的 covariance-only 变化，经后端 canonicalization 后匹配该 action；
2. Workbench 已注册的 recommended action，且 action ID 必须匹配该 action。

用户明确请求也必须经过 operation registry、editable schema、上下文 fingerprint 和风险策略。
v1.7.2 不开放 LLM 自己发明模型参数、模型公式、数据清洗或 custom code patch。

## 11. 两类恢复与执行前拒绝

v1.7.2 明确区分三类状态变化。

### 11.1 Proposal validation rejection

适用情况：

- cluster 字段不存在；
- cluster 字段有缺失；
- cluster 数量不满足 policy；
- source context 已过期；
- patch 不是 covariance-only；
- primary comparison target 缺失。

处理方式：

```text
proposal rejected
→ no execution key
→ no effect
→ no child
→ user changes intent
→ backend creates a new IntentValidationResult or, after preflight passes, a new PlanDiff/proposal
```

失败的 intent 不产生 PlanDiff；这不是分析语义修复，也不进入 reconcile。

### 11.2 基础设施恢复

适用情况：

- lease 过期；
- projection pending；
- terminalization 中断；
- effect 已提交但 projection 尚未完成。

处理方式：

```text
same operation
same execution key
same confirmed payload
reconcile
```

不得创建新的分析 child。

### 11.3 分析语义修复

适用情况：

- cluster 字段非法；
- covariance 配置需要改变；
- 用户改用另一个 cluster variable；
- 模型失败后需要修改分析参数。

处理方式：

```text
new proposal
→ new confirmation
→ new execution key
→ new child run
```

模型执行失败后，原 failed child 和失败型 ValidationPacket 必须保留在 lineage 中；不得
覆盖、删除或把它替换成新 child。不得把语义变化包装成原操作的技术重试。

## 12. Thin Agent Driver 职责

Agent 可以：

- 判断用户是在询问、请求 covariance-only rerun 还是查看比较；
- 使用用户明确指定的 cluster variable；
- 解释后端产生的诊断和 PlanDiff；
- 提交包含 `action_id` 和用户意图的 untrusted intent；
- 请求后端 canonicalization、PlanDiff 和 schema-valid proposal；
- 执行后读取 ValidationPacket、ComparePacket 和分类结果；
- 用自然语言解释 primary target 的不确定性和显著性变化。

Agent 不可以：

- 自行计算 source/child diff；
- 自行选择 alpha 或容差；
- 自行判断样本是否相同；
- 按显示名称模糊匹配系数；
- 从相似字段名猜测 cluster variable；
- 自行选择或修改 ComparisonTarget；
- 修改模型公式；
- 在后端返回 `unknown` 时生成确定结论；
- 在用户确认前执行操作。

## 13. UI 形态

首个 UI 闭环只需要展示：

1. 当前 source 是成功的 OLS，covariance 为 conventional；
2. cluster variable 校验结果；
3. primary ComparisonTarget 及其选择来源；
4. PlanDiff、计划 hash 和不变量；
5. 用户确认入口；
6. child 执行与 reconcile 状态；
7. ValidationPacket 的四层状态和 blocking checks；
8. ComparePacket 的 compare status、integrity findings、参数/数据/结果/target 四层；
9. Agent 基于 packet 的 primary target 解释；
10. 如果不可比较或未知，明确展示原因，不显示推测性结论。

执行前不得展示伪造的新结果数值。执行后不得将 ValidationPacket 的 warning 隐藏在普通成功文案中。

## 14. 测试与验收

### 14.1 正常路径

- conventional → clustered 成功；
- source/child lineage 正确；
- dataset snapshot、analysis sample、point-estimation 和 coefficient schema fingerprint 不变；
- inference configuration fingerprint 按确认的 covariance policy 受控变化；
- 数据、公式和分析行数作为可读诊断不变；
- 系数点估计在容差内一致；
- primary comparison target 稳定存在；
- SE、CI、p-value 正确比较；
- Agent 解释与分类一致。

### 14.2 显著性与不确定性

- 显著 → 不显著；
- 不显著 → 显著；
- `p == alpha` 不显著；
- p-value 为 NaN、null 或 infinity 时 target status 为 unknown；
- confidence level 不同会阻塞分类；
- CI width 只有浮点噪声时不产生扩大/缩小标签；
- alpha 和 strategy version 被持久化；
- 不同 coefficient 的不确定性可分别扩大或缩小，并绑定稳定 result ID；
- 同一 coefficient 不得同时产生扩大和缩小标签。

### 14.3 数据与 proposal 约束

- cluster 字段不存在；
- cluster 字段有缺失；
- cluster 字段为常量；
- cluster 数量不满足 policy；
- cluster 数量为 2 时允许，低于 30 时产生 warning，少于 2 时拒绝；
- boolean、float、混合 object、null/NaN cluster 值按 policy 拒绝；
- singleton cluster 被记录；全部 singleton 时产生 warning；
- correction、自由度、`use_t`、推断分布、p-value/CI 方法和 engine 版本与 policy 一致；
- analysis row count 意外变化；
- primary comparison target 缺失或 result ID 不稳定；
- proposal validation rejection 不创建 execution key 或 child；
- Agent 不猜测相似字段；
- 非 covariance-only patch 被拒绝。

### 14.4 完整性异常

- child 使用错误 cluster 字段；
- plan hash 或 canonical patch hash 不匹配；
- draft hash 不匹配；
- dataset snapshot fingerprint 改变；
- analysis sample fingerprint 改变；
- point-estimation fingerprint 改变；
- inference configuration 与确认 patch 不一致；
- coefficient schema fingerprint 改变；
- formula 意外改变；
- 系数点估计超出容差；
- `entity_col` 进入 formula、改变样本或改变系数；
- confirmed payload 与 executed payload 不一致；
- artifact 缺失；
- coefficient identity 无法匹配。

### 14.5 生命周期恢复

- effect committed、projection pending；
- lease 过期后 reconcile；
- 重复确认不重复创建 child；
- 重复生成同一 packet 返回同一 packet ID；
- packet 生成后进程崩溃可以幂等恢复；
- strategy v2 不修改 strategy v1 的历史 packet；
- 基础设施恢复沿用 execution key；
- 分析语义变化创建新的 proposal 和 execution key；
- failed child 和失败型 ValidationPacket 保留在 lineage。

### 14.6 比较降级

- source artifact 缺失；
- child 尚未完成；
- 部分指标不可计算；
- primary target 不可匹配时不允许 partial；
- secondary coefficient 缺失时可 partial，但只解释完整的 primary target；
- 正确区分 packet status、compare status、integrity finding 和 target status；
- 正确返回 `pending`、`partial`、`unknown`、`not_comparable` 或 `blocked_by_integrity`；
- 不因缺少数据而生成确定性结论。

### 14.7 Wire contract

- `entity_col` 不进入 OLS model formula；
- `entity_col` 不改变分析样本、行顺序或 coefficient schema；
- `entity_col` 只传给 covariance estimator；
- source 使用 `covariance=unadjusted` 才能进入 conventional flow；
- `robust`、HC0、HC1 等 source 不得误判为 conventional；
- clustered covariance 的实际 correction、degrees of freedom、`use_t`、engine 和版本可追溯。

受保护的 honest-DID 测试文件不修改。v1.7.2 测试不得调用真实 LLM/API；Agent provider 只使用现有 fail-closed 配置和测试替身。

## 15. 性能与可观测性约束

v1.7.2 不开展全面性能重构，但必须为后续判断记录以下阶段耗时：

- NodeOperationContext 构建；
- PlanDiff 生成；
- ValidationPacket 生成；
- ComparePacket 生成；
- child indexing / focus；
- 从确认到 operation terminalization 的总耗时。

记录数据规模、Graph 节点数量、artifact 数量和是否发生重复读取。只有确认这些指标造成用户可感知阻塞后，才进入独立性能优化。

P-SBX2 和 P-CE1 是并行的非阻塞专项，不属于 v1.7.2 golden-flow DoD；除非经过单独批准的
scope change 提升优先级，否则它们不应阻塞本版本主线。P-SBX2 仍可作为安全测试可信度专项，
P-CE1 只有在不改变执行一致性和崩溃恢复契约时才实施。

## 16. 完成定义

v1.7.2 首个 golden flow 只有在以下条件全部满足时才算完成：

- 一个真实的 OLS conventional source 可以经过用户确认产生 clustered child；
- source、child、Operation Record、ValidationPacket、ComparePacket 和 lineage 可互相定位；
- source contract version 满足 `ols_result_contract_v1`，旧 source 不做隐式回填；
- primary ComparisonTarget 有稳定 result ID，且 target 来源可追踪；
- 执行前没有伪造结果数值；
- 执行后 dataset snapshot、analysis sample、point-estimation、coefficient schema、公式、
  样本和 estimate 不变量可被确定性验证；
- inference configuration 的变化恰好匹配确认的 covariance/cluster policy；
- SE、CI、p-value 的变化可被确定性比较；
- 分类策略、alpha、confidence level、浮点容差、cluster correction 参数和版本被持久化；
- PlanDiff、confirmation 和 executed payload 由 source context、plan hash 和 canonical
  patch hash 强绑定；
- packet envelope、schema version、状态、provenance 和幂等唯一键被持久化；
- comparison status、integrity findings、target status 和 semantic labels 分层；
- 基础设施恢复与分析语义修复不会混淆；
- 所有不可比较和未知状态都 fail closed；
- Agent 只解释后端事实，不自行计算或猜测；
- backend、frontend、Agent harness 和 golden flow 验证均通过；
- 未修改 v1.7.1 worktree、受保护测试文件或公共依赖环境。
