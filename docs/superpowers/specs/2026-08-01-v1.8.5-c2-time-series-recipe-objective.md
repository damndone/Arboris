# v1.8.5 C2 — Time-Series Recipe Objective

This is the bounded FMS objective for C2 of
`2026-07-31-v1.8.5-typed-memory-and-model-family-design.md`. The parent
design remains the only version-scope authority.

## Objective

Admit the existing ETS and ARMA/GARCH capabilities to Notebook and Agent
genesis through a server-owned `RecipeContract`. A Recipe has time/value input
semantics and its own published model-options vocabulary; it is not a
regression branch with empty predictors.

## Scope

- Define `time_series.ets` and `time_series.arma_garch` RecipeContracts with
  input-column validation, published option fields, expected artifacts and
  bounded Agent/Table/Report result projections.
- Compile a selected Recipe only into an independent dataset `model.genesis`
  Draft. The server validates `time_column` and `value_column` against the
  current dataset, validates `model_options` through the existing owner
  contract, and preserves server-owned binding facts.
- Genesis Draft validation derives the absence of regression predictors from
  the RecipeContract. It does not retain an ARMA/GARCH model-name exception,
  and it never treats a Recipe as an `operation.multi_step` regression branch.
- Remove the short server-owned total planning deadline that makes a valid
  multi-turn Notebook plan fail merely because it exceeds 180 seconds. Keep
  cancellation, bounded inspection rounds, and a five-minute provider-call
  timeout, so a stalled upstream call cannot become an unbounded background
  task.
- Add TDD coverage for accepted ETS/ARMA-GARCH paths and refusal paths:
  missing time/value columns, invalid or unconfirmed ARMA/GARCH transforms,
  missing predictors being accepted only for recipes, and legacy regression
  genesis still requiring the fields its ModelFamilyContract declares.
- Add regression coverage that a Notebook plan can span multiple provider
  turns without a short aggregate deadline, while each provider call remains
  cancellable and bounded.
- Preserve the declared `observation_order` semantic through the existing
  ARMA/GARCH split boundary projection when the source time column is parsed as
  datetime. This is a runtime representation fix: it must not infer a calendar
  cadence, change an estimator, or turn an explicit user-confirmed semantic
  into a hidden default.
- Record every Notebook planning outcome (completed, failed, or cancelled) in
  the project-level AI activity timeline, and preserve a typed terminal trace
  for failed or cancelled planning. Keep the existing Table/figure Ask AI
  records and add the corresponding failure record for Report generation, so
  the bottom AI activity panel is an honest cross-surface history rather than
  a success-only subset.
- Preserve the effective model type from the registered result envelope when
  recording Graph lineage. A completed Recipe run must never be displayed or
  summarized as OLS merely because its result uses the pack result envelope;
  this is a presentation/lineage correction only and must not alter estimator
  selection or numerical results.
- When a Forest deduplicates the same result node across runs, select the
  newest canonical presentation metadata for that shared node. This prevents
  a historical incorrect label from masking the corrected label of an
  identical later Recipe result; individual historical `graph.json` files
  remain immutable.

## Explicit non-scope

- No estimator, diagnostics, numerical-method, model-options-contract, pack,
  capability-registration, custom-capability, memory-default, or frontend
  layout redesign. The narrowly scoped activity-record behavior above is in
  scope.
- No time-series multi-step workflow, model-family alias, automatic frequency
  inference, visual conclusion without an evidence packet, or change to
  historical manual Runs.

## Acceptance

Tests must first fail, then pass for both RecipeContracts and their Notebook
materialization. Existing ETS and ARMA/GARCH known-truth tests must remain
green. A later browser acceptance run must demonstrate Dataset → Notebook
option → Draft → confirmation → execution → Result/Table/Report for both
recipes, while unsupported or incomplete inputs fail closed before a Draft is
persisted. A failed/cancelled Notebook plan and a failed Report generation must
also appear in the bottom AI activity timeline with a bounded error summary;
existing Table/figure Ask AI success and failure records must remain present.
