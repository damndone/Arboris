# Approved criteria and registered delivery evidence

Implementation design under the approved v1.9.1 M3 scope and continuing repair
authorization. The user did not separately approve this document verbatim.
This changes the delivery contract; it does not change numerical methods,
scoring, permissions, or execution.

The observed gap is that an approved plan can retain unverified criteria while
the playbook check passes. Execution progress and deliverable verification must
remain separate. A successful operation, free-text claim, or reviewer warning
alone cannot certify a criterion.

## Contract

Keep the existing completion source, scope, target and playbooks. Add optional
`completion.requirements`, each containing:

```json
{
  "id": "primary_fit",
  "covers": [{"criterion_index": 0}, {"step_id": "fit", "output_index": 0}],
  "operation": {"step_id": "fit", "operation_id": "model.genesis", "spec": {}},
  "allow_not_applicable": false
}
```

`spec` is the existing registered operation's scientific specification, validated
by its existing declaration. The empty object above denotes that schema position,
not a valid model request. Input declarations retain the existing workflow
`source.from_step/output` and branch vocabulary. This first verifier supports
registered source/model references; symbolic upstream definitions remain
explicitly unverified until their scientific definitions can also be checked.
No new expression language, JSONPath, numerical target oracle or executor exists.

Every criterion and every expected-output string is an addressed slot. A slot
without an approved typed requirement stays unverified. Binding text to an
explicit typed requirement is an operational definition approved by the person;
it does not certify the scientific truth of the prose. Unsupported operations or
outputs remain unverified with an explicit reason.

Add `completion_evidence.requirements` entries:

```json
{
  "requirement_id": "primary_fit",
  "operation_record_id": "oprec_existing",
  "workflow_step_id": "fit",
  "artifacts": [{"run_id": "existing_run", "artifact_id": "existing_model"}]
}
```

These are references, not caller-owned success flags. Verification reads the
original proposal revision/fingerprint, the completed OperationRecord and the
registered products. It checks the precise resolved request, scientific spec,
producer/step, source lineage, artifact bytes and the producer-specific computed
output. Raw files, another fit, generic successful operations and labels cannot
stand in for those products. Reusing old products creates no execution receipt.

## Lifecycle

Draft requirements may be supplemented. Adding a machine interpretation to an
already approved unbound slot requires a new approval. Changing criteria,
expected outputs, source or scientific spec invalidates prior coverage and
requires approval; prior versions remain in the append-only history. Evidence
updates and execution progress do not reopen approval or change the requirement
basis. Omitted fields preserve existing definitions.

Ask retains its existing per-request approval route: each verified obligation
may rely on the original valid human confirmation of that exact scientific
request instead of a separate plan approval. Machine actors require the approved
plan basis. This is independent of the current UI mode and does not turn adopted
results into preregistered results. A pending substantive plan revision remains
unverified until its existing approval boundary is satisfied.

The basis digest covers the question, criteria, expected outputs, completion
source/scope/target/playbooks and requirement definitions. It excludes evidence,
step execution states, timestamps and ephemeral later result IDs. Products and
resolved requests receive server-derived hashes in verification. Restart repeats
read-only verification. Changed bytes, missing receipts, wrong source, changed
spec or ambiguous provenance remain unverified; nothing is rerun automatically.

Historical request verification must not call the request execution resolver:
its current-head freshness rule intentionally expires after execution. It reads
the original immutable proposal and actual execution instead. Current execution
continues through the unchanged permission/approval/freshness path.

NA is accepted only when the approved requirement explicitly permits it and the
supported producer verifier supplies an applicable source-bound typed NA. An
Agent's reason, unavailable capability, exception, or empty output is not NA.
Otherwise the obligation remains partial or the person explicitly revises it.

## Result and integration

`delivery_check(root, plan)` remains the shared tool/final/review check. Preserve
the original `playbook_status`. Any unbound, unsupported or failed requirement
makes the overall full-analysis status `partial`; existing question-scope target
checks and safety floors remain unchanged. Missing machine definitions remain
partial even if a legacy plan has no textual slots; empty declarations cannot
bypass the gate.

Return `criteria_verification` with `plan_id`, `plan_version`, `basis_sha256`,
`status`, `requirements` (`id`, `status`, string `reason`, bounded
`verified_artifacts`) and `unbound_slots`. No observations or model estimates are
included. Plan GET stays light. A separate on-demand read-only verification GET
and UI are owned by the root agent; they use this same function. Execution
`completed_operation_ids` and the progress counter are untouched.

Initial producer support targets exact model-genesis specifications, registered
model products, existing typed joint-F post-estimation products and report.compose.
Report verification reuses the existing registered report integrity and selected
result-source coverage check; it does not judge the report's prose.
The existing joint-F producer supports its declared OLS envelope; it cannot
certify a panel time-F test. Registered VIF and other unsupported native diagnostic
operations stay unverified; no verifier is invented. None of these first readers
has a supported typed NA path, so allow_not_applicable alone never yields a pass.

## Validation and cost

Red cases: playbook pass with unbound criteria/outputs; unsupported verifier;
successful unrelated operation; changed source/spec/artifact; failed or missing
record; ambiguous branch; stale approval; forged NA. Positive cases reuse real
registered model outputs from the ordinary executor, including after restart,
without another execution. Evidence-only updates retain approval and receipt
history. Changed covariance declarations are rejected or remain unverified under
the existing scientific input contract. Symbolic upstream verification and native
diagnostic readers remain open scope; this is not a claim that M3 is fully closed.

Reuse the existing bounded product reader and per-check cache. Check addressed
slots and unique referenced records/products; do not scan all runs, parse source
CSV rows, refit a model, or call a provider. New timing claims await a separate
exclusive measurement. Old cohort records and scores remain immutable.
