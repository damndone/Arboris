# Workbench v1.8.9 — AI-native SPSS/Stata parity foundation

> 状态：设计方向已获用户确认，等待本文件最终评审
> 日期：2026-08-15
> 基线：当前 main 的 live registry 与 v1.8.8 final integration evidence
> 本文件性质：产品与架构主 spec，不是实现代码，也不替代 formal development line

## 0. 摘要与版本决策

Workbench 不以“复制 SPSS/Stata 的菜单和命令数量”为最终目标，而是以：

1. 具备统计工具的可信正确性；
2. 具备 SPSS/Stata 的核心数据消费和统计能力；
3. 在 Agent 能发挥优势的地方超过传统 GUI；
4. 让每个能力都能通过自然语言被发现、组合、确认、执行和解释；
5. 让新增第 N+1 个能力不需要修改一堆固定流程；

作为 v1.8.9 及后续版本的共同基础。

本版本的硬范围是：

- P0：工作流统计正确性、分支恢复、fail-closed、结果证据契约；
- P0：Capability Manifest、Analysis Intent、Agent Plan IR、Port Type、两阶段 discovery 和 typed recovery；
- P1：数据消费层、数据元数据和直接 UI；
- P1：分类 ML 的完整基础，包括严格数据切分、交叉验证、模型比较、校准和解释性；
- P0/P1 的 Agent、Notebook、Report、UI 统一接线和验收。

P2/P3 写入本 spec，目的是锁定未来的模块边界、接入契约和优先级；本版本不以继续堆模型族数量为完成条件。除非 P0/P1 的退出门槛全部通过，不得通过增加模型数量掩盖基础层未完成。

### 1.3 当前必须优先修复的正确性风险

在继续增加能力前，当前树已有两类必须写入 P0 的问题：

1. 非 OLS post-estimation 可能进入 OLS 风格 refit/inference 路径，并产生不属于该模型语义的 F 统计和 p 值。相关路径位于 backend/workbench/agent/workflow_runtime.py 的 _refit_completed_ols_branch 及其持久化逻辑。
2. WorkflowStepState 未完整持久化 model branches。首次执行某个模型后中断，再恢复依赖该模型的步骤时，恢复过程可能无法重新绑定已完成的模型分支。

这两类问题不是“以后再优化”的技术债，而是能够使报告正常生成却表达错误统计语义的 P0 缺陷。任何“模型数量增加”都不能排在它们之前。

### 1.4 证据声明规则

所有未来状态报告必须区分以下证据：

| 证据层 | 能证明什么 | 不能证明什么 |
|---|---|---|
| Registry/contract | 能力已声明、字段和入口存在 | 数值正确、真实 LLM 会规划 |
| Deterministic evaluator | typed proposal、拒绝和边界行为稳定 | provider-backed LLM 质量 |
| Numerical oracle | 数值与独立实现或参考软件一致 | Agent/UI 已接线 |
| Runtime/persistence | 运行、artifact、lineage、resume 正确 | 浏览器用户路径 |
| Browser acceptance | 用户可见页面可操作 | 外部真人身份或真实 LLM 泛化 |
| Provider benchmark | 指定 provider 的规划质量 | 所有 provider 的质量 |
| Security/adversarial | 对注入、越权、危险输入的防护 | 统计方法本身正确 |

禁止把其中一种证据写成另一种证据。

## 2. 对标范围与产品定位

SPSS 官方能力目录覆盖数据准备、回归、Custom Tables、决策树、预测、神经网络、复杂抽样、缺失值、精确检验等。Stata 官方能力目录把数据管理、面板/纵向数据、多层模型、复杂抽样、SEM 和时间序列作为成熟的一等能力。

对标参考：

- IBM SPSS Statistics Features：<https://www.ibm.com/products/spss-statistics/features>
- Stata Features：<https://www.stata.com/features/>
- Stata Panel/Longitudinal Data：<https://www.stata.com/features/panel-longitudinal-data/>
- Stata Survey Features：<https://www.stata.com/features/overview/survey-features/>
- Stata SEM：<https://www.stata.com/features/overview/structural-equation-modeling/>
- Stata Time Series：<https://www.stata.com/features/time-series/>

Workbench 的定位不是立即复刻全部长尾命令，而是：

- 首先达到研究员日常使用所需的数据、结果和可信度；
- 用 Agent 把“发现问题、提出方案、组合步骤、解释证据”做得比传统菜单更好；
- 用 typed contracts 和 lineage 保证这种超越不会变成静默自动化；
- 把长尾模型接入成本压缩到“实现能力 + 注册契约 + 外部验证 + 消费者适配”。

## 3. 北极星与不可违反的原则

### 3.1 AI-native 优先，但不让 LLM 成为统计真相源

Agent 可以超过 SPSS/Stata 的地方：

- 自动发现数据形状、测量级别、缺失、时间结构、潜在泄漏和 merge 风险；
- 根据目标、约束和数据证据提出多个可比较方案；
- 把数据准备、诊断、建模、稳健性分析、可视化和报告串成一个 typed DAG；
- 对不同模型族做同一数据切分下的比较；
- 在假设冲突时主动解释“为什么不能直接运行”；
- 提出有限、可审阅的 robustness branch；
- 从多个 run 的真实 artifact 中生成带证据引用的回答；
- 把用户的自然语言目标编译为可复现、可重跑、可比较的方案。

Agent 不得：

- 静默选择或更换统计估计量；
- 静默修改原始数据或丢弃行列；
- 自行发明 run、node、artifact、column 或 capability identity；
- 将自然语言解释当作数值结果；
- 在证据不足时用猜测填充结果；
- 通过提示词绕过 confirmation、权限、资源限制或安全策略。

### 3.2 正确性优先于自动化

任何结果必须能够回答：

- 使用了什么数据版本；
- 使用了哪些列和角色；
- 使用了什么 estimator、假设和选项；
- 哪些结果是精确计算，哪些是近似、描述性或不可用；
- 哪些诊断通过、失败或未检查；
- 哪些外部依赖和 oracle 验证存在；
- 结果是否可以被 Agent、Notebook、Report 和 UI 共同读取。

无法回答时，系统必须返回显式的 unavailable、degraded、blocked 或 failed 状态。

### 3.3 组合优先于固定流程

Workbench 不实现“一个自然语言意图对应一个硬编码流程”。能力应当通过：

- typed input/output ports；
- 数据和模型 artifact binding；
- 可验证的前置条件；
- 可持久化的 DAG；
- 可组合的 result/evidence projection；
- 声明派生的 Agent vocabulary；

自由组合。

固定的推荐流程可以作为 preset，但 preset 只是一个可审阅的 plan builder，不能成为唯一执行路径。

### 3.4 不过拟合实现与评测

禁止：

- 针对某个 fixture、某个 prompt 或某个列名写特殊分支；
- 用 capability 数量硬编码验收；
- 用固定 prompt 通过来代表自然语言能力；
- 用 xfail、静默 skip 或缩小 denominator 掩盖能力缺口；
- 让单一数据集决定通用数据契约。

必须使用：

- declaration-derived inventory；
- 通用 contract tests；
- 多种数据形状；
- holdout prompt；
- 正常、模糊、缺字段、错误、危险、provider error 和 prompt injection 场景；
- mutation testing 验证每条守卫真的会阻断目标错误；
- 独立数值 oracle；
- 不同 family 的最小兼容 fixture。

### 3.5 研究问题先于模型

AI-native 不能退化成“用户说一句话，Agent 猜一个模型”。任何建模计划都应先形成可审阅的 Analysis Intent：

- analysis mode：descriptive、inferential、predictive 或 causal；
- research question；
- estimand、prediction target 或 decision target；
- unit of analysis；
- target population；
- observation time、prediction time 和 prediction horizon；
- 数据、成本、延迟、解释性和风险约束；
- primary metric 或 primary evidence；
- 用户已经明确声明的假设；
- 尚未解决、需要追问的事实。

模型只是 Analysis Intent 的一个下游实现候选。Agent 可以提出多个模型或工作流，但不能在 intent、estimand、数据结构或目标人群不清楚时，靠模型名称补齐这些事实。

## 4. 总体架构

### 4.1 分层

目标架构分为十层：

1. Analysis Intent Layer：研究问题、analysis mode、estimand/target、约束和待确认事实；
2. Data Identity Layer：数据集、节点、artifact、列、标签、测量级别和 provenance；
3. Capability Manifest Layer：能力身份、发现信息和各独立契约的组合根；
4. Plan IR/Compiler Layer：LLM 可提出的符号计划、服务器编译和 typed ports；
5. Workflow Layer：可组合 DAG、来源承诺、bindings、分支、恢复和幂等性；
6. Execution Layer：确定性数值引擎、资源控制、依赖控制和运行状态；
7. Evidence Layer：结果、诊断、图表、警告、假设、oracle 和 provenance；
8. Consumer Layer：Agent、Notebook、UI、Report 共同消费的 projection；
9. Agent/Notebook Layer：发现、规划、追问、proposal、恢复建议和证据回答；
10. Provider/Interaction Layer：LLM provider、用户确认、浏览器交互和安全审计。

上层不能通过字符串猜测下层语义。每层通过版本化 typed contract 连接。

### 4.2 CapabilityManifest：组合根，不扩成超级 CapabilityContract

当前 backend/workbench/agent/capability_contract.py 中的 CapabilityContract 负责能力身份、种类、摘要和自然语言可达路径。它应继续保持这个清晰职责，不能扩成同时管理执行、结果、UI、Report 和安全策略的超级 dataclass。

新增目标是 CapabilityManifestV1：它是对现有独立契约的组合根，而不是另一份重复事实。它引用：

- 当前 CapabilityContract；
- WORKFLOW_STEP_SPEC_CONTRACTS 中的 StepSpecContract；
- ModelFamilyContract 或其他 family contract；
- result-shape registry；
- execution adapter registry；
- consumer projection registry；
- safety、dependency 和 oracle policy registry；
- natural-language discovery descriptor。

逻辑形状如下；每个 ref 指向独立版本化契约。一个 capability 可以拥有多个 direct/composition/read-only exposure path，Manifest 不得把多条真实路径压成单个 step 或 adapter：

~~~json
{
  "manifest_version": "capability-manifest/v1",
  "capability_ref": "capability-contract-ref",
  "descriptor_ref": "capability-descriptor-ref",
  "exposure_paths": [
    {
      "path_id": "stable-path-identity",
      "exposure": "direct|composition|read_only|closed",
      "operation_ref": "operation-contract-ref-or-null",
      "step_contract_ref": "step-spec-ref-or-null",
      "family_contract_ref": "family-contract-ref-or-null",
      "execution_adapter_ref": "execution-adapter-ref-or-null",
      "result_contract_refs": ["result-shape-ref"],
      "evidence_contract_refs": ["evidence-contract-ref"],
      "projection_refs": {
        "agent": "projection-ref",
        "notebook": "projection-ref",
        "ui": "projection-ref",
        "report": "projection-ref"
      }
    }
  ],
  "safety_policy_ref": "safety-policy-ref",
  "dependency_policy_ref": "dependency-policy-ref",
  "oracle_policy_ref": "oracle-policy-ref"
}
~~~

要求：

- manifest 从各注册表派生，不维护第二份 capability 列表；
- `ContractRefV1` 固定包含 `kind`、`logical_id`、`semantic_version` 和 `contract_digest`；所有 registry 使用同一 resolver 和 unresolved/duplicate 错误语义；
- 每个 ref 必须能在启动或注册时解析；
- manifest pin 住各契约 semantic version；
- 某个 projection 不适用时使用显式 not_applicable contract，不使用空 ref；
- direct path 通过不能掩盖 composition path 断线；一个 result shape 有 projection 不能代表同 capability 的其他 result shape 已覆盖；
- 新增 ref 类型必须有覆盖 live registry 的元测试；
- manifest 只连接模块，不把模块内部算法复制进来。

迁移必须是增量式的：

- 第一阶段只建立从现有 registry 派生的只读 manifest projection，不搬移或复制既有声明；
- 既有 registry 在对应 consumer 完成切换前仍是权威来源，不允许双写两个事实源；
- consumer 按 Agent、Notebook、UI、Report 分批切换，每一步都要有等价性和回退证据；
- 旧接口最终只能成为新契约的兼容 projection，不能长期形成平行执行栈；
- 已持久化 workflow 和 artifact 继续按其 pin 住的旧 contract version 重放，不做隐式升级。

### 4.3 AnalysisIntent、AgentPlanIR 与编译边界

为同时获得 LLM 的组合能力和服务器的安全性，规划必须分成三种不同对象：

~~~text
AnalysisIntentV1
  → DraftAgentPlanV1
  → server compilation
  → CompilationRecordV1
  → confirmed execution
  → ExecutionRecord
~~~

AnalysisIntentV1：

- 表达研究目标、analysis mode、estimand/target、约束和待确认项；
- 可以由用户直接给出，也可以由 Agent 提议后由用户确认；
- 不携带可执行 artifact identity。

DraftAgentPlanV1：

- 是 provider 可以生成的符号 DAG；
- 只引用 capability descriptor、角色、符号 source 和 typed options；
- 可以包含多个候选方案和理由；
- 不能携带服务器权限、真实 artifact identity、risk authorization 或 execution key；
- 不能直接进入 runtime。

DraftAgentPlanV1 和 CompiledWorkflowV1 是 Agent Plan IR 的不可信与可信两个阶段，不再额外定义第三种同义 plan schema。

CompiledWorkflowV1：

- 只能由服务器 compiler 生成；
- 解析并 pin capability、operation 和 contract version；
- 将符号列、角色和 source 绑定到真实 identity；
- 检查 port type、前置条件、DAG、风险、权限和资源预算；
- 生成 preview fingerprint、`semantic_plan_hash`、PlanDiff 和待持久化的 compilation record；
- 编译失败时返回 typed diagnostics，不产生运行状态。

CompilationRecordV1：

- 是服务器持久化的 authority record，绑定 principal、project、compiler version、contract/catalog/policy snapshot、source commitments、PlanDiff 和 `semantic_plan_hash`；
- confirmation 绑定 compilation record identity、plan revision 和 semantic hash；方法、风险、数据影响、资源策略或输出口径变化必须使旧确认失效；
- 上游执行完成后，服务器把真实 run/node/artifact identity 和 digest 解析为 `execution_instance_hash`，但不得借此改变用户已确认的方法、风险或数据影响；
- runtime route 只接受 `compilation_record_id` 和 confirmation reference，不接受客户端回传的完整 CompiledWorkflow 作为 authority；
- canonicalization 必须复用仓库唯一的 `canonical_json_v1` 语义，不能由 workflow、compiler 和 confirmation 各自实现一套 hash。

ExecutionRecord：

- 只接受服务器重新验证后的 CompilationRecordV1；
- 保存 `semantic_plan_hash`、`execution_instance_hash`、confirmation revision、contract/catalog/policy snapshot；
- 不能在执行期重新解释用户自然语言；
- provider 原始输出永远不是执行授权。

这条编译边界是“像编程一样自由组合”和“准确安全”的共同地基。LLM 负责生成候选程序，Workbench 负责编译、类型检查、授权和执行。

v1.8.9 的 compiler 是现有 proposal canonicalization、`operation.multi_step` 和 workflow runtime 外侧的增量安全层，不是新写一套执行引擎。它应先以 shadow compile 方式对现有合法计划做等价性比较，再逐条 consumer path 切换；任何不等价都必须 fail closed 并保留旧路径，直到原因被解释和验证。

### 4.4 Port Type 与分析模式

只检查 step 顺序不足以保证可组合。每个输入/输出 port 必须有机器可判定的类型：

- artifact kind：dataset、model branch、statistical result、prediction result、evidence、figure、report；
- dataset kind：IID、panel、time series、survey、event history、study records 等；
- analysis mode：descriptive、inferential、predictive、causal；
- semantic roles：outcome、predictor、target、feature、entity、time、group、weight、treatment、instrument 等；
- structure/availability：StructureSpec、AvailabilitySpec 或明确 unknown；
- cardinality：single、collection、bounded map；
- effect：read-only、dataset mutation、model fit、report mutation；
- trust/availability level。

compiler 必须检查 producer port 与 consumer port 是否兼容。SMOTE 等 prediction-data 输出因此不能进入 inference family；time-series feature 没有 availability 证据时不能自动进入 temporal prediction。

例外组合只能通过显式、版本化 adapter 声明，不能在 workflow runtime 中增加 operation-specific if/else。

### 4.5 Workflow DAG

Workflow 必须以数据流和 artifact binding 为核心，而不是以 operation 名称列表为核心。

每个 step 至少包含：

- step identity；
- capability identity 和 semantic version；
- input bindings；
- literal source 或 upstream output source commitment；
- typed options；
- preconditions；
- expected outputs；
- risk level；
- confirmation policy；
- replay/idempotency policy；
- result/evidence binding。

数据源允许两种形式：

~~~text
literal source:
  run_id + node_ref + artifact_id + context_fingerprint

upstream source commitment:
  from_step + output_port
~~~

链式 step 在规划时校验 DAG、output port 和类型；在上游执行完成后注入真实的 run/node/artifact identity，再为下游计算 preview fingerprint。不能为了支持组合而放弃 stale 检查。

持久化 workflow state 使用显式版本化边界：

- `WorkflowExecutionStateV2` 保存 schema version、semantic/execution hash、contract/catalog snapshot 和 typed output bindings；
- `PortBindingV1`、`ModelBranchRefV1` 只保存 immutable identity/digest/ref，不复制一份可漂移的模型事实；
- 每个 output port 必须由其 schema resolver 校验后才能成为 resume 输入；存在 `schema_version` 字段不等于 payload 已验证；
- old-version → current-version 使用显式 migration matrix；没有安全 migrator 时返回 `MIGRATION_REQUIRED`，不得填默认值后继续；
- resume 不重新读取当前 active head 推测历史绑定。

架构允许 sequence、parallel、bounded branch 和 diagnostic-gated branch，但每种控制结构都必须：

- 有明确的最大步数、最大分支数和资源预算；
- 由服务器验证；
- 将每个分支写入 lineage；
- 对用户显示采用了什么条件；
- 不能由 LLM 自己修改安全策略。

允许的通用组合原语由 registry 声明：

- sequence；
- parallel/fork；
- compare；
- bounded map over declared outcomes/groups/models；
- diagnostic gate；
- collect evidence。

这些是控制结构，不包含固定统计公式。preset 和 reusable recipe 必须编译成同一 Agent Plan IR，并在展开后让用户看到真实 steps、风险和数据影响。

本版本只实现现有 DAG runtime 能原生表达的 sequence、fork/compare 和编译期静态展开的 bounded map。diagnostic gate 和动态 branch 先保留 typed contract 与 proposal 表达，不在没有幂等、预算、恢复和 lineage 证据时加入新的运行时控制流。

### 4.6 数据 Artifact 与元数据

原始数据不可变。任何清洗、转换、标签或类型改变都产生有 provenance 的子节点。

数据身份至少区分：

- dataset identity；
- graph node identity；
- artifact identity；
- schema revision；
- metadata revision；
- source fingerprint；
- row/column shape；
- availability/provenance status。

列元数据包含：

- name；
- dtype；
- semantic/measurement level；
- variable label；
- value labels；
- missing-value policy；
- role candidates；
- unique count；
- missing rate；
- time/entity/group/survey role；
- privacy or sensitivity marker。

元数据缺失不能静默推断成确定事实。推断只能作为 advisory，需在 proposal 和 result 中标记来源与置信边界。

### 4.7 Result/Evidence Envelope

所有能力都返回共同外壳和 family-specific payload。执行状态、可用性、完整性质量、数值方法、推断基础、评估设计和验证等级是彼此独立的维度，不能用一个 `truth_level` 相互替代：

~~~json
{
  "result_identity": {},
  "execution_status": "completed|partial|blocked|failed",
  "availability": "available|not_available|not_applicable",
  "completeness_status": "complete|degraded|insufficient|not_applicable",
  "degradation_reasons": [],
  "numerical_method": "closed_form|deterministic_numeric|simulation|approximate_algorithm",
  "inference_basis": "exact_distribution|asymptotic|bootstrap|descriptive|not_applicable",
  "evaluation_design": "in_sample|holdout|cross_validation|nested_cross_validation|cross_fitting|bootstrap|not_applicable",
  "validation_summary": {
    "levels_present": [],
    "minimum_required": "none|same_library_regression|known_answer|independent_implementation|reference_software",
    "requirement_status": "met|not_met|not_applicable"
  },
  "method": {},
  "estimand": {},
  "input_provenance": {},
  "assumptions": [],
  "diagnostics": [],
  "numeric_facts": [],
  "family_evidence": {},
  "figures": [],
  "warnings": [],
  "dependencies": [],
  "oracle": {},
  "lineage_refs": []
}
~~~

规则：

- `degraded` 只属于 completeness/quality 轴，表示结果可用但存在结构化缺口；它不能替代 `partial` execution、`not_available` 或 validation failure；
- exact-distribution、closed-form、deterministic-numeric 和 independent validation 是不同声明；同库 direct call 只能标为 `same_library_regression`；
- approximate algorithm 或 asymptotic inference 必须说明方法；
- not_applicable 不是缺失字段；
- not_available 必须给出原因；
- blocked 必须说明哪条前置条件或安全策略阻断；
- warning 必须是结构化事实，不由 LLM 根据数字临时编造；
- family-specific payload 可以扩展，但不能覆盖共同字段的语义；
- 图表必须引用真实 numeric source，不能只保存图片；
- 每个 NumericFact 至少绑定 fact identity、estimand/statistic、sample denominator、weight、scale/unit、SE/CI 方法、置信水平、检验方向、reference distribution/df、multiple-comparison family/correction、evaluation design、source selector、oracle checks 和自己的 validation level；不适用字段必须显式 not_applicable；
- Envelope 的 validation summary 只能列出事实级等级和是否满足最低要求，不能取最高等级并扩散到其他 facts；
- Report、Agent、Notebook 和 UI 只能消费这个 envelope 或其声明适配器，不能各自重新解析裸 artifact。

EvidenceEnvelope 必须在执行完成路径中一次性生成并事务持久化，而不是消费者读取时重新 projection：

~~~text
execution completion
  → artifact admission and family validation
  → version-pinned EvidenceEnvelope projection
  → transactional immutable persistence
  → artifact/envelope digest binding
  → bounded consumer read facade
~~~

该链路必须有唯一 `EvidencePersistencePortV1` 和 package-local implementation owner，覆盖 crash/retry、重复写入、旧 artifact migration、projector version 变化、envelope invalidation 和 append-only replacement refs。消费者只能读取已持久化 envelope；projector 升级不得静默改写历史证据。

### 4.8 Consumer Adapter

每个 capability 必须提供或明确继承：

- Agent summary adapter；
- Notebook result adapter；
- UI result/detail adapter；
- Report evidence adapter；
- error/warning adapter；
- figure adapter。

适配器只负责投影，不负责重新估计或改变统计语义。

若某个消费者暂时不能展示某类结果，应返回带 capability_id 和 reason 的 unavailable，而不是吞掉结果、显示空卡片或把 family-specific 结果伪装成通用回归表。

consumer coverage 必须由 CapabilityManifest 派生一张实时矩阵，原始 row key 至少包含：

~~~text
capability
× exposure path
× operation/step contract version
× input/output contract version
× result/evidence shape version
× consumer
~~~

每个 row 至少区分：

- registered；
- contract-valid；
- projected；
- browser-visible；
- provider-verified；
- blocked/not_applicable。

capability 级状态只能由这些 path rows 聚合。这张矩阵用于发现“做出来但够不着”，不能通过 summary 字符串、单一 happy path 或手工 allowlist 维护。

### 4.9 Agent、Notebook 与自治等级

Agent 和 Notebook 使用同一份 server-owned vocabulary，但可以有不同的交互入口：

- Main Agent：项目级 advisory/read-only discovery，不拥有未选中 graph 的 mutation authority；
- Chain Agent：面向当前 graph/head 的 proposal 和多步计划；
- Notebook：面向 analysis contract、options、run family 和可复用叙事；
- UI：面向编辑、预览、确认、查看和对比；
- Report：面向事实、图表、引用和导出。

Notebook 是持久化规划和叙事 projection，不是第二套 execution truth。Agent 会话分支、Notebook option 和 Graph fork 必须通过 durable identity 映射，不能各自维护不可对账的状态。

自治等级：

| 等级 | 允许行为 |
|---|---|
| Inspect | 读取受限上下文、诊断和解释，不产生 mutation |
| Propose | 生成 AnalysisIntent 或 DraftAgentPlan，不执行 |
| Confirmed execution | 执行用户确认后的 CompiledWorkflow |
| Delegated bounded execution | 未来能力；需要显式 policy、预算和可撤销边界，本版本不开放 |

自然语言编译链：

~~~text
user intent
  → AnalysisIntent
  → bounded context compiler
  → capability descriptor discovery
  → full-contract retrieval
  → DraftAgentPlan candidates
  → clarification or typed proposal
  → server compiler/canonicalization
  → preflight and risk classification
  → user confirmation
  → execution
  → evidence projection
  → grounded answer
~~~

LLM 输出只能提供 intent、候选方案、理由和用户可读说明。artifact identity、列 identity、能力 identity、选项合法性、风险和执行结果必须由服务器绑定或验证。

### 4.10 可扩展的 Capability Discovery

当能力从 129 增长到数百或更多时，不能把所有完整 schema 塞进每次 prompt。自然语言全覆盖采用两阶段发现：

第一阶段 Capability Descriptor Index：

- capability identity 和 version；
- user intents；
- analysis modes；
- accepted dataset/port kinds；
- required semantic roles；
- assumptions/preconditions；
- output/evidence kinds；
- risk、cost 和 dependency class；
- direct/composition/read-only/closed exposure；
- concise description 和 multilingual aliases。

第二阶段 Full Contract Retrieval：

- 只为 shortlist 中的能力加载完整 proposal、step、result、evidence 和 safety contracts；
- server 保留可见 shortlist、未选原因和截断计数；
- Agent 不得调用 shortlist 或 full contract 中不存在的 identity；
- retrieval 失败时追问或 blocked，不猜 capability。

Descriptor index 和 full contracts 都从 live registry 派生。评测必须测 capability recall、错误 shortlist、虚构 identity、token budget 和中英文 paraphrase，而不是只测固定英文 prompt。

Descriptor 和 multilingual aliases 只影响检索与解释，不能决定执行 identity、默认选项或风险等级。aliases 必须作为 capability 自有的版本化本地化元数据生成和审核，不能成为第二份手工 capability 清单。

### 4.11 Typed Failure 与受控恢复

统一 FailureEnvelope 至少包含：

- failure class：invalid_request、incompatible_input、stale、unavailable_evidence、optional_dependency、nonconvergence、resource_limit、policy_block、execution_failure、corrupted_state；
- stable reason code；
- capability/step identity；
- evidence refs；
- retryable；
- safe remediation choices；
- whether user confirmation is required；
- partial outputs and their trust status。

Agent 可以读取 FailureEnvelope，提出新的 DraftAgentPlan 或向用户追问；不得：

- 自动重试 mutation；
- 静默更换模型或删除数据；
- 把 failed/blocked 改写为 partial success；
- 在没有新证据时重复相同 proposal。

恢复循环必须有 server-owned turn、step、time 和 cost budget。每次修订都形成新的 plan revision 和 lineage reason。

### 4.12 扩展方式

新增 capability 的最小接入单元：

1. 实现确定性能力；
2. 实现或复用现有 CapabilityContract、StepSpecContract 和 family contract；
3. 注册 CapabilityManifest 和 Descriptor；
4. 声明输入/输出 PortType 和前置条件；
5. 注册执行 adapter；
6. 注册 result/evidence projection；
7. 提供独立 oracle 或明确验证等级；
8. 自动进入 Agent/Notebook discovery 和 vocabulary；
9. 通过通用 compiler、registry、runtime、consumer 和 gate。

新增能力不允许：

- 在 orchestrator 增加一个专属流程分支作为默认方式；
- 在 Agent prompt 中加入只对该能力生效的隐藏规则；
- 在 UI 中用 capability registry 之外的第二份清单；
- 静默忽略不支持的输入或输出。

### 4.13 增量落地顺序

为避免把基础设施优化变成高风险大重写，落地遵循以下顺序：

1. 只读派生 Manifest、Descriptor 和 consumer coverage，不改变执行；
2. 用元测试证明 live registry 的 identity、version、projection 和 not_applicable 状态无遗漏；
3. compiler 进入 shadow mode，对当前 direct 和 `operation.multi_step` 合法计划生成 compiled representation，并与现有 canonical plan 比较；
4. 先切换只读 discovery/preview，再切换低风险 execution，最后切换 mutation path；
5. 每次切换都保留 plan hash、PlanDiff、失败原因、browser evidence 和回退边界；
6. 只有全部已知 consumer 完成等价性验证后，才允许移除旧入口；不得以长期 dual-write 维持兼容。

这个顺序只约束迁移方式，不削弱最终架构：目标仍是一套真相源、一条编译边界和一个 runtime。

### 4.14 Contract Lock、Provider Contribution 与并行扩展

为了让多个 subagent 和未来插件能够并行增加能力而不争写中央控制面，v1.8.9 采用 Contract-first Release Train。并行工作开始前必须先形成：

1. Plan Lock：包含获批主 spec、implementation program、所有 child plans 和精确 ownership；
2. Contract Lock：包含版本化公共 schemas、canonical fixtures、mock producer/consumer packets、provider loader 和 compatibility tests；
3. Wave Lock：每个并行 wave 的全部 lane 从同一不可变 commit 开始。

`ProviderContributionV1` 是 refs 的声明集合，不是新的超级 CapabilityContract。每个 package-local provider 可以贡献：

- capability/exposure path refs；
- operation/step/port refs；
- adapter declaration，其中 request schema、executor ref 和 result validator 必须成组版本化；
- result/evidence projection refs；
- consumer renderer refs；
- dependency、resource、safety 和 oracle policy refs。

Provider JSON 只能引用 opaque adapter/executor IDs，不能携带 Python import path、module attribute traversal 或任意 callable identity。Agent/Notebook Cutover 单一拥有 `TrustedExecutorRegistry`：server composition 注入带 owner/signature/effect/request/result refs 的 `ProviderRuntimeContributionV1` 和实际预注册 callable，启动时与 JSON declaration 做一对一 join；missing/duplicate/extra/mismatch 全部 fail closed，registry 永不按 JSON 路径动态 import。

Provider loader 的规则：

- 本版本只加载仓库内固定受信任 provider package，不开放任意 Python entry point、用户路径、网络下载或自动安装；
- provider 按稳定顺序加载；duplicate identity、versionless ref、unresolved ref、digest mismatch 和 incompatible major version 必须 fail closed，禁止 last-write-wins；
- feature lane 只新增自己拥有的 provider declaration、adapter 和核心实现，不修改中央 registry、Notebook planner 或 runtime dispatch；
- CapabilityManifest、Descriptor、Agent vocabulary、consumer coverage 和 UI renderer catalog 都从 provider/registry 派生；
- provider/catalog digest 进入 CompilationRecord、EvidenceRecord 和 Evaluation Evidence Manifest；catalog 变化使旧覆盖和评测证据失效；
- Contract Lock 后如公共 schema 不够表达需求，受影响 lane 必须停止并提交 Contract Change Request；不得在 payload 偷塞未版本化字段。

Evaluation 时序必须避免 candidate/evidence 自引用：先完成并关闭 Harness 实现线；Integration 把 wave heads 与不含自身 SHA/evaluation digest 的 lock manifest 形成 clean C1/C2/C3 candidate commit，并在 C3 前冻结全部 acceptance harness/tests；随后独立 E1/E2/E3 run line 在 candidate 自己的 cwd/interpreter/PYTHONPATH/frontend root 上评测 exact SHA，并在独立 evaluation worktree 写 sidecar manifest/admission。下一 wave 只从被 sidecar admission 接纳的 exact candidate SHA 启动。E3 后 Final Acceptance line 只在独立 control worktree 写 browser/provider/full-gate/handoff sidecars，不回写 C3。Candidate、lock、test、fixture 或 harness 任一变化都使 admission 失效。

默认并发拓扑为 3 条 feature lane + 1 条独立 Evaluation lane。共享 contracts、Workflow runtime admission、Context Egress gateway、Evidence persistence、中央 registry、Agent/Notebook cutover 和最终 integration 都有单一 owner。Evaluation 不修产品，Integration 不修改统计语义、confirmation、Graph、安全或 UI 行为；行为缺陷必须退回功能 owner。

## 5. AI-native 超越 SPSS/Stata 的目标能力

### 5.1 Agent 主动发现而不是等待菜单选择

用户可以说：

~~~text
请评估这份数据是否适合做面板 DID，并给出可执行的分析方案。
~~~

Agent 应该：

1. 发现数据集和节点；
2. 检查 entity/time/treatment/outcome 的候选列；
3. 报告缺失、重复、时间排序、处理组支持和可能的泄漏；
4. 给出一个或多个 typed plan；
5. 明确哪些信息需要用户确认；
6. 只在用户确认后运行。

这比传统菜单强，但最终判断必须可追溯，不能因为“Agent 感觉可以”就放行。

### 5.2 假设冲突驱动的方案分支

诊断可以提出分支，但不能静默修改方案：

- 时间序列不平稳：提示差分、滞后阶或模型族候选；
- EFA KMO/Bartlett 不满足：拒绝直接解释因子，提出数据或目标调整；
- merge 出现多对多：阻断并请求用户决定；
- 分类数据严重不平衡：提出 class weight 或预测专用重采样；
- 面板/时序预测缺安全 split：阻断 generic prediction；
- 多重比较风险：提示校正或确认探索性定位。

每个分支都必须写入 plan、理由、输入证据和用户选择。

### 5.3 Evidence-grounded analyst

Agent 的回答必须引用：

- result identity；
- artifact/node；
- 数据 fingerprint；
- method/options；
- numeric fact；
- diagnostic/warning；
- availability reason。

LLM 只能对已存在的 evidence 做解释、比较和提问，不得创造不存在的 coefficient、p-value、图表或“模型已成功”的结论。

### 5.4 组合能力像编程，但受 typed contract 约束

用户可以自然语言表达：

~~~text
先按地区合并两份数据，去掉收入缺失的样本，构造滞后变量，
比较固定效应和随机效应模型，再把诊断和稳健性比较写进报告。
~~~

系统应编译成可审阅 DAG，而不是调用一个固定 preset。每一步可独立检查、重跑、替换、分支和比较。

### 5.5 可复用 Recipe 像函数，不是隐藏流程

用户和 Agent 可以把已验证 plan 保存为参数化 AnalysisRecipe：

- 声明输入 PortType；
- 声明参数和默认值来源；
- 声明输出 PortType；
- pin capability/contract version；
- 声明风险和 confirmation policy；
- 展开为可见的 DraftAgentPlan；
- 生成新的 compiled plan hash；
- 保留 recipe revision 和来源。

Recipe 不能隐藏 steps。执行前必须展开并显示真实数据源、变量绑定、方法、风险、成本和输出。更新 recipe 产生新 revision，不静默改变旧分析的重放语义。

### 5.6 追问、候选方案和受控恢复

Agent 的优势包括知道什么时候不该猜：

- identity、role、estimand、time horizon 或风险选择不明确时，产生 typed clarification request；
- 存在真实方法取舍时，最多给出少量有实质差异的 plan candidates；
- 不为凑数量制造伪差异；
- 排序依据必须来自 data evidence、用户约束或声明的 policy；
- 无法 evidence-gated 排序时显示 tied 或 insufficient_evidence；
- 执行失败后基于 FailureEnvelope 提出修订方案，并重新经过编译和确认。

这使 Agent 能在传统 GUI 之外承担“研究助理”的工作，但每次决定仍然可见、可拒绝、可追溯。

## 6. P0：正确性、运行真相和统一结果证据

P0 是本版本不可延期的基础层。

### 6.1 P0-A：family-aware post-estimation

要求：

- post-estimation 必须由上游模型 family 的 contract 决定；
- 非 OLS 模型不得进入 OLS refit；
- 某个诊断或检验不适用于当前 family 时，返回 typed blocked/not_available；
- 适用于 Logit/Probit/Poisson/Panel/IV/Survival/ML 的统计量必须使用各自语义；
- 禁止用 model_id 字符串猜测模型类型；
- 禁止硬编码 model_artifact_id；
- 结果 envelope 必须保存上游 family、estimator、covariance 和数据 fingerprint；
- 任何 family fallback 必须是声明的 compatibility adapter，而不是异常后的隐式降级。

验证：

- 用 Logit、Poisson、Panel、IV、Cox 等真实已完成模型分别触发 post-estimation；
- 对每个不兼容组合验证阻断原因；
- 对兼容组合用独立 oracle 或解析关系验证数值；
- 通过 mutation 将 family 路由改为 OLS，测试必须真实变红；
- 不能只断言流程 completed，必须断言统计量语义和 family identity。

### 6.2 P0-B：branch/resume truth

要求：

- WorkflowStepState 持久化所有完成模型分支、output ports、artifact identity、family identity 和 evidence refs；
- resume 重新加载后必须能解析依赖链；
- 同一 execution key 重试不能产生重复 child node 或重复业务效果；
- 上游完成、下游失败后恢复，只重做必要的下游步骤；
- source commitment 解析失败时返回结构化错误；
- 分支之间的输入不能被后续步骤静默覆盖；
- 恢复过程不得通过重新读取当前 active head 猜测历史输入；
- 任何旧 state 缺少必要字段都必须迁移或 fail closed，不能填默认值后继续执行。

验证：

- 首次完成模型、故意让后续步骤失败、进程重启、恢复并完成；
- 在恢复前改变 active head，确认恢复仍使用原始 branch binding；
- 注入重复 confirm、超时重试、部分写入和 crash-after-persist 场景；
- 检查最终 lineage 只有预期节点和 operation records；
- 对缺失 branch 的旧 state 验证明确 blocked/migration-required。

### 6.3 P0-C：统一 Result/Evidence contract

要求：

- 所有已注册能力必须拥有 result shape 和 evidence shape；
- 通用字段从 capability declaration 派生；
- family-specific 结果使用 namespaced payload；
- 结果必须分别声明 execution status、availability、completeness/degradation、numerical method、inference basis、evaluation design，并在每个 fact/oracle check 上声明 validation level；
- diagnostics、figures、warnings 和 assumptions 都必须可结构化读取；
- 每个 numeric fact 必须有来源、单位、估计对象和可选 oracle；
- 图表必须有 numeric source；
- 不适用字段不能用空字符串冒充；
- 不可用结果不能被渲染为“成功但没有内容”；
- approximate inference 必须保留方法标签；
- 小样本、非收敛、支持不足、前提失败和外部依赖缺失必须是结构化状态。

### 6.4 P0-D：Agent/Notebook/Report/UI 投影

要求：

- Agent summary 只能从 evidence projection 生成；
- Notebook option 必须绑定自己的 result/evidence contract；
- Report 只能引用真实 packet 中存在的 fact 和 figure；
- UI 可以按 family 展示不同卡片，但卡片字段来自声明；
- 新增 family 时如果没有某个 consumer projection，必须在 registry 中显式暴露；
- consumer 不得通过“字段缺席”推断零值或通过 capability name 生成 summary；
- projection validation 必须针对选定 option 的 artifact contract，而不是整个 run 的所有 artifact。

### 6.5 P0-E：Reachability 与自然语言契约

要求：

- live capability inventory 只能从声明派生；
- direct exposure、composition exposure 和 explicit exemption 分开；
- code.execute 等安全关闭项必须保留理由；
- model.genesis 作为 workflow carrier 的组合路径必须明确；
- 每个可达 capability 至少有一个 direct 或 composition path；
- 每个 path 必须有实际消费者，不得只在 registry 写字符串；
- Agent、Notebook 和 operation.multi_step 使用同一份 workflow vocabulary；
- natural_language_enabled=false 的能力不能被描述成独立顶层入口；
- 新增能力必须触发 inventory、schema、consumer 和 reachability 元测试。

### 6.6 P0-F：Manifest、Plan IR、Port Type 与 Failure Contract

要求：

- 保持当前 CapabilityContract 的 identity/reachability 职责，不把它扩成超级契约；
- CapabilityManifest 从现有 registry 和 adapter 派生；
- AnalysisIntent、DraftAgentPlan 和 CompiledWorkflow 是三个不同对象；
- runtime 只接受服务器持久化、重新校验并绑定有效 confirmation 的 CompilationRecord；
- `ExecutionAdmissionV1` 是所有 HTTP、Notebook、service、测试工具和兼容入口进入 runtime 的唯一 choke point；runtime public entry 不接受 Draft、客户端 CompiledWorkflow 或无 admission receipt 的内部调用；
- 每个 workflow port 有 artifact、dataset、analysis mode、role、effect 和 availability 类型；
- 编译器在运行前拒绝不兼容连接；
- capability discovery 使用 descriptor shortlist + full contract retrieval；
- consumer coverage 从 manifest 的 exposure-path/result-shape/consumer rows 派生；
- FailureEnvelope 提供 stable reason code、retryability 和 remediation；
- PlanDiff 在用户确认前展示数据影响、方法、风险、资源和预期输出；
- plan hash、contract versions 和 server-bound identities 进入 durable record。
- 所有 provider-bound context 必经 `ContextEgressGatewayV1`；gateway 绑定 sensitivity policy、destination/provider、selected/redacted refs、budget 和 receipt，直接调用 provider client、旧 context builder 或无 receipt context 必须被拒绝。

验证：

- provider 输出带伪造 identity、risk authorization 或 execution key 时被拒绝；
- 绕过 compiler 直接提交 DraftAgentPlan 时被拒绝；
- prediction-data port 连接 inference consumer 时编译失败；
- unknown StructureSpec/AvailabilitySpec 不会静默变成 IID；
- descriptor 检索遗漏、截断和不存在 identity 都可观测；
- 相同 intent 和 server state 产生稳定 compiled plan hash；
- shadow compiler 对现有合法 direct/multi-step 计划生成等价 canonical representation；
- consumer 分批切换期间不存在 registry 或 manifest 双写；
- FailureEnvelope 驱动的新方案需要新的 proposal/confirmation；
- 将 PortType 检查改成恒真时，元测试必须变红。

### 6.7 P0 退出门槛

P0 只有在以下全部成立时完成：

- 非 OLS post-estimation 不再发生 OLS 语义泄漏；
- branch/resume 的 red-to-green 测试通过；
- 所有持久化 artifact identity 和 lineage binding 可恢复；
- 每个当前 capability 的 result/evidence projection 有明确状态；
- Agent、Notebook、Report、UI 的 projection contract 通过；
- 所有安全关闭项有显式理由；
- Manifest、Plan IR、compiler、PortType、discovery 和 FailureEnvelope 的通用契约通过；
- provider 输出不能直接触发 runtime；
- execution completion 事务持久化 immutable EvidenceEnvelope，且消费者不在读取时重新 projection；
- runtime call-site inventory 证明没有绕过 ExecutionAdmission 的内部入口；
- Agent、Notebook、clarification、recovery 和 evidence-answer 的全部远程上下文都经过 ContextEgressGateway；
- consumer coverage matrix 没有未解释缺口；
- 数值 oracle、focused tests、browser evidence 和 host full gate 分开记录；
- provider-backed LLM benchmark 若未执行，仍标记 NOT VERIFIED；
- 没有通过静默 skip、xfail 或缩小 denominator 掩盖问题。

## 7. P1：数据消费层

P1 的目标不是再增加一个清洗函数，而是让真实用户和 Agent 能可靠地看、理解、修改、组合和复现数据。

### 7.1 P1-A：Data Profile 与变量语义

数据 profile 必须同时服务 UI、Agent、Notebook 和 Report。

需要支持：

- 数据集和节点列表；
- dataset/node/artifact identity；
- 行数、列数、schema revision；
- dtype、unique count、missing rate；
- variable label、value labels；
- measurement level；
- candidate role；
- user-defined missing value；
- group/entity/time/survey role；
- derived/recoded/lagged/reweighted provenance；
- sensitivity/PII marker；
- profile generation timestamp 和 source fingerprint。

profile 必须区分：

- observed fact；
- deterministic derived fact；
- heuristic advisory；
- user declaration；
- unavailable fact。

LLM 不能把 heuristic advisory 改写成 observed fact。

### 7.2 P1-B：直接数据 UI

当前数据操作 backend 已比直接 UI 更完整。P1 要把普通用户能够使用的消费面补齐：

- 数据集浏览和节点选择；
- 数据预览、列排序、分页和缺失显示；
- 变量管理器；
- 标签和测量级别编辑；
- 值标签查看与编辑；
- 类型转换预览；
- 缺失值策略预览；
- 行筛选预览；
- merge/append/reshape/subset 预览；
- dedupe、rename、aggregate、fill missing、lag、tsset；
- feature recipe、derived variable、recode；
- 过滤、权重、split-file、group-by 等声明；
- 统一 Operation Record、diff、child node 和 lineage；
- reload 后状态可恢复。

UI 不应拥有第二套 operation schema。表单、Agent proposal、Notebook option 和后端 validator 必须由同一份声明派生。

直接 UI 采用“通用 schema-driven operation panel + 少量 family-specific specialized view”：

- 通用 panel 负责字段、类型、required、preview、risk、confirmation 和 diff；
- specialized view 只改善复杂交互，不定义第二套语义；
- 新增普通 data operation 应自动获得可用的通用 UI；
- specialized view 缺失不能让 capability 在 UI 完全不可达；
- UI schema renderer 与 Agent/Notebook validator 必须有一致性元测试。

### 7.3 P1-C：安全的数据操作表达式

subset/filter 不允许直接执行任意 Python 或任意字符串表达式。使用封闭、可验证的 typed predicate AST：

~~~text
eq
ne
gt
ge
lt
le
in
not_in
between
is_missing
not_missing
~~~

每个 predicate 必须声明 column、operator、typed value 和 missing policy。

要求：

- 类型不兼容时阻断并说明如何转换；
- 日期、数值、字符串和分类值不能静默互转；
- in/not_in 的值集合必须显示；
- missing 不得隐式等同于空字符串或零；
- 过滤结果必须提供 row count before/after；
- 条件不能引用不存在的列；
- 用户确认前只生成 preview，不写 child node；
- 所有修改产生不可变 child dataset node。

### 7.4 P1-D：可组合数据操作

现有数据操作应通过通用 step contract 组合：

- merge：secondary dataset identity、keys、join cardinality、how、unmatched policy；
- append：schema compatibility、column alignment、source provenance；
- reshape：wide/long、id/time/index roles、duplicate cell policy；
- subset：typed predicate AST；
- feature recipe：输入、输出、参数和可重放 recipe；
- dedupe：key、保留策略、重复计数；
- rename：显式 old/new mapping；
- aggregate：group keys、aggregations、missing policy；
- fill missing：方法、窗口、group/time semantics；
- tsset/lag：entity/time order、gap policy、lag semantics；
- recode：源值、目标值、other/missing policy。

每个操作都必须声明 consumed inputs、produced outputs、row/column effects 和 replayability。

### 7.5 P1-E：数据互操作

目标包括：

- CSV、XLSX、Parquet 等通用格式的明确导入导出；
- SPSS .sav/.zsav；
- Stata .dta；
- 标签、值标签、缺失值、日期、权重和 metadata 的保真边界；
- 编码、类型和截断风险的 import preview；
- 可重放的 import manifest；
- 明确列出保留、转换、丢失或不支持的 metadata loss manifest；
- 可选依赖缺失时返回 typed optional_dependency blocked，而不是静默跳过。

格式兼容不能只验证“文件能打开”，还要验证 schema、标签、缺失值和抽样值的 round-trip。

### 7.6 P1-F：Agent/Notebook 数据消费

Agent 至少需要一个受服务器约束的项目数据发现工具，返回：

- 所有可见 dataset/node/artifact identity；
- 行列规模；
- 列名；
- 点名数据集后的 dtype、unique count、missing rate 和标签；
- 被截断的部分和计数；
- 权限、可用性和 provenance 状态。

Agent 不得通过猜测 artifact_id 或列名提出 merge、filter、reshape 或 model proposal。

Notebook 必须保存：

- 生成 proposal 时看到的数据上下文；
- 使用的 profile revision；
- plan 中的 source commitments；
- 用户确认前后的 option revision；
- 结果对应的 data fingerprint。

### 7.7 P1-G：Provider Context Egress 与隐私

Agent 的 server-side inspection tool 可以读取授权范围内的数据，但发送给外部 LLM provider 的内容必须经过 ContextEgressPolicy：

- 默认发送 schema、类型、统计摘要、结构化 evidence 和最小必要样本；
- 默认不发送完整原始行；
- sensitivity/PII 列默认不发送原值；
- 数据单元格、列名和值标签都按 untrusted content 编码，不能与 system instruction 混合；
- policy 记录 provider、允许字段、采样方式、row/token cap、redaction 和用户授权；
- local-only provider 和 remote provider 可以有不同 policy，但必须显式；
- provider 不可用或 policy 不允许时，Agent 使用 server-side tools 返回的 bounded evidence，或明确 blocked；
- trace 记录实际发送的 context manifest 和省略计数，不记录被策略禁止的原始秘密。

Agent 需要更多信息时，应调用受限 inspection tool 或向用户请求授权，不能通过扩大 prompt 上下文绕过 policy。

### 7.8 P1 数据层退出门槛

- 所有现有 data workflow steps 有直接 UI 或明确的只读/组合边界；
- UI、Agent、Notebook 使用同一 operation schema；
- 预览、确认、child node、diff、lineage、reload 全链路通过；
- 标签、缺失值和测量级别能够被 Agent 和 Report 正确消费；
- 通用 schema-driven UI 能渲染一个新注册的普通数据 operation，不需要新增专属分发；
- 过滤、merge、append、reshape 等危险语义有专门拒绝测试；
- 至少一组多数据集自然语言组合在浏览器中可见完成；
- 导入导出 round-trip 只在明确支持的格式上报告成功；
- 不支持格式、依赖和权限问题均能显式 blocked；
- import/export 的 metadata loss manifest 完整；
- remote provider context 遵守 egress、redaction 和 token/row budget；
- 不存在 arbitrary expression 或 silent coercion 路径。

## 8. P1：分类 ML 基础

分类 ML 的目标不是做一个“自动模型按钮”，而是建立可组合、可比较、可解释、无泄漏的 prediction capability foundation。

### 8.1 P1-ML-A：分类任务契约

分类任务必须明确：

- analysis mode 固定为 predictive；
- target column；
- binary 或 multiclass；
- class label mapping；
- feature columns；
- numeric/categorical preprocessing；
- sample weight；
- group/entity/time structure；
- missing policy；
- leakage exclusions；
- primary metric；
- decision threshold policy；
- optional DecisionPolicy ref；
- split strategy；
- random seed；
- resource budget。

target、feature、group、time 和 weight 必须来自服务器绑定的列 identity，不接受 LLM 只给字符串后由后端模糊匹配。

每个 feature 还必须进入 FeatureAvailabilityContract：

- feature observation time；
- feature available-at time；
- prediction origin；
- target event time；
- prediction horizon；
- 来源和生成 recipe；
- 是否在真实预测时可获得；
- 是否可能直接或间接包含 target。

AvailabilitySpec 未声明时，IID classification 可以显示未知边界；涉及 temporal、panel 或真实未来预测的请求必须 fail closed 或要求用户补充，不得把 unknown 当作“当前可用”。

### 8.2 P1-ML-B：安全切分与交叉验证

支持的 split strategy 至少包括：

- IID；
- stratified；
- group；
- temporal；
- panel/entity；
- user-declared holdout。

选择规则：

- time/entity 存在且影响泄漏时，不能默认 IID；
- preprocessing 必须只在训练 fold fit；
- test/holdout 不能参与调参；
- target encoding、imputation、scaling、feature selection 不能跨 fold 泄漏；
- resampling 只能在训练 fold 发生；
- temporal/panel 不满足安全 split profile 时 fail closed；
- temporal/panel contract 必须区分 known-entity future prediction 与 new-entity prediction，并声明允许的 entity overlap profile；
- 每行都必须满足机器可判定的 interval predicates：feature `available_at <= prediction_origin`，训练 label window 不与 validation/holdout label window 或其 purge window 相交；无法建立 label start/end、available-at、prediction origin 或 entity membership 时 fail closed；
- purge 由重叠 label/information windows 推导；embargo 只可由明确的 serial-dependence、policy 或业务冷却窗口声明。没有依据时不得自动发明 embargo，要求显式声明或保持 blocked；
- 嵌套角色固定为：inner train 用于 preprocessing/feature/hyperparameter fit；cross-fitted OOF 只用于 calibration 与 threshold；outer validation 只评估完整选择流程；final development refit 冻结 model/calibration/threshold/policy；sealed holdout 只允许一次最终评估；
- 每次评估保存 split manifest 和 row identity；
- seed 和 library/runtime version 必须进入 artifact。

StructureSpec 和 AvailabilitySpec 是 split compiler 的输入，不是 Agent prose。Agent 可以提出声明候选，但只有用户确认或服务器事实才能把 unknown 改成已知。

`HoldoutSealV1` 是 server-owned 状态机，至少绑定 data/split、feature recipe、candidate/search、calibration、threshold、DecisionPolicy、metric release plan 和 principal：

~~~text
sealed
  → all development hashes frozen
  → one authorized evaluation
  → declared metric bundle released
  → access ledger closed
~~~

重复评估、部分 metric 探测、subgroup/shift 探测和失败后的再次开封都进入访问账本和预算。Holdout subgroup/slice/shift 只有在 seal 前把 columns、bins/min support、statistics 和 multiplicity policy 纳入同一 metric-release bundle 时，才能随一次 authorized release 计算；未预声明请求返回 not_available，不能探索性开封。任何 feature/model/calibration/threshold/policy 修订都必须使用新的 holdout identity。隐藏 labels 但允许反复查看指标，不算 sealed holdout。

### 8.3 P1-ML-C：模型适配器

当前版本优先实现模型无关的 prediction contract，并用两个已有、服务器已准入且归纳偏置不同的基础引擎证明它：

- Logistic classification adapter；
- 当前 Random Forest prediction capability 的 classification adapter。

这两个适配器足以验证线性概率边界与非线性树集成的统一 fit、predict、score、artifact、explainability 和 evidence contract。Decision Tree、boosting、神经网络、深度学习和更复杂的 AutoML 不作为本版本 Gate 2 的完成条件；它们在 foundation 通过后以独立 capability pack 接入。

如果现有 estimator 不能诚实满足 prediction contract，必须修 adapter 或明确 blocked，不能为了复用而把 inference result 直接冒充 prediction evidence。

sample weight 必须贯穿 split、fit、preprocessing、resampling、metric、calibration、baseline、comparison 和 evidence。每个 stage/adapter 显式声明 `supports_weight`；不支持时 blocked，不得接收后静默忽略。Evidence 同时记录 row count、weight sum、weighted/unweighted denominator、effective sample size 和 metric weighting definition。

### 8.4 P1-ML-D：指标与评估

分类结果至少支持：

- confusion matrix；
- accuracy；
- balanced accuracy；
- precision；
- recall；
- F1；
- ROC AUC；
- PR AUC；
- log loss；
- Brier score；
- calibration curve；
- threshold-dependent metrics；
- per-class metrics；
- support/count；
- missing/filtered row accounting。

结果必须同时显示 metric 定义、positive class、threshold、averaging policy 和 split scope。

不能只给一个 accuracy，也不能在类别不平衡时把 accuracy 自动写成“模型表现良好”。

每个模型还必须和以下基线或负对照比较：

- majority/prevalence baseline；
- server-declared simple baseline；
- 适用时、保持合法 exchangeability structure 的 shuffled-target negative control；temporal/panel 只能按声明的 entity/time block 或其他合法 unit 打乱，禁止全局随机打乱；
- 适用时的 temporal-order negative control。

fold distribution、bootstrap interval 或明确的单一 holdout 边界必须随 aggregate metric 一起报告。不能把 CV folds 当作独立总体样本夸大显著性。随机 estimator/preprocessing 还必须运行 bounded multi-seed sensitivity，报告性能、校准和 explanation 的变动范围，不能挑选有利 seed。

预测分数与真实行动必须分离。需要推荐阈值或行动时，DecisionPolicy 至少声明：

- false-positive/false-negative 成本或效用；
- capacity、预算或最大处理量约束；
- 是否允许 abstain/manual review；
- threshold 的选择数据、方法和版本；
- 适用人群、时间范围和失效条件。

如果这些事实未知，Workbench 可以展示 threshold curve 和情景分析，但不能由 Agent 猜测成本后推荐“最佳阈值”。阈值只能在 training/validation 内选择；最终 holdout 只评估冻结后的模型与 DecisionPolicy，不得反向调节。

### 8.5 P1-ML-E：模型比较与调参

模型比较必须：

- 使用同一 data snapshot 和同一 split manifest；
- 保存候选模型列表；
- 显示 metric 差异和不确定性；
- 保存同一 split 上的 paired prediction/difference refs；IID、group、temporal/panel 分别声明合法的 row、group/entity 或 time-block resampling unit；无法给出合法区间时只报告 descriptive distribution；
- 说明是否使用 cross-validation、bootstrap 或单一 holdout；
- 对多模型、多指标比较给出 multiple-comparison 或 exploratory warning；
- 让用户选择 primary metric；
- 不由 Agent 静默选“冠军模型”；
- 将最终模型和比较过程分开持久化。

ranking 是 evidence projection，不是自动决策。最终选择必须来自用户确认或预先声明、可审阅的 selection policy；policy、tie、insufficient_evidence 和 Pareto trade-off 均进入 artifact。

超参数搜索必须：

- 有 server-side budget；
- 只使用训练/validation 数据；
- 不读取 test/holdout；
- 可取消；
- 可恢复；
- 保存 search space、seed、trial status 和失败原因；
- 资源超限时返回 partial/blocked，不继续无界运行。

### 8.6 P1-ML-F：解释性与稳定性

需要区分：

- predictive explanation；
- feature association；
- causal interpretation。

默认不得把 feature importance 写成因果影响。

解释性至少支持：

- permutation importance 或模型原生 importance；
- 预测概率和局部预测说明；
- 重要性在多个 resample/fold 上的稳定性；
- feature direction/scale caveat；
- subgroup performance；
- train/validation/holdout distribution-shift diagnostics；
- explanation availability reason。

SHAP 或其他可选依赖可以作为 adapter，但依赖缺失必须 typed blocked。解释图必须有 numeric source 和 sample scope。

### 8.7 P1-ML-G：类别不平衡和重采样

SMOTE、oversample、undersample 只能作为 prediction-data step：

- 需要离散 target；
- 需要显式 feature columns；
- 只在训练 fold 执行；
- 必须记录生成/删除行数；
- 不得作为 OLS、DID、IV、survey inference 的输入而不经专门声明；
- 在结果中标记 class weights/resampling policy；
- Agent 必须解释重采样改变的是预测目标或训练分布，不是原始样本的因果证据。

### 8.8 P1-ML-H：分类 Agent 能力

自然语言请求：

~~~text
请比较适合这个不平衡二分类任务的模型，按 PR AUC 和校准表现排序，
不要使用时间之后的数据训练，并解释最稳定的特征。
~~~

Agent 应生成：

- 任务识别；
- target/class mapping；
- temporal split；
- imbalance policy；
- candidate models；
- primary/secondary metrics；
- comparison plan；
- explanation plan；
- 用户确认点；
- resource estimate。

Agent 不得直接执行，也不得把“排序第一”写成“真实世界最优”。

若用户要求部署阈值或行动建议，Agent 必须先追问成本、容量和人工复核边界；缺失时只提供可审阅的情景，不生成自动决策 policy。

### 8.9 P1-ML 退出门槛

- 所有模型都遵守统一 PredictionModelContract；
- IID、group、temporal 三类 split 至少各有真实防泄漏测试；
- 预处理、调参和重采样没有跨 fold 泄漏；
- test/holdout 未进入搜索；
- classification metrics、threshold、class mapping 和 support 可追溯；
- FeatureAvailabilityContract、prediction horizon 和 StructureSpec 可追溯；
- 至少两种模型可以在同一 split manifest 下比较；
- 模型表现同时对照 baseline/negative control；
- explanation 明确区分预测解释和因果解释；
- ranking 与最终选择分离；
- prediction score、threshold 和 DecisionPolicy 分离，holdout 不参与阈值选择；
- 不平衡数据有专门的安全和报告路径；
- Agent/Notebook/Report/UI 能读取同一个 classification evidence envelope；
- 浏览器路径证明用户能审阅 proposal、确认、查看结果和比较；
- provider-backed planner 如未执行，仍显示 NOT VERIFIED。

## 9. P2：在基础层稳定后的模型族扩展

P2 不允许重新设计基础协议。每个新 family 必须复用 P0/P1 的 capability、workflow、result、evidence、consumer 和 safety contracts。

每个 P2 family 还必须：

- 提供 Capability Descriptor 以进入两阶段 discovery；
- 声明 AnalysisMode 和 PortType；
- 通过现有 AgentPlan compiler；
- 进入 CapabilityManifest 和 consumer coverage matrix；
- 不增加 family-specific planner prompt 或 workflow control structure；
- 不修改通用 compiler 才能让单个 family 工作，除非发现的是可被至少一类能力复用的真实类型缺口。

### 9.1 P2-A：复杂抽样的估计量扩展

当前 survey variance engine 已有，但 estimator 接入有限。后续扩展：

- Ordinal/Multinomial；
- Cox；
- Quantile；
- IV；
- Panel FE；
- DID；
- Mixed/GLM 等适用族。

每个 estimator 必须声明：

- 可组合的 survey design；
- Taylor/replicate variance 适配；
- degrees of freedom；
- weight/stratum/PSU 语义；
- single PSU policy；
- unsupported design combinations。

时间序列 + survey design 的概念边界继续保持 fail closed，不为追求菜单对齐而强行组合。

### 9.2 P2-B：多层与相关数据

扩展：

- GEE；
- GLMM；
- 更完整的 repeated measures；
- correlated random effects；
- dynamic panel；
- panel VAR；
- panel unit-root/cointegration。

所有模型必须明确：

- cluster/group identity；
- random effect structure；
- correlation structure；
- convergence；
- singular fit；
- small cluster warning；
- marginal vs conditional estimand。

### 9.3 P2-C：有限因变量与生存扩展

扩展：

- Tobit；
- censored/truncated models；
- sample selection；
- AFT；
- competing risks；
- multi-event survival。

Cox、AFT、competing risks 不能共用一个“survival result”扁平结构；各自的 risk set、estimand、censoring、time scale 和 diagnostics 必须声明。

### 9.4 P2-D：SEM、CFA 与潜变量

扩展：

- CFA；
- SEM；
- GSEM；
- latent growth；
- MIMIC；
- indirect/direct/total effects；
- multi-group/invariance；
- FIML；
- fit indices；
- modification indices；
- survey-aware SEM；
- IRT/finite mixture 的 future packs。

SEM 结果必须支持 measurement model、structural model、identification、convergence、fit、modification 和 effect interpretation 的分层证据，不能套用普通回归 coefficient card。

### 9.5 P2-E：高级因果与计量

扩展：

- RDD；
- Dynamic Panel；
- System GMM；
- 更多 nonlinear/system/GMM；
- Bayesian models；
- spatial regression；
- heterogeneous treatment effect/CATE。

每个 family 必须声明 identification assumptions、estimand、support、bandwidth/lag/moment policy、weak identification 和 sensitivity diagnostics。

### 9.6 P2-F：时间序列深化

已有 ARIMA/SARIMA、VAR/VECM、ETS、ARMA/GARCH 等能力，后续重点不是简单增加命令，而是：

- state-space/Kalman；
- richer ARMAX/ARCH variants；
- rolling forecast；
- expanding-window evaluation；
- forecast interval coverage；
- multivariate forecast comparison；
- model residual diagnostics；
- forecast artifact and deployment boundary；
- time-series-aware Agent planning。

时序 feature 不能绕过 availability/provenance；列级 lookahead 无法证明安全时必须保留 warning 或 block。

### 9.7 P2 共同退出门槛

新增 family 只有同时具备以下内容才算接入：

- capability declaration；
- typed input/output contract；
- deterministic executor；
- independent oracle 或明确验证等级；
- result/evidence projection；
- Agent/Notebook reachability；
- UI/Report consumer；
- unsupported conditions；
- convergence and resource guard；
- browser path；
- mutation and adversarial tests；
- release evidence。

只实现一个 Python 函数、只通过一个 fixture 或只出现在 registry 中，不算 family 完成。

## 10. P3：工作流生态与长尾对标

P3 是在核心研究工作流稳定后，处理“用户能否把 SPSS/Stata 替换掉”的生态问题。

P1 负责数据文件和 metadata 的互操作；P3 负责命令、workflow、报告、插件和扩展生态，二者不得重复维护格式语义。

### 10.1 P3-A：命令和脚本生态

目标：

- 把自然语言 plan 持久化为可读 syntax；
- 提供 Workbench-native script representation；
- 支持从既有 syntax/do-file 解析为 typed draft；
- 每条脚本语句绑定 capability、input、output 和 evidence；
- 脚本执行仍经过同一 confirmation、resource、security 和 lineage；
- 不把任意外部代码执行伪装成受支持的统计能力。

传统语法兼容应采用 parser/adapter pack，输出 DraftAgentPlan，再通过同一个 server compiler 生成 CompiledWorkflow。parser 不能绕过 server-owned contracts，也不能把无法翻译的语句静默丢掉。

### 10.2 P3-B：Custom Tables 与出版级报告

目标：

- 多模型、多 subgroup、多 outcome 的可配置表；
- 标题、脚注、标签、显著性规则和小数位；
- table cell 的 numeric fact source；
- assumptions、warning、sample accounting；
- HTML、DOCX、LaTeX、PDF/print 等 export；
- report revision、引用节点和可重现生成；
- Agent 可根据研究问题提出表格方案，但不得改写数字。

### 10.3 P3-C：第三方能力与插件

插件必须声明：

- package identity/version；
- license；
- input/output contract；
- resource and network policy；
- reproducibility；
- oracle/validation level；
- supported consumers；
- failure and optional dependency behavior；
- security review status。

未知包不能由 Agent 自动下载执行。依赖缺失显示 optional_dependency blocked。

### 10.4 P3-D：长尾统计能力

长尾模型按用户价值、统计可信度和可复用 adapter 排序，不按菜单数量排序。任何新增长尾能力都必须进入同一 registry 和 evidence matrix，不能建一个“legacy commands”旁路。

### 10.5 P3-E：Agent Research Sandbox 与能力晋升

长期来看，Agent 可以帮助实现或适配新的统计算法，这是 AI-native 超越传统软件的重要方向；但 research mode 与 product mode 必须分离。

Research Sandbox 要求：

- 在隔离的 research branch/workspace 中运行；
- 不得自动修改 main、正式 registry 或发布状态；
- 不得自动安装未批准依赖或开放网络；
- 保存代码、依赖、seed、环境和输入 fingerprint；
- 生成独立 DGP、known-answer、oracle、invariant、adversarial 和 regression evidence；
- 结果标记 experimental/unverified；
- 由人类审核并显式批准 promotion；
- promotion 后仍需标准 CapabilityManifest、PortType、consumer、browser 和 release gates。

Agent 可以生成候选 adapter、测试和验证计划，但不能批准自己的算法、证明自己的正确性或自行发布。

## 11. 统一自然语言覆盖目标

最终目标是“自然语言可调用 Workbench 全部已准入能力”，但“可调用”必须拆成五种状态：

| 状态 | 含义 |
|---|---|
| Direct | 有独立顶层 proposal operation |
| Composable | 可作为 operation.multi_step 或其他 typed plan 的步骤 |
| Read-only | 可被 Agent 解释、诊断或比较，但不产生 mutation |
| Closed | 因安全或产品政策不进入自然语言执行面，并有稳定理由 |
| Runtime blocked | 能力本身可达，但当前数据、权限、依赖、证据或资源不满足 |

每个 capability 必须至少落在一个声明路径上；同一能力可以同时具备 direct 和 composition 路径，但所有关闭项必须有明确理由。

“自然语言调用全部能力”的完成定义是：

- 所有 executable/admitted capability 至少有 direct 或 composition path；
- 所有 read-only capability 有 typed inspection/evidence path；
- 所有 closed capability 能被 Agent 准确解释关闭原因，但不能被执行；
- runtime blocked 不算 reachability gap，前提是 reason、remediation 和所缺 evidence 可见；
- 任一路径都必须经过 Descriptor discovery、full contract retrieval 和 server compiler。

### 11.1 Natural-language acceptance

每个 capability 的自然语言验收至少包含：

- 一个正常目标请求；
- 一个缺字段请求；
- 一个模糊请求；
- 一个数据不适用请求；
- 一个错误 operation/options 请求；
- 一个危险或越权请求；
- 一个 provider error；
- 一个 prompt injection 或恶意数据值；
- 一个组合请求；
- 一个恢复/重跑请求。

prompt 集至少包含：

- 中文和英文；
- 同义改写；
- 长目标描述与短命令；
- 先说目标后补约束；
- 用户纠正 Agent 的多轮请求；
- capability 名称未直接出现的意图请求。

验收必须同时验证：

- capability discovery；
- typed proposal；
- server canonicalization；
- preflight；
- confirmation；
- runtime；
- result/evidence；
- lineage；
- Agent/Notebook/Report/UI consumer；
- refusal or blocked reason。

deterministic evaluator 和真实 provider benchmark 分开记录。

### 11.2 Agent 规划质量

未来 provider-backed benchmark 至少测量：

- capability selection；
- descriptor retrieval recall/precision；
- full-contract retrieval correctness；
- column/role binding；
- data source identity；
- plan ordering；
- assumption handling；
- unsupported refusal；
- evidence citation；
- multi-step composition；
- correction after user feedback；
- prompt injection resistance；
- hallucinated identity rate；
- unsafe mutation rate；
- unsupported success rate。

还必须测量：

- compiler rejection precision；
- clarification quality；
- plan revision correctness；
- token/context budget；
- 中英文和未见 paraphrase 的性能差异；
- capability 数量增长后的 discovery degradation。

不能只用“是否调用了正确 operation”一个指标。

## 12. 安全与准确性模型

### 12.1 Threat model

必须考虑：

- 数据单元格中的 prompt injection；
- 恶意列名和恶意标签；
- 恶意或损坏的导入文件；
- provider 返回的未知字段或危险 proposal；
- provider 尝试伪造 CompiledWorkflow、server identity 或 confirmation；
- 可选依赖和第三方包；
- 资源耗尽；
- 越权读取项目数据；
- 跨 notebook/run 的 identity confusion；
- 自动 retry 导致重复 mutation；
- 把预测解释误写成因果结论；
- 时间序列 lookahead；
- 抽样设计和权重误用；
- 小样本、非收敛、支持不足和多重比较。

### 12.2 安全控制

- data content 一律视为不可信输入；
- context compiler 对数据内容和指令分层；
- provider 输出一律视为不可信 DraftAgentPlan；
- runtime 只接受服务器持久化、重新校验并绑定有效 confirmation 的 CompilationRecord；
- capability、operation、column、artifact identity 由服务器绑定；
- remote provider context 受 ContextEgressPolicy、redaction 和最小必要原则约束；
- mutation 必须 confirmation；
- 高风险操作需要 risk authorization；
- arbitrary shell、network 和自然语言 code execution 保持关闭；
- 运行有 timeout、step limit、row/memory/CPU budget；
- mutation operation 不自动 retry；
- 只有分类为安全且幂等的读操作才允许受控 retry；
- 权限和 project scope 每一步验证；
- 结果和 trace append-only；
- 用户确认时显示 PlanDiff、数据影响、analysis mode、风险、成本和输出；
- optional dependency 不静默降级；
- 所有 block/error 显示具体 capability 和 reason。

### 12.3 统计准确性控制

- 不用 LLM 计算数值；
- AnalysisIntent 和 AnalysisMode 防止 predictive、inferential、causal 语义混用；
- 使用独立 oracle；
- 记录模型、数据、选项、seed 和 runtime version；
- 对默认类别顺序、base category、缺失值、权重、测量级别等高风险默认值发出 advisory 或要求显式声明；
- 外部结果与 Workbench 结果不一致时保留差异，不静默“修正”；
- approximate inference 以结构化字段标记；
- estimand、target、positive class、time horizon 和 primary metric 的重要变更需要重新确认；
- 不把 warning 自动转换成 success；
- 不把用户未确认的建议写入执行状态。

### 13.2 P0/P1 测试分层

测试分为 feature-owned TDD 与独立 Evaluation 两类。Feature lane 负责自己的 red/green、focused regression 和 mutation anchor；Independent Evaluation 在不同 worktree 中负责 canonical fixtures、known-truth、fault injection、holdout intents、跨 consumer 一致性和 evidence manifest，不能修改产品实现、feature expected values、golden 或容差。

Planner evaluation 必须区分两层：仓库可见的 public adversarial/regression corpus，以及 feature worker 不可读取 expected intents/answers 的 evaluator-only sealed corpus；sealed corpus 只向 release train 暴露 digest、case count、score 和 bounded failure refs。Descriptor/aliases 自动生成的 cases 只证明 plumbing，不能称 holdout。

数值 oracle 必须区分 same-library regression、known answer、independent implementation 和 reference software，不能统称 independent oracle。分类 foundation 的最低 oracle matrix 为：metric arrays 和 calibration/threshold 使用手算 known-answer；Logistic coefficient/probability 使用独立实现或 reference software；RF 使用 same-library regression + deterministic replay + metamorphic invariants，不冒充闭式或独立数值复现；split/leakage 使用独立 interval/information-set checker。

- host full gate；
- release notes 和 handoff 的证据分层。

Lane-local gate 默认只运行 focused/impacted suites、contract fixtures、mutation、scope-owner 和 formal verification；每个 wave 合流后运行跨契约和受影响 regression；`bash scripts/gate.sh --full` 只在最终不可变 release-candidate SHA 上作为发布闸门运行。最终 full gate 后任何产品、contract、registry、fixture、test、golden 或 gate 变化都会使该证据失效并要求在新 SHA 重跑。

P2/P3 在本版本只完成设计契约和边界，不作为 Gate 4 的模型数量指标。

## 15. 后续实现计划的模块边界

本主 spec 后续拆成 Contract-first Release Train，而不是一个巨大死流程或六个争写共享文件的 feature branch：

1. Contract Lock：公共 refs/schemas、provider loader、canonical fixtures 和 compatibility tests；
2. P0 Workflow Truth Core：post-estimation、branch、resume、idempotency 和 package-local provider；
3. P0 Evidence Core：Evidence contracts/registry/projection kernel，不接线共享 consumer；
4. P0 Agent Compiler Core：Manifest、Descriptor、Plan IR、PortType、Failure、CompilationRecord 和 shadow compiler；
5. P1 Data Consumer Core：profile、metadata、typed operations、formats、egress 和 package-local provider/UI；
6. P1 Classification ML Core：split/CV、metrics、comparison、explainability、persistence 和 package-local provider/renderer；
7. Consumer Projection Core：Results、Agent、Notebook、Report、UI 的 bounded evidence adapters 与 path-level coverage；
8. Agent/Notebook Cutover：共享 registry/runtime/Notebook/Report/UI mount 的单一-owner 接线；
9. Independent Evaluation Harness + E1/E2/E3 Runs：先冻结 harness，再对 C1/C2/C3 exact SHA 生成 sidecar evidence/admission；
10. Foundation Integration：merge queue、evidence invalidation、browser、final full gate 和 handoff；
11. P2/P3 各自独立的 capability pack 和 ecosystem plans。

每个 plan 必须：

- 在开始前通过 scripts/devline_control.py start 创建正式 development line；
- 提供准确 baseline、affected paths、tests 和 known gates；
- 先写 red test，再实现；
- 使用 live registry，不猜 capability/operation id；
- 不修改其他并行线未授权的文件；
- `affected/allowed` 使用精确文件或单-owner package，不能以 `backend/workbench`、`tests` 或 `frontend/src` 作为并行许可根；
- 每个 wave 从同一 Contract/Wave Lock 建独立 worktree；feature lane 不从其他 feature branch pull/rebase；
- 共享文件只由 cutover/integration work order 指定的单一 owner 修改；机械冲突与行为冲突分开，行为冲突必须退回 owner；
- Evaluation 和 Integration 使用不同 devline、worktree、owned paths 和 evidence records；
- 通过 formal event stream 及时记录每个 material FAILURE、ERROR、GAP、WASTE、REVIEW、GATE 和 STATE_CHANGE；
- 在完成前重新验证 Git、测试、浏览器和 release boundary。

## 16. 明确非目标

本 spec 不承诺：

- v1.8.9 立即覆盖 SPSS/Stata 全部长尾命令；
- 让 Agent 自主运行任意 Python、shell 或网络代码；
- 让 Agent 静默决定模型、数据清洗或报告数字；
- 让 provider 输出直接成为可执行 workflow；
- 把现有 CapabilityContract 扩成同时承担所有职责的超级对象；
- 把全部完整 capability schema 无差别塞进每次 prompt；
- 用一个万能 result schema 抹平所有 family 的统计差异；
- 通过 AutoML 或深度学习替代统计诊断；
- 用增加 Decision Tree、boosting 或神经网络数量代替分类 ML foundation；
- 用远程 witness 或真人身份证明代替统计和产品验收；
- 用 deterministic planner evaluator 声称真实 LLM 已验证；
- 用固定 preset 代替通用可组合 workflow；
- 为了支持一个 fixture 而新增特殊分支。

## 17. Definition of Done

当且仅当以下条件同时满足，才可以说本版本达到了本 spec 的基础目标：

1. 非 OLS post-estimation 不再产生 OLS 语义泄漏；
2. 失败后 resume 能恢复真实 branch 和 artifact identity；
3. 所有当前能力都有明确的 result/evidence/consumer 状态；
4. 数据能被用户和 Agent 发现、理解、预览、组合和复现；
5. 数据操作没有 arbitrary expression、silent coercion 或 silent fallback；
6. 分类 ML 没有 train/test/fold leakage；
7. 分类模型可以公平比较、校准、解释和重现，预测分数与行动决策保持隔离；
8. Agent、Notebook、Report、UI 使用共同的 server-owned contracts；
9. provider 只能生成 DraftAgentPlan；runtime 只接受服务器持久化、重新校验并绑定有效 confirmation 的 CompilationRecord；
10. PortType 能阻止 analysis mode、数据结构和 availability 不兼容的组合；
11. 所有 executable/admitted 能力都有 direct 或 composition path，read-only/closed 能力有诚实路径；
12. capability discovery 在中英文和 holdout paraphrase 上有独立证据；
13. 被关闭、阻断、依赖缺失或证据不足的能力都明确说明原因；
14. remote provider context 遵守 egress 和敏感数据边界；
15. P0/P1 通过数值、运行时、消费者、浏览器和安全验收；
16. P2/P3 没有被伪装成当前版本已交付；
17. 所有完成声明都保留证据等级和已知限制。
18. 所有已实现能力通过 provider/registry 自动进入 path-level Manifest、自然语言 discovery 和 consumer coverage；注入第三个 fixture provider 不需要修改 compiler、Notebook planner 或通用 UI 才能被发现和安全拒绝/接纳。
19. 最终 release evidence 指向同一不可变 candidate SHA；Evaluation、browser、formal、provider、full gate 和 release 状态不互相替代。

这份 spec 的核心判断是：Workbench 的竞争力不在于先拥有更多模型按钮，而在于把“统计能力、数据流、证据、Agent 规划和用户确认”组合成一个可信的可编程系统。模型族扩展必须建立在这套基础之上。
