# Workbench v1.8.9 — AI-native SPSS/Stata parity foundation

> 状态：设计方向已获用户确认，等待本文件最终评审
> 日期：2026-08-15
> 基线：当前 main 的 live registry 与 v1.8.8 final integration evidence
> 本文件性质：产品与架构主 spec，不是实现代码，也不替代 formal development line

## 0. 摘要与版本决策

Workbench 不以“复制 SPSS/Stata 的菜单和命令数量”为最终目标，而是以：

1. 具备统计工具的可信正确性；
2. 具备 SPSS/Stata 的核心数据消费和统计能力；
3. 在 Agent 能发挥优势的地方超过传统 GUI；
4. 让每个能力都能通过自然语言被发现、组合、确认、执行和解释；
5. 让新增第 N+1 个能力不需要修改一堆固定流程；

作为 v1.8.9 及后续版本的共同基础。

本版本的硬范围是：

- P0：工作流统计正确性、分支恢复、fail-closed、结果证据契约；
- P1：数据消费层、数据元数据和直接 UI；
- P1：分类 ML 的完整基础，包括严格数据切分、交叉验证、模型比较、校准和解释性；
- P0/P1 的 Agent、Notebook、Report、UI 统一接线和验收。

P2/P3 写入本 spec，目的是锁定未来的模块边界、接入契约和优先级；本版本不以继续堆模型族数量为完成条件。除非 P0/P1 的退出门槛全部通过，不得通过增加模型数量掩盖基础层未完成。

### 1.3 当前必须优先修复的正确性风险

在继续增加能力前，当前树已有两类必须写入 P0 的问题：

1. 非 OLS post-estimation 可能进入 OLS 风格 refit/inference 路径，并产生不属于该模型语义的 F 统计和 p 值。相关路径位于 backend/workbench/agent/workflow_runtime.py 的 _refit_completed_ols_branch 及其持久化逻辑。
2. WorkflowStepState 未完整持久化 model branches。首次执行某个模型后中断，再恢复依赖该模型的步骤时，恢复过程可能无法重新绑定已完成的模型分支。

这两类问题不是“以后再优化”的技术债，而是能够使报告正常生成却表达错误统计语义的 P0 缺陷。任何“模型数量增加”都不能排在它们之前。

### 1.4 证据声明规则

所有未来状态报告必须区分以下证据：

| 证据层 | 能证明什么 | 不能证明什么 |
|---|---|---|
| Registry/contract | 能力已声明、字段和入口存在 | 数值正确、真实 LLM 会规划 |
| Deterministic evaluator | typed proposal、拒绝和边界行为稳定 | provider-backed LLM 质量 |
| Numerical oracle | 数值与独立实现或参考软件一致 | Agent/UI 已接线 |
| Runtime/persistence | 运行、artifact、lineage、resume 正确 | 浏览器用户路径 |
| Browser acceptance | 用户可见页面可操作 | 外部真人身份或真实 LLM 泛化 |
| Provider benchmark | 指定 provider 的规划质量 | 所有 provider 的质量 |
| Security/adversarial | 对注入、越权、危险输入的防护 | 统计方法本身正确 |

禁止把其中一种证据写成另一种证据。

## 2. 对标范围与产品定位

SPSS 官方能力目录覆盖数据准备、回归、Custom Tables、决策树、预测、神经网络、复杂抽样、缺失值、精确检验等。Stata 官方能力目录把数据管理、面板/纵向数据、多层模型、复杂抽样、SEM 和时间序列作为成熟的一等能力。

对标参考：

- IBM SPSS Statistics Features：<https://www.ibm.com/products/spss-statistics/features>
- Stata Features：<https://www.stata.com/features/>
- Stata Panel/Longitudinal Data：<https://www.stata.com/features/panel-longitudinal-data/>
- Stata Survey Features：<https://www.stata.com/features/overview/survey-features/>
- Stata SEM：<https://www.stata.com/features/overview/structural-equation-modeling/>
- Stata Time Series：<https://www.stata.com/features/time-series/>

Workbench 的定位不是立即复刻全部长尾命令，而是：

- 首先达到研究员日常使用所需的数据、结果和可信度；
- 用 Agent 把“发现问题、提出方案、组合步骤、解释证据”做得比传统菜单更好；
- 用 typed contracts 和 lineage 保证这种超越不会变成静默自动化；
- 把长尾模型接入成本压缩到“实现能力 + 注册契约 + 外部验证 + 消费者适配”。

## 3. 北极星与不可违反的原则

### 3.1 AI-native 优先，但不让 LLM 成为统计真相源

Agent 可以超过 SPSS/Stata 的地方：

- 自动发现数据形状、测量级别、缺失、时间结构、潜在泄漏和 merge 风险；
- 根据目标、约束和数据证据提出多个可比较方案；
- 把数据准备、诊断、建模、稳健性分析、可视化和报告串成一个 typed DAG；
- 对不同模型族做同一数据切分下的比较；
- 在假设冲突时主动解释“为什么不能直接运行”；
- 提出有限、可审阅的 robustness branch；
- 从多个 run 的真实 artifact 中生成带证据引用的回答；
- 把用户的自然语言目标编译为可复现、可重跑、可比较的方案。

Agent 不得：

- 静默选择或更换统计估计量；
- 静默修改原始数据或丢弃行列；
- 自行发明 run、node、artifact、column 或 capability identity；
- 将自然语言解释当作数值结果；
- 在证据不足时用猜测填充结果；
- 通过提示词绕过 confirmation、权限、资源限制或安全策略。

### 3.2 正确性优先于自动化

任何结果必须能够回答：

- 使用了什么数据版本；
- 使用了哪些列和角色；
- 使用了什么 estimator、假设和选项；
- 哪些结果是精确计算，哪些是近似、描述性或不可用；
- 哪些诊断通过、失败或未检查；
- 哪些外部依赖和 oracle 验证存在；
- 结果是否可以被 Agent、Notebook、Report 和 UI 共同读取。

无法回答时，系统必须返回显式的 unavailable、degraded、blocked 或 failed 状态。

### 3.3 组合优先于固定流程

Workbench 不实现“一个自然语言意图对应一个硬编码流程”。能力应当通过：

- typed input/output ports；
- 数据和模型 artifact binding；
- 可验证的前置条件；
- 可持久化的 DAG；
- 可组合的 result/evidence projection；
- 声明派生的 Agent vocabulary；

自由组合。

固定的推荐流程可以作为 preset，但 preset 只是一个可审阅的 plan builder，不能成为唯一执行路径。

### 3.4 不过拟合实现与评测

禁止：

- 针对某个 fixture、某个 prompt 或某个列名写特殊分支；
- 用 capability 数量硬编码验收；
- 用固定 prompt 通过来代表自然语言能力；
- 用 xfail、静默 skip 或缩小 denominator 掩盖能力缺口；
- 让单一数据集决定通用数据契约。

必须使用：

- declaration-derived inventory；
- 通用 contract tests；
- 多种数据形状；
- holdout prompt；
- 正常、模糊、缺字段、错误、危险、provider error 和 prompt injection 场景；
- mutation testing 验证每条守卫真的会阻断目标错误；
- 独立数值 oracle；
- 不同 family 的最小兼容 fixture。

## 4. 总体架构

### 4.1 分层

目标架构分为七层：

1. Data Identity Layer：数据集、节点、artifact、列、标签、测量级别和 provenance；
2. Capability Layer：能力契约、版本、输入角色、前置条件、结果和证据声明；
3. Workflow Layer：可组合 DAG、来源承诺、bindings、分支、恢复和幂等性；
4. Execution Layer：确定性数值引擎、资源控制、依赖控制和运行状态；
5. Evidence Layer：结果、诊断、图表、警告、假设、oracle 和 provenance；
6. Consumer Layer：Agent、Notebook、UI、Report 共同消费的 projection；
7. Provider/Interaction Layer：LLM provider、用户确认、浏览器交互和安全审计。

上层不能通过字符串猜测下层语义。每层通过版本化 typed contract 连接。

### 4.2 CapabilityContract 目标

每个能力最终都必须能够声明以下信息。字段名以当前 live registry 为准，若实现时需要改名，必须同步更新所有消费者和契约测试，不能保留两套事实源。

~~~json
{
  "capability_id": "family.operation",
  "semantic_version": "v1",
  "kind": "model|test|data_operation|prediction|pack|selector",
  "family": "declared_family",
  "input_roles": [],
  "preconditions": [],
  "proposal_contract": {
    "schema": {},
    "example_prompts": [],
    "ui_description": ""
  },
  "step_contract": {
    "consumes": [],
    "produces": [],
    "bindings": [],
    "replayable": true
  },
  "execution_adapter": "registry_owned_adapter",
  "result_contract": {
    "shape": "family_specific",
    "status_values": []
  },
  "evidence_contract": {
    "required_facts": [],
    "diagnostics": [],
    "figures": [],
    "warnings": []
  },
  "consumer_projections": {
    "agent": {},
    "notebook": {},
    "ui": {},
    "report": {}
  },
  "safety_policy": {},
  "dependency_policy": {},
  "oracle_policy": {},
  "natural_language_surface": {
    "direct": false,
    "composable": true,
    "exemption_reason": null
  }
}
~~~

契约的目标不是把所有算法细节塞进一个大 JSON，而是声明跨层边界。family-specific 的估计量、诊断和图表放在自己的命名空间，不强迫非回归方法伪造 coefficient、CI 或 marginal effect。

### 4.3 Workflow DAG

Workflow 必须以数据流和 artifact binding 为核心，而不是以 operation 名称列表为核心。

每个 step 至少包含：

- step identity；
- capability identity 和 semantic version；
- input bindings；
- literal source 或 upstream output source commitment；
- typed options；
- preconditions；
- expected outputs；
- risk level；
- confirmation policy；
- replay/idempotency policy；
- result/evidence binding。

数据源允许两种形式：

~~~text
literal source:
  run_id + node_ref + artifact_id + context_fingerprint

upstream source commitment:
  from_step + output_port
~~~

链式 step 在规划时校验 DAG、output port 和类型；在上游执行完成后注入真实的 run/node/artifact identity，再为下游计算 preview fingerprint。不能为了支持组合而放弃 stale 检查。

未来允许 sequence、parallel、bounded branch 和 diagnostic-gated branch，但每种控制结构都必须：

- 有明确的最大步数、最大分支数和资源预算；
- 由服务器验证；
- 将每个分支写入 lineage；
- 对用户显示采用了什么条件；
- 不能由 LLM 自己修改安全策略。

### 4.4 数据 Artifact 与元数据

原始数据不可变。任何清洗、转换、标签或类型改变都产生有 provenance 的子节点。

数据身份至少区分：

- dataset identity；
- graph node identity；
- artifact identity；
- schema revision；
- metadata revision；
- source fingerprint；
- row/column shape；
- availability/provenance status。

列元数据包含：

- name；
- dtype；
- semantic/measurement level；
- variable label；
- value labels；
- missing-value policy；
- role candidates；
- unique count；
- missing rate；
- time/entity/group/survey role；
- privacy or sensitivity marker。

元数据缺失不能静默推断成确定事实。推断只能作为 advisory，需在 proposal 和 result 中标记来源与置信边界。

### 4.5 Result/Evidence Envelope

所有能力都返回共同外壳和 family-specific payload：

~~~json
{
  "result_identity": {},
  "status": "completed|partial|not_available|blocked|failed",
  "truth_level": "exact|approximate|descriptive|not_applicable",
  "method": {},
  "estimand": {},
  "input_provenance": {},
  "assumptions": [],
  "diagnostics": [],
  "numeric_facts": [],
  "family_evidence": {},
  "figures": [],
  "warnings": [],
  "dependencies": [],
  "oracle": {},
  "availability": {},
  "lineage_refs": []
}
~~~

规则：

- exact 结果必须来自确定性引擎，而不是 LLM；
- approximate 结果必须说明近似方法；
- not_applicable 不是缺失字段；
- not_available 必须给出原因；
- blocked 必须说明哪条前置条件或安全策略阻断；
- warning 必须是结构化事实，不由 LLM 根据数字临时编造；
- family-specific payload 可以扩展，但不能覆盖共同字段的语义；
- 图表必须引用真实 numeric source，不能只保存图片；
- Report、Agent、Notebook 和 UI 只能消费这个 envelope 或其声明适配器，不能各自重新解析裸 artifact。

### 4.6 Consumer Adapter

每个 capability 必须提供或明确继承：

- Agent summary adapter；
- Notebook result adapter；
- UI result/detail adapter；
- Report evidence adapter；
- error/warning adapter；
- figure adapter。

适配器只负责投影，不负责重新估计或改变统计语义。

若某个消费者暂时不能展示某类结果，应返回带 capability_id 和 reason 的 unavailable，而不是吞掉结果、显示空卡片或把 family-specific 结果伪装成通用回归表。

### 4.7 Agent 与 Notebook 适配

Agent 和 Notebook 使用同一份 server-owned vocabulary，但可以有不同的交互入口：

- Agent：面向当前 graph/head 的 proposal 和多步计划；
- Notebook：面向 analysis contract、options、run family 和可复用叙事；
- UI：面向编辑、预览、确认、查看和对比；
- Report：面向事实、图表、引用和导出。

自然语言编译链：

~~~text
user intent
  → bounded context compiler
  → capability discovery
  → plan candidates
  → typed proposal
  → server canonicalization
  → preflight and risk classification
  → user confirmation
  → execution
  → evidence projection
  → grounded answer
~~~

LLM 输出只能提供 intent、候选方案、理由和用户可读说明。artifact identity、列 identity、能力 identity、选项合法性、风险和执行结果必须由服务器绑定或验证。

### 4.8 扩展方式

新增 capability 的最小接入单元：

1. 实现确定性能力；
2. 实现或复用 CapabilityContract；
3. 声明输入/输出 ports 和前置条件；
4. 注册执行 adapter；
5. 注册 result/evidence projection；
6. 提供独立 oracle 或明确验证等级；
7. 自动进入 Agent/Notebook vocabulary；
8. 通过通用 registry、runtime、consumer 和 gate。

新增能力不允许：

- 在 orchestrator 增加一个专属流程分支作为默认方式；
- 在 Agent prompt 中加入只对该能力生效的隐藏规则；
- 在 UI 中用 capability registry 之外的第二份清单；
- 静默忽略不支持的输入或输出。

## 5. AI-native 超越 SPSS/Stata 的目标能力

### 5.1 Agent 主动发现而不是等待菜单选择

用户可以说：

~~~text
请评估这份数据是否适合做面板 DID，并给出可执行的分析方案。
~~~

Agent 应该：

1. 发现数据集和节点；
2. 检查 entity/time/treatment/outcome 的候选列；
3. 报告缺失、重复、时间排序、处理组支持和可能的泄漏；
4. 给出一个或多个 typed plan；
5. 明确哪些信息需要用户确认；
6. 只在用户确认后运行。

这比传统菜单强，但最终判断必须可追溯，不能因为“Agent 感觉可以”就放行。

### 5.2 假设冲突驱动的方案分支

诊断可以提出分支，但不能静默修改方案：

- 时间序列不平稳：提示差分、滞后阶或模型族候选；
- EFA KMO/Bartlett 不满足：拒绝直接解释因子，提出数据或目标调整；
- merge 出现多对多：阻断并请求用户决定；
- 分类数据严重不平衡：提出 class weight 或预测专用重采样；
- 面板/时序预测缺安全 split：阻断 generic prediction；
- 多重比较风险：提示校正或确认探索性定位。

每个分支都必须写入 plan、理由、输入证据和用户选择。

### 5.3 Evidence-grounded analyst

Agent 的回答必须引用：

- result identity；
- artifact/node；
- 数据 fingerprint；
- method/options；
- numeric fact；
- diagnostic/warning；
- availability reason。

LLM 只能对已存在的 evidence 做解释、比较和提问，不得创造不存在的 coefficient、p-value、图表或“模型已成功”的结论。

### 5.4 组合能力像编程，但受 typed contract 约束

用户可以自然语言表达：

~~~text
先按地区合并两份数据，去掉收入缺失的样本，构造滞后变量，
比较固定效应和随机效应模型，再把诊断和稳健性比较写进报告。
~~~

系统应编译成可审阅 DAG，而不是调用一个固定 preset。每一步可独立检查、重跑、替换、分支和比较。

## 6. P0：正确性、运行真相和统一结果证据

P0 是本版本不可延期的基础层。

### 6.1 P0-A：family-aware post-estimation

要求：

- post-estimation 必须由上游模型 family 的 contract 决定；
- 非 OLS 模型不得进入 OLS refit；
- 某个诊断或检验不适用于当前 family 时，返回 typed blocked/not_available；
- 适用于 Logit/Probit/Poisson/Panel/IV/Survival/ML 的统计量必须使用各自语义；
- 禁止用 model_id 字符串猜测模型类型；
- 禁止硬编码 model_artifact_id；
- 结果 envelope 必须保存上游 family、estimator、covariance 和数据 fingerprint；
- 任何 family fallback 必须是声明的 compatibility adapter，而不是异常后的隐式降级。

验证：

- 用 Logit、Poisson、Panel、IV、Cox 等真实已完成模型分别触发 post-estimation；
- 对每个不兼容组合验证阻断原因；
- 对兼容组合用独立 oracle 或解析关系验证数值；
- 通过 mutation 将 family 路由改为 OLS，测试必须真实变红；
- 不能只断言流程 completed，必须断言统计量语义和 family identity。

### 6.2 P0-B：branch/resume truth

要求：

- WorkflowStepState 持久化所有完成模型分支、output ports、artifact identity、family identity 和 evidence refs；
- resume 重新加载后必须能解析依赖链；
- 同一 execution key 重试不能产生重复 child node 或重复业务效果；
- 上游完成、下游失败后恢复，只重做必要的下游步骤；
- source commitment 解析失败时返回结构化错误；
- 分支之间的输入不能被后续步骤静默覆盖；
- 恢复过程不得通过重新读取当前 active head 猜测历史输入；
- 任何旧 state 缺少必要字段都必须迁移或 fail closed，不能填默认值后继续执行。

验证：

- 首次完成模型、故意让后续步骤失败、进程重启、恢复并完成；
- 在恢复前改变 active head，确认恢复仍使用原始 branch binding；
- 注入重复 confirm、超时重试、部分写入和 crash-after-persist 场景；
- 检查最终 lineage 只有预期节点和 operation records；
- 对缺失 branch 的旧 state 验证明确 blocked/migration-required。

### 6.3 P0-C：统一 Result/Evidence contract

要求：

- 所有已注册能力必须拥有 result shape 和 evidence shape；
- 通用字段从 capability declaration 派生；
- family-specific 结果使用 namespaced payload；
- 结果必须区分 exact、approximate、descriptive、not applicable；
- diagnostics、figures、warnings 和 assumptions 都必须可结构化读取；
- 每个 numeric fact 必须有来源、单位、估计对象和可选 oracle；
- 图表必须有 numeric source；
- 不适用字段不能用空字符串冒充；
- 不可用结果不能被渲染为“成功但没有内容”；
- approximate inference 必须保留方法标签；
- 小样本、非收敛、支持不足、前提失败和外部依赖缺失必须是结构化状态。

### 6.4 P0-D：Agent/Notebook/Report/UI 投影

要求：

- Agent summary 只能从 evidence projection 生成；
- Notebook option 必须绑定自己的 result/evidence contract；
- Report 只能引用真实 packet 中存在的 fact 和 figure；
- UI 可以按 family 展示不同卡片，但卡片字段来自声明；
- 新增 family 时如果没有某个 consumer projection，必须在 registry 中显式暴露；
- consumer 不得通过“字段缺席”推断零值或通过 capability name 生成 summary；
- projection validation 必须针对选定 option 的 artifact contract，而不是整个 run 的所有 artifact。

### 6.5 P0-E：Reachability 与自然语言契约

要求：

- live capability inventory 只能从声明派生；
- direct exposure、composition exposure 和 explicit exemption 分开；
- code.execute 等安全关闭项必须保留理由；
- model.genesis 作为 workflow carrier 的组合路径必须明确；
- 每个可达 capability 至少有一个 direct 或 composition path；
- 每个 path 必须有实际消费者，不得只在 registry 写字符串；
- Agent、Notebook 和 operation.multi_step 使用同一份 workflow vocabulary；
- natural_language_enabled=false 的能力不能被描述成独立顶层入口；
- 新增能力必须触发 inventory、schema、consumer 和 reachability 元测试。

### 6.6 P0 退出门槛

P0 只有在以下全部成立时完成：

- 非 OLS post-estimation 不再发生 OLS 语义泄漏；
- branch/resume 的 red-to-green 测试通过；
- 所有持久化 artifact identity 和 lineage binding 可恢复；
- 每个当前 capability 的 result/evidence projection 有明确状态；
- Agent、Notebook、Report、UI 的 projection contract 通过；
- 所有安全关闭项有显式理由；
- 数值 oracle、focused tests、browser evidence 和 host full gate 分开记录；
- provider-backed LLM benchmark 若未执行，仍标记 NOT VERIFIED；
- 没有通过静默 skip、xfail 或缩小 denominator 掩盖问题。

## 7. P1：数据消费层

P1 的目标不是再增加一个清洗函数，而是让真实用户和 Agent 能可靠地看、理解、修改、组合和复现数据。

### 7.1 P1-A：Data Profile 与变量语义

数据 profile 必须同时服务 UI、Agent、Notebook 和 Report。

需要支持：

- 数据集和节点列表；
- dataset/node/artifact identity；
- 行数、列数、schema revision；
- dtype、unique count、missing rate；
- variable label、value labels；
- measurement level；
- candidate role；
- user-defined missing value；
- group/entity/time/survey role；
- derived/recoded/lagged/reweighted provenance；
- sensitivity/PII marker；
- profile generation timestamp 和 source fingerprint。

profile 必须区分：

- observed fact；
- deterministic derived fact；
- heuristic advisory；
- user declaration；
- unavailable fact。

LLM 不能把 heuristic advisory 改写成 observed fact。

### 7.2 P1-B：直接数据 UI

当前数据操作 backend 已比直接 UI 更完整。P1 要把普通用户能够使用的消费面补齐：

- 数据集浏览和节点选择；
- 数据预览、列排序、分页和缺失显示；
- 变量管理器；
- 标签和测量级别编辑；
- 值标签查看与编辑；
- 类型转换预览；
- 缺失值策略预览；
- 行筛选预览；
- merge/append/reshape/subset 预览；
- dedupe、rename、aggregate、fill missing、lag、tsset；
- feature recipe、derived variable、recode；
- 过滤、权重、split-file、group-by 等声明；
- 统一 Operation Record、diff、child node 和 lineage；
- reload 后状态可恢复。

UI 不应拥有第二套 operation schema。表单、Agent proposal、Notebook option 和后端 validator 必须由同一份声明派生。

### 7.3 P1-C：安全的数据操作表达式

subset/filter 不允许直接执行任意 Python 或任意字符串表达式。使用封闭、可验证的 typed predicate AST：

~~~text
eq
ne
gt
ge
lt
le
in
not_in
between
is_missing
not_missing
~~~

每个 predicate 必须声明 column、operator、typed value 和 missing policy。

要求：

- 类型不兼容时阻断并说明如何转换；
- 日期、数值、字符串和分类值不能静默互转；
- in/not_in 的值集合必须显示；
- missing 不得隐式等同于空字符串或零；
- 过滤结果必须提供 row count before/after；
- 条件不能引用不存在的列；
- 用户确认前只生成 preview，不写 child node；
- 所有修改产生不可变 child dataset node。

### 7.4 P1-D：可组合数据操作

现有数据操作应通过通用 step contract 组合：

- merge：secondary dataset identity、keys、join cardinality、how、unmatched policy；
- append：schema compatibility、column alignment、source provenance；
- reshape：wide/long、id/time/index roles、duplicate cell policy；
- subset：typed predicate AST；
- feature recipe：输入、输出、参数和可重放 recipe；
- dedupe：key、保留策略、重复计数；
- rename：显式 old/new mapping；
- aggregate：group keys、aggregations、missing policy；
- fill missing：方法、窗口、group/time semantics；
- tsset/lag：entity/time order、gap policy、lag semantics；
- recode：源值、目标值、other/missing policy。

每个操作都必须声明 consumed inputs、produced outputs、row/column effects 和 replayability。

### 7.5 P1-E：数据互操作

目标包括：

- CSV、XLSX、Parquet 等通用格式的明确导入导出；
- SPSS .sav/.zsav；
- Stata .dta；
- 标签、值标签、缺失值、日期、权重和 metadata 的保真边界；
- 编码、类型和截断风险的 import preview；
- 可重放的 import manifest；
- 可选依赖缺失时返回 typed optional_dependency blocked，而不是静默跳过。

格式兼容不能只验证“文件能打开”，还要验证 schema、标签、缺失值和抽样值的 round-trip。

### 7.6 P1-F：Agent/Notebook 数据消费

Agent 至少需要一个受服务器约束的项目数据发现工具，返回：

- 所有可见 dataset/node/artifact identity；
- 行列规模；
- 列名；
- 点名数据集后的 dtype、unique count、missing rate 和标签；
- 被截断的部分和计数；
- 权限、可用性和 provenance 状态。

Agent 不得通过猜测 artifact_id 或列名提出 merge、filter、reshape 或 model proposal。

Notebook 必须保存：

- 生成 proposal 时看到的数据上下文；
- 使用的 profile revision；
- plan 中的 source commitments；
- 用户确认前后的 option revision；
- 结果对应的 data fingerprint。

### 7.7 P1 数据层退出门槛

- 所有现有 data workflow steps 有直接 UI 或明确的只读/组合边界；
- UI、Agent、Notebook 使用同一 operation schema；
- 预览、确认、child node、diff、lineage、reload 全链路通过；
- 标签、缺失值和测量级别能够被 Agent 和 Report 正确消费；
- 过滤、merge、append、reshape 等危险语义有专门拒绝测试；
- 至少一组多数据集自然语言组合在浏览器中可见完成；
- 导入导出 round-trip 只在明确支持的格式上报告成功；
- 不支持格式、依赖和权限问题均能显式 blocked；
- 不存在 arbitrary expression 或 silent coercion 路径。

## 8. P1：分类 ML 基础

分类 ML 的目标不是做一个“自动模型按钮”，而是建立可组合、可比较、可解释、无泄漏的 prediction capability foundation。

### 8.1 P1-ML-A：分类任务契约

分类任务必须明确：

- target column；
- binary 或 multiclass；
- class label mapping；
- feature columns；
- numeric/categorical preprocessing；
- sample weight；
- group/entity/time structure；
- missing policy；
- leakage exclusions；
- primary metric；
- decision threshold policy；
- split strategy；
- random seed；
- resource budget。

target、feature、group、time 和 weight 必须来自服务器绑定的列 identity，不接受 LLM 只给字符串后由后端模糊匹配。

### 8.2 P1-ML-B：安全切分与交叉验证

支持的 split strategy 至少包括：

- IID；
- stratified；
- group；
- temporal；
- panel/entity；
- user-declared holdout。

选择规则：

- time/entity 存在且影响泄漏时，不能默认 IID；
- preprocessing 必须只在训练 fold fit；
- test/holdout 不能参与调参；
- target encoding、imputation、scaling、feature selection 不能跨 fold 泄漏；
- resampling 只能在训练 fold 发生；
- temporal/panel 不满足安全 split profile 时 fail closed；
- 每次评估保存 split manifest 和 row identity；
- seed 和 library/runtime version 必须进入 artifact。

### 8.3 P1-ML-C：模型适配器

当前版本优先实现模型无关的 prediction contract，并接入可验证的基础模型：

- Logistic classification；
- Random Forest classification；
- Decision Tree classification；
- 一个服务器允许的 boosting/tree ensemble adapter。

模型数量不是验收核心。每个模型都必须实现同一套 fit、predict、score、artifact、explainability 和 evidence contract。神经网络、深度学习和更复杂的 AutoML 不作为本版本完成条件，未来作为独立 pack 接入。

### 8.4 P1-ML-D：指标与评估

分类结果至少支持：

- confusion matrix；
- accuracy；
- balanced accuracy；
- precision；
- recall；
- F1；
- ROC AUC；
- PR AUC；
- log loss；
- Brier score；
- calibration curve；
- threshold-dependent metrics；
- per-class metrics；
- support/count；
- missing/filtered row accounting。

结果必须同时显示 metric 定义、positive class、threshold、averaging policy 和 split scope。

不能只给一个 accuracy，也不能在类别不平衡时把 accuracy 自动写成“模型表现良好”。

### 8.5 P1-ML-E：模型比较与调参

模型比较必须：

- 使用同一 data snapshot 和同一 split manifest；
- 保存候选模型列表；
- 显示 metric 差异和不确定性；
- 说明是否使用 cross-validation、bootstrap 或单一 holdout；
- 对多模型、多指标比较给出 multiple-comparison 或 exploratory warning；
- 让用户选择 primary metric；
- 不由 Agent 静默选“冠军模型”；
- 将最终模型和比较过程分开持久化。

超参数搜索必须：

- 有 server-side budget；
- 只使用训练/validation 数据；
- 不读取 test/holdout；
- 可取消；
- 可恢复；
- 保存 search space、seed、trial status 和失败原因；
- 资源超限时返回 partial/blocked，不继续无界运行。

### 8.6 P1-ML-F：解释性与稳定性

需要区分：

- predictive explanation；
- feature association；
- causal interpretation。

默认不得把 feature importance 写成因果影响。

解释性至少支持：

- permutation importance 或模型原生 importance；
- 预测概率和局部预测说明；
- 重要性在多个 resample/fold 上的稳定性；
- feature direction/scale caveat；
- subgroup performance；
- explanation availability reason。

SHAP 或其他可选依赖可以作为 adapter，但依赖缺失必须 typed blocked。解释图必须有 numeric source 和 sample scope。

### 8.7 P1-ML-G：类别不平衡和重采样

SMOTE、oversample、undersample 只能作为 prediction-data step：

- 需要离散 target；
- 需要显式 feature columns；
- 只在训练 fold 执行；
- 必须记录生成/删除行数；
- 不得作为 OLS、DID、IV、survey inference 的输入而不经专门声明；
- 在结果中标记 class weights/resampling policy；
- Agent 必须解释重采样改变的是预测目标或训练分布，不是原始样本的因果证据。

### 8.8 P1-ML-H：分类 Agent 能力

自然语言请求：

~~~text
请比较适合这个不平衡二分类任务的模型，按 PR AUC 和校准表现排序，
不要使用时间之后的数据训练，并解释最稳定的特征。
~~~

Agent 应生成：

- 任务识别；
- target/class mapping；
- temporal split；
- imbalance policy；
- candidate models；
- primary/secondary metrics；
- comparison plan；
- explanation plan；
- 用户确认点；
- resource estimate。

Agent 不得直接执行，也不得把“排序第一”写成“真实世界最优”。

### 8.9 P1-ML 退出门槛

- 所有模型都遵守统一 PredictionModelContract；
- IID、group、temporal 三类 split 至少各有真实防泄漏测试；
- 预处理、调参和重采样没有跨 fold 泄漏；
- test/holdout 未进入搜索；
- classification metrics、threshold、class mapping 和 support 可追溯；
- 至少两种模型可以在同一 split manifest 下比较；
- explanation 明确区分预测解释和因果解释；
- 不平衡数据有专门的安全和报告路径；
- Agent/Notebook/Report/UI 能读取同一个 classification evidence envelope；
- 浏览器路径证明用户能审阅 proposal、确认、查看结果和比较；
- provider-backed planner 如未执行，仍显示 NOT VERIFIED。

## 9. P2：在基础层稳定后的模型族扩展

P2 不允许重新设计基础协议。每个新 family 必须复用 P0/P1 的 capability、workflow、result、evidence、consumer 和 safety contracts。

### 9.1 P2-A：复杂抽样的估计量扩展

当前 survey variance engine 已有，但 estimator 接入有限。后续扩展：

- Ordinal/Multinomial；
- Cox；
- Quantile；
- IV；
- Panel FE；
- DID；
- Mixed/GLM 等适用族。

每个 estimator 必须声明：

- 可组合的 survey design；
- Taylor/replicate variance 适配；
- degrees of freedom；
- weight/stratum/PSU 语义；
- single PSU policy；
- unsupported design combinations。

时间序列 + survey design 的概念边界继续保持 fail closed，不为追求菜单对齐而强行组合。

### 9.2 P2-B：多层与相关数据

扩展：

- GEE；
- GLMM；
- 更完整的 repeated measures；
- correlated random effects；
- dynamic panel；
- panel VAR；
- panel unit-root/cointegration。

所有模型必须明确：

- cluster/group identity；
- random effect structure；
- correlation structure；
- convergence；
- singular fit；
- small cluster warning；
- marginal vs conditional estimand。

### 9.3 P2-C：有限因变量与生存扩展

扩展：

- Tobit；
- censored/truncated models；
- sample selection；
- AFT；
- competing risks；
- multi-event survival。

Cox、AFT、competing risks 不能共用一个“survival result”扁平结构；各自的 risk set、estimand、censoring、time scale 和 diagnostics 必须声明。

### 9.4 P2-D：SEM、CFA 与潜变量

扩展：

- CFA；
- SEM；
- GSEM；
- latent growth；
- MIMIC；
- indirect/direct/total effects；
- multi-group/invariance；
- FIML；
- fit indices；
- modification indices；
- survey-aware SEM；
- IRT/finite mixture 的 future packs。

SEM 结果必须支持 measurement model、structural model、identification、convergence、fit、modification 和 effect interpretation 的分层证据，不能套用普通回归 coefficient card。

### 9.5 P2-E：高级因果与计量

扩展：

- RDD；
- Dynamic Panel；
- System GMM；
- 更多 nonlinear/system/GMM；
- Bayesian models；
- spatial regression；
- heterogeneous treatment effect/CATE。

每个 family 必须声明 identification assumptions、estimand、support、bandwidth/lag/moment policy、weak identification 和 sensitivity diagnostics。

### 9.6 P2-F：时间序列深化

已有 ARIMA/SARIMA、VAR/VECM、ETS、ARMA/GARCH 等能力，后续重点不是简单增加命令，而是：

- state-space/Kalman；
- richer ARMAX/ARCH variants；
- rolling forecast；
- expanding-window evaluation；
- forecast interval coverage；
- multivariate forecast comparison；
- model residual diagnostics；
- forecast artifact and deployment boundary；
- time-series-aware Agent planning。

时序 feature 不能绕过 availability/provenance；列级 lookahead 无法证明安全时必须保留 warning 或 block。

### 9.7 P2 共同退出门槛

新增 family 只有同时具备以下内容才算接入：

- capability declaration；
- typed input/output contract；
- deterministic executor；
- independent oracle 或明确验证等级；
- result/evidence projection；
- Agent/Notebook reachability；
- UI/Report consumer；
- unsupported conditions；
- convergence and resource guard；
- browser path；
- mutation and adversarial tests；
- release evidence。

只实现一个 Python 函数、只通过一个 fixture 或只出现在 registry 中，不算 family 完成。

## 10. P3：生态、互操作与长尾对标

P3 是在核心研究工作流稳定后，处理“用户能否把 SPSS/Stata 替换掉”的生态问题。

### 10.1 P3-A：命令和脚本生态

目标：

- 把自然语言 plan 持久化为可读 syntax；
- 提供 Workbench-native script representation；
- 支持从既有 syntax/do-file 解析为 typed draft；
- 每条脚本语句绑定 capability、input、output 和 evidence；
- 脚本执行仍经过同一 confirmation、resource、security 和 lineage；
- 不把任意外部代码执行伪装成受支持的统计能力。

传统语法兼容应采用 parser/adapter pack，不能让 parser 绕过 server-owned contracts。

### 10.2 P3-B：Custom Tables 与出版级报告

目标：

- 多模型、多 subgroup、多 outcome 的可配置表；
- 标题、脚注、标签、显著性规则和小数位；
- table cell 的 numeric fact source；
- assumptions、warning、sample accounting；
- HTML、DOCX、LaTeX、PDF/print 等 export；
- report revision、引用节点和可重现生成；
- Agent 可根据研究问题提出表格方案，但不得改写数字。

### 10.3 P3-C：第三方能力与插件

插件必须声明：

- package identity/version；
- license；
- input/output contract；
- resource and network policy；
- reproducibility；
- oracle/validation level；
- supported consumers；
- failure and optional dependency behavior；
- security review status。

未知包不能由 Agent 自动下载执行。依赖缺失显示 optional_dependency blocked。

### 10.4 P3-D：长尾统计能力

长尾模型按用户价值、统计可信度和可复用 adapter 排序，不按菜单数量排序。任何新增长尾能力都必须进入同一 registry 和 evidence matrix，不能建一个“legacy commands”旁路。

## 11. 统一自然语言覆盖目标

最终目标是“自然语言可调用 Workbench 全部已准入能力”，但“可调用”必须拆成四种状态：

| 状态 | 含义 |
|---|---|
| Direct | 有独立顶层 proposal operation |
| Composable | 可作为 operation.multi_step 或其他 typed plan 的步骤 |
| Read-only | 可被 Agent 解释、诊断或比较，但不产生 mutation |
| Closed/Blocked | 有明确安全、依赖、数据或产品理由不可调用 |

每个 capability 必须至少落在一个声明路径上；同一能力可以同时具备 direct 和 composition 路径，但所有关闭项必须有明确理由。

### 11.1 Natural-language acceptance

每个 capability 的自然语言验收至少包含：

- 一个正常目标请求；
- 一个缺字段请求；
- 一个模糊请求；
- 一个数据不适用请求；
- 一个错误 operation/options 请求；
- 一个危险或越权请求；
- 一个 provider error；
- 一个 prompt injection 或恶意数据值；
- 一个组合请求；
- 一个恢复/重跑请求。

验收必须同时验证：

- capability discovery；
- typed proposal；
- server canonicalization；
- preflight；
- confirmation；
- runtime；
- result/evidence；
- lineage；
- Agent/Notebook/Report/UI consumer；
- refusal or blocked reason。

deterministic evaluator 和真实 provider benchmark 分开记录。

### 11.2 Agent 规划质量

未来 provider-backed benchmark 至少测量：

- capability selection；
- column/role binding；
- data source identity；
- plan ordering；
- assumption handling；
- unsupported refusal；
- evidence citation；
- multi-step composition；
- correction after user feedback；
- prompt injection resistance；
- hallucinated identity rate；
- unsafe mutation rate；
- unsupported success rate。

不能只用“是否调用了正确 operation”一个指标。

## 12. 安全与准确性模型

### 12.1 Threat model

必须考虑：

- 数据单元格中的 prompt injection；
- 恶意列名和恶意标签；
- 恶意或损坏的导入文件；
- provider 返回的未知字段或危险 proposal；
- 可选依赖和第三方包；
- 资源耗尽；
- 越权读取项目数据；
- 跨 notebook/run 的 identity confusion；
- 自动 retry 导致重复 mutation；
- 把预测解释误写成因果结论；
- 时间序列 lookahead；
- 抽样设计和权重误用；
- 小样本、非收敛、支持不足和多重比较。

### 12.2 安全控制

- data content 一律视为不可信输入；
- context compiler 对数据内容和指令分层；
- capability、operation、column、artifact identity 由服务器绑定；
- mutation 必须 confirmation；
- 高风险操作需要 risk authorization；
- arbitrary shell、network 和自然语言 code execution 保持关闭；
- 运行有 timeout、step limit、row/memory/CPU budget；
- mutation operation 不自动 retry；
- 只有分类为安全且幂等的读操作才允许受控 retry；
- 权限和 project scope 每一步验证；
- 结果和 trace append-only；
- optional dependency 不静默降级；
- 所有 block/error 显示具体 capability 和 reason。

### 12.3 统计准确性控制

- 不用 LLM 计算数值；
- 使用独立 oracle；
- 记录模型、数据、选项、seed 和 runtime version；
- 对默认类别顺序、base category、缺失值、权重、测量级别等高风险默认值发出 advisory 或要求显式声明；
- 外部结果与 Workbench 结果不一致时保留差异，不静默“修正”；
- approximate inference 以结构化字段标记；
- 不把 warning 自动转换成 success；
- 不把用户未确认的建议写入执行状态。

### 13.3 变异验活

每条重要守卫必须至少有一个行为变异：

## 15. 后续实现计划的模块边界

本主 spec 后续应拆成独立 implementation plans，而不是写成一个巨大的死流程：

1. P0 Workflow Truth：post-estimation、branch、resume、idempotency；
2. P0 Evidence Projection：Result/Evidence envelope、consumer adapters；
3. P1 Data Consumer：profile、metadata、UI、typed data operations、formats；
4. P1 Classification ML：prediction contract、split/CV、comparison、explainability；
5. P0/P1 Integration QA：Agent、Notebook、Report、browser、provider、full gate；
6. P2/P3 各自独立的 capability pack 和 ecosystem plans。

每个 plan 必须：

- 在开始前通过 scripts/devline_control.py start 创建正式 development line；
- 提供准确 baseline、affected paths、tests 和 known gates；
- 先写 red test，再实现；
- 使用 live registry，不猜 capability/operation id；
- 不修改其他并行线未授权的文件；
- 通过 formal event stream 记录 FAILURE、GAP、REVIEW、GATE 和 STATE_CHANGE；
- 在完成前重新验证 Git、测试、浏览器和 release boundary。

## 16. 明确非目标

本 spec 不承诺：

- v1.8.9 立即覆盖 SPSS/Stata 全部长尾命令；
- 让 Agent 自主运行任意 Python、shell 或网络代码；
- 让 Agent 静默决定模型、数据清洗或报告数字；
- 用一个万能 result schema 抹平所有 family 的统计差异；
- 通过 AutoML 或深度学习替代统计诊断；
- 用远程 witness 或真人身份证明代替统计和产品验收；
- 用 deterministic planner evaluator 声称真实 LLM 已验证；
- 用固定 preset 代替通用可组合 workflow；
- 为了支持一个 fixture 而新增特殊分支。

## 17. Definition of Done

当且仅当以下条件同时满足，才可以说本版本达到了本 spec 的基础目标：

1. 非 OLS post-estimation 不再产生 OLS 语义泄漏；
2. 失败后 resume 能恢复真实 branch 和 artifact identity；
3. 所有当前能力都有明确的 result/evidence/consumer 状态；
4. 数据能被用户和 Agent 发现、理解、预览、组合和复现；
5. 数据操作没有 arbitrary expression、silent coercion 或 silent fallback；
6. 分类 ML 没有 train/test/fold leakage；
7. 分类模型可以公平比较、校准、解释和重现；
8. Agent、Notebook、Report、UI 使用共同的 server-owned contracts；
9. 自然语言可以调用所有已准入能力的 direct 或 composition path；
10. 被关闭、阻断、依赖缺失或证据不足的能力都明确说明原因；
11. P0/P1 通过数值、运行时、消费者、浏览器和安全验收；
12. P2/P3 没有被伪装成当前版本已交付；
13. 所有完成声明都保留证据等级和已知限制。

这份 spec 的核心判断是：Workbench 的竞争力不在于先拥有更多模型按钮，而在于把“统计能力、数据流、证据、Agent 规划和用户确认”组合成一个可信的可编程系统。模型族扩展必须建立在这套基础之上。
