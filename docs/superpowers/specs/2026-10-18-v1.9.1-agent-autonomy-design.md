> 依据：objective `objectives/2026-10-17-v1.9.1-objective.md`（已批准）；M0 证据 `evaluations/2026-10-17-v1.9.1-m0-baseline.md`；
> v1.9.0 Agent 上下文设计 `specs/2026-10-14-v1.9.0-agent-context-design.md`；研究规划设计 `specs/2026-09-30-...` §5、§7。

## 1. 问题与参照

M0 失败分类里最重的三条（F1–F3）是同一个根因：**执行不是 Agent 回合的一部分**。
- 提案落盘后回合结束，确认走另一条 HTTP 路径执行；
- 执行结果只作为一条系统消息留在会话里，没有人去唤醒模型；
- 下一次用户说话时，模型看到的是"有人确认了"，而不是"你的工具调用返回了这个结果"。

Codex 和 Claude Code 的做法一致：
- 执行就是工具调用；
- 需要批准时，工具调用在原地**挂起**，等人的决定；
- 决定之后，工具返回结果（或"被拒绝"），模型在同一个回合里接着推进。

审批是工具执行的一个阶段，不是回合的终点。本设计把 Workbench 改成这个形状，并保留现有的全部安全机制：
- 确认即执行闸门（设计 §8.2）；
- risk authorization；
- 只读预算；
- 外发管控；
- 数字核对。

## 2. 回合运行时（M1-2、M1-4）

### 2.1 回合是后台任务

- 首批接线先保留同步响应：registry 强引用持有独立后台 task；同步 HTTP 请求只 `shield` 等待原结果。激活/退出 Core 仍由原 runner 所有，reservation 只由后台 task 的 finally 释放；请求等待者取消不能提早释放或允许同会话重入。后台异常必须被观察，仍在等待的调用者收到原异常。此项只保证同进程任务生命周期，不宣称页面恢复、通知、持久回合或重启恢复。
- 回合在服务进程内作为后台任务运行，异步请求返回稳定的 `turn_id`。保留现有同步响应合同；现有客户端保持等待语义，迁移后的客户端显式选择异步启动，不能用必须包含 `assistant` 的旧响应类型返回任务收据。
- 2026-10-18 核查：现有 `GET /agent/sessions/{id}/events` 是 JSON replay，前端仅在本地提交期间轮询，尚无 SSE。后台任务的状态与事件读取必须在页面重开后由服务器状态恢复，不能依赖本地 `isSubmitting`。传输层迁移不得丢失事件序号及 replay 能力。
- 回合状态持久化为会话里的 `turn_state` 记录：`running | awaiting_approval | interrupted | completed | failed`，以及当前计划、预算用量、挂起的审批请求 id。
  - 进程内只保留可以重建的东西（模型流、abort 事件）。

### 2.2 恢复

- 服务启动时扫描各会话最新的 `turn_state`：
  - `awaiting_approval`：原样保留，审批到来时继续。不需要进程内状态，因为挂起点就是一个已落盘的工具调用。
  - `running`：标为 `interrupted`，在下一次事件订阅或显式 `resume` 时，从最后一条落盘消息重新发起模型调用。
- 已执行的操作有幂等键（现有 operation record），不会因重放而重复执行。
- 本地 Chain/head 执行锁的存活期现在由持锁 FD 的 acquire→release 覆盖。JSON 的 300 秒期限只在内核锁已空闲时用于原有恢复规则；期限到达不能让仍在运行的线程/进程被另一个操作取代。取消 drain 与域提交也处在该锁内。这不证明进程重启后的工具结果核对或分布式互斥。
- 此项是待证明的验收条件，不能仅凭已有幂等键宣称实现：恢复前必须将未完成 `tool_call_id` 与原操作记录及执行键核对；副作用完成但工具结果尚未落盘的窗口必须单独测试。禁止重新提交原始 question 作为恢复。
- 后台运行：关掉窗口不影响回合；完成或需要批准时，经 `notifications` 事件发系统通知（前端用 Notification API，权限由用户授予）。

### 2.3 预算

- 每轮 10 步的上限改为**计划预算**：Auto 模式下由计划声明（步数、墙钟、推断次数）。
- Ask 模式下每次用户输入给一个回合预算，默认 40 步、30 分钟，可在设置里改。
- 防循环保护保留（重复相同工具调用的限制、只读推断预算 `SESSION_INFERENTIAL_BUDGET`）。

### 2.4 持久化与所有权约束（2026-10-18 实地核查）

- 普通新命令创建预算；显式 `resume` 恢复原 turn/command ID、累计步数和墙钟用量，不能重新提交 question 获得新预算。生产 turn/continue 已接 compact TurnStore 与私有 session checkpoint；steer/follow-up、取消意图及精确工具回执持久化。进程中断期间也计入原墙钟预算。
- 文件锁、版本 CAS 与 lease fencing 共同防止同一回合被两个工作进程执行；过期所有者不得提交新状态。发现未完成执行只标记 interrupted，先 reconcile，再决定可恢复路径。
- 2026-10-18 核查时 app 生命周期没有项目根枚举及恢复 worker；后续实现见 §2.5。持久化层测试通过不等于后台运行、恢复或运行级取消已通过验收。
- 恢复接线前还必须补齐：完整 assistant/tool payload 的可核对提交、可信 command/step/call 到 Proposal/Plan 的 prepared 身份与原业务时间、队列先应用再标消费、在途步数与中断时间不返还，以及跨 session/Proposal/Plan 提交的 fencing。只在 TurnStore 写前检查 lease 不能封住检查后提交的竞态。未知副作用或不可恢复的 Notebook phase 保留 interrupted，禁止重提 question、重建 episode 或重执行。安全 lease 时钟始终使用真实当前时间，不能随业务记录回放。

2026-10-19 接线细化：

- 同一 session 的非阻塞 OS execution guard 从命令开始持有到工具 drain、回执和终态提交结束；JSON lease 过期不代表旧 runtime 已死亡。恢复必须先取得该 guard，再释放遗留 claim 或标记 running orphan，随后核对原回执。此处是合作的本地 runtime 互斥，不是分布式锁，也不把旧 API/任意 Python 调用者都视为已经 fencing。
- 私有 `turn_input` 固定接受的完整输入和初始检查点；provider 步数在调用之前落盘；assistant 及工具意图在执行之前固定；最终 ToolResult 经原预算/重复提示后写 `tool_receipt`，再 append-once 写公开 tool message。读回执核对原调用完整摘要、command/step/call/invocation 与当前 branch。原回执不存在时，不从事后权限、计划或结果投影伪造它；已提交副作用与 WAL 之间仍非原子，保持 interrupted 待核对。
- 排队输入先写完整 `input` 检查点，再 append-once 应用 user message，最后标记消费。重启覆盖消费已成功但下一 provider 尚未 checkpoint 的窗口。数值纠正同样先固定扣减后的额度和完整纠正消息，再分别 append-once；不能返还纠正额度。
- 新 `/turn-state` 与 `agent turn-state` 不调用模型；`/resume` 与 `agent resume` 恢复原预算及模式。新 turn/continue 遇到未终结记录，在写新 outcome/context/mode 或初始化 provider 之前返回 409。resume 不刷新原模型上下文，并核对模型配置、工具 schema、压缩配置与原预算；配置改变需明确处理，不能静默换模型继续。
- 严格回放增加 owner-scoped 业务身份日志，固定 Core command、Proposal/Plan ID 和业务时间；不拦截真实租约或 timeout 时钟，不忽略模型请求里的业务字段。CLI replay 绑定完整输入、同路径初始项目字节及 model/business journal 摘要；空 key 离线 runtime 只能使用严格 ReplayAdapter，不读取当前 provider。回放实际重新执行统计和报告工具。
- 已验证的恢复范围是已知项目显式 resume，包括真实第三 provider step 之后 `os._exit` 的统计＋检验＋报告。生产 Notebook phase restorer 已接入，恢复原上下文、证据、episode、transcript 和累计预算（§6.1）；启动核对见 §2.5。完整分析回放当前验证明确已有 session、同绝对路径的精确初态，不承诺新建 session、任意路径迁移、所有模型 genesis 或嵌套 provider 的全面离线封锁。

### 2.5 已知项目的启动核对（2026-10-20 用户批准）

- 共同 turn/continue/resume 路径登记经过验证的项目根目录及 device/inode 绑定。默认清单目录是 `~/.config/econometrics-workbench/agent-recovery`，`WORKBENCH_AGENT_RECOVERY_DIR` 可指定隔离位置；测试隔离于真实用户配置。清单不授予执行权限，不存会话正文，不扫描未登记目录。
- app 启动只核对清单中的项目。先核对根目录绑定，再以 TurnStore 的非阻塞执行锁和版本 CAS 标记 running 孤儿为 interrupted；持锁运行跳过，等待批准的记录保持原样。预算、队列、取消意图、checkpoint 和工具回执不重建；未知副作用仍等待原恢复路径核对。项目被替换或不可读取时显式记录启动诊断，不删除清单或项目。
- 启动核对不加载 Provider 配置、不调用模型、不自动执行。继续分析仍使用原 HTTP/CLI resume，恢复原模式和累计预算。旧版本未登记项目须先进入共同回合路径，不承诺发现所有磁盘项目。
- 对外身份统一为 `Arboris Agent`；项目和所选链只是作用域。新命令更新旧会话的身份与协议，保留原审计记录；resume 不刷新原模型上下文。
- M1 宿主全量在 `8dfc4445` 得到 9062 passed / 29 failed / 8 skipped / 1 xfailed。29 个失败按实际路由所有者、CLI 人工确认、原生授权夹具、生成类型及拆分依赖等根因修复；随后以受影响测试复验，不将其写作整套全量重跑通过。M5 真实评测、浏览器与 full gate 未执行。

## 3. 执行工具与审批（M1-3、M2-6）

组合操作保留每个子项的操作 ID、权限类别和风险。项目 deny、安全底线和 ask 逐项检查，优先于外层 allow 或会话授权；不能通过给禁止的分析附加一个报告步骤绕过限制。没有外层授权时，每个子项必须分别获准，父级预算限制向子项传递。Agent 自动执行和人工确认使用同一决策。

### 3.1 一个执行工具

`run_operation` 取代 `propose_operation`、`propose_analysis_loop`、fork 提案和 Notebook `propose_batch` 的执行入口：
- 参数是**操作请求**：`operation_id`、`target`、`changes`（扁平、按操作声明校验）、`evidence_refs`、`expected_effect`、`plan_step_id`（可选）；
- 返回值是**执行回执**：状态、产物 id、新节点或新 run 的确切位置（解决 F3），以及按需读取全文的引用。

旧的四条入口保留为薄转发，版本结束前删除。持久化格式沿用 `ProposalStore` 与 operation record，新增字段只增不改。

2026-10-20：已退休重复可调用名 `propose_operation` 及 `execute_confirmed_proposal` / `execute_confirmed_fork` / `reconcile_confirmed_proposal` 三个执行转发，调用方直达共同执行入口。终态 reconcile 保持原样返回，不追加观察。历史工具名只在独立的结果分类表中保留，不再注册或向模型发布；旧记录不会因此被改写或误标为 unclassified。专用 Analysis Loop 的精确结果选择已迁至 `run_operation.target.result_id`；`create_proposal` 兼容转发也退休，真实调用方直接提交 `OperationRequest`。

2026-10-20 用户批准的目标冲突修正：来源主估计量仍由原解析器决定，但共享提案边界拒绝与显式请求不符的结果，且在写 PlanDiff、提案、执行记录之前拒绝。Agent 与手动 HTTP 返回同一份结构化恢复计划，列出请求目标、来源主估计量、只读核查调用、保留请求目标／审阅主估计量替代方案，以及可继续的独立步骤；该计划没有执行权限。Agent 在原 Core 回合内接收失败回执、核查来源并保存修正计划，受影响步骤标为 awaiting，不得删除 result_id 绕过拒绝或宣称完成。前端在折叠推理之外展示修正卡片，两种选择均只通过普通输入请求生成方案；目标变更、计划和实际操作仍各走原有批准路径。用户明确选择目标后，新提案重新绑定结果、来源和 PlanDiff，不重放失败请求。冲突以 append-once 方式进入现有会话审计，绑定原来源、节点和请求目标。更正提案固定该审计引用，并在 Expected 中显示原目标与拟用目标；共同权限引擎把未解决目标决策作为必须询问的条件，项目 allow、会话授权和已批准计划均不能绕过。即使删去 selector 重试或重启仍需用户确认；只有原有共同用户确认记录能解决该目标决策，后续重复请求沿用同一更正提案身份。会话撤回到冲突之前时，审计投影随分支回退；没有第二个授权存储或审批中心。恢复输出遵守工具声明和 8000 字符上限。离线假模型验证流程接线，不作为真实模型改善、统计方法有效性或 M5 验收结论。

### 3.2 权限引擎

纯函数 `decide(mode, op_class, risk, in_plan, rules, session_grants) -> allow | ask | deny`。
- 输入全部来自声明，不读模型文字（落实 v1.9.0 复盘 #30："只读是影响分类，不是越过用户要求的确认的许可"）。
- 写成状态机规格（§3.4），穷举测试。

**操作类别**：在操作声明上新增 `permission_class` 字段，并有漂移测试；不再按 operation id 前缀推断（现有 `analysis_ledger._PREFIXES` 只作迁移期的交叉校验）。

| 类别 | 含义 | 例 |
|---|---|---|
| `read` | 只读检查 | `inspect_*`、`calculate` |
| `analyze` | 只读计算：描述统计、检验，不改任何数据和模型 | `statistical.explore`、`test.*`、`postestimation.*` |
| `derive` | 在分支上产生新东西：派生列、新数据集阶段、模型拟合、草稿 | `data.*`（派生）、`model.genesis`、`report.compose`（草稿）、`graph.fork` |
| `modify` | 改动已有对象：元数据、标签、重跑覆盖 | `metadata.edit` |
| `external` | 离开 Workbench：导出、外发、代码执行、外部工具 | `export.*`、`code.execute`、外部工具调用 |
| `high` | 注册表 `risk_level = high` | 现有登记项 |

项目权限文档必须整份有效：重复 JSON 键、未知类别/字段、无效操作限定符、损坏文本或读取失败均明确报错，不能转成空规则或丢弃 deny。只有文件确实缺失时才使用默认规则。turn/continue 在任何会话写入和 provider 初始化之前校验；此处不宣称 Global 执行权限的完整接线已完成。

### 3.3 两种模式的决定表

| 类别 | Ask every step | Auto within plan（计划内） | Auto（计划外） |
|---|---|---|---|
| `read` | allow | allow | allow |
| `analyze` | allow，超出推断预算后 ask | allow，超出计划声明的推断次数后 ask | ask |
| `derive` | ask | allow（类别在计划的允许清单里） | ask |
| `modify` | ask | ask，除非计划逐项列出该对象 | ask |
| `external` | ask | ask | ask |
| `high` | ask + risk authorization | ask + risk authorization | ask + risk authorization |

- **安全底线**：`external`、`high`、改原始数据（以 `modify` 作用于源数据集为准）在任何模式、任何规则下都是 `ask`；规则只能收紧这几项，不能放宽，有测试守住。
- **会话授权**："本会话内同类操作不再询问"只能授予 `analyze`、`derive`、作用于非源对象的 `modify`。
- **项目规则**：`<project>/workbench/agent-permissions.json`，形如 `{allow|ask|deny: [{class, operation_id?, target?}]}`，设置页可编辑。`deny` 优先。

### 3.4 状态机

工具调用的状态：`requested → (decided: allow → executing | ask → awaiting_approval | deny → denied)`。
- `awaiting_approval → approved → executing`；
- `awaiting_approval → edited → (重新决定) → executing`；
- `awaiting_approval → skipped`，返回模型"用户跳过"；
- `awaiting_approval → stopped`，回合结束，计划保留；
- `executing → completed | failed | cancelled`。

所有转移落盘。测试穷举 模式 × 类别 × 风险 × 计划内外 × 规则 × 会话授权 的组合，断言决定表、安全底线，以及每个终态都把结果交回模型（`stopped` 除外）。

### 3.5 审批接口

- `GET /agent/sessions/{id}/approvals`：当前挂起的审批。
- `POST /agent/sessions/{id}/approvals/{request_id}`：`{decision: approve | edit | skip | stop, changes?, grant_session?: bool}`。
  - `approve` 走现有确认与执行路径：先 `confirm_proposal`，再 `execute_confirmed_operation`，指纹与 active head 校验不变；
  - 然后把回执作为该工具调用的结果交回模型，后台回合继续。
- Ask 模式下，同一模型回合里的多个同类请求合并成一张卡片，卡片内可以逐项勾选。

### 3.6 提案准入的 prepared 身份（M1-4 前置合同）

- Core 沿用调度器已分配的服务端 command ID；没有调度命令时才生成一个。每次工具调用的 provider step、call ID 和不可混淆的 invocation ID 由 Core 注入，覆盖调用方的同名辅助 metadata；模型参数不能改变这些身份。对话 fingerprint 不能冒充操作来源合同的 fingerprint。
- 新 invocation 路径在创建提案前，先持久保存完整 prepared revision（原 proposal ID、业务时间、全部请求字段与 scope）。同一 invocation 的重试必须精确匹配语义字段并复用该 revision，不重抽 UUID 或时间；不同内容、scope 或已损坏记录明确冲突。原有未携带 invocation 的 API 与序列化路径保持。
- prepared 写入、proposal 首 revision 核对/提交需要跨实例/进程串行化；不能只用实例 RLock。提案通知消息再用 session `append_once`，已 off-branch 的身份不能复活。
- 只可复用仍是原 revision 且 pending 的准入结果。提案已经被用户修订、确认、拒绝或执行时，返回明确的待核对错误；不能重新执行、回报 pending 或套用当前参数。完成后的 operation/result 由后续恢复核对接回，此前不开放该窗口的自动恢复。
- 这只是准入的可追溯身份与提交窗口，不等于完整工具结果日志、跨存储 fencing、Plan prepared 提交、原生运行取消、进程重启或完整分析回放验收。安全 lease 与过期时间绝不使用重放的业务时间。

## 4. 计划（M2-7）

- 计划是会话里的类型化记录 `plan`，带版本。
- Agent 用 `update_plan` 工具写入（参照 Codex `update_plan`、Claude Code TodoWrite），但步骤是带类型的：
  ```
  {plan_id, version, question, criteria: [...], budget: {steps, wall_s, inferential},
   allowed_classes: [...], steps: [{step_id, title, permission_class, operation_id?, depends_on: [...],
   expected_outputs: [...], status: pending|running|awaiting|done|skipped|failed, added_after_results: bool}]}
  ```
- **Auto 模式**：
  - 先出计划，经 `POST /agent/sessions/{id}/plans/{plan_id}/approve`（可附用户编辑）批准；
  - 批准时写台账 `criteria_fixed`，并开出分支；
  - 之后的修改由服务端比较版本差异：新增步骤标 `added_after_results`；越出 `allowed_classes` 或预算的修改会挂起，等用户批准。
- **Ask 模式**：计划可选，不需要批准，只用于显示。
- 步骤的有向无环图由服务端校验（无环、依赖存在）。没有依赖关系的 `analyze`、`derive` 步骤可以并行执行，受机器重负载锁约束。
- 台账新增 `criteria_fixed`、`question_change`，每个分析带 `specification_status`（预先设定 / 探索性），判定规则见研究规划设计 §7.1。

### 4.1 计划提交与批准的审计边界（M2 实施合同）

- Auto 的计划授权与完成标记使用同一就绪步骤选择：open 步骤的全部依赖须为 done，一个步骤完整覆盖本次请求；不得拼接几个步骤的权限。独立步骤仍可选择。计划 DAG 校验不代替运行时依赖检查。
- 计划读—校验—修改使用同一进程锁及跨进程文件锁；批准在锁内检查用户提供的准确版本。历史 JSON 行仍是原 Plan 形状，原子替换后同步文件与目录；不自动恢复损坏历史。
- 批准先写幂等 `criteria_fixed` 研究意图，再落盘 approved Plan，最后通过 append_once 写模型通知。研究意图自己不授予权限；写入失败不激活计划。计划提交失败时已记录的意图保留，不能假称批准已完成；通知失败可在同一已审计版本上补回。旧批准不补造或倒填事件。
- 修改已批准的问题先记录 `question_change`，再提交 needs_approval 版本。首次意图固定该修订的生成时间；重试仅在其余字段全部匹配时复用首份完整快照，不改写已有意图。它不替代完整分析回放。
- 运行期间计划发生变化时，结果仍属于已完成的操作记录；不得用旧快照覆盖新计划，也不重新执行。返回明确的计划状态核对提示。
- `criteria_fixed` 只是问题与判断标准被记录的证据。结果暴露时间、同一问题归属及 `specification_status` 的判定尚未完整接线；不得因此自动把任何步骤标成 pre-specified。报告分节仍是待交付项。

### 4.2 机器完成门（M3，首批实施边界）

- `update_plan.completion` 固定 playbooks 和注册数据来源 `{run_id, artifact_id, sha256}`；证据引用另存 `completion_evidence`。普通修订保留合同，Agent 不得删减或换来源。用户通过现有版本化计划编辑入口明确修正；已批准计划须重新批准，原证据清空，历史保留。旧计划没有这些字段时不输出新键，避免改变历史意图摘要。
- `inspect_analysis_completion` 是只读、离线的共同检查，也可先核验一个数据来源并返回 SHA；相同检查接在 Main/Chain 的共同 Core 发布边界。产物索引由 context compiler 读取：唯一注册 ID、实际内容 SHA、数据依赖与报告结果依赖分别核对，不接受模型自报 done 或步骤标签代替产物。
- OLS 的合成合同正例先覆盖已持久化的模型、计算诊断、不同点估计指纹的真实敏感性拟合和来源绑定报告。检测高影响观测后，仅不同控制变量不足，另须样本对照。随后补原生 OLS 拟合、诊断、样本对照和 HTML 的正例（含 clustered/HAC 的实际模型身份）；这仍不是数值有效性或完整产品浏览器验收。该样本变化检查仍不能证明排除的正是全部高影响点，也不能证明其科学合理性。
- 面板/DID、IV、时间序列、GARCH 已有缺项门；这些家族的原生结果/诊断/敏感性合同正例校准仍未完成，当前明确返回 `native_profile_unverified`，保持部分完成。不得用通用 p-value 字典冒充各家族的原生诊断。还需逐家族接真实生产格式与正反例，本条不代表七家族正向验收通过。
- 在有完成门的 Core 中，正文 delta 暂存至核对后发布；工具和运行事件继续发送。拒绝的完成宣称替换为“部分完成＋缺项”，无完成宣称的有效阶段性结果保留。单结果查询和单次导入的完成回执不强制要求完整分析剧本。自然语言宣称识别只是补充，机器状态/证据才是依据，不能声称覆盖全部措辞。
- 恢复 assistant 或 terminal checkpoint 时重新核验产物，追加有界、幂等的修正记录；不重跑工具、不新增模型步数、不退还预算。检查输出最多展示 8 个验证引用，其余保留数量和全体验证清单摘要。
- 只冻结开发集六个真实失败的必要原始产物和最终 JSONL 行：影响点、生存、重复测量、伪回归、GARCH、IV；源会话 SHA、行号、字节 SHA 和筛选说明在测试 manifest 中。回放不跑 M0 评测器、不使用留出集，不构成候选真实能力评分。
- `requirements_met` 仅表示这些交付证据齐全；方法选择、识别、推断有效性和报告内容忠实度一律未获认证。M3 其余剧本、自动修复、设定曲线、独立复核及真实候选评测仍待完成。

### 4.3 原生来源适配与 LMM 附属证据（已批准实施）

- 原生 HTML/PDF/Markdown 报告的存在、摘要和来源可核验；渲染质量与内容忠实度不因此获认证。`workflow-report-collection.v1` 只采用 completed 步骤的已注册引用；`run_id:artifact_id` 按原生产格式跨运行解析，不猜文件路径。
- 变换后的子运行只在其 raw artifact 字节摘要等于 `run_inputs.upload.sha256`、父数据当前摘要等于 `dataset_source.source_sha256` 时接回来源。顶层和嵌套来源冲突则不采用；核验清单包含所用 run_inputs 的实际 SHA。已有 derived_data 也可作为冻结的数据来源。
- 已有部分完成回复恢复后，重新核验仍缺项则显示当前缺项；要求现已满足则显示交付证据核验状态，不重新发布过期的部分完成文本，不新增 Provider 调用或预算。
- **用户已批准本版补齐 LMM 原生诊断及来源附属产物**。通过正式 CLI 扩展 pack、原 FD 持久化所有者和只读适配器的 affected paths。原结果身份已绑定数据指纹和设定；执行 seal 绑定配置，谱系/推断 kernel 已有数据边，不能说原系统没有数据来源。新附属产物补上可直接核验的分析数据边和残差描述，不另建来源真相或授权中心，不改旧估计结果/packet 合同/批准机制。
- `linear_mixed_effects.analysis_evidence@1.0` 记录主 packet 字节 SHA、执行 seal 身份、实际注册输入的 SHA、逐行保留位置及集合摘要。位置以实际注册分析输入（如 cleaned_dataset）的行序为准，不能称为未经变换的上传文件行号。写方通过原 pinned FD 读取注册数据，核对真实 frame，再走同一 admission/不可变 writer；重复发布幂等，关闭的 admission 不能复用。旧 packet 无附属产物时仍可由旧 reader 查看，但新的完整分析门明确部分完成。
- 逐行保存边际残差 `y-Xβ`、条件残差 `y-Xβ-Zb̂`、条件拟合值及除以残差标准差的条件残差，附均值、RMS、范围和分位数；BLUP 按组解 `V=ZΨZ′+σ²I`，不要求 Ψ 可逆。这些是描述性检查，缩减后的条件残差不独立，也不是 studentized residual；不认证正态性、协方差设定、识别、推断有效性或结果解释。拟合失败或来源未核验保留明确 unavailable/reason，不替换成成功。
- 完成门只接受严格解析的原生结果和附属产物。复核当前数据、主结果、seal、所有已记录的 executable/executed 配置、保留行集合、方法定义和摘要；模型仅读有界摘要，不发送逐行残差。还须不同真实设定的敏感性拟合和绑定结果来源的报告，才能标 requirements_met；指纹只采用实际入模值、受试者分区和模型设定；读取时从当前真实数据重建保留行并核对，不重新拟合。改名称、只改未入模列、复用同一结果或通用 JSON 字典均不计。
- 离线验证含 ML/REML × 随机截距/斜率、不平衡及缺失值的 R lme4/Stata mixed 原生逐行预测/残差对照（预先固定 atol=rtol=2e-6）、原数据/脚本/软件版本和摘要；另覆盖真实 HTTP 原生流程、重复发布、重启只读、来源/主结果/seal/配置/行映射篡改、缺少诊断和重复敏感性。它们不替代真实 Provider 评测、M5 浏览器验收或统计科学有效性审查。

### 4.4 其余家族的原生诊断与敏感性证据

- 常规 Cox/面板/IV 产物沿用原 artifact owner，LMM 继续独占其 admission/FD writer，不因通用证据读写另开授权中心。附属产物绑定实际注册输入、主结果规范化内容摘要、实际分析行和入模定义；换标准误、换名称或修改未入模数据不算新的点估计设定。诊断仍采用各家族原生合同，不用 OLS 字典改名。
- Cox 原有 Schoenfeld 残差与时间相关系数只是描述，不能充当比例风险得分检验。新增对中心化 log(event time) 系数交互的得分检验，原系数作为 nuisance，使用完整信息矩阵的 Schur complement、逐列及全局 chi-square 参考分布；先开放无权重、无分层、单条记录/受试者、右删失的 Breslow/Efron。手算小风险集和指定版本 R survival::cox.zph(transform="log", terms=FALSE) 校准；另保留 Stata 原生估计及标准误对照，预设 rtol=1e-7/atol=1e-9；固定种子仿真为 200 次零假设、60 次非 PH、n=400、alpha=.05，全部拟合纳入，零假设 MCSE=.0154，预定拒绝率范围 [.005,.11]、检验功效下限 .8。主估计、旧生存合同和批准不变。延迟入组明确 unverified，不替代为无入组检验。
- Cox PH 全局检验在预设 alpha=.05 下拒绝时，保留原检验和估计并要求明确的适用模型修订，完成门仍 partial；不得自动搜索不拒绝的设定。未拒绝也不证明 PH 或因果性。方法有效性、报告忠实度和真实 Agent 成效继续与交付证据齐全分开。


### 4.5 IV／AR 全局认证（2026-10-20 用户批准的范围例外）

- 用户明确批准“扩大本版范围，补齐 AR 置信集合的全局认证”，取代“保留有限网格未认证、全局算法留待 v1.9.2”的候选方案。一般推断内核和 HC/CR 策略仍留到下一版；受保护目录不变。既有网格参考和 M0 冻结输入保留，不能修改旧证据以制造改进。
- 定义：单个内生变量 x，外生 W，排除工具 Z，R=[W,Z] 满列秩。HC0 AR 是对辅助回归 y-bx~R 的工具系数做 HC0 Wald 检验，以 chi-square(q) 为渐近参考；不使用 HC1 缩放、F=10 或 104.7 阈值代替该检验。有限样本异方差下不宣称精确覆盖率。独立观测、有效工具及适用的矩条件仍须论证；聚类/HAC、权重、多内生变量均不替换成 iid HC0。
- 数学认证对象是实际逐行 binary64 数值及已记录 scipy 临界值的精确有理数表示，不是四舍五入的充分统计量，也不认证超越数分位点或数据生成假设。设 (R′R)^(-1)=A/D，U=AR′y、V=AR′x、E=Dy-RU、F=Dx-RV、K=AR′。M(b)=sum K_i K_i′(E_i-bF_i)^2，则 AR(b)=D²(U-bV)′M(b)^(-1)(U-bV)。以 bordered determinant 构造 AR-critical 的整数多项式分子和 PSD 协方差行列式分母；不消除奇异共同因子。
- Sturm 序列与严格 Cauchy 界精确计数/隔离所有互异实根，包含偶数重根、切点、窄分量、任意远处分量及无穷两尾；逐个有理开区间判号，再处理闭端点。证据保存多项式、根个数、互不相交有理根括号和接受标记；根宽固定 <=max(1,abs(root))*2^-44，显示浮点只作近似。重根可形成单点集合；不能用符号翻转查找替代根计数。协方差任意实奇异点使统计集合 unavailable：保留 defined-domain 分量和 undefined_points，不用伪逆、连续延拓或静默删点冒充全局置信集合。恒奇异、秩不足等也明确不可用。
- HC0 当前独立校准开放边界：单内生、1–4 个排除工具、辅助列数 <=12、无权重 iid 观测；超过边界明确 unavailable/partial，不能声称所有工具数都已验证。同方差路径以 F(q,n-rank(R)) 检验的精确二次不等式认证，残差 df 必须为正；精确 F 参考另需同方差正态独立误差。两条路径都认证整个实轴，不使用 centre/scale 搜索窗。
- 一阶段按 linearmodels 7.0 实际 f.dist 报告 partial F 或 Wald chi-square，后者的 first_stage_f 留 null，另提供真实 statistic/reference_distribution/per-endogenous。10/104.7 只作单工具、单内生、同方差设计的条件性历史基准；其他设计 unassessed，不能称“strong”。稳健拟合采用原生 Wooldridge regression exogeneity 和 robust over-identification score；同方差拟合保留 Wu–Hausman/Sargan 并标适用性；聚类/HAC没有兼容验证时不挪用 iid over-id。检验不拒绝不能证明外生性或排除限制，拒绝不能直接指出哪条工具无效。附 AR 的检查含结果信息，blinding 改为 post_fit，不能作为结果盲材料。
- 原生完成附属产物绑定主结果、注册输入、实际行、实际 W/x/Z/权重及列角色、诊断文件摘要；只换误差估计不算敏感性。集合未认证/不可用、空集或过度识别拒绝时要求具体修订，仍 partial；不是自动筛选不拒绝的工具集合。来源可信且真实敏感性与报告齐全才可 requirements_met；scientific_validity 仍 not_certified。
- 验证材料：`tests/fixtures/agent_completion/iv_ar/manifest.json` 固定原始行、版本、来源、命令及 SHA。手算有理数例、纯多项式全部拓扑/重根、原始数据整轴/两射线、近共线/高杠杆/可逆工具变换、远区间、奇异点和旧 M0 1500 行 IV 请求的零调用真拟合回放。R car::linearHypothesis(lm(...), vcov.=sandwich::vcovHC(HC0)) 与 Stata regress/test 为独立原生逐点 oracle；Stata HC1 Wald 按 N/df_r 转回 HC0。原生 R 局部端点对照不冒充全局证明；旧手写 R 网格只保留为历史局部参考。预定 rtol=1e-7/atol=1e-9，端点 atol=1e-7，不扩容差。固定弱工具异方差仿真：seed=20261021，n=180，q=2，gamma=.02，beta=1，200 次，alpha=.05，名义 MCSE=.0154，拒绝率范围 [.005,.11]；全部原生检验保留，前六个固定样本另做全局反演。认证、方法覆盖、Agent 真实表现与 M5 验收分别记录。


### 4.6 面板／TWFE DID 的原生证据与限制

- 仅发布附属诊断，不更改既有估计量、聚类内核、数值结果和原批准；PanelOLS 仍不放进旧 OLS 残差诊断循环。原生读取 linearmodels 7.0 PanelData.values2d、resids、not_null 和实际效应分区；聚类预筛选与实际行对应，核对真实入模 y，来源及主结果/诊断摘要继续绑定。实际点估计指纹含数值设计和效应分区，不含标准误设置，重复同一设定不能算敏感性。
- 残差定义 y-Xβ-所有拟合固定效应，逐行保存，并按单位给 n/均值/RMS/最大绝对值、完整参数秩（含吸收效应）、斜率参数数、残差 df、实际聚类计数、CR1/t(G-1) 定义。时间相邻相关仅在用户声明单位及时间后按单位内的已观测时间排序计算；间隔可不等，不能说成 lag-1 检验，更不拼接不同单位做 DW。没有真实时间字段时不从内部顺序伪造时间诊断。这些是描述性证据，不是自相关/独立性或方法有效性认证。
- CLUSTER_COUNT 是 G<30 caution／G<10 severe 的唯一阈值源。少于 10 个聚类或固定 T 的 FE 仅用逐行 HC 时，完成门保持 partial，要求适用推断；10–29 个聚类保留 caution，达到 30 也不认证独立聚类或覆盖率。该版不通过这条线引入 wild bootstrap 或修改受保护推断核。
- DID 沿用原生 ATT 字段、事件研究、Goodman–Bacon 和完整协方差的联合前导项检验；没有可估计前导项返回 unavailable（原来误标 not_rejected），记录被省略前导项。有限分母 df 报 Wald/q 与 F(q,df)；无有限 df 报真正 Wald chi-square(q)，并明确 statistic_definition，旧无定义记录只显示 legacy statistic，不能悄悄重解释。未拒绝零前导项不证明反事实平行趋势；拒绝、部分未识别、无前导项或 staggered interpretation_restriction 均为具体缺项。交错 TWFE 不自动变更为另一目标量/估计器，也不无条件解释为一般 ATT。
- 手算双向去均值与 R stats::lm 显式单位/时间指标、Stata xtreg/predict,e 校准单向/双向、不平衡面板的逐行残差和参数秩；固定 rtol=1e-7/atol=1e-9。既有 Stata 面板/DID/事件研究系数、SE、p、CI、联合 F 的更严容差原样保留。真实原生流程覆盖行筛选、不同设定、来源报告、少聚类、HC 的不适用限制、单一 cohort 的有预处理期正例、两期无法检验、交错解释限制。材料目录 `tests/fixtures/agent_completion/panel/manifest.json`；不虚构额外 M0 轨迹，也不把这些交付/数值回放算成真实 Agent 成效评测。

## 5. 纠正与中断（M2-8）

- `POST /agent/sessions/{id}/steer {text}`：进入 `AgentCore` 已有的 steer 队列，在下一个工具调用间隙作为用户消息插入；同时发事件，界面显示"已采纳"。
- `POST /agent/sessions/{id}/follow_up {text}`：当前回合结束后执行。
- 中断：沿用现有 `abort` 接口，并下传到运行级取消（`events.request_cancel`）。目标：回合 ≤ 1 s 停下，长计算 ≤ 2 s 停下。
- 已验证的实施约束：取消 `asyncio.to_thread` 的等待不会停止原生线程。生命周期必须保留所有权，等 effect 绑定和域提交结束后才能释放租约、回抛调用者取消；HTTP 此时仍只承诺 `cancelling`。该修复不满足运行级 ≤ 2 s 目标，也不替代进程终止后的核对，二者继续作为开放验收项。
- 撤回：一次自主执行所在的分支可以整段撤回。谱系上用现有 fork / rewind 能力，对话回到分支起点（会话 rewind 已有）。

### 6.1 Notebook 规划进入同一个 Core（M1-2 实施合同）

- 规划是确定性的 `CorePhase[T]`，只提供请求描述、已收集事件的受限规范化/严格校验、检查或提交的状态转移、纠正反馈及 checkpoint。它不持有 adapter，不调用 Core，不重试模型。
- `PhaseRequest` 声明 messages、tools、response_schema、model_config、单次 provider 期限。`PhaseStep[T]` 声明 continue/completed/refused、需追加一次的消息及 typed terminal result。通用 Core 不依赖 Notebook 的结果类。
- 模型步骤仍由 `AgentCore` 现有回合驱动：扣减共享 step/wall → 一次 provider stream → phase 校验/确定性处理 → 继续同一回合或退出阶段。不得另写一个 phase provider 循环，也不得在工具 handler 内创建另一个 Core。生产请求原有 model_config 与初始消息保持；阶段不自动混入通用身份或预算提示。
- phase 先检查恰好一个 typed call，再只补齐服务器拥有的 envelope 字段，最后执行现有 parse/semantic validation。通用 ToolRegistry 的前置严格 schema 不得抢在这个受限规范化之前。
- 保留检查去重、completed/partial 不重复检查、失败可纠正、推荐来源与证据规则，以及原有异常类型/错误文本。原 Notebook 收集器会读到 EOF，通用 Core 在 done 停止；共用 provider step 必须显式保留两者的完整性语义和超时分类。
- inspection/correction 子预算与当前 turn 的累计预算同时生效。进入阶段不调用 `_begin` 重置已有回合；独立旧入口才创建一次 standalone Core。phase 的 episode ID 只在显式新规划时生成，恢复不能重建 episode 或重复推荐/Option revision。checkpoint 接口不是恢复验收。
- 持久化 phase 保存原 context、evidence、transcript、catalog/config、episode、检查/纠正计数；恢复前核验当前来源与原运行合同，累计 step/wall 不重置，停机时间不退还。已返回 provider reply 与已完成 transition 分别保留原回执，补写公开消息不重发 provider、不重做 transition；最后一步已生成的提案可以只补写，不能借此获得额外模型步数。
- transition 已开始而缺少完成回执时，保持 interrupted 并要求原回执核对，不盲目重放检查或发布。只证明已覆盖的离线恢复边界；未知副作用不会被标成成功。恢复 provider 失败保留原错误类型，并不伪造一次新 provider 观测。
- 旧 `NotebookPlanningAgent.plan/plan_async` 保留签名，改为 standalone Core 的兼容入口，删除内部规划循环。生产 Notebook endpoint 显式注入项目内 repository/events/runner；不能从 `NotebookPlanningContextV1` 猜存储路径。无运行时注入的旧程序调用可使用短命 runner，明确不提供持久恢复。
- endpoint 保留最终 evidence 持久化 → 重新编译 context/freshness → server recommendation → `propose_batch` 的顺序。手动 drafts 不创建模型或 Core。规划完成不等于执行批准，plan/action 与 ask/auto 保持正交。
- 项目级执行的 scope admission 另行接入；本批不把 main session 改名为 chain，不冒用 manual runner 或伪造 active head。共用模型循环通过不代表项目级执行、审批挂起或后台恢复已通过。

### 4.9 Durable bounded failure recovery

- Common Core counts tool rejection and native failed-operation receipts as failed attempts. The logical step is tool + operation/contained workflow operation kinds + bound source, within one explicit user command. A new explicit user command has a new budget; automatic continuation of the original command does not.
- Session-branch failure records are durable and keyed by invocation; original receipt replay does not append another failure or rewrite the original receipt. No checkpoint schema migration is needed. A process restart retains the first failure. The second failure stops automatic provider/tool continuation, records the actual bounded reason and correction options, and reports partial completion. Outstanding calls in the same already-generated batch receive nonexecution receipts; no unknown side effect is retried. Original approval, cancellation and source requirements remain unchanged.
