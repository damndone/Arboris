> 状态：待用户评审
> 日期：2026-08-07
> 基线：`1b950fc`（worktree `workbench-v1.8.8`）
> 上游交接书：`docs/superpowers/handoff/2026-08-07-v1.8.8-kickoff-handoff.md`

## 1. 问题

产品主线是「上传数据 → 一句话说想干什么 → Agent 出方案 → 批准 → Agent 自己跑完」。
只要数据需要先 reshape 或 merge 才能建模，这条链**在第一步就断**。

原因不是能力缺失，是**注册缺失**。`merge` / `append` / `reshape` / `subset` 与五个
feature recipe 的后端已经完备且会提交 lineage（`data_operations.py:508` 的
`apply_data_transform` 与 `:750` 的 `apply_feature_recipe_operation` 都会写 artifact →
写 recipe → 注册 → 提交 graph 子节点 → 写 node_index），但它们不在 Agent 的两张词表里：

- `OperationRegistry.operation_ids()` —— 16 条，无数据转换
- `WORKFLOW_STEP_SPEC_CONTRACTS` —— 10 条，无数据转换

本版把它们接进去，并按用户在 brainstorm 中的决定，同时提升这一层的通用性。

## 2. 三个设计决策

### 决策一：操作粒度 —— 每种转换一个 OperationDefinition（偏离交接书 §4 B1）

交接书 §4 B1 的方案是一个 `data.transform@v1` 用 `operation` 枚举覆盖四种。**本设计不采纳。**

**理由**：四种转换的字段几乎不相交。`merge` 必须有
`secondary_run_id`/`secondary_node_id`/`secondary_artifact_id` 三元组 + `keys` + `how`；
`subset` 一个都不要；`reshape` 的两个方向连参数名都不同（`wide_to_long` 用
`id_columns`/`value_columns`，`long_to_wide` 用 `index`/`columns`/`values`）。

合成一份 `proposal_schema` 就只能把这些字段全标成可选。而 **LLM 读的是
`proposal_schema`**（§7.2 的教训），可选意味着模型漏填 merge 的 secondary 三元组
**不构成违规**，一道校验从「schema 层当场拒」降级为「运行时才炸」。

拆开的额外收益：每个操作有自己的 `example_prompts` 与 `ui_description`，
语义锚点是合并方案的数倍——**对措辞变化的鲁棒性更强，不是更弱**。

**拆开的成本可以按掉**：所有转换操作共用 `executor_key="data.transform"`，
orchestrator 四处分发点认的是 executor_key，因此**每处仍只加一个分支**，不是每处加 N 个。
多出来的只有 `operations.py` 里的注册样板。

**五个 feature recipe 合为一个 `data.feature_recipe@v1`**：它们结构同形（都是「由若干现有列
派生一列」），底层 `FeatureRecipe` 本来就是 `operation_id`/`inputs`/`outputs`/`parameters`
的通用形状，一份 schema 能如实表达，不存在「必填退化为可选」的问题。

### 决策二：数据集发现工具 —— `list_project_datasets`

**为什么必须新造**：`inspect_project_dataset_schema`（`context_tools.py:1674`）只吃一个
`run_id`，读那一个 run 的 `staged/data_profile.json`，**不返回 `artifact_id`、不枚举节点、
不跨 run**。而且现存工具**没有一个能列出项目里有哪些 run**——run_id 一律由调用方递进去。

所以 Agent 目前连「第二份数据存在」都不知道，`merge` 在自然语言下不可能被正确提出。
它会**编一个 id**（§7.3 那类事故的形状）。

**形状**：

```
list_project_datasets(detail_for?: [{run_id, node_id}])   # detail_for 上限 8
  → {
      datasets: [
        { run_id, node_id, artifact_id,          # 身份，永不截断
          row_count, column_count,
          columns: [名字, ...],                   # 受预算；超出报 columns_omitted
          columns_omitted: int,
          columns_without_missing: bool,          # 见下
          column_details?: [                      # 仅 detail_for 点名的数据集
            { name, dtype, unique_count, missing_rate? }
          ]
        }, ...
      ],
      datasets_omitted: 0,                        # 恒为 0；写出来是为了让守卫能断言
      omitted_sections: ["raw_rows", "column_descriptives"]
    }
```

四条约束：

1. **身份永不截断。** 数据集的数量与 `(run_id, node_id, artifact_id)` 三元组必须全给，
   哪怕 50 份。「不知道某数据存在」会让模型编 id；「知道存在但不清楚有什么列」只会让它追问一次。
   这两种失败严重性差一个量级。
2. **分层深度。** 未点名的只给列名；`detail_for` 点名的（≤8）给 `dtype` / `unique_count`。
   merge 场景一次调用即可完成「环顾 → 锁定两份 → 看详情」。
3. **稀疏编码，但不用隐式约定。** `dtype` 与 `unique_count` 恒出（前者决定要不要先 cast，
   后者决定 merge 是一对一还是一对多——后端就是拿它硬拦多对多的）。`missing_rate`
   仅在非零时出现，并由**每个数据集一个显式的 `columns_without_missing` 布尔**兜底。
   不采用「字段缺席即为零」——那是隐式约定，正是 §7 反复警告的形状。
4. **截断必报计数。** 任何截断都要有对应的 `*_omitted`。静默截断是上一版截距 SE 事故
   （静默 `continue`）的同一种病。

**id 三元组必须能直接填进 spec**，不要求模型拼接。

**性能不是约束**：工具只读几个 JSON，毫秒级。唯一稀缺资源是上下文，因此所有取舍
以「每 token 的决策价值」为准。

### 决策三：diff 语义 —— 沿用 `data.schema_diff.v1`，不新造 kind

初稿曾打算新造 `data.frame_diff.v1`，理由是 schema diff 说不清 merge/append 改变行数、
reshape 改变形状。**查过消费者后推翻。**

`frontend/src/lineage/detail/sections/DataColumnCastSection.tsx:193-238` 的 `ProvenanceDiff`
**故意不按 `kind` 分支**（注释原话：读 present 的字段，"so a new data operation renders
without touching this"），且**已经**渲染 `row_count_before`/`row_count_after`、
`columns_added`、`columns_removed`、`dtype_changes`。

那正是 merge/append/reshape 需要表达的全部内容。新造 kind 收益为零（消费方不看 kind），
还会在 `AiActivityPanel.tsx:296` 显示一个陌生标签。

**方案**：沿用 `data.schema_diff.v1`，按操作填既有字段：

| 操作 | 填的字段 |
|---|---|
| merge | `row_count_before/after`、`columns_added`、来源 artifact 列表 |
| append | `row_count_before/after`、（union 策略下）`columns_added` |
| reshape | `row_count_before/after`、`columns_added`、`columns_removed`、`direction` |
| subset | `row_count_before/after`、`columns_removed` |
| dedupe / fill_missing | `row_count_before/after` |
| rename | `columns_added`、`columns_removed` |
| aggregate | `row_count_before/after`、`columns_added`、`columns_removed` |
| feature_recipe | `columns_added` |

> 实现时若发现某个 diff 消费方读不了，回到本节修订而非绕过。

## 3. 范围：三个杠杆

用户在 brainstorm 中决定三个杠杆全做。**这改变了本版的性质**：从交接书设想的
「只接线、不写统计代码」变成「接线 + 新能力」，体量约翻倍，发版周期相应拉长。
此处如实记录，便于中途按阶段收口。

### 杠杆一：组合 ≫ 枚举（必做，且交接书 §4 与 §6 之间有缺口）

**缺口**：交接书 §6 的端到端验收要求「Agent 出**含转换步骤的方案** → 批准 → 跑出模型结果」——
转换与建模在**同一个方案**里。这要求转换进入 `operation.multi_step` 的
step 词表（`WORKFLOW_STEP_SPEC_CONTRACTS`）。但 §4 的 B1/B2 只讲了顶层提议面的注册。
**只做 B1/B2 通不过 §6。**

因此每个新转换要注册**两次**：一次进 `OperationRegistry`（顶层可提议），
一次进 `WORKFLOW_STEP_SPEC_CONTRACTS`（可与建模同方案）。

组合也是通用性的最大杠杆：N 个原子操作的组合空间远大于 N。
例：anti-join = `merge(how="outer")` → `subset` 筛出仅左侧出现的行，无需新代码。

### 杠杆二：加深现有四种（必做，便宜）

**`subset` 的行筛选只支持相等**——`data_operations.py:412` 是
`parameters.get("equals", {})`，没有 `>` / `<` / `between` / `in` / `is missing` / `not`。
「只保留 2020 年以后的」「去掉收入缺失的行」这类最普通的筛选现在做不了。
这一个缺口覆盖的真实用例可能多于再加三种新转换。

**方案**：把 `equals` 扩成一组**封闭**的比较算子：

```
filters: [ { column, op, value? } ]
op ∈ { eq, ne, gt, ge, lt, le, in, not_in, between, is_missing, not_missing }
```

保留 `equals` 的旧形式以兼容既有手动路径与已落盘的 recipe。
算子集合封闭（不是表达式求值），安全闸门形态不变。

`merge` 增加可选 `indicator`，使 anti-join 的两步组合可表达。

### 杠杆三：新增原子操作（本版新写后端）

| 操作 | 参数 | 备注 |
|---|---|---|
| `data.dedupe` | `columns`（考虑哪些列）、`keep` ∈ first/last | 行数只减 |
| `data.rename` | `mapping` {旧: 新} | 需拒绝重名冲突 |
| `data.aggregate` | `group_by`、`aggregations: [{column, func, output}]`，`func` ∈ sum/mean/median/min/max/count/std | 行数大幅收缩 |
| `data.fill_missing` | 每列 `strategy` ∈ drop_rows/constant/mean/median/mode | mean/median 需数值列校验 |
| ~~`data.sort`~~ | `by: [{column, order}]` | **建议不做，见下** |

**关于 `data.sort`**：它对截面数据的统计结果没有任何影响，只对时序/面板有意义，
而通用 `tsset` 与滞后算子按交接书 §8 属于时间序列线、不在本版。
建议本版**不做 sort**，理由是它是五个里唯一无法改变任何下游结果的操作。
请在评审中确认。

## 4. 架构

五个面，边界清晰：

```
                    ┌─ 注册面 (operations.py, workflow_contracts.py)
                    │   N 个 OperationDefinition，各带闭合 proposal_schema
                    │   + 同样 N 个 workflow step contract
                    │
自然语言 ─→ Agent ──┼─ 发现面 (context_tools.py)
                    │   list_project_datasets：让模型知道数据在哪
                    │
                    ├─ 执行面 (orchestrator.py)
                    │   共用 executor_key="data.transform"
                    │   → _data_transform_spec / _prepare_data_transform_effect
                    │   四处分发点各加一个分支
                    │
                    ├─ diff 面：沿用 data.schema_diff.v1
                    │
                    └─ 前端 (AgentPanel.tsx changeSummary)
                        提议读起来是人话，UI 字符串全英文
```

**后端统计逻辑复用现有的 `apply_data_transform` / `apply_feature_recipe_operation`，
一行都不重写**（杠杆二、三的新参数与新操作除外，那些落在
`_execute_data_transform` 内部，与注册层无关）。

`_DATA_CHILD_NODE_OPERATIONS`（`orchestrator.py:81`）要加入全部新 operation_id，
否则「没有 child_chain_id」会被当成 bug。

`scope_requirements` 必须含 `"chain"`（理由见 `operations.py:245-252` 的注释：
自然语言白名单按 scope 选，漏了 chain 则 Chain Agent 够不着）。

## 5. 分期

每期自洽、可单独验收，便于中途收口。

- **P1 接线**：四种转换 + feature recipe 注册进两张词表；orchestrator 四处分发；
  `_DATA_CHILD_NODE_OPERATIONS`；diff 填充。**此期结束即满足交接书原定范围。**
- **P2 发现**：`list_project_datasets`；merge 在自然语言下可达。
- **P3 加深**：`subset` 比较算子；`merge` indicator。
- **P4 新原子操作**：dedupe / rename / aggregate / fill_missing。
- **P5 前端 + 端到端**：`changeSummary` 分支；真机走通 §6 那条端到端。

## 6. 测试策略

三层，外加 §7 教训对应的守卫。

**契约层**：每个操作的 `proposal_schema` / `editable_schema` / validator / step contract。

**执行层**：四处分发点各走通一次；stale preview 被拒；安全闸门（多对多阻断、
行增长上限、append schema 不兼容、subset 行索引越界）各有一例。

**守卫层（本版最容易做假的地方）**：

1. **断言 LLM 真正读到的那份**：守卫直接读 `proposal_schema`（不是 `editable_schema`），
   断言 merge 的 secondary 三元组在 `required` 里。
2. **断言调用有正确结果，不是「方法存在」**：新工具走注册的 handler 实际调用一次，
   断言返回值形状，而非断言 provider 上有这个方法。
3. **两个半边都测**：既测「Agent 能提出转换」，也测「Agent 能读到转换的结果」。
4. **按 shape 写守卫，不按族名**。
5. **词表守卫**：断言两张词表（`OperationRegistry` 与 `WORKFLOW_STEP_SPEC_CONTRACTS`）
   都含全部新操作——只进一张是本版最可能的静默失败。
6. **发现工具的有界性**：构造超预算场景，断言 `*_omitted` 计数被如实报出，
   且数据集身份**一条不少**。
7. **未接入的部分在测试里显式列出**，不静默排除。

**真机**：真 DeepSeek，浏览器里走通端到端。确认提议前**核对提议内容与刚发的那句话对得上**
（v1.8.7 曾确认了旧提议导致验收作废）。

## 7. 验收标准

沿用交接书 §6 全部条目，另加本设计引入的：

- [ ] 每种转换与五个 recipe 各能由一句自然语言提出 typed proposal
- [ ] merge 场景下 Agent **自己找到**第二份数据的三元组，不需用户报 id
- [ ] 转换与 `model.genesis` 能出现在**同一个** `operation.multi_step` 方案里
- [ ] 确认后执行产生 graph 子节点，`node_index` 有条目，lineage 可追
- [ ] 提议在面板上是人话不是 JSON dump
- [ ] `subset` 能表达「大于 / 小于 / 缺失 / 在集合内」
- [ ] **端到端真机**：上传需 reshape 才能建模的数据 → 一句话 → 含转换步骤的方案 →
      批准 → 跑出模型结果
- [ ] 撞到做不到的转换时，Agent 明说做不到并列出会什么（用户在 brainstorm 中的选择）
- [ ] full gate PASSED，BE ≥ 4750 / FE ≥ 1648 / tsc 0
- [ ] `docs/releases/v1.8.8-release-notes.md` 含验证等级与已知限制
- [ ] v1.8.7 发布说明里那条数据管理限制改写为已解决（或如实说明解决了多少）

## 8. 不做什么

- `code.execute` / `model.custom` —— 用户既定决定，保持关闭
- 通用 `tsset` 与滞后算子 —— 属时间序列线
- `data.sort` —— 见 §3 杠杆三的说明，建议排除，待评审确认
- anti-join / 模糊匹配作为独立操作 —— 前者可由 merge + subset 组合表达；
  后者语义不确定，不适合自动执行
- C 类多元统计（PCA / EFA / Cronbach's α / 聚类 / 判别 / SEM）—— 候选 v1.8.9
- P1-5 时间序列（ARIMA/SARIMA、单位根、协整、VAR/VECM、Granger、IRF）—— 另开

## 9. 已知风险

1. **本版体量。** 三个杠杆全做使范围显著超出交接书。若中途需要收口，
   P1+P2 已满足交接书原定目标与 §6 的核心验收。
2. **两张词表的同步。** 注册进一张漏掉另一张是最可能的静默失败，
   由 §6 守卫 5 专门拦截。
3. **`proposal_schema` 的复发风险。** 本版改的正是契约与接线，
   §7 那五次失效模式的复发概率高于平常。守卫 1 专门拦截。
4. **`aggregate` 的行数收缩**与现有 `_enforce_growth_policy`（只管增长）方向相反，
   需确认收缩不会绕过任何既有校验。
