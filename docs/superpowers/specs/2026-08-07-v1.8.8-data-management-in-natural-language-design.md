## 0. 三条北极星约束

本版每个决策都要能回答这三条。写在最前面，因为后面所有取舍都由它们裁决。

1. **AI-native 优先**：能发挥 LLM/Agent 长处的地方要**超过** SPSS/Stata，
   而不只是追平。但超越的形式**只能是**「Agent 提议 → 人批准 → 理由入 lineage」，
   不能是静默替用户做决定。
2. **准确性与安全性是基石**：任何为了灵活性而削弱确定性契约、绕过安全闸门、
   或让错误结果能静默通过的设计，一律否决。**基石优先于一切。**
3. **模块化与可组合**：能力要能像编程一样自由组合，而不是固定公式 + 死流程。
   第 N+1 个能力的接入成本必须显著低于第 N 个。终局是
   **自然语言可调用 Workbench 的全部能力**。

## 1. 问题

### 1.1 已核实的现状（问注册表与运行时本身，非 grep 字面量）

**能力散落在互不相干的注册表里，没有统一的能力清单。**

| 注册表 | 内容 |
|---|---|
| `capabilities.model_types` | 23 个模型族 |
| `statistical_tests.TEST_FAMILIES` | 8 个检验族 |
| `data_operations.py` | merge / append / reshape / subset + 5 个 feature recipe |
| `OperationRegistry` | **16 条**操作 |
| `WORKFLOW_STEP_SPEC_CONTRACTS` | **10 条** step |

> **注意**：常被误列的 `data.cleaning` / `analysis.explain` / `analysis.suggest` /
> `workspace.arbitrary` **均未注册**。这四个字符串来自一次 grep 字面量的盘点错误，
> 交接书 §3 已记录，此处再标一次以免复发。

### 1.2 缺口一：不存在「能力」这个概念，所以可达性无法被保证

上一版声称「全部能力自然语言可达」，实际**只核对了模型族**，数据操作族漏了。
根因不是疏忽，是**系统里没有一份能力全集**——没人能枚举「全部能力」，
所以「全部可达」不可验证。

`model.genesis` **一个操作**覆盖 23 个模型族。因此**按操作写的守卫，
在新增第 24 个模型族时照样是绿的**。守卫必须建在**能力**层，不是操作层。

### 1.3 缺口二：组合不存在（第二稿的错误，已核实推翻）

第二稿写「组合 ≫ 枚举，anti-join = merge → subset」。**核实后不成立。**

`workflow_runtime.py` 的每个 step 都从 **`draft.target`** 解析数据源
（第 287、302、327、537、573、645、703、731 行皆为 `draft.target[...]`）。
`depends_on` 只做拓扑排序与失败阻断，**没有任何数据在 step 之间流动**——
一个方案里所有 step 读的是同一份原始数据。

后果是硬的：

- `merge` → `subset` 的组合：subset 读原始表，不是 merge 的结果
- **交接书 §6 的端到端验收（reshape → 建模 同方案）：模型读原始宽表，reshape 白做**

**本版存在的理由那条验收标准，用现有架构无法实现。** 这也正是北极星 3
「像编程一样组合」缺的东西——编程的本质是**值在表达式之间流动**，
`depends_on` 只是分号。

> 这个错误本身是交接书 §7 教训的实例：第二稿**断言了**组合能力存在，
> **没去看消费者**。记录在案。

### 1.4 缺口三、四：数据管理够不着；时间序列与多元统计空白

- **数据管理**（能力约 85%）：后端完备且会提交 lineage
  （`apply_data_transform`、`apply_feature_recipe_operation` 都会写 artifact →
  写 recipe → 注册 → 提交 graph 子节点 → 写 node_index），但不在两张词表里。
  by-group 已有（`GROUPABLE_OPERATIONS`），变量/值标签 v1.8.7 已补。
- **时间序列**：ARMA-GARCH 与 ETS 只是一部分。`adfuller` 确实在算，
  但只在 `engine/packs/arma_garch/` **包内部**服务于自身平稳化决策；
  `contracts/model/time_series_diagnostics.py:300` 的注释写明该契约
  **不执行 ADF 计算**，只记录 p 值来源。所以独立单位根检验确实缺。
- **多元统计**：PCA / EFA / Cronbach's α 完全空白。探针的少数命中全是子串误报
  （`sem` 匹配 assemble、`cluster` 匹配聚类稳健 SE）。好处是不依赖回归引擎，
  可独立成 pack。

## 2. 设计决策

### 决策零：组合 seam —— 本版的地基（新增，最高优先级）

**问题**：step 之间没有数据流动。

**冲突**：现有架构在**提议时**计算 `context_fingerprint`，执行时 preview 对不上即判
stale 拒绝——这是准确性的基石之一（北极星 2）。但链式 step 的输入**在提议时还不存在**：
step 2 要吃 step 1 的输出，而 step 1 尚未执行，**无法计算内容指纹**。

这是架构级冲突，不是实现细节。为灵活性直接放弃指纹校验会违反北极星 2，**否决**。

**方案：来源承诺 + 传递性验证。**

step 的数据源从「字面 id」扩展为二选一：

```
source: { run_id, node_ref, artifact_id }          # 字面来源（现状，不变）
source: { from_step: "s1", output: "data_child_node_id" }   # 来源承诺（新增）
```

- **提议时**：链式 step 的前置条件不是内容指纹，而是**来源承诺**——
  「我的输入是 s1 产出的那个节点」。编译期校验该引用可解析、DAG 无环、
  被引用的 output 键在 s1 的 `bindings` 契约里确实存在。
- **执行时**：s1 完成后，其真实的 `(run_id, node_id, artifact_id)` 注入 s2，
  **此时**才计算 s2 的 preview 指纹并做常规 stale 校验。
- **链首**仍是字面来源，指纹照旧钉死。

于是指纹沿链**传递性成立**：链首被改动 → 链首指纹失配 → 整条链失效。
**确定性一分不减，组合得以成立。**

**这是本版最高优先级的工作。** 没有它，能力注册得再多也只是并列的孤岛，
北极星 3 无从谈起，交接书 §6 的端到端验收也无法通过。

**确认粒度**（需用户确认，默认按此实现）：一个方案里的高风险步骤（改数据、
mutating）在方案内**逐条标记**，用户批准方案即批准其中全部步骤。
理由：逐步确认会把「一句话跑完」退化成多轮点击，违背产品主线；
而逐条标记保证用户批准前看得见每一处风险。

### 决策一：能力契约 CapabilityContract —— 让拓展性成为结构，而非纪律

**问题**：能力散在多个注册表，接入要手工接四处线，可达性靠人工核对。

**方案**：定义一份能力契约。任何能力（模型族 / 检验族 / 数据操作 / pack）实现它，
即**自动**获得四件事：

| 契约字段 | 自动带来 |
|---|---|
| `capability_id` / `family` / `kind` | 进入统一能力清单，可被守卫枚举 |
| `proposal_schema` + `example_prompts` + `ui_description` | 自然语言可达（顶层提议面） |
| `step_contract`（含 `bindings` 输出键） | 可作为 step 参与组合，并被别的 step 引用 |
| `diff_builder_key` / `verification_builder_key` | diff 与验证 |

**统一能力清单**是本版真正的地基产物：它让「全部能力」第一次成为**可枚举的对象**，
守卫才能断言「全部可达」。

v1.8.7 已抽出 `ModelFamilyContract`，这是它的推广，不是另起炉灶。

**衡量标准**：接入第 N+1 个能力应只需实现契约 + 写能力本身，
**不需要改 orchestrator 的四处分发**。做不到就说明契约没抽对。

### 决策二：操作粒度 —— 每种转换一个定义（偏离交接书 §4 B1）

交接书 §4 B1 的方案是一个 `data.transform@v1` 用 `operation` 枚举覆盖四种。**不采纳。**

四种转换的字段几乎不相交：`merge` 必须有 secondary 三元组 + `keys` + `how`；
`subset` 一个都不要；`reshape` 两个方向连参数名都不同。合成一份 `proposal_schema`
就只能把这些字段全标成可选。而 **LLM 读的是 `proposal_schema`**（§7.2 的教训），
可选意味着模型漏填 merge 的 secondary 三元组**不构成违规**——一道校验从
「schema 层当场拒」降级为「运行时才炸」，违反北极星 2。

拆开还使每个操作有自己的 `example_prompts` 与 `ui_description`，
**语义锚点是合并方案的数倍，对措辞变化更鲁棒**。

成本可按掉：共用 `executor_key="data.transform"`，四处分发点各仍只加一个分支。

**五个 feature recipe 合为一个**：它们结构同形，底层 `FeatureRecipe` 本就是
`operation_id`/`inputs`/`outputs`/`parameters` 的通用形状，一份 schema 能如实表达。

### 决策三：数据集发现工具 —— `list_project_datasets`

`inspect_project_dataset_schema`（`context_tools.py:1674`）只吃一个 `run_id`，
**不返回 `artifact_id`、不枚举节点、不跨 run**；且现存工具**没有一个能列出项目里
有哪些 run**。所以 Agent 连「第二份数据存在」都不知道，`merge` 在自然语言下
不可能被正确提出——它会**编一个 id**（§7.3 那类事故的形状）。

```
list_project_datasets(detail_for?: [{run_id, node_id}])   # detail_for 上限 8
  → { datasets: [ { run_id, node_id, artifact_id,        # 身份，永不截断
                    row_count, column_count,
                    columns: [名字...], columns_omitted: int,
                    columns_without_missing: bool,
                    column_details?: [{name, dtype, unique_count, missing_rate?}] } ],
      datasets_omitted: 0,
      omitted_sections: [...] }
```

1. **身份永不截断**：「不知道数据存在」会让模型编 id；「不清楚有什么列」只会让它
   追问一次。两种失败严重性差一个量级。
2. **分层深度**：未点名的只给列名；`detail_for`（≤8）给 `dtype` / `unique_count`。
3. **稀疏编码但不用隐式约定**：`dtype` 与 `unique_count` 恒出（前者决定要不要先 cast，
   后者决定 merge 是一对一还是一对多——后端就是拿它硬拦多对多的）；`missing_rate`
   仅非零时出现，由 `columns_without_missing` 显式兜底。**不采用「缺席即为零」**。
4. **截断必报计数**：静默截断是上一版截距 SE 事故（静默 `continue`）的同一种病。

### 决策四：diff 语义 —— 沿用 `data.schema_diff.v1`，不新造 kind

初稿曾打算新造 `data.frame_diff.v1`，**查过消费者后推翻**。
`DataColumnCastSection.tsx:193-238` 的 `ProvenanceDiff` **故意不按 `kind` 分支**
（注释原话：读 present 的字段，"so a new data operation renders without touching this"），
且已渲染 `row_count_before/after`、`columns_added`、`columns_removed`、`dtype_changes`。
新造 kind 收益为零，还会在 `AiActivityPanel.tsx:296` 显示陌生标签。

## 3. AI-native：哪里超过 SPSS/Stata

三条，全部建立在既有 typed-proposal 架构上——**Agent 提议、人批准、理由入 lineage**，
绝不静默替用户决定（北极星 1 的形式约束）。

### 3.1 前置诊断即提议

SPSS 要求用户**自己知道**数据是宽表、需要先 reshape。Agent 有发现工具后可以
自己看出来，并**主动把转换作为方案的第一步提出，附上理由**。

这正是交接书 §6 端到端验收描述的场景，也是决策零的直接受益者。

### 3.2 假设违反的自动串联

SPSS 会照跑并把诊断塞进输出末尾，用户不看就不知道。Agent 应该**把假设检查接进链条**：

- VAR 特征根模 ≥ 1 → **明说不稳定**，提议差分或改滞后阶，而不是照出一份错报告
- EFA 的 KMO 过低 / Bartlett 不显著 → **拒绝执行**（硬闸，见 §4.C）
- merge 撞上多对多 → 已有的硬闸

**关键分寸**：诊断结论是**拒绝或提议**，不是自动改。自动改会违反北极星 2。

### 3.3 方案即可复现制品

Stata 的 do 文件、SPSS 的 syntax 文件是纯脚本。Workbench 的方案是**带 provenance 与
verification 的 typed 对象**：每一步的输入指纹、输出 artifact、验证结果都在 lineage 里，
链式组合后**整条链可追溯、可重放、可比对**。这是脚本做不到的。

> 不做的：让 Agent 自主选择统计方法而不告知理由；自动修数据；
> 用 LLM 的判断替代数值检验。这三条都违反北极星 2。

## 4. 能力范围

### 4.A 数据管理

**加深现有四种**：`subset` 的行筛选**只支持相等**（`data_operations.py:412` 是
`parameters.get("equals", {})`），「只保留 2020 年以后的」「去掉收入缺失的行」现在做不了。
扩成一组**封闭**算子（不是表达式求值，安全闸门形态不变）：

```
filters: [ { column, op, value? } ]
op ∈ { eq, ne, gt, ge, lt, le, in, not_in, between, is_missing, not_missing }
```

保留 `equals` 旧形式以兼容既有手动路径与已落盘 recipe。
`merge` 增加可选 `indicator`，使 anti-join 的两步组合可表达（**依赖决策零**）。

**新增原子操作**：

| 操作 | 参数 |
|---|---|
| `data.dedupe` | `columns`、`keep` ∈ first/last |
| `data.rename` | `mapping` {旧: 新}，拒绝重名冲突 |
| `data.aggregate` | `group_by`、`aggregations: [{column, func, output}]`，func ∈ sum/mean/median/min/max/count/std |
| `data.fill_missing` | 每列 `strategy` ∈ drop_rows/constant/mean/median/mode |
| `data.tsset` | `time_column`、`frequency`、可选 `panel_id_column` —— **时间序列层的硬前置** |
| `data.lag` | `columns`、`lags: [int]`、可选 `difference` 阶数 |

> `data.sort` **不做**：唯一对统计结果无影响的操作，且 `tsset` 已承担时序排序语义。

### 4.B 时间序列层

| 能力 | 契约要点 |
|---|---|
| **单位根** | ADF / KPSS / PP 独立化。须保留 `time_series_diagnostics.py` 已有的 p 值来源语义（`approximate` / `unavailable`），**不得把近似 p 值当精确值报** |
| **ARIMA / SARIMA** | `(p,d,q)(P,D,Q,s)`；定阶（AIC/BIC/HQIC）；Ljung-Box 残差诊断；**预测区间必须与点预测同时给** |
| **协整** | Engle-Granger 两步 + Johansen（迹检验与最大特征根）；**协整秩是结论，不是输入** |
| **VAR** | 滞后阶选择、稳定性（特征根模 < 1）、Granger 因果、**正交化 IRF 含置信带**、FEVD |
| **VECM** | 协整秩 + 调整系数 α + 协整向量 β；与 VAR 共用滞后阶与稳定性契约 |

**共同前置**：要求已 `tsset` 的时间索引。缺索引时**拒绝并给出下一步**，不猜测。

**IRF 置信带是这层最容易做假的地方**：点估计好算，置信带 bootstrap 与渐近
结论可能不同。契约必须**显式记录用的是哪种**。

### 4.C 多元统计 pack（独立，不依赖回归引擎）

| 能力 | 契约要点 |
|---|---|
| **PCA** | 相关阵 vs 协方差阵**必须显式声明，不设默认**；成分数选择（Kaiser / 碎石 / 累计方差）；载荷 + 得分 + 解释方差比 |
| **EFA** | 提取（主轴 / 最大似然）；**旋转**（varimax / promax / oblimin）；共同度 |
| **Cronbach's α** | item-total 相关 + 「删除该项后的 α」；反向计分项须显式声明 |

**适用性检查是硬闸不是提示**：KMO 过低或 Bartlett 不显著时 EFA 结果无意义，
**拒绝执行并说明**，而不是照跑再附一句警告（北极星 2）。

## 5. 架构

```
                 ┌─ 能力面：CapabilityContract（决策一）
                 │    统一能力清单 ← 守卫在这里枚举
                 │    模型族 / 检验族 / 数据操作 / packs 全部实现同一份契约
                 │
自然语言 ─→Agent─┼─ 注册面：实现契约即自动进两张词表
                 │
                 ├─ 发现面：list_project_datasets（决策三）
                 │
                 ├─ 组合面：workflow + 来源承诺（决策零）★本版地基★
                 │    source: {from_step, output} → 执行期注入 → 指纹传递性验证
                 │
                 ├─ 执行面：orchestrator 四处分发
                 │    数据转换共用 executor_key="data.transform"
                 │
                 ├─ diff 面：沿用 data.schema_diff.v1（决策四）
                 │
                 └─ 前端：changeSummary 分支，UI 字符串全英文
```

数据管理层**复用现有 `apply_data_transform` / `apply_feature_recipe_operation`，
统计逻辑一行不重写**。两个新 pack 参考 `engine/packs/arma_garch/`、`engine/packs/anova/`。

`_DATA_CHILD_NODE_OPERATIONS`（`orchestrator.py:81`）加入全部新的**数据**操作。
`scope_requirements` 必须含 `"chain"`（`operations.py:245-252` 的注释）。

## 6. 分期

**顺序由依赖关系决定，不可随意调换。**

| 期 | 内容 | 为什么在这个位置 |
|---|---|---|
| **P0** | **组合 seam**：来源承诺 + 传递性指纹验证 + 编译期引用校验 | 地基。没有它，后面全是孤岛，§7 端到端不可能通过 |
| **P1** | **CapabilityContract + 统一能力清单** | 让「全部能力」成为可枚举对象；必须早于任何新能力 |
| **P2** | **能力级可达性守卫** | 在造新能力**之前**就位，新能力从第一天起被强制可达 |
| **P3** | 数据管理接入：四种转换 + feature recipe 走新契约进两张词表 | 第一次用 P0–P2 的地基，同时验证契约抽对了 |
| **P4** | `list_project_datasets` | merge 真正可达 |
| **P5** | `subset` 比较算子；`merge` indicator | 覆盖最大单点缺口 |
| **P6** | dedupe / rename / aggregate / fill_missing / tsset / lag | 数据管理闭环 |
| **P7** | 多元统计 pack（PCA / EFA / α） | 独立于回归引擎，**用来检验契约的可插拔性** |
| **P8** | 时间序列层（单位根 → ARIMA/SARIMA → 协整 → VAR/VECM → Granger/IRF） | 依赖 P6 的 `tsset`；内部仍可逐段收口 |
| **P9** | 前端 `changeSummary`；端到端真机 | 本版存在的理由 |

**收口点**：P0–P4 已满足交接书全部原定目标与 §6 核心验收。P7/P8 可择期。

**P7 的特殊作用**：它是**第一个完全按 CapabilityContract 从零建的能力**。
若接入它仍需改 orchestrator 的四处分发，说明契约没抽对，**回到 P1 修契约**，
不要绕过。这是本版拓展性目标的真实检验。

## 7. 测试策略

**契约层**：每个能力的 `proposal_schema` / `editable_schema` / validator / step contract。

**组合层（P0 专属）**：
- 来源承诺可解析、无环、引用的 output 键在被引用 step 的 bindings 契约里存在
- 链首被改动 → **整条链失效**（传递性验证的核心断言）
- 链中某步失败 → 下游**阻断而非跳过**
- 三步链（转换 → 转换 → 建模）端到端产出正确结果**且每步读的是上一步的输出**，
  不是原始数据。**这一条是 P0 的验收本身**

**执行层**：四处分发点各走通一次；stale preview 被拒；安全闸门各有一例
（多对多阻断、行增长上限、append schema 不兼容、subset 行索引越界、
KMO/Bartlett 不达标、VAR 不稳定、缺时间索引）。

**守卫层 —— 本版最容易做假的地方**：

- **A. 能力级可达性（本版核心守卫）**：从**统一能力清单**枚举，断言每个能力
  自然语言可达且可作为 step 组合。**必须按能力枚举，不是按操作**——
  `model.genesis` 一个操作覆盖 23 个模型族，按操作写的守卫在新增第 24 个族时照样绿，
  这正是上一版「只核对了模型族」的根因。有意例外（`code.execute` / `model.custom` 关闭）
  **显式列入白名单并写明理由，不得静默排除**。
- **B. 断言 LLM 真正读到的那份**：直接读 `proposal_schema`（不是 `editable_schema`），
  断言 merge 的 secondary 三元组在 `required` 里。
- **C. 断言调用有正确结果，不是「方法存在」**：新工具走**注册的 handler** 实际调用，
  断言返回值形状。
- **D. 两个半边都测**：既测「能提出」，也测「能读到结果」。
- **E. 按 shape 写守卫，不按族名。**
- **F. 发现工具有界性**：超预算场景下 `*_omitted` 如实报出，数据集身份**一条不少**。
- **G. 数值正确性对外部基准**：新统计能力**不接受「自洽即通过」**。
  ARIMA/VAR/协整对 statsmodels 或 R；PCA/EFA 对 R `psych`；α 对 R。
  容差参照 v1.5.8/v1.5.9 对 R 的做法（~1e-13）。
- **H. 拓展性回归**：断言接入 P7 的能力**没有改动 orchestrator 的四处分发**。
  这条把「拓展性」从口号变成可失败的测试。

**真机**：真 DeepSeek，浏览器走通端到端。确认提议前**核对提议内容与刚发的那句话
对得上**（v1.8.7 曾确认旧提议导致验收作废）。

## 8. 验收标准

**地基**

- [ ] 三步链（转换 → 转换 → 建模）中每步读的是**上一步的输出**，不是原始数据
- [ ] 链首被改动导致整条链失效（指纹传递性）
- [ ] 守卫 A 通过：统一能力清单里每个能力都自然语言可达，例外显式白名单化
- [ ] 守卫 H 通过：P7 的能力接入未改 orchestrator 四处分发

**数据管理**

- [ ] 四种转换 + 五个 recipe 各能由一句自然语言提出 typed proposal
- [ ] merge 场景下 Agent **自己找到**第二份数据的三元组，不需用户报 id
- [ ] 确认后执行产生 graph 子节点，`node_index` 有条目，lineage 可追
- [ ] `subset` 能表达「大于 / 小于 / 缺失 / 在集合内」
- [ ] 提议在面板上是人话不是 JSON dump

**时间序列**

- [ ] 单位根可独立提议，p 值来源语义（精确/近似/不可用）如实保留
- [ ] ARIMA/SARIMA 点预测与**预测区间**同时给出
- [ ] VAR 报告稳定性、Granger 因果、IRF **含置信带且标明 bootstrap 还是渐近**
- [ ] 协整秩由检验得出，不由用户指定
- [ ] 缺时间索引时**拒绝并给下一步**

**多元统计**

- [ ] PCA 显式声明相关阵还是协方差阵
- [ ] EFA 的 KMO / Bartlett 是**硬闸**，不达标即拒绝执行
- [ ] Cronbach's α 含 item-total 与删除该项后的 α

**AI-native**

- [ ] 数据形状不匹配时，Agent **主动**把转换作为方案第一步提出并附理由
- [ ] 假设违反（VAR 不稳定 / KMO 过低）导致**拒绝或提议**，不是照跑加脚注
- [ ] **端到端真机**：上传需 reshape 才能建模的数据 → 一句话 → 含转换步骤的方案 →
      批准 → 跑出模型结果

## 9. 不做什么

- `code.execute` / `model.custom` —— 用户既定决定，保持关闭
- `data.sort` —— 唯一对结果无影响的操作
- anti-join / 模糊匹配作为独立操作 —— 前者由 merge + subset 组合表达（决策零之后成立）；
  后者语义不确定，不适合自动执行
- C 类其余（聚类 / 判别 / 对应分析 / SEM / CFA）—— 本版只做 PCA / EFA / α
- A 类残余（MANOVA / Scheffé / Cramér's V / McNemar / 功效分析）
- B 类残余（Tobit / 截断回归 / Heckman / 条件 logit）；WLS 已在权重路径内部使用
  但**未暴露为可选模型**，本版不改变这一点
- GEE（工作相关结构）
- P2 全部（ZIP/NB、Hurdle、Beta、Matching、Synthetic Control、GMM、Spatial、Bayesian）
- **让 Agent 自主选择统计方法而不告知理由 / 自动修数据 / 用 LLM 判断替代数值检验**
  —— 违反北极星 2，永久不做

## 10. 已知风险

1. **P0 是架构改动，不是接线。** 组合 seam 触及 workflow 的编译、执行、状态与指纹语义，
   是本版风险最高的一段。它先行的理由正是：若它做不成，后面的分期都要重排，
   早发现比晚发现好。
2. **体量。** 本版从「把数据管理接进自然语言」扩为「地基 + 三块能力」，
   合计约为交接书原范围的三到四倍。§6 分期为此设计，P0–P4 即可收口。
3. **确定性与组合的张力。** 决策零的传递性验证是本设计的核心假设，
   若实现中发现某类 step 无法给出稳定的 bindings 输出键，需回到决策零修订，
   **不得改为放弃指纹校验**（北极星 2）。
4. **`proposal_schema` 复发风险。** 本版改的正是契约与接线，§7 那五次失效模式
   复发概率高于平常。守卫 B 专门拦截。
5. **新统计能力的「自洽即通过」风险。** IRF 置信带、EFA 旋转、协整秩这类结果，
   自洽的错误实现完全可能全绿。守卫 G 是唯一可靠拦截。
6. **`aggregate` 行数收缩**与 `_enforce_growth_policy`（只管增长）方向相反，
   需确认收缩不绕过既有校验。
7. **确认粒度待确认**：方案级批准 + 步骤级标记是默认方案，见决策零末段。
