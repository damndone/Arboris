# v1.8.1 Spec — Agent Notebook 与 AnalysisOption

> 状态：设计定稿（四个开放问题已于 2026-07-22 拍板；同日追加 DEC-CTX-001 /
> DEC-TRACE-001 两条范围决议），未实现。
> 上游：`roadmap/2026-07-22-agent-analysis-system-roadmap.md` §2。
> 范围：Notebook 的 family 绑定、Option 的对象模型与状态、Artifact Contract 执行，
> 外加两项正确性基础设施——有界上下文编译（§12）与 Core Trace（§13）。
> Notebook 渲染与选中文本交互另立 spec，但都建在本文对象之上。

> **v1.8.1 是一个 Notebook 产品功能 + 三项正确性基础设施**：一等 RunFamily
> （谁属于哪条分析演化线）、Bounded Context Compiler（Agent 当时究竟看到了什么）、
> Core Trace（当时究竟发生了什么）。三者都只做支撑 Notebook 闭环所需的最窄版本。

## 0. 决议

```
DEC-NB-001 — Notebook Run-Family Scope
A notebook MUST bind to exactly one run_family_id.
All materialized options and active_head_run_id values MUST belong to
that run family. Cross-family runs MAY be referenced for read-only
comparison, but MUST NOT become the notebook active head.
active_head_run_id MUST refer to a committed run that passed required
artifact validation. Failed attempts MUST NOT advance the active head.
```

```
DEC-OPT-001 — Option Revisioning
Notebook options MUST have a stable option_id and append-only
option_revision snapshots. Revalidation against changed context MUST
create a new option_revision and MUST NOT overwrite an earlier revision.
Execution MUST pin option_id, option_revision, proposal_id,
proposal_revision, and source context fingerprint.
```

```
DEC-OPT-002 — Option Generation Limit
One agent planning pass MUST produce no more than three options:
one recommended option and at most two alternatives. Fewer options are
allowed. Options MUST NOT materialize Graph branches until explicitly
selected and confirmed.
```

```
DEC-NB-002 — RunFamily as a First-Class Identity
RunFamily is a first-class persisted identity.
A RunFamily MAY exist before any Run exists.
Run-family membership MUST be persisted and MUST NOT be re-derived
from run ancestry for newly created runs.
RunFamily identity MUST NOT depend on root_run_id.
```

```
DEC-ART-001 — Artifact Contract Enforcement in v1.8.1
Artifact contract matching in v1.8.1 MUST be limited to the
persisted dimensions supported by the current artifact registry:
artifact_id, artifact_type, count, and optionally step.
A missing, incorrectly typed, incorrectly counted, or incorrectly
scoped required artifact MUST fail post-execution validation and
MUST block active-head advancement.
A missing optional artifact SHOULD produce a warning.
An additional valid artifact SHOULD NOT block commit unless an
explicit maximum count or prohibition is violated.
Payload schema compatibility is NOT evaluated in v1.8.1 and MUST
NOT be reported as validated. schema_ref is not part of the
v1.8.1 artifact-contract vocabulary and MUST NOT be silently
accepted or ignored.
```

```
DEC-ART-FUTURE-001 — Payload Schema Contracts
Versioned artifact payload schemas, schema_ref declaration,
compatibility rules, and legacy migration are deferred to a
separate artifact-schema milestone.
Once implemented, a required artifact whose declared payload
schema is missing or incompatible MUST fail validation.
```

```
DEC-CTX-001 — Bounded Notebook Context Compilation
Notebook option generation in v1.8.1 MUST consume a single typed,
bounded, and deterministic context profile: notebook-plan/v1.
The compiler MUST emit a source manifest, explicit omission records,
a canonical compiled-context hash, and a separate freshness dependency
fingerprint.
The generation-context hash MUST represent what the Agent actually saw.
The freshness fingerprint MUST include only upstream dependencies whose
change requires option revalidation.
General semantic RAG, vector retrieval, and cross-project context
discovery are outside the scope of v1.8.1.
```

```
DEC-TRACE-001 — Core Agent Trace in v1.8.1
v1.8.1 MUST record an append-only, versioned Core Agent Trace for
Notebook planning and option execution.
The trace MUST capture the compiled context reference and hash,
agent output, option and proposal revisions, user decisions,
validation outcomes, execution outcomes, artifact-contract outcomes,
and active-head changes.
The Core Trace records what occurred. Evaluation episode boundaries,
success labels, rewards, and scoring metrics are deferred to the
v1.8.2 evaluation harness.
Raw project data MUST NOT be duplicated into the JSONL event stream.
Full context snapshots MUST remain project-scoped and follow the
project's access-control and retention policies.
```

## 1. 问题与不做的事

Agent 看完数据后给出多条推荐路径，用户选一条。**其余的不能只留一段自然语言**——
自然语言不能被校验、不能一键执行、也无法判断它是否还成立。

但也不该为每条备选预建空 Graph 分支：分支有代价（节点、目录、血缘边），
而大多数备选永远不会被选中。

所以 Option 是**尚未 materialize 的、带上下文指纹的 typed branch proposal**：

```
Agent 生成 option  ≠  创建 Graph branch  ≠  创建 Run
```

只有用户选择、确认并 materialize 之后，才产生真正的分支。

**不建设第二套执行状态。** Graph 仍是唯一事实源。Option 不持有参数的第二份副本用于
渲染——它持有的就是将来提交给校验器的那一份。

**不另造 stale 机制。** 仓库已有一套（§4），本文复用它，只补缺失的求值时机。

## 2. Notebook 与 run family

### 2.1 强不变量

> **一个 Notebook 是一条 run family 的叙事与操作界面，不是跨 family 的报告容器。**

一条 family 内可以有多个分支、多个 head、自动选模与手工设定、主模型与稳健性模型、
被选择和被延后的 option、以及 Run Compare。但 Notebook 只能有一个 `run_family_id`。

```
active_head_run_id == null
或
run[active_head_run_id].run_family_id == notebook.run_family_id
```

### 2.2 三个语义必须分开

一个字段承担三种含义是烂账的开始：

| 字段 | 语义 | 持久化 |
|---|---|---|
| `active_head_run_id` | **持久化的当前分析状态**：由用户选定、已成功验证并完成 commit 的 family leaf run | 是 |
| `focused_run_id` | 用户此刻正在看的对象（UI 态） | 否（前端） |
| `last_attempt_run_id` | 最近一次执行尝试，可失败 | 可选 |

约束：

- 成功执行**且通过 required artifact 验证**的新 child 才可以成为 active head；
- 执行失败或 artifact 验证失败，**不推进** active head；
- 用户查看历史 run **不修改** active head；
- family 有多个 head 时，`active_head_run_id` 表示**当前主叙事所在的那个 head**，
  而不是"创建时间最新的 run"。

### 2.3 RunFamily 升为一等对象（前置项 1）

```
Notebook 创建 → RunFamily 创建 → Notebook.run_family_id 写入 → active_head_run_id = null
```

先绑定后执行。**不做兼容性绕行**（"family 先留 null，第一次执行后再从 root run 推导"），
那会重新引入一堆语义问题：首次执行失败时 Notebook 到底有没有 family；两个 option
并发 materialize 时谁决定 root；option revision 的 context fingerprint 绑定什么 family；
执行前的 Notebook 状态无法稳定引用；`active_head_run_id` 的成员约束只能事后判断。

**一等对象不等于必须有 `root_run_id`。** 新 family 的身份不得再依赖 root run：

```
RunFamily
---------
run_family_id
project_id
created_at
created_by
origin
legacy_anchor_run_id?    仅兼容旧数据
```

`root_run_id` 即使保留也只能是 **nullable 的描述性字段**，不是身份来源。
新 Notebook 可能先产生 family、之后才出现第一条 run；将来也可能出现多个没有直接
parent-child 关系但属于同一分析 family 的初始候选。

**新 family 的 ID 与 run 无关**，例如 `run-family:<uuid>`。
不要让新 ID 继续编码某条 run——那只是把"派生身份"换个写法。

#### 迁移

既有 family 身份**字符串原样保留**（`legacy-family:<root_run_id>`）：

```
1. 用现有 legacy_family_anchor() 扫描既有 run
2. 为每个派生 family 创建持久化 RunFamily 记录
3. run 与 family 建立持久化成员关系
4. 原 run_family_id 字符串完全不变
5. legacy_family_anchor() 降级为迁移与旧记录读取 fallback
6. 新 run 不再依赖 legacy_family_anchor() 决定 family
```

#### 读取优先级（兼容期）

```
persisted run_family_id 存在        → 使用持久化值
persisted run_family_id 缺失        → legacy_family_anchor() 计算，记兼容性告警
新建 run 但无 persisted family      → 拒绝
```

**fallback 只用于旧数据，绝不能成为新写入路径。**

#### 继承规则

```
新建 Notebook                          → 创建新 RunFamily
从既有 Run 创建 Notebook                → 绑定该 Run 已持久化的 run_family_id
从 Notebook option 创建首个 Run         → 使用 notebook.run_family_id
rerun / fork                           → 继承 source_run.run_family_id
把其他 family 的 Run 设为 active head   → RUN_FAMILY_MISMATCH
```

`notebook.run_family_id` **创建后不可修改**。需要另一个 family 就另建 Notebook。

### 2.4 跨 family

允许**只读引用**，不得成为运行状态：

```
Notebook (family A)
├─ active_head_run_id  只能来自 A
├─ Option materialize   只能落到 A
└─ external_references  family B 的 Compare artifact、family C 的只读结果引用
```

将来需要跨 family 讲完整故事时，增加更高层容器（Study / Report /
Workspace Collection）聚合多个 Notebook，**不把 Notebook 本身做成跨 family**。

存储上**暂不对 `run_family_id` 加 UNIQUE**：一个 Notebook 只属于一个 family，
但"同一 family 是否可派生两个不同叙事 Notebook"现在不锁死。

## 3. Option 对象模型

稳定身份与不可变快照分离。

### 3.1 `NotebookOption` — 稳定身份

```
option_id                 str    创建后不变
notebook_id               str
lifecycle_status          enum   ↓ §3.4
current_option_revision   int
generation_batch_id       str    同一次规划产生的 option 共享
rank_in_batch             int    1..3，1 = recommended
created_at                str
archived_at               str?
```

### 3.2 `NotebookOptionRevision` — 不可变快照

```
option_id                    str
option_revision              int
generation_context_id        str    ↓ §12   Agent 当时收到的编译上下文
generation_context_hash      str    ↓ §4.0  它的 canonical hash（复现用）
freshness_dependency_fingerprint  str  ↓ §4.0  上游依赖指纹（stale 判定用）
rationale                    str    给人看，不参与校验
assumptions                  [str]  该方案依赖的前提
typed_proposal_id            str
typed_proposal_revision      int
artifact_contract            obj    ↓ §5
risk_level                   enum   low | medium | high，取自 operation registry
validation_status            enum   valid | invalid | unvalidated
validation_issues            [obj]
supersedes_option_revision   int?
created_at                   str

PRIMARY KEY (option_id, option_revision)
```

`rationale` / `assumptions` 是 Agent 的自然语言产物，**不参与任何校验**，
不得据其推断执行内容。执行内容只看 `typed_proposal`。

`artifact_contract` 属于 revision 而非 option——proposal 变了，预期产出通常一起变。

### 3.3 `OptionExecution` — 钉死版本

```
option_id
option_revision
proposal_id
proposal_revision
freshness_dependency_fingerprint     ← 确认时重算并比对的就是它
generation_context_id                ← 只作证据留存，不参与门禁
run_id
```

**注意钉的是哪一个**：确认时重新编译并逐字段比对的是
`freshness_dependency_fingerprint`。`generation_context_id` 一并钉住是为了事后
能取回"Agent 当时看到什么"，**它不参与 stale 判定**——否则会触发 §4.0 的自引用问题。

防的是这个竞态：

```
用户看到 revision 2 → 数据或 active head 改变 → Agent 生成 revision 3
                   → 用户仍点了 revision 2 的确认按钮
```

服务端必须拒绝，返回结构化错误：

```
OPTION_REVISION_STALE
requested_revision: 2
current_revision: 3
```

### 3.4 三条正交状态轴

**不把 stale 和 revision 混成一个状态。**

```
lifecycle_status:   proposed | deferred | selected | executing | executed | rejected | archived
freshness_status:   fresh | stale | revalidating
validation_status:  valid | invalid | unvalidated
```

三者正交。一个 option 可以同时是：

```
lifecycle_status  = deferred
freshness_status  = stale
validation_status = valid      # 对旧上下文曾经 valid
```

重新验证后：

```
option_revision: 2 → 3
freshness_status  = fresh
validation_status = valid
```

### 3.5 lifecycle 迁移

```
                      ┌──────────┐
        Agent 生成 →  │ proposed │
                      └────┬─────┘
         ┌─────────────────┼─────────────────┐
         ↓                 ↓                 ↓
   ┌──────────┐      ┌──────────┐      ┌──────────┐
   │ selected │←────→│ deferred │      │ rejected │ (终态)
   └────┬─────┘      └──────────┘      └──────────┘
        ↓
   ┌───────────┐     ┌──────────┐
   │ executing │────→│ executed │ (终态)
   └─────┬─────┘     └──────────┘
         │ 执行失败或 artifact 验证失败
         └──────────→ selected（保留 last_attempt_run_id，不推进 active head）
```

`archived` 用于旧 batch 折叠，不是失败态。

**`executed` 必须有对应的 `OptionExecution` 记录**，否则无法反查它变成了图上哪一枝——
违反"没有 lineage 的结果不能成为结论"。

### 3.6 revision 递增规则

- 同一上下文中重复读取，**不**增加 revision；
- 上下文改变后重新验证，**始终**生成新 revision；
- proposal 内容、artifact contract、风险等级或前置条件改变，生成新 revision；
- **旧 revision 永不覆盖或删除**；
- 执行必须引用精确的 option 与 proposal revision。

### 3.7 `option_revision` vs `proposal_revision`

两个层次，不要混：

| | 表示什么 | 例 |
|---|---|---|
| `proposal_revision` | 同一 proposal 身份内部的修订 | `cluster_variable: company_id → region_id` |
| `option_revision` | 整个分析选项包的版本（理由、适用条件、上下文绑定、proposal 引用、artifact contract、风险、验证结果） | ↓ |

若 stale 重新验证后得出的是**另一套完整方案**——如从
`model.rerun / OLS robust SE` 变成 `graph.fork / negative binomial`——
那不是原 proposal 的 revision，而是：

```
新 proposal_id
proposal_revision = 1
option_revision  += 1
```

### 3.8 反面设计

```
notebook_options
  typed_proposal JSON   ← 每次重新验证直接覆盖
  option_revision += 1
```

有 revision 数字，但旧内容已消失，**无法审计 stale 之后为什么变成了这样**。

## 4. 上下文指纹与 stale 判定

### 4.0 两个 hash，不能合成一个

**这是本节最容易做错的地方，必须在 Context Compiler 落地之前定死。**

若直接拿"完整编译上下文"的哈希当 stale 依据，会立刻出现**自引用**：编译上下文里
包含"当前已有的 Option"，Agent 生成新 Option 后上下文随即改变，于是**刚生成的
Option 自己就 stale 了**。同一次 planning 产出的三条备选也会互相把对方判 stale。

因此拆成两个用途不同的值：

| | `generation_context_hash` | `freshness_dependency_fingerprint` |
|---|---|---|
| 回答 | Agent 生成这一版时**实际看到**了什么 | 哪些上游事实一变，这条 Option **必须重新验证** |
| 用途 | Trace、复现、调试、比较不同 Agent 输出、证明什么被纳入/省略 | stale 判定，`confirm()` 门禁 |
| 参与门禁 | **否** | **是** |

`freshness_dependency_fingerprint` **只包含**影响分析有效性的依赖：

```
Analysis Contract revision
Dataset version / profile revision
notebook 的 run_family_id
active_head_run_id
相关 Node / Run / Artifact revision
选中文本的 message / block hash
相关 vocabulary 或 capability 的 semantic version
```

**不得包含**（放进去就等于制造抖动或自引用）：

```
compiled_at / trace_id / token 数 / 耗时
输出格式空格、纯展示字段
Option 自己
同批次新增的 sibling option
UI 展开状态
budget report / omissions（属于 generation hash）
```

确认时的流程：

```
重新编译 freshness dependency manifest
→ 与钉住的 fingerprint 比对
→ 不一致 → OPTION_REVISION_STALE
```

### 4.1 复用既有指纹

`agent/proposals.py` 的 `confirm()` 已经在比对两个前置条件，不一致就写一条
`status="stale"` 记录并抛 `ProposalStaleError`：

| 字段 | 覆盖 | 计算处 |
|---|---|---|
| `context_fingerprint` | `nocv1:xxxxxxxx`——候选 run 引用集、共享该节点的 run 集、owner head 创建时间 | `lineage/node_write_validation.py: compute_context_fingerprint` |
| `active_head_run_id` | 该链当前活动头 | `agent/chains.py` |

模型域另有三个内容哈希，Compare 已在用：`analysis_view_hash`、`contract_hash`、
`split_hash`（见 `analysis_loop/time_series_compare.py`）。节点自身有 Merkle
identity（`node_index.json` 的 `node_hash` / `cas_ref`）。

`freshness_dependency_fingerprint` 是这些**既有字段的快照 + §4.0 白名单里
Notebook 特有的几项**（Analysis Contract revision、dataset profile revision、
选中文本 hash），**不引入新的哈希算法**，也不改既有字段的计算方式。

`generation_context_hash` 则由 Context Compiler 产出（§12.4），走 canonical
序列化，与上表无关。两者算法不同、用途不同，不得互相替代。

### 4.2 缺失的那一环：求值时机

既有机制在**确认时**判定，fail-closed，正确。但 deferred option 需要用户
**在 Notebook 里看到它时**就知道是否还成立，而不是点下去才被拒绝。

因此只补一个**读时求值**，不改写时语义：

```
evaluate_option_freshness(option_revision, current_context) -> fresh | stale
```

- 纯读、无副作用、不写任何记录；
- 与 `confirm()` 用**同一套比对字段**，避免两处判断打架；
- 结果只驱动 UI 呈现与 `freshness_status`；
- **真正的把关仍在 `confirm()`**。

> ⚠️ 读时判 fresh **不构成执行许可**——两次求值之间上游仍可能变。
> **必须有测试**：读时 fresh、确认时上游已变 → `confirm()` 仍须拒绝。
> 否则读时求值会退化成一道可绕过的假门禁。

### 4.3 stale 之后

stale **不是终态**。用户可以：

- **请求重新验证** → `freshness_status = revalidating` → Agent 用当前上下文
  重新生成 → 产生新 `option_revision`（`option_id` 不变，便于追溯"这条建议一直在"）；
- **直接拒绝** → `rejected`。

**系统不得自动把 stale 刷新为 fresh。** 上游变了意味着推荐理由可能已不成立，
必须由 Agent 重新判断，而不是把旧参数套到新数据上。

## 5. Artifact Contract（严格版 B）

匹配维度**只用现有真实持久化字段**：`artifact_id` + `artifact_type` + count，
`step` 可选。

### 5.1 不引入假的 `role`

`register_artifact()` 目前持久化的是 `artifact_id` / `artifact_type` / `step`。
本仓库的 `artifact_id` 本就是稳定语义标识（`ts.parameters`、`ts.chart.qq`、
`ts.final_model`），不是文件名。

> **v1.8.1 中，`artifact_id` 就是稳定语义 artifact key，承担此前被称为 "role"
> 的匹配职能。不引入独立的 `role` 字段。**

在 spec 里写 `role` 再由实现层偷偷映射到 `artifact_id`，会凭空造出一个尚不存在的
抽象，让读者以为 **artifact 实例身份**与 **artifact 语义角色**已经在数据模型里
正式分离。将来真需要分离时再单独迁移为 `artifact_instance_id` + `artifact_role`，
**本版不假装已有这两个概念**。

### 5.2 Schema

```json
{
  "contract_profile": "artifact-identity-type-count/v1",
  "expectations": [
    {
      "artifact_id": "ts.parameters",
      "artifact_type": "table",
      "required": true,
      "min_count": 1,
      "max_count": 1
    },
    {
      "artifact_id": "ts.chart.qq",
      "artifact_type": "figure",
      "required": false,
      "min_count": 0,
      "max_count": 1
    }
  ]
}
```

`step` 在语义稳定处可作**可选**精确限定，不强制所有 contract 声明：

```json
{ "artifact_id": "ts.parameters", "artifact_type": "table", "step": "model_fit",
  "required": true, "min_count": 1, "max_count": 1 }
```

**`contract_profile` 的作用**：明确记录本次究竟验证了哪些维度。将来加入 schema 后
会出现 `artifact-schema-aware/v2`，旧 run 的验证结果**不会被新版本误读为
"当时也检查过 payload schema"**。

### 5.3 `schema_ref` 是"不支持"，不是"忽略"

不得允许 Agent 提交 `schema_ref` 然后服务端悄悄忽略、仍声称 proposal 有效。
正确行为是在 **proposal 校验阶段拒绝**：

```
ARTIFACT_SCHEMA_CONTRACT_UNSUPPORTED
```

实现上二选一：v1.8.1 的 typed schema 中**不包含** `schema_ref`（`additionalProperties:
false` 自然拒绝），或 validator 显式拒绝该字段。

**不可以**做成"接受字段 → 不执行校验 → 给一条普通 warning"——那仍会让调用方
以为 schema 要求已被部分处理。

### 5.4 "未校验"不是每次运行的警告

payload schema 不存在，不代表每个 run 都出了异常——它是**当前 validator 的能力边界**。
所以验证结果必须区分二者：

```json
{
  "validation_profile": "artifact-identity-type-count/v1",
  "validation_status": "passed",
  "checked_dimensions": ["artifact_id", "artifact_type", "count"],
  "not_evaluated_dimensions": ["payload_schema"]
}
```

UI 显示：

```
输出契约通过
已检查：标识、类型、数量
未检查：Payload schema
```

**不得**显示泛化的"Artifact 已完整验证"。

### 5.5 处理矩阵

| 实际情况 | v1.8.1 处理 |
|---|---|
| required `artifact_id` 缺失 | **验证失败** |
| required artifact 类型错误 | **验证失败** |
| required artifact 数量低于 `min_count` | **验证失败** |
| 数量高于明确的 `max_count`，造成歧义 | **验证失败** |
| 声明了 `step`，但产物来自错误 step | **验证失败** |
| required artifact lineage 不属于当前 run | **验证失败** |
| 产生禁止类型或不可信来源 artifact | **安全失败** |
| optional artifact 缺失 | 警告 |
| 额外产生合法 artifact | 信息，必要时警告 |
| artifact payload 不符合某个 schema | **v1.8.1 无法判断，不得声称通过或失败** |
| contract 请求使用 `schema_ref` | proposal 校验阶段拒绝为 unsupported |
| 现有专用 Pack validator 报 payload 错误 | 按该专用 validator 失败，**但不得描述为通用 `schema_ref` 校验** |

最后一行是重点：现有代码对某些具体 artifact 已有 manifest / 字段 / 模型结果检查，
这些仍然有效，但必须按**真实名称**报告（如 `TS_PARAMETERS_MANIFEST_INVALID`），
不能统一包装成尚不存在的 `ARTIFACT_SCHEMA_REF_MISMATCH`。

### 5.3 执行成功与契约满足是两个维度

```
execution_status:   pending | running | succeeded | failed
validation_status:  pending | passed | passed_with_warnings | failed
```

**commit gate**：

```
execution_status == succeeded  AND  validation_status IN {passed, passed_with_warnings}
```

缺少 required artifact 时：

```
execution_status  = succeeded
validation_status = failed
```

此时：

- **保留已产生的 artifact**，供排错；
- run **不**成为 `active_head_run_id`；
- option **不**标记为正常完成；
- 报告层**不得**把它当作正式结果；
- 返回结构化 `artifact_contract_issues`。

用户看到的是"模型其实拟合完成了，但正式结果表没有按契约生成"，
而不是一个含糊的 `RUN_FAILED`。

### 5.4 required 不能由 LLM 随意声明

否则 Agent 幻觉出一个不存在的图表，就会把一次正常运行判为失败。

```
Analysis Pack / Capability Registry 声明的输出   → 可以 required
Agent 额外希望获得的输出                          → 默认 optional
经 proposal validator 确认该能力必然支持后         → 才可升级为 required
```

required 契约必须来自**已发布 vocabulary 或注册能力清单**，不是自由文本。

## 6. 生成限制

```json
{ "options": { "type": "array", "maxItems": 3 } }
```

```
rank 1  recommended
rank 2  alternative
rank 3  alternative
```

Agent 可以只返回 1 或 2 条，**不得为了凑满 3 条制造伪差异**。

不算三条独立 option：

```
OLS  /  OLS max_iter=500  /  OLS max_iter=1000
```

参数微调属于**一个 option 内部的诊断或修复建议**。

真正适合作为不同 option 的：

```
OLS + robust SE  /  分位数回归  /  GAM 非线性
顺序估计  /  联合 MLE  /  半参数稳健估计
```

### 语义 validator 规则

- 最多一个 `rank_in_batch = 1`；
- 同一 batch 内不同 option 的 **canonical proposal hash 不得相同**；
- 每条 option 必须说明相对首选方案的**实质差异**。

### 多批次

用户要求"再给我其他方案"时生成新 batch，每批仍最多 3 条。
UI 默认只展开当前 batch 与已 pin 的 option，旧 batch 折叠或 `archived`——
历史保留，但不形成第二套难读的 option 图（参考 G1 的折叠方案）。

## 7. 创建时校验

创建 option revision 时即调用对应 operation 的 validator 做 dry-run。
**校验不过的 revision 不允许创建**，Agent 需重新生成。

> 理由：v1.8.0 实测中 `propose_operation` 每轮首调必失败（字段以 `arma.p` 点号广告、
> patch 却须嵌套）。若允许存下"看着合理但校验不过"的 option，用户会在几天后点击
> 一个从来就不可能执行的方案。**创建时校验一次，比展示时道歉便宜。**

## 8. 持久化

沿用既有 JSONL append-only 约定（同 `agent-sessions/` 与 operation records）：

```
workbench/notebooks/<notebook_id>/notebook.jsonl
workbench/notebooks/<notebook_id>/options/<option_id>.jsonl
```

每次 lifecycle 迁移与每个新 revision append 一条，末条为当前态。
崩溃可恢复、迁移可审计、不就地改写。

## 9. 验收标准

1. Notebook **不维护独立执行状态**；option 里的参数与最终提交给校验器的是同一份。
2. Notebook 绑定**恰好一个** `run_family_id`；跨 family run 只能只读引用，
   不得成为 active head。
3. `active_head_run_id` 只在 `execution_status == succeeded` **且**
   `validation_status ∈ {passed, passed_with_warnings}` 时推进。
4. 三个 run 语义字段不混用（active head / focused / last attempt）。
5. 旧 `option_revision` **永不被覆盖**；stale 重新验证产生新 revision。
6. 执行钉死 `(option_id, option_revision, proposal_id, proposal_revision,
   freshness_dependency_fingerprint)`；不匹配返回 `OPTION_REVISION_STALE`。
7. stale 判定与 `confirm()` 使用同一套字段；**读时判 fresh 不构成执行许可**
   （须有测试：读时 fresh、确认时上游已变仍须拒绝）。
7b. **自引用测试（§4.0 的命门）**：一次 planning 产出 3 条 option 后，这 3 条
   **都必须仍是 fresh**——sibling option 的产生不得使彼此或自身 stale。
   同理，`generation_context_hash` 变化而 freshness 白名单字段未变时，
   `confirm()` **不得**拒绝。
8. 校验不过的 option revision 不允许创建。
9. 一次规划最多 3 条，最多一条 rank 1，同批 canonical proposal hash 不重复。
10. 缺 required artifact → `execution_status=succeeded` 且
    `validation_status=failed`，artifact 保留、active head 不推进、
    报告层不得引用为正式结果。
11. required 契约只能来自注册能力清单，不能来自 Agent 自由文本。
12. `executed` 必有 `OptionExecution`，可反查图上分枝。
13. 验证结果必须返回 `contract_profile` / `checked_dimensions` /
    `not_evaluated_dimensions`；UI 不得显示"已完整验证"。
14. 含 `schema_ref` 的 contract 在**执行前**即被拒绝。

### 9.1 RunFamily 验收测试

```
1. 创建没有 Run 的 Notebook → RunFamily 已持久化，active_head_run_id = null
2. 从该 Notebook 执行首个 Option → 新 Run 继承 Notebook 的 run_family_id
3. 对该 Run rerun / fork → child 保持同一 run_family_id
4. 把其他 family 的 Run 设为 active head → RUN_FAMILY_MISMATCH
5. 迁移既有 Run → 迁移前后 legacy-family:<root_run_id> 完全相同
6. persisted family 与 ancestry 推导冲突 → 以 persisted identity 为准并报告
   数据一致性错误，**不得静默重写 family**
```

### 9.2 Artifact Contract 验收测试

```
1. 缺少 required ts.parameters → execution succeeded、validation failed、
   active head 不推进
2. ts.parameters 被注册为 figure 而非 table → validation failed
3. optional ts.chart.qq 缺失 → passed_with_warnings
4. 产生未声明但合法的诊断图 → passed，记 informational issue
5. proposal 含 schema_ref → 执行前以 ARTIFACT_SCHEMA_CONTRACT_UNSUPPORTED 拒绝
6. 验证结果必须返回 contract_profile / checked_dimensions /
   not_evaluated_dimensions
```

## 10. 实现前置项

**前置项 1 — RunFamily 升为一等对象**（§2.3）：须先于 Option 完成。

**前置项 2 — Bounded Notebook Context Compiler**（§12，DEC-CTX-001）：
须先于**任何真实 Option 流量**接通。理由不是工程洁癖，见 §12.1 的四条阻塞理由。

**前置项 3 — Core Trace v1**（§13，DEC-TRACE-001）：可与前置项 2 并行，
但同样须在真实 Option 流量开始前接通——**trace 是唯一无法事后补采的东西**。

`schema_ref` 已按 DEC-ART-001 排除在本版之外，
不构成 Option 的前置依赖。它进入独立的 Artifact Schema Registry 里程碑
（见 BACKLOG `ARTIFACT-SCHEMA-REGISTRY`），并被设为
**Capability Extension 晋升 verified 之前的强制前置 Gate**：

```
ARTIFACT-SCHEMA-REGISTRY
        ↓ blocks verified promotion
V1.8.3-CAPABILITY-EXT
```

理由：v1.8.1 的 Notebook 用的是仓库内已注册、已知行为的能力，
`artifact_id + type + count` 足够挡住主要产物缺失。但到了外部依赖 Adapter 或
Agent 生成新 Capability 时，只知道"它产出一个 table"远远不够——系统还必须知道
该 table 是否确实含参数名、估计值、标准误、区间、样本量、模型标识。
**实验性 capability 可以构建与测试，但在没有 payload contract 前不得晋升为
可产出可信数字的 `verified`。**

## 12. Bounded Notebook Context Compiler（前置项 2）

### 12.1 它为什么阻塞正确性

不是"加个检索层"，而是四条具体的正确性依赖：

1. **不知道 Option 的依据。** 若每次调用临时拼 prompt（一点数据摘要 + 当前聊天 +
   几个 run + 某些 diagnostics），那么 revision 3 与 revision 2 的差异就无法归因：
   是数据变了？active head 变了？拼接顺序变了？某个 Artifact 被截断了？还是模型随机性？
2. **`stale` 失去可比语义。** §4.0 的 fingerprint 只有在上下文由**唯一**编译器
   生成时才可比。否则每个调用方各算各的 hash，`stale` 变成看起来严格、实际不可比的值。
3. **Trace 无从记录真实输入**（§13.3）。没有统一 compiler，trace 只能存一堆散落的
   工具调用，凑不出"Agent 本次到底看到了什么"。
4. **预算问题只能在这里解决。** v1.8.0 真机的 `tool_output_budget_exceeded`
   说明缺的不是更多检索，而是按列投影、聚合摘要、限制样本行数 / lineage 深度 /
   Artifact 数量，以及**显式截断**。

外加一条权限理由：Compiler 是统一入口，须保证 Notebook 引用了某个外部对象
**不等于** Agent 能读到本无权限的内容。

### 12.2 它不是什么

```
不是向量数据库
不是跨项目语义搜索
不是自动检索任意历史聊天
不是 Raw Data RAG
不是 Agent 自行决定无限读取哪些 Artifact
不是通用 Context DSL 平台
```

它只是一条路径：

```
确定当前 Notebook planning 所需的源对象
→ 按类型做有界投影
→ 按固定顺序规范化
→ 明确记录省略内容
→ 生成 typed context bundle
→ 计算 fingerprint
```

### 12.3 `NotebookPlanningContextV1`

```
context_id
context_profile                   固定为 notebook-plan/v1
notebook_id
run_family_id
active_head_run_id
analysis_contract
dataset_profile
active_run_summary
bounded_lineage
diagnostics
artifact_summaries
available_capabilities
existing_option_summaries
user_focus
source_manifest
omissions
budget_report
generation_context_hash
freshness_dependency_fingerprint
```

**必须完整保留**（不得截断）：

```
Analysis Contract
当前用户目标
当前选中文本及其来源
run_family_id
active_head_run_id
严重阻塞性 diagnostics
```

**必须有界投影**，默认预算（可配置，但必须有固定默认值）：

```
数据集字段摘要   ≤ 30
直接 lineage 节点 ≤ 10
关键 Artifact 摘要 ≤ 5
现有 Option 摘要  ≤ 3
每表预览行数     ≤ 20
```

### 12.4 确定性是硬要求

```
相同 source refs
+ 相同 source revisions
+ 相同 context profile semantic version
+ 相同 budget configuration
→ 必须产生相同的 canonical context 与相同的 generation_context_hash
```

**不得参与 canonical hash** 的字段：`compiled_at`、随机 ID、日志 sequence、
运行耗时、展示层格式。

排序必须固定：

```
Lineage      拓扑序 + 稳定 ID
Artifact     artifact_id + step
Diagnostics  severity + code
Option       batch + rank + option_id
```

**所有截断都必须显式记录，不得静默丢内容**：

```json
{
  "section": "artifact_summaries",
  "included_count": 5,
  "available_count": 17,
  "reason": "section_budget_exceeded"
}
```

> 验收照 §9 的约定：断言具体内容。**"上下文已编译"不是验收**；
> "同一批源对象编译两次，`generation_context_hash` 逐字节相等，且
> `omissions` 含 `artifact_summaries` 的 5/17 记录"才是。

## 13. Core Trace v1（前置项 3）

### 13.1 采什么、不采什么

**现在采、以后无法恢复**的信息：Agent 实际看到哪一版上下文、哪些内容因预算被截断、
当时的 prompt / 模型 / vocabulary 版本、Agent 原始生成了哪些 Option、哪些被
validator 拒绝、用户看见的是 revision 2 还是 3、用户选择/修改/延后/拒绝了什么、
执行后 required Artifact 是否满足、active head 为何推进或未推进。

**现在不设计**的东西——因为这些还没拍板：评测 episode 如何切分、"用户选择了"是否
算正反馈、哪些结果需要专家标签、Option 排序准确率怎么算、方法合理性 / 结果忠实度 /
成本如何分别计分、一次任务里多次重试如何归因。

```
Trace              = 当时真实发生了什么          ← v1.8.1
Evaluation Episode = 哪些事件组成一个样本，如何评价 ← v1.8.2 从 Trace 构建
```

### 13.2 稳定事件外壳

现有 JSONL 继续作为存储方式，但**写入内容必须先过版本化 schema**——否则它只是
debug log，不是以后能稳定消费的证据。

```json
{
  "trace_schema": "agent-trace-event/v1",
  "event_id": "evt_...",
  "trace_id": "trace_...",
  "sequence": 12,
  "occurred_at": "2026-07-22T14:30:00Z",
  "event_type": "option.revision.created/v1",
  "scope": { "project_id": "...", "notebook_id": "...", "run_family_id": "..." },
  "actor": { "type": "agent" },
  "versions": {
    "app_commit": "...", "model_id": "...", "prompt_version": "...",
    "vocabulary_version": "...", "context_profile": "notebook-plan/v1"
  },
  "refs": {
    "context_id": "ctx_...", "option_id": "...", "option_revision": 3,
    "proposal_id": "...", "proposal_revision": 1, "run_id": null
  },
  "payload_schema": "option-revision-created/v1",
  "payload": {}
}
```

外壳稳定，`payload` 按事件类型走各自的 typed schema。
**关键事件不得塞进无约束的 `payload: any`。**

### 13.3 v1.8.1 必须采集的事件

不必给所有工具调用建模。先覆盖一条 Option 的完整决策链：

```
context.compiled
agent.plan.requested
agent.plan.completed
option.revision.created
option.lifecycle.changed
user.decision.recorded
proposal.validation.completed
option.execution.started
option.execution.completed
artifact_contract.validation.completed
active_head.changed
operation.error
```

`user.decision.recorded` 至少区分：

```
selected | deferred | rejected | edited
requested_more_options | requested_explanation
```

> ⚠️ **用户选择只是一条行为证据，Trace 层不得把它标记成"正确答案"或 reward。**
> 打标签是 v1.8.2 评测工装的职责，混进 Trace 会污染以后所有样本。

### 13.4 必须能取回 Agent 实际看到的上下文

只存 `context_hash` 不够——哈希可验证一致性，但取不回内容。三件一起存：

```
context_manifest              源对象 ID / revision / hash / 选择原因
compiled_context_blob_ref     Agent 当时实际接收的规范化上下文快照
compiled_context_hash         完整性校验
```

**不得**把完整数据集或大量原始行复制进 JSONL。快照优先放摘要、有限投影与
Artifact 引用，并沿用项目的权限与保留策略。

### 13.5 项目审计 Trace ≠ 产品遥测

**从第一天就分开**，否则"以后做评测"会无意中变成数据权限事故：

| | 项目审计 Trace | 产品遥测 |
|---|---|---|
| 存放 | 项目 / 租户范围 | 独立通道 |
| 内容 | 可含实际上下文快照 | 只含脱敏元数据与聚合 |
| ACL | 与项目数据同权限 | 不含原始数据与完整 prompt |
| 用途 | 复现、排错、**用户授权后**的评测 | 产品指标 |

**项目 Trace 不得自动上传为训练数据。**
