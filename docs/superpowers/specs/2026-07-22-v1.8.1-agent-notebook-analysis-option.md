# v1.8.1 Spec — AnalysisOption：Agent Notebook 的备选方案对象

> 状态：设计中，未实现。
> 上游：`roadmap/2026-07-22-agent-analysis-system-roadmap.md` §2。
> 范围：本文只定义 `AnalysisOption` 的 schema、状态机与 stale 判定。
> Notebook 渲染与选中文本交互另立 spec，但都建在本对象之上。

## 1. 问题

Agent 看完数据后会给出多条推荐路径，用户选一条。**其余的不能只留一段自然语言**——
自然语言不能被校验、不能一键执行、也无法判断它是否还成立。

但也不该为每条备选预先创建一个空 Graph 分支：分支是有代价的（节点、目录、
血缘边），而大多数备选永远不会被选中。

所以 `AnalysisOption` 是：**一个尚未 materialize 的、带上下文指纹的 typed branch proposal**。

选中它 → 才生成真正的 proposal 并走既有确认链路 → 才产生 Graph 分支。

## 2. 不要做的事

**不建设第二套执行状态。** Graph 仍是唯一事实源。`AnalysisOption` 不持有参数的
第二份副本用于渲染——它持有的是**将来会提交给校验器的那一份**，两者必须是同一份。

**不另造 stale 机制。** 仓库已有一套，见 §5。本对象复用它，只补一个缺失的求值时机。

## 3. Schema

```
AnalysisOption
  option_id            str    稳定标识，创建后不变
  notebook_id          str    所属 notebook
  title                str    一行摘要，给人看
  rationale            str    为什么推荐，给人看
  assumptions          [str]  该方案依赖的前提（如"误差同方差"）
  typed_proposal       obj    ↓ §4
  expected_artifacts   [str]  预期产出的 artifact_id 前缀（如 ts.chart.*）
  risk_level           enum   low | medium | high，取自 operation registry
  source_context       obj    ↓ §5
  status               enum   ↓ §6
  created_at           str
  updated_at           str
  materialized         obj?   仅 executed 态：{proposal_id, record_id, run_id}
  rejected_reason      str?   仅 rejected 态
```

`title` / `rationale` / `assumptions` 是 Agent 的自然语言产物，**不参与任何校验**，
不得据其推断执行内容。执行内容只看 `typed_proposal`。

## 4. `typed_proposal`

与既有 proposal **同形**，不新增方言：

```
operation_id        如 "model.rerun" / "graph.fork"
operation_version   如 "v1"
target              既有 target 形状（owner_run_id / op_node_id / node_hash / …）
changes             既有 changes 形状（如 {"model_options": {...}}）
```

**必须能通过既有校验器**。创建 option 时即调用对应 operation 的 validator 做一次
dry-run 校验；校验不过的 option **不允许创建**，Agent 需重新生成。

> 理由：v1.8.0 实测中 `propose_operation` 每轮首调必失败（字段以 `arma.p` 点号广告、
> patch 却须嵌套）。若允许创建"看起来合理但校验不过"的 option，用户会在几天后点击
> 一个从来就不可能执行的方案。**创建时校验一次，比展示时道歉便宜。**

## 5. `source_context` 与 stale 判定

### 5.1 复用既有指纹，不要新造

仓库已有的两个前置条件（`backend/workbench/agent/proposals.py`）：

| 字段 | 含义 | 计算处 |
|---|---|---|
| `context_fingerprint` | `nocv1:xxxxxxxx`，覆盖候选 run 引用集、共享该节点的 run 集、owner head 创建时间 | `lineage/node_write_validation.py: compute_context_fingerprint` |
| `active_head_run_id` | 该链当前活动头 | `agent/chains.py` |

时间序列/模型域另有三个内容哈希，Compare 已在用：

| 字段 | 覆盖 | 出处 |
|---|---|---|
| `analysis_view_hash` | 分析视图（变换后的数据身份） | `ts.train_validation_split` 等 artifact metadata |
| `contract_hash` | 模型合约 | `contracts/model/arma_garch.py: contract_hash` |
| `split_hash` | 冻结的训练/验证切分 | `ts.train_validation_split` |

节点自身还有 Merkle identity（`node_index.json` 的 `node_hash` / `cas_ref`）。

**`source_context` = 这些既有字段的快照**，不引入新的哈希算法：

```
source_context
  context_fingerprint   str   创建时的 nocv1:…
  active_head_run_id    str
  node_hash             str   option 所针对节点的 Merkle identity
  analysis_view_hash    str?  模型域 option 才有
  contract_hash         str?
  split_hash            str?
  captured_at           str
```

### 5.2 缺失的那一环：求值时机

既有 stale 机制是**确认时**判定的：`confirm()` 里比对 `preconditions` 与当前值，
不一致就写一条 `status="stale"` 的确认记录并抛 `ProposalStaleError`。这是
fail-closed，正确。

但 deferred option 的需求不同：**用户在 Notebook 里看到它时就要知道它是否还成立**，
而不是点下去才被拒绝。

所以本 spec 只补一个**读时求值**，不改写时语义：

```
evaluate_option_freshness(option, current_context) -> fresh | stale
```

- 纯读，无副作用，不写任何记录；
- 与 `confirm()` 用**同一套比对字段**，避免两处判断打架；
- 结果只驱动 UI 呈现（新鲜 = 可一键执行；stale = 需重新验证）；
- **真正的把关仍在 `confirm()`**。读时判新鲜不构成执行许可——两次求值之间上游仍可能变。

> 这条边界必须写进测试：读时判为 fresh、但确认时上游已变 → `confirm()` 仍须拒绝。
> 否则读时求值会退化成一道可被绕过的假门禁。

### 5.3 stale 之后

stale 不是终态。用户可以：

- **请求重新验证** → Agent 用当前上下文重新生成 `typed_proposal`，产生该 option 的
  新 revision（`option_id` 不变，便于追溯"这条建议一直在"）；
- **直接拒绝** → `rejected`。

系统**不得**自动把 stale option 静默刷新为 fresh。上游变了意味着推荐理由可能已不成立，
必须由 Agent 重新判断，而不是把旧参数套到新数据上。

## 6. 状态机

```
                    ┌──────────┐
      Agent 生成 →  │ proposed │
                    └────┬─────┘
                         │
        ┌────────────────┼────────────────┬──────────────┐
        ↓                ↓                ↓              ↓
   ┌──────────┐    ┌──────────┐    ┌──────────┐   ┌──────────┐
   │ selected │    │ deferred │    │ rejected │   │  stale   │
   └────┬─────┘    └────┬─────┘    └──────────┘   └────┬─────┘
        │               │             (终态)            │
        │               │ 用户后来选中                   │ 重新验证
        │               └──────→ selected               └──→ proposed(新 revision)
        ↓                                                    或 rejected
   ┌──────────┐
   │ executed │  ← 走完 typed→validate→confirm→execute→verify→commit
   └──────────┘
      (终态)
```

允许的迁移：

| from | to | 触发 |
|---|---|---|
| proposed | selected | 用户选中 |
| proposed | deferred | 用户选了别的，本条留待以后 |
| proposed | rejected | 用户明确拒绝 |
| proposed / deferred / selected | stale | 读时或确认时检出上下文已变 |
| selected | executed | 确认后执行成功 |
| selected | deferred | 执行前反悔 |
| stale | proposed | 重新验证后产生新 revision |
| stale | rejected | 用户放弃 |

**终态**：`executed`、`rejected`。二者不可再迁移。

**`executed` 必须携带 `materialized`**（proposal_id / record_id / run_id），
否则无法反查它变成了图上的哪一枝——违反"没有 lineage 的结果不能成为结论"。

## 7. 持久化

沿用既有 JSONL append-only 约定（同 `agent-sessions/` 与 operation records）：

```
workbench/notebooks/<notebook_id>/options/<option_id>.jsonl
```

每次状态迁移 append 一条，末条为当前态。理由与既有 proposal store 一致：
崩溃可恢复、迁移可审计、不就地改写。

## 8. 验收标准

1. Notebook **不维护独立执行状态**；option 里的参数与最终提交给校验器的是同一份。
2. 每个 option 可反向定位到产生它的上下文（`source_context` + 产生它的 message）。
3. 未选方案不丢失：deferred option 跨会话、跨重启可见。
4. 上游变化后旧方案标记为 stale，且 **stale 判定与 `confirm()` 用同一套字段**。
5. 读时判 fresh **不构成执行许可**；确认时上游已变仍须拒绝（须有测试）。
6. 校验不过的 option 不允许创建。
7. 所有正式数字仍来自既有注册能力；option 不引入新的执行路径。
8. `executed` 态必有 `materialized`，可反查图上分枝。

## 9. 开放问题

1. **notebook 与 run family 的关系**：一个 notebook 对应一条 run family，还是可以
   跨 family？倾向前者（否则 `active_head_run_id` 语义不清），但需确认。
2. **option 的 revision 存哪**：复用 proposal 的 `revision` 字段，还是 option 自持？
   倾向 option 自持一个 `option_revision`，因为 stale→重新验证会换掉整个
   `typed_proposal`，而 proposal revision 语义是"同一提案的修订"。
3. **Agent 一次生成几条**：需要上限，否则 option 列表会变成第二个图爆炸问题
   （参考 G1 的折叠方案）。
4. **expected_artifacts 是否可校验**：执行后可比对实际产出与预期，不符时是警告
   还是失败？倾向警告并记入 Notebook，但不阻断。
