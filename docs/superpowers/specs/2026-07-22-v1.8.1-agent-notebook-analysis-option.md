# v1.8.1 Spec — Agent Notebook 与 AnalysisOption

> 状态：设计定稿（四个开放问题已于 2026-07-22 拍板），未实现。
> 上游：`roadmap/2026-07-22-agent-analysis-system-roadmap.md` §2。
> 范围：Notebook 的 family 绑定、Option 的对象模型与状态、Artifact Contract 执行。
> Notebook 渲染与选中文本交互另立 spec，但都建在本文对象之上。

## 0. 四条决议

```
DEC-NB-001 — Notebook Run-Family Scope
A notebook MUST bind to exactly one run_family_id.
All materialized options and active_head_run_id values MUST belong to
that run family. Cross-family runs MAY be referenced for read-only
comparison, but MUST NOT become the notebook active head.
active_head_run_id MUST refer to a committed run that passed required
artifact validation. Failed attempts MUST NOT advance the active head.
```

```
DEC-OPT-001 — Option Revisioning
Notebook options MUST have a stable option_id and append-only
option_revision snapshots. Revalidation against changed context MUST
create a new option_revision and MUST NOT overwrite an earlier revision.
Execution MUST pin option_id, option_revision, proposal_id,
proposal_revision, and source context fingerprint.
```

```
DEC-OPT-002 — Option Generation Limit
One agent planning pass MUST produce no more than three options:
one recommended option and at most two alternatives. Fewer options are
allowed. Options MUST NOT materialize Graph branches until explicitly
selected and confirmed.
```

```
DEC-ART-001 — Artifact Contract Enforcement
Missing, incompatible, or incorrectly linked required artifacts MUST
fail post-execution validation and MUST block commit. Missing optional
artifacts and additional valid artifacts SHOULD produce warnings without
blocking commit.
Execution success and artifact validation success MUST be represented
separately.
```

## 1. 问题与不做的事

Agent 看完数据后给出多条推荐路径，用户选一条。**其余的不能只留一段自然语言**——
自然语言不能被校验、不能一键执行、也无法判断它是否还成立。

但也不该为每条备选预建空 Graph 分支：分支有代价（节点、目录、血缘边），
而大多数备选永远不会被选中。

所以 Option 是**尚未 materialize 的、带上下文指纹的 typed branch proposal**：

```
Agent 生成 option  ≠  创建 Graph branch  ≠  创建 Run
```

只有用户选择、确认并 materialize 之后，才产生真正的分支。

**不建设第二套执行状态。** Graph 仍是唯一事实源。Option 不持有参数的第二份副本用于
渲染——它持有的就是将来提交给校验器的那一份。

**不另造 stale 机制。** 仓库已有一套（§4），本文复用它，只补缺失的求值时机。

## 2. Notebook 与 run family

### 2.1 强不变量

> **一个 Notebook 是一条 run family 的叙事与操作界面，不是跨 family 的报告容器。**

一条 family 内可以有多个分支、多个 head、自动选模与手工设定、主模型与稳健性模型、
被选择和被延后的 option、以及 Run Compare。但 Notebook 只能有一个 `run_family_id`。

```
active_head_run_id == null
或
run[active_head_run_id].run_family_id == notebook.run_family_id
```

### 2.2 三个语义必须分开

一个字段承担三种含义是烂账的开始：

| 字段 | 语义 | 持久化 |
|---|---|---|
| `active_head_run_id` | **持久化的当前分析状态**：由用户选定、已成功验证并完成 commit 的 family leaf run | 是 |
| `focused_run_id` | 用户此刻正在看的对象（UI 态） | 否（前端） |
| `last_attempt_run_id` | 最近一次执行尝试，可失败 | 可选 |

约束：

- 成功执行**且通过 required artifact 验证**的新 child 才可以成为 active head；
- 执行失败或 artifact 验证失败，**不推进** active head；
- 用户查看历史 run **不修改** active head；
- family 有多个 head 时，`active_head_run_id` 表示**当前主叙事所在的那个 head**，
  而不是"创建时间最新的 run"。

### 2.3 创建时序

```
Notebook 创建 → RunFamily 创建 → Notebook.run_family_id 写入 → active_head_run_id = null
```

先绑定后执行，比"第一次执行后再决定属于哪个 family"稳定，也避免两个 option
并发执行时争夺 family 归属。

从已有 Run 创建 Notebook 时，复用该 Run 的 `run_family_id`。

> ⚠️ **前置缺口**：`run_family_id` 目前是**派生**的，不是被创建的实体——
> `agent/chains.py: legacy_family_anchor()` 由 `scan_family()` 找到根 run 后拼成
> `legacy-family:<root_run_id>`。本决议要求它成为可先于任何 run 存在的一等对象。
> 这是本 spec 的第一个实现前置项，须在 Option 之前完成，且必须保证既有 legacy
> family id 的向后兼容（现存 run 的 family 身份不得改变）。

### 2.4 跨 family

允许**只读引用**，不得成为运行状态：

```
Notebook (family A)
├─ active_head_run_id  只能来自 A
├─ Option materialize   只能落到 A
└─ external_references  family B 的 Compare artifact、family C 的只读结果引用
```

将来需要跨 family 讲完整故事时，增加更高层容器（Study / Report /
Workspace Collection）聚合多个 Notebook，**不把 Notebook 本身做成跨 family**。

存储上**暂不对 `run_family_id` 加 UNIQUE**：一个 Notebook 只属于一个 family，
但"同一 family 是否可派生两个不同叙事 Notebook"现在不锁死。

## 3. Option 对象模型

稳定身份与不可变快照分离。

### 3.1 `NotebookOption` — 稳定身份

```
option_id                 str    创建后不变
notebook_id               str
lifecycle_status          enum   ↓ §3.4
current_option_revision   int
generation_batch_id       str    同一次规划产生的 option 共享
rank_in_batch             int    1..3，1 = recommended
created_at                str
archived_at               str?
```

### 3.2 `NotebookOptionRevision` — 不可变快照

```
option_id                    str
option_revision              int
context_fingerprint          str    ↓ §4
rationale                    str    给人看，不参与校验
assumptions                  [str]  该方案依赖的前提
typed_proposal_id            str
typed_proposal_revision      int
artifact_contract            obj    ↓ §5
risk_level                   enum   low | medium | high，取自 operation registry
validation_status            enum   valid | invalid | unvalidated
validation_issues            [obj]
supersedes_option_revision   int?
created_at                   str

PRIMARY KEY (option_id, option_revision)
```

`rationale` / `assumptions` 是 Agent 的自然语言产物，**不参与任何校验**，
不得据其推断执行内容。执行内容只看 `typed_proposal`。

`artifact_contract` 属于 revision 而非 option——proposal 变了，预期产出通常一起变。

### 3.3 `OptionExecution` — 钉死版本

```
option_id
option_revision
proposal_id
proposal_revision
source_context_fingerprint
run_id
```

防的是这个竞态：

```
用户看到 revision 2 → 数据或 active head 改变 → Agent 生成 revision 3
                   → 用户仍点了 revision 2 的确认按钮
```

服务端必须拒绝，返回结构化错误：

```
OPTION_REVISION_STALE
requested_revision: 2
current_revision: 3
```

### 3.4 三条正交状态轴

**不把 stale 和 revision 混成一个状态。**

```
lifecycle_status:   proposed | deferred | selected | executing | executed | rejected | archived
freshness_status:   fresh | stale | revalidating
validation_status:  valid | invalid | unvalidated
```

三者正交。一个 option 可以同时是：

```
lifecycle_status  = deferred
freshness_status  = stale
validation_status = valid      # 对旧上下文曾经 valid
```

重新验证后：

```
option_revision: 2 → 3
freshness_status  = fresh
validation_status = valid
```

### 3.5 lifecycle 迁移

```
                      ┌──────────┐
        Agent 生成 →  │ proposed │
                      └────┬─────┘
         ┌─────────────────┼─────────────────┐
         ↓                 ↓                 ↓
   ┌──────────┐      ┌──────────┐      ┌──────────┐
   │ selected │←────→│ deferred │      │ rejected │ (终态)
   └────┬─────┘      └──────────┘      └──────────┘
        ↓
   ┌───────────┐     ┌──────────┐
   │ executing │────→│ executed │ (终态)
   └─────┬─────┘     └──────────┘
         │ 执行失败或 artifact 验证失败
         └──────────→ selected（保留 last_attempt_run_id，不推进 active head）
```

`archived` 用于旧 batch 折叠，不是失败态。

**`executed` 必须有对应的 `OptionExecution` 记录**，否则无法反查它变成了图上哪一枝——
违反"没有 lineage 的结果不能成为结论"。

### 3.6 revision 递增规则

- 同一上下文中重复读取，**不**增加 revision；
- 上下文改变后重新验证，**始终**生成新 revision；
- proposal 内容、artifact contract、风险等级或前置条件改变，生成新 revision；
- **旧 revision 永不覆盖或删除**；
- 执行必须引用精确的 option 与 proposal revision。

### 3.7 `option_revision` vs `proposal_revision`

两个层次，不要混：

| | 表示什么 | 例 |
|---|---|---|
| `proposal_revision` | 同一 proposal 身份内部的修订 | `cluster_variable: company_id → region_id` |
| `option_revision` | 整个分析选项包的版本（理由、适用条件、上下文绑定、proposal 引用、artifact contract、风险、验证结果） | ↓ |

若 stale 重新验证后得出的是**另一套完整方案**——如从
`model.rerun / OLS robust SE` 变成 `graph.fork / negative binomial`——
那不是原 proposal 的 revision，而是：

```
新 proposal_id
proposal_revision = 1
option_revision  += 1
```

### 3.8 反面设计

```
notebook_options
  typed_proposal JSON   ← 每次重新验证直接覆盖
  option_revision += 1
```

有 revision 数字，但旧内容已消失，**无法审计 stale 之后为什么变成了这样**。

## 4. 上下文指纹与 stale 判定

### 4.1 复用既有指纹

`agent/proposals.py` 的 `confirm()` 已经在比对两个前置条件，不一致就写一条
`status="stale"` 记录并抛 `ProposalStaleError`：

| 字段 | 覆盖 | 计算处 |
|---|---|---|
| `context_fingerprint` | `nocv1:xxxxxxxx`——候选 run 引用集、共享该节点的 run 集、owner head 创建时间 | `lineage/node_write_validation.py: compute_context_fingerprint` |
| `active_head_run_id` | 该链当前活动头 | `agent/chains.py` |

模型域另有三个内容哈希，Compare 已在用：`analysis_view_hash`、`contract_hash`、
`split_hash`（见 `analysis_loop/time_series_compare.py`）。节点自身有 Merkle
identity（`node_index.json` 的 `node_hash` / `cas_ref`）。

`NotebookOptionRevision.context_fingerprint` 是这些**既有字段的快照**，
不引入新的哈希算法。

### 4.2 缺失的那一环：求值时机

既有机制在**确认时**判定，fail-closed，正确。但 deferred option 需要用户
**在 Notebook 里看到它时**就知道是否还成立，而不是点下去才被拒绝。

因此只补一个**读时求值**，不改写时语义：

```
evaluate_option_freshness(option_revision, current_context) -> fresh | stale
```

- 纯读、无副作用、不写任何记录；
- 与 `confirm()` 用**同一套比对字段**，避免两处判断打架；
- 结果只驱动 UI 呈现与 `freshness_status`；
- **真正的把关仍在 `confirm()`**。

> ⚠️ 读时判 fresh **不构成执行许可**——两次求值之间上游仍可能变。
> **必须有测试**：读时 fresh、确认时上游已变 → `confirm()` 仍须拒绝。
> 否则读时求值会退化成一道可绕过的假门禁。

### 4.3 stale 之后

stale **不是终态**。用户可以：

- **请求重新验证** → `freshness_status = revalidating` → Agent 用当前上下文
  重新生成 → 产生新 `option_revision`（`option_id` 不变，便于追溯"这条建议一直在"）；
- **直接拒绝** → `rejected`。

**系统不得自动把 stale 刷新为 fresh。** 上游变了意味着推荐理由可能已不成立，
必须由 Agent 重新判断，而不是把旧参数套到新数据上。

## 5. Artifact Contract

`expected_artifacts` 从名称列表升级为契约。匹配对象是 artifact 的**稳定 role、
类型与 schema，不是文件名**。

### 5.1 Schema

```json
{
  "artifact_contract": [
    {
      "role": "primary_estimate_table",
      "artifact_type": "table",
      "required": true,
      "min_count": 1,
      "max_count": 1,
      "schema_ref": "model.coefficient_table.v2"
    },
    {
      "role": "residual_diagnostic_plot",
      "artifact_type": "figure",
      "required": false,
      "min_count": 0,
      "max_count": 1
    }
  ]
}
```

> ⚠️ **前置缺口**：`artifacts.py: register_artifact()` 目前只有
> `artifact_id` / `artifact_type` / `step`，**没有 `role`，也没有 `schema_ref`**。
> 好消息是 `artifact_id` 在本仓库本就是稳定语义标识（`ts.parameters`、
> `ts.chart.qq`、`ts.final_model`），不是文件名，可直接充当 role。
> **缺的是 `schema_ref`**——artifact 不声明其 payload 符合哪个 schema 版本。
> 这是本 spec 的第二个实现前置项：要么补 `schema_ref`，要么先只支持
> role + type + count 三维匹配、把 `schema_ref` 标为 v1.8.1 范围外。
> 两者都可以，但**不得假装 schema 校验已经发生**。

### 5.2 处理矩阵

| 情况 | 处理 |
|---|---|
| 缺少 required artifact | **验证失败** |
| required artifact 类型错误 | **验证失败** |
| required artifact schema 不兼容 | **验证失败** |
| required artifact lineage 不属于当前 run | **验证失败** |
| required artifact 数量不足 | **验证失败** |
| 超过明确的 `max_count`，导致结果歧义 | **验证失败** |
| 产生禁止类型或不可信来源 artifact | **安全失败** |
| optional artifact 缺失 | 警告 |
| 产生额外的合法 artifact | 信息或警告 |

### 5.3 执行成功与契约满足是两个维度

```
execution_status:   pending | running | succeeded | failed
validation_status:  pending | passed | passed_with_warnings | failed
```

**commit gate**：

```
execution_status == succeeded  AND  validation_status IN {passed, passed_with_warnings}
```

缺少 required artifact 时：

```
execution_status  = succeeded
validation_status = failed
```

此时：

- **保留已产生的 artifact**，供排错；
- run **不**成为 `active_head_run_id`；
- option **不**标记为正常完成；
- 报告层**不得**把它当作正式结果；
- 返回结构化 `artifact_contract_issues`。

用户看到的是"模型其实拟合完成了，但正式结果表没有按契约生成"，
而不是一个含糊的 `RUN_FAILED`。

### 5.4 required 不能由 LLM 随意声明

否则 Agent 幻觉出一个不存在的图表，就会把一次正常运行判为失败。

```
Analysis Pack / Capability Registry 声明的输出   → 可以 required
Agent 额外希望获得的输出                          → 默认 optional
经 proposal validator 确认该能力必然支持后         → 才可升级为 required
```

required 契约必须来自**已发布 vocabulary 或注册能力清单**，不是自由文本。

## 6. 生成限制

```json
{ "options": { "type": "array", "maxItems": 3 } }
```

```
rank 1  recommended
rank 2  alternative
rank 3  alternative
```

Agent 可以只返回 1 或 2 条，**不得为了凑满 3 条制造伪差异**。

不算三条独立 option：

```
OLS  /  OLS max_iter=500  /  OLS max_iter=1000
```

参数微调属于**一个 option 内部的诊断或修复建议**。

真正适合作为不同 option 的：

```
OLS + robust SE  /  分位数回归  /  GAM 非线性
顺序估计  /  联合 MLE  /  半参数稳健估计
```

### 语义 validator 规则

- 最多一个 `rank_in_batch = 1`；
- 同一 batch 内不同 option 的 **canonical proposal hash 不得相同**；
- 每条 option 必须说明相对首选方案的**实质差异**。

### 多批次

用户要求"再给我其他方案"时生成新 batch，每批仍最多 3 条。
UI 默认只展开当前 batch 与已 pin 的 option，旧 batch 折叠或 `archived`——
历史保留，但不形成第二套难读的 option 图（参考 G1 的折叠方案）。

## 7. 创建时校验

创建 option revision 时即调用对应 operation 的 validator 做 dry-run。
**校验不过的 revision 不允许创建**，Agent 需重新生成。

> 理由：v1.8.0 实测中 `propose_operation` 每轮首调必失败（字段以 `arma.p` 点号广告、
> patch 却须嵌套）。若允许存下"看着合理但校验不过"的 option，用户会在几天后点击
> 一个从来就不可能执行的方案。**创建时校验一次，比展示时道歉便宜。**

## 8. 持久化

沿用既有 JSONL append-only 约定（同 `agent-sessions/` 与 operation records）：

```
workbench/notebooks/<notebook_id>/notebook.jsonl
workbench/notebooks/<notebook_id>/options/<option_id>.jsonl
```

每次 lifecycle 迁移与每个新 revision append 一条，末条为当前态。
崩溃可恢复、迁移可审计、不就地改写。

## 9. 验收标准

1. Notebook **不维护独立执行状态**；option 里的参数与最终提交给校验器的是同一份。
2. Notebook 绑定**恰好一个** `run_family_id`；跨 family run 只能只读引用，
   不得成为 active head。
3. `active_head_run_id` 只在 `execution_status == succeeded` **且**
   `validation_status ∈ {passed, passed_with_warnings}` 时推进。
4. 三个 run 语义字段不混用（active head / focused / last attempt）。
5. 旧 `option_revision` **永不被覆盖**；stale 重新验证产生新 revision。
6. 执行钉死 `(option_id, option_revision, proposal_id, proposal_revision,
   source_context_fingerprint)`；revision 不匹配返回 `OPTION_REVISION_STALE`。
7. stale 判定与 `confirm()` 使用同一套字段；**读时判 fresh 不构成执行许可**
   （须有测试：读时 fresh、确认时上游已变仍须拒绝）。
8. 校验不过的 option revision 不允许创建。
9. 一次规划最多 3 条，最多一条 rank 1，同批 canonical proposal hash 不重复。
10. 缺 required artifact → `execution_status=succeeded` 且
    `validation_status=failed`，artifact 保留、active head 不推进、
    报告层不得引用为正式结果。
11. required 契约只能来自注册能力清单，不能来自 Agent 自由文本。
12. `executed` 必有 `OptionExecution`，可反查图上分枝。

## 10. 实现前置项（须先于 Option 完成）

1. **RunFamily 升为一等对象**（§2.3）：可先于任何 run 存在，且既有
   `legacy-family:<root_run_id>` 身份向后兼容。
2. **Artifact 的 `schema_ref`**（§5.1）：补上，或明确把 schema 维度排除在
   v1.8.1 之外并只做 role + type + count 匹配。二选一，但不得假装已校验。
