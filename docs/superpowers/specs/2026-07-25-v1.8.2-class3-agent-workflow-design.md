# v1.8.2 Class 3 Agent Workflow Design

## Status

Design revision after review. This document is the contract for the v1.8.2
one-sentence Class 3 teaching workflow. It stays inside the existing
`workbench-v1.8.2` development line and does not change the protected v1.8.1
release line.

## Goal

Allow a user to say, in natural language, that Workbench should complete the
Class 3 Stata exercise over the selected Raw data node, while keeping every
statistical meaning server-owned, typed, evidence-backed, reproducible, and
visible in Graph.

The first version is intentionally semantic-locked. The Agent may identify
columns and group values from inspected data, but it may not choose a different
operation, percentile definition, comparison operator, missing-value policy,
covariance default, or report contract.

## Non-goals

- No `code.execute`, Python, shell, Stata, R, or arbitrary user code path.
- No automatic model selection or user-prompted reinterpretation of the
  assignment.
- No mutation of the Raw data node.
- No independent workflow steps for coefficient confidence intervals,
  residuals, or fitted values; these are required artifacts of an OLS step.
- No silently substituted estimator, empty group, missing column, or partial
  success reported as a completed assignment.

## Product shape

The Agent receives the user's request and the bounded Raw schema/context. It
proposes the registered `operation.multi_step@v1` operation, whose changes
contain a typed `WorkflowDraft` with an ordered DAG of nine real
operations. The server compiles and validates every operation before any
mutation is allowed. The UI shows the complete step list, source scope,
variables, fixed statistical semantics, expected artifacts, and risks. One
confirmation authorizes the workflow as a whole. The workflow executor then
runs the steps in dependency order, recording one durable state transition per
step and preserving completed artifacts if a later step fails.

The workflow authorization is a distinct audit fact. Each child operation
record must contain `workflow_id`, `workflow_confirmation_id`, `workflow_step_id`,
and the workflow plan fingerprint. The audit exporter must describe the child
operation as individually executed under a single explicit workflow
confirmation, not as an individually confirmed operation.

## The nine real operations

The operation identity is fixed by the server template. The Agent can supply
only evidence-backed column names and, where applicable, the six observed year
values.

1. `statistical.explore@v1` — grouped descriptive statistics for 1998, 2002,
   2006, 2010, 2014, and 2016.
2. `statistical.explore@v1` — missingness summary over the pooled source.
3. `statistical.explore@v1` — pooled Pearson correlation matrix using the
   Workbench/Stata-compatible missing-value policy.
4. `statistical.explore@v1` — detailed statistics for `totreg` and `pfl`,
   including the locked Stata percentile contract.
5. `statistical.derive_boolean@v1` — derive `small_school`, `large_school`,
   `poor_school`, and `least_poor_school` from thresholds sourced from step 4.
6. `statistical.explore@v1` — summarize `adj_dppupil_comp` for the four
   derived groups.
7. `statistical.explore@v1` — produce the two spending scatter plots.
8. `model.genesis@v1` — create and execute the two OLS model branches. Its
   expected artifact contract includes coefficient CI/N, model result, and all
   configured residual/fitted diagnostics.
9. `report.class3@v1` — assemble the workflow log, tables, figures, model
   outputs, diagnostics, and PDF/HTML report into one report artifact pack.

Steps 1–7 are read-only analysis artifacts except step 5, which creates typed
derived child data nodes. Step 8 creates immutable model runs. Step 9 creates
the final report artifacts. The workflow executor may internally materialize
multiple model branches for step 8, but they share one workflow step identity
and one expected-artifact contract.

Only `operation.multi_step@v1` is exposed as the Agent's single confirmation
entry point. The numbered identities are server-owned internal step templates;
they are not nine separate Agent confirmations.

## Server-owned semantic templates

`WorkflowDraft` stores both the submitted intent and the compiled server
template. A submitted step is rejected with 422 if it attempts to change any
of these fields:

- operation identity and operation version;
- summarize/detail/correlation/plot method;
- percentile algorithm and percentile values;
- comparison operators for derived booleans;
- variablewise/listwise/complete-case missing policy;
- OLS covariance policy and expected model family;
- artifact contract and report composition rules.

The server validates the final compiled `ExplorationSpec` through its existing
`__post_init__` path and validates OLS options through
`validate_ols_model_options`. Unknown fields are rejected. Missing source
columns are rejected before execution with the exact missing-column list.

## Stata percentile contract

Step 4 and step 5 use an explicit versioned quantile method, not pandas'
implicit default. v1.8.2 fixes the method to the Stata `summarize, detail`
semantics used by the assignment and persists:

```json
{
  "quantile_method": "stata_summarize_detail_v1",
  "percentiles": [25, 75],
  "source_artifact_id": "...",
  "source_fingerprint": "..."
}
```

The four boolean thresholds must reference the step-4 artifact and its
fingerprint. Literal Agent-provided threshold numbers are not accepted. The
threshold, source scope, comparison operator, and resulting row counts are
included in the derived recipe and artifact metadata.

## Empty groups and fail-closed behavior

An empty typed group is a failed workflow step, not a warning. If a grouped
summary returns any `empty_group_values`, the executor marks that step
`failed`, records the offending values and filter specification, and marks all
dependent later steps `blocked`. It never reports the workflow as completed.

Boolean filters are evaluated against typed boolean columns without string
coercion. Invalid boolean filter values and a zero-row result caused by a
typed-group mismatch are validation/execution failures, not silently empty
successes.

## Workflow state and idempotent resume

The workflow is append-only and fingerprint-addressed:

```text
planned -> confirmed -> running -> completed
                              \-> failed
dependent steps: pending -> blocked
```

Every step fingerprint includes the source artifact fingerprint, compiled
spec, dependency artifact fingerprints, and workflow template version. A
resume reuses a completed step only when that fingerprint and artifact contract
match exactly. A conflicting derived recipe at an occupied deterministic path
is a hard conflict, never an overwrite. A failed step can be retried only after
the same preconditions and dependency fingerprints are revalidated.

## Log and report foundation

Before workflow orchestration, v1.8.2 adds a run/workflow-level exploration
log JSONL and extends the report builder to consume the complete exploration
collection. Each event includes workflow/step identity, operation/spec
fingerprint, source and dependency artifact ids, row counts, status, and error
details. The report view model includes the same collection rather than
reconstructing it from unrelated PDFs.

The final report artifact is blocked unless all required steps are completed
and every expected artifact in the OLS contract is present. A partial workflow
can still be inspected through its step artifacts and log, but it cannot be
presented as the completed Class 3 report.

## Acceptance criteria

The implementation is accepted only when a real Agent request proves:

1. zero `code.execute` records;
2. nine real workflow steps, with OLS diagnostics represented as expected
   artifacts rather than ghost steps;
3. step-5 thresholds point to step-4's artifact fingerprint;
4. every submitted semantic deviation receives a server-side 422;
5. missing columns fail before execution with the exact column names;
6. empty groups fail and dependent steps are `blocked`;
7. a resumed workflow reuses completed fingerprint-matching steps and does not
   overwrite a conflicting derived recipe;
8. both OLS branches persist explicit covariance values;
9. workflow authorization is visible in every child operation record and audit
   export;
10. the final report includes the complete exploration log, tables, figures,
    model outputs, CI/N, residual/fitted diagnostics, and PDF/HTML artifacts;
11. backend, frontend, TypeScript, gate, and browser evidence all pass for the
    real `newschools9816` dataset.

## Implementation order

1. Add the workflow exploration JSONL and report aggregation foundation.
2. Register and execute the typed statistical operations, including the Stata
   quantile contract and boolean-derived operation.
3. Register the locked workflow templates and compile the nine-step plan.
4. Add single-confirmation workflow execution, audit binding, blocked state,
   and fingerprint-based resume.
5. Enable the Chain Agent natural-language path for the workflow and verify
   that it cannot emit `code.execute` or alter server-owned semantics.
6. Complete frontend Graph/Table/report readers and run backend/frontend,
   TypeScript, gate, and browser acceptance.
