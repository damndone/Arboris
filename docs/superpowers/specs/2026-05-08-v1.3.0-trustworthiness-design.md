# V1.3.0: Report Trustworthiness — Design Spec

日期：2026-05-08

## 1. 目标

V1.3.0 的目标不是新增统计方法，而是让系统产出的报告**值得信任**。具体来说：

- 用户看到 severity 标签时，能一眼区分"这报告不能用""这个解释要小心""这是系统行为说明"。
- 所有变量系数和诊断结论都在报告里用一致语言解释，不会出现 Facts 说"已编码"但 Diagnostics 说"请考虑编码"的矛盾。
- 报告从结构上区分事实、诊断、解释、风险提示。
- 为未来 AI 深度介入设计好泛化 JSON 接口（schema），当前版本用规则模板填充，不调 AI。

## 2. 范围与非范围

**进入 V1.3.0：**

1. Severity 四级枚举 + 现有 issue 重分级
2. Issue 统一数据结构
3. `diagnostic_summary.json` artifact — 泛化 JSON schema
4. 报告五段式结构（Facts / Data diagnostics / Model diagnostics / Coefficient interpretation / Causal caution）
5. 因果语言防线 — 默认禁止 causal language
6. Cook's distance 语言软化 — screening threshold ≠ 模型失败
7. 报告模板按 severity 四区展示

**不进入 V1.3.0：**

- 新统计方法（DID、ARIMA、ML 等）
- 真实 AI API 调用
- Categorical 变量在描述统计和 variable importance 中的展示修复（进 V1.3.2）
- Treatment-proxy 四档分级阈值落地（进 V1.3.3）
- Per-model 诊断图（deferred）

## 3. Severity 四分法

### 3.1 枚举定义

```python
class Severity(str, Enum):
    BLOCKER = "BLOCKER"   # 报告不应生成，或模型失败
    WARNING = "WARNING"   # 可能影响核心解释，需显著标记
    CAUTION = "CAUTION"   # 模型可用但解释需谨慎
    INFO = "INFO"         # 系统行为说明，不影响结论
```

### 3.2 现有 issue 重分级

#### BLOCKER（Critical Errors）

| Issue | 说明 |
|---|---|
| `INSUFFICIENT_SAMPLE` | 样本不足以估计 |
| `MODEL_FIT_FAILED` | 模型拟合失败 |
| `MODEL_RESULTS_MISSING` | 无法交付任何分析结果 |
| `REPORT_RENDER_FAILED_NO_RESULTS` | 报告坏了，结果也不可用 |
| `PERFECT_SEPARATION` | Logistic 系数不可正常估计 |
| `SINGULAR_MATRIX` | 矩阵不可逆，模型不能估计 |
| `NO_VARIATION_IN_Y` | 因变量无变异 |
| `TOO_FEW_ROWS` | 行数不足以估计 |

#### WARNING（模型可跑，但核心解释受影响）

| Issue | 条件 |
|---|---|
| `TREATMENT_PROXY_CORRELATION` | abs(r) ≥ 0.7，或 abs(r) ≥ 0.9 加注 redundancy |
| `QUASI_SEPARATION` | 模型不稳定但不一定完全失败 |
| `RARE_EVENT_WARNING` | 见下方 EPP 分档表 |
| `OVERDISPERSION_DETECTED` | 影响 Poisson/count model 选择 |
| `AUTOCORRELATION_DETECTED` | Durbin-Watson 显著偏离 2 |
| `HETEROSKEDASTICITY_DETECTED` | 未用 robust SE 时 |
| `REPORT_RENDER_FAILED_RESULTS_AVAILABLE` | HTML/PDF 坏了但 model_results 还在 |
| `MODEL_RESULTS_AVAILABLE_REPORT_NOT_FOUND` | 可展示 fallback summary |
| `VARIABLE_DROPPED`（核心变量） | 用户指定的 treatment/main variable 被 drop |
| `VARIABLE_DROPPED`（大量变量） | 模型结构因 drop 明显改变 |
| `HIGH_VIF` | VIF > 10 |
| Cook's distance max D ≥ 0.5 |
| Cook's distance max D ≥ 1.0（高亮） |
| Cook's distance 极少样本且高影响点主导（模型不可估计时升 BLOCKER） |

#### CAUTION（模型可用，解释需谨慎）

| Issue | 条件 |
|---|---|
| `TREATMENT_PROXY_CORRELATION` | 0.5 ≤ abs(r) < 0.7 |
| `CATEGORICAL_CANDIDATE` | 系统不确定，需用户确认 |
| `BINARY_CORRELATION` | abs(r) < 0.8 |
| `VARIABLE_DROPPED`（普通控制变量） | 因共线性被 drop |
| `HETEROSKEDASTICITY_DETECTED` | 已用 robust SE 时 |
| `RESIDUAL_NON_NORMALITY` | Jarque-Bera p < 0.05 |
| `HIGH_LEVERAGE_POINTS` | 非极端情况 |
| `HIGH_VIF` | 5–10 |
| Cook's distance max D < 0.5（部分 obs > 4/n） |

#### INFO（System Notes）

| Issue | 说明 |
|---|---|
| `CATEGORICAL_AUTO_DUMMY_CODED` | 系统已自动编码 |
| `COERCED_X_DTYPE` | 非数值列自动转换 |
| `PANEL_POOLED_MODEL` | panel 数据但用了 pooled 模型 |
| `SUSPICIOUS_DTYPE` | datetime 列低唯一值 |

#### RARE_EVENT_WARNING — events-per-predictor（EPP）分档

| 条件 | Severity | 说明 |
|---|---|---|
| event rate < 5%，但 EPP ≥ 10 | WARNING | 事件少但每个 predictor 有足够事件支撑 |
| EPP 5–10 | WARNING | 提示 estimates may be unstable |
| EPP < 5 | WARNING | 强提示，建议 penalized / Firth logistic |
| positive 或 negative class 数量 = 0 | BLOCKER | 无法估计 logistic 模型 |
| perfect separation | BLOCKER | 系数不可正常解释 |

不分 CAUTION——rare event 只要触发就至少是 WARNING，因为会影响模型可靠性。

#### 条件升级规则

- `VARIABLE_DROPPED`：普通控制变量 CAUTION → 核心变量 WARNING → 全部核心 drop BLOCKER
- `BINARY_CORRELATION`：abs(r) ≥ 0.8 升 WARNING
- `TREATMENT_PROXY_CORRELATION`：abs(r) < 0.5 不触发
- `REPORT_RENDER_FAILED`：拆为 `_RESULTS_AVAILABLE`（WARNING）和 `_NO_RESULTS`（BLOCKER）
- Cook's distance：max D 决定 severity，4/n screening 只是阈值

### 3.3 UI 显示

```
Critical Errors（BLOCKER）  → 红色，报告顶部
Warnings（WARNING）         → 橙色
Cautions（CAUTION）         → 黄色
System Notes（INFO）        → 灰色，底部
```

## 4. 通用 Issue 数据结构

所有 issue 统一使用以下结构：

```python
@dataclass(frozen=True)
class GuardrailIssue:
    severity: Severity
    code: str
    message: str
    evidence: Mapping[str, Any] = field(default_factory=dict)
    issue_id: str = ""            # 唯一标识，供 coefficient table 和 UI 引用
    affected_stage: str = ""      # estimation / diagnostics / interpretation / report
    variables: list[str] = field(default_factory=list)
    metric: str = ""              # pearson_r / vif / cooks_d / overdispersion_ratio
    value: float | None = None
    threshold: float | None = None
    template_key: str = ""        # 模板文案 key
    template_params: dict[str, Any] = field(default_factory=dict)
    recommended_action_key: str = ""
    is_user_action_required: bool = False
```

Issue 通过 `to_dict()` 序列化时，以上字段全部写入。

## 5. `diagnostic_summary.json` — 泛化 JSON Schema

文件位置：`runs/{run_id}/diagnostic_summary.json`

`schema_version: "1.0"`

### 5.1 `run_status` — 全局状态

```json
{
  "model_fit_status": "success",
  "report_render_status": "success",
  "has_blockers": false,
  "has_warnings": true,
  "model_results_available": true,
  "report_available": true,
  "safe_to_generate_report": true
}
```

前端和报告生成器可直接读取，无需从 issue list 推断。

### 5.2 `model_identity` — 模型身份

```json
{
  "model_family": "ols_robust",
  "model_label": "OLS with robust standard errors",
  "y_variable": "continuous_score_y",
  "x_variables": ["x1_budget", "x2_exposure", "..."],
  "n_observations": 700,
  "n_predictors_original": 10,
  "n_predictors_after_encoding": 14,
  "dataset_kind": "cross_section",
  "interpretation_mode": "associational"
}
```

`n_predictors_original` = 用户选的 X 数量。`n_predictors_after_encoding` = dummy coding 后进入模型的 predictor 数量。两者区分可消除"10 个 X 为什么变成 15 列"的困惑。

### 5.3 `preprocessing` — 预处理状态

```json
{
  "variable_roles": {
    "possible_treatment": ["x8_treatment"],
    "possible_proxy": ["x10_interaction_proxy"],
    "possible_categorical": ["x7_region_code"],
    "possible_exposure": [],
    "id_variables": [],
    "time_variables": []
  },
  "categorical_encoded": [
    {"variable": "x7_region_code", "n_levels": 4, "reference": "region_1", "method": "treatment_dummy"}
  ],
  "exposure_variable": null,
  "variables_dropped": [],
  "coercions_applied": [],
  "column_count_after_encoding": 15
}
```

`variable_roles` 记录系统对每个变量角色的判断。后续很多 warning 是由"角色 + 统计关系"共同触发的——例如 treatment-like 变量和 proxy-like 变量高相关才是 treatment interpretation risk，普通变量之间高相关只是 multicollinearity。

### 5.4 `diagnostics` — 按 severity 分组的 issue 列表

```json
{
  "blockers": [...],
  "warnings": [
    {
      "issue_id": "diag_001",
      "code": "TREATMENT_PROXY_CORRELATION",
      "severity": "WARNING",
      "affected_stage": "interpretation",
      "variables": ["x8_treatment", "x10_interaction_proxy"],
      "metric": "pearson_r",
      "value": 0.791,
      "threshold": 0.7,
      "detail": {"vif_treatment": 4.4, "vif_proxy": 5.7},
      "template_key": "treatment_proxy_high",
      "template_params": {"r": "0.791", "treatment": "x8_treatment", "proxy": "x10_interaction_proxy"},
      "recommended_action_key": "interpret_jointly",
      "is_user_action_required": false
    }
  ],
  "cautions": [...],
  "info": [...]
}
```

每个 issue 必须包含 `issue_id`，供 `coefficients_summary.rows[*].linked_issues` 交叉引用。

### 5.5 `coefficients_summary` — 系数摘要

```json
{
  "interpretation_mode": "associational",
  "rows": [
    {
      "variable": "x8_treatment",
      "display_name": "x8_treatment",
      "estimate": 0.123,
      "std_error": 0.05,
      "p_value": 0.04,
      "significance_label": "significant_5pct",
      "interpretation_guide": "warn_joint",
      "linked_issues": ["diag_001"],
      "template_key": "coef_binary_association_warn_joint"
    }
  ],
  "full_table_ref": "model_results/ols_1.json"
}
```

`interpretation_guide` 取值：`"standard"` / `"warn_joint"` / `"reference_only"` / `"categorical_coef"` / `"do_not_interpret_independently"`。

`linked_issues` 将系数与 diagnostic 关联，报告生成时可为系数附加具体警告。

### 5.6 `model_quality` — 模型质量指标（可变）

```json
{
  "metrics": {
    "r_squared": 0.42,
    "f_statistic": 12.3,
    "f_p_value": 0.001,
    "aic": 1234.5,
    "bic": 1280.1
  },
  "primary_metric_keys": ["r_squared", "aic", "bic"],
  "metric_notes": []
}
```

不同模型类型可放不同 metrics，`primary_metric_keys` 指示报告应突出哪些指标。Logit 可能用 pseudo_r2 替代 r_squared，Poisson 可能用 deviance 和 overdispersion_ratio。

### 5.7 `narrative_contract` — 报告叙述契约

```json
{
  "summary": "OLS model with categorical auto-encoding and treatment-proxy correlation detected.",
  "constraints": {
    "causal_language_allowed": false,
    "allowed_effect_language": "association_only",
    "must_not_claim_policy_effect": true,
    "must_not_interpret_treatment_independently": true,
    "must_acknowledge_treatment_proxy_correlation": true,
    "must_note_categorical_encoded": true,
    "must_not_hide_blockers": true,
    "must_not_change_severity": true,
    "must_not_add_uncomputed_statistics": true
  },
  "required_mentions": [
    "treatment-proxy correlation",
    "categorical auto-encoding"
  ],
  "forbidden_claims": [
    "causal effect of treatment",
    "one-hot encoding required"
  ]
}
```

`narrative_contract` 是规则模板和未来 AI 都必须遵守的契约。它会作为 report 生成或 AI prompt 的硬约束输入。取名不包含 `ai_` 前缀——V1.3.0 用规则模板，V1.3.x 可平滑切换到 AI。

## 6. 报告五段式结构

报告 HTML 改为五段式：

```
1. Facts               — 客观信息，不解释。Model / y / X / N / categorical / dataset kind
2. Data Diagnostics    — 数据结构问题。Categorical 处理、missing rate、exposure 检测
3. Model Diagnostics   — 模型可靠性。Heteroskedasticity、autocorrelation、VIF、Cook's distance
4. Coefficient Interpretation — 每个系数的标准化解释模板
5. Causal Caution      — 默认加注 associational_not_causal
```

### 6.1 系数解释模板

所有系数解释遵循统一模板：

> Holding other selected regressors constant, [variable] is associated with [estimate] change in [y]. This association is [significant / not significant] at [level].

禁止使用：

- "X causes Y"
- "X improves Y"
- "treatment leads to Y"
- "the effect of X"

### 6.2 Causal Caution 模板

**普通模型（OLS/Logit/Poisson）：**

> These estimates are associations, not necessarily causal effects. Statistical significance does not imply causality.

**存在 treatment-like 变量时附加：**

> Because this model includes a treatment-like variable, causal interpretation requires additional design assumptions such as random assignment, parallel trends, valid controls, or an explicit identification strategy. The treatment coefficient should not be interpreted as a standalone causal effect.

### 6.3 Cook's distance 语言

不写：

> 34 observations exceed threshold

改写为：

> 34 observations exceed the conservative screening threshold (4/n = 0.0057). However, no single observation dominates the model (max Cook's D = 0.0172, well below 0.5). This is not a model failure — it is a standard screening check and is generally expected with moderate sample sizes.

## 7. 报告模板 severity 四区

`report.html.j2` 现有三区（Errors / Warnings / Diagnostics）扩展为四区：

```jinja2
{% set blockers = report.warnings | selectattr("severity", "equalto", "BLOCKER") | list %}
{% set warnings = report.warnings | selectattr("severity", "equalto", "WARNING") | list %}
{% set cautions = report.warnings | selectattr("severity", "equalto", "CAUTION") | list %}
{% set infos = report.warnings | selectattr("severity", "equalto", "INFO") | list %}
```

四区显示：

- **Critical Errors**（红，有 blockers 时报告顶部显著警告）
- **Warnings**（橙）
- **Cautions**（黄）
- **System Notes**（灰）

每个 issue 卡片内容：message + 可选 `recommended_action` + 相关变量列表 + metric value。

## 8. 不改动的部分

- 所有统计计算、模型估计、p-value、VIF、诊断检验保持 deterministic code
- `GuardrailIssue` 序列化保持 `to_dict()` 格式向后兼容——新增字段、不改旧字段名
- `errors.json` 继续写入（向后兼容），`diagnostic_summary.json` 作为**新增** artifact

## 9. 测试策略

- `test_severity_enum.py` — Severity 四级枚举 + issue 重分级验证
- `test_issue_structure.py` — 所有 issue 包含必填字段
- `test_diagnostic_summary_schema.py` — JSON schema 验证
- `test_narrative_contract.py` — 各模型类型的 narrative_contract 生成
- `test_report_trustworthiness.py` — 端到端：给定输入 → 报告不包含 forbidden claims
- `test_cook_distance_language.py` — 报告文案包含"conservative screening"而非纯吓人语言
- `test_causal_caution.py` — 报告默认包含 associational 声明

## 10. 三层架构定位

```
Layer 1: Deterministic Code    → 不做改动（当前已满足）
Layer 2: Rule Engine           → V1.3.0 重点：severity 四级 + issue 统一结构 + diagnostic_summary.json
Layer 3: AI Interpretation     → V1.3.0 用规则模板（template_key → 模板文案），JSON schema 为未来 AI 预留
```

## 11. 后续版本衔接

V1.3.2（categorical integrity）和 V1.3.3（interpretation boundaries）直接消费 `diagnostic_summary.json`，改模板文案或加 threshold 档位即可，不需改 schema。
