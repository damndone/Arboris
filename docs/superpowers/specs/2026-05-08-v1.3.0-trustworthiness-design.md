# V1.3.0: Report Trustworthiness — Design Spec

日期：2026-05-08

## 1. 目标

V1.3.0 的目标不是新增统计方法，而是让系统产出的报告**值得信任**。具体来说：

- 用户看到 severity 标签时，能一眼区分"这报告不能用""这个解释要小心""这是系统行为说明"。
- 所有变量系数和诊断结论都在报告里用一致语言解释，不会出现 Facts 说"已编码"但 Diagnostics 说"请考虑编码"的矛盾。
- 报告从结构上区分事实、诊断、解释、风险提示。
- 为未来 AI 深度介入设计好泛化 JSON 接口（schema），当前版本用规则模板填充，不调 AI。

## 2. 范围与非范围

**进入 V1.3.0：**

1. Severity 四级枚举 + 现有 issue 重分级
2. Issue 统一数据结构
3. `diagnostic_summary.json` artifact — 泛化 JSON schema
4. Template registry — 结构化微文案映射（Python dict，不用 Jinja2 碎片）
5. 变量角色判定 — 名称规则 + 数据特征双重判断，confirmed/candidate/rejected 三级 + evidence 记录
6. 报告渲染管线 — diagnostic_summary.json → ReportViewModel adapter → 模板渲染
7. 报告五段式结构（Facts / Data diagnostics / Model diagnostics / Coefficient interpretation / Causal caution）
8. 因果语言防线 — 默认禁止 causal language
9. Cook's distance 语言软化 — screening threshold ≠ 模型失败
10. 报告模板按 severity 四区展示

**不进入 V1.3.0：**

- 新统计方法（DID、ARIMA、ML 等）
- 真实 AI API 调用
- Categorical 变量在描述统计和 variable importance 中的展示修复（进 V1.3.2）
- Treatment-proxy 四档分级阈值落地（进 V1.3.3）
- Per-model 诊断图（deferred）

## 3. Severity 四分法

### 3.1 枚举定义

```python
class Severity(str, Enum):
    BLOCKER = "BLOCKER"   # 报告不应生成，或模型失败
    WARNING = "WARNING"   # 可能影响核心解释，需显著标记
    CAUTION = "CAUTION"   # 模型可用但解释需谨慎
    INFO = "INFO"         # 系统行为说明，不影响结论
```

### 3.2 现有 issue 重分级

#### BLOCKER（Critical Errors）

| Issue | 说明 |
|---|---|
| `INSUFFICIENT_SAMPLE` | 样本不足以估计 |
| `MODEL_FIT_FAILED` | 模型拟合失败 |
| `MODEL_RESULTS_MISSING` | 无法交付任何分析结果 |
| `REPORT_RENDER_FAILED_NO_RESULTS` | 报告坏了，结果也不可用 |
| `PERFECT_SEPARATION` | Logistic 系数不可正常估计 |
| `SINGULAR_MATRIX` | 矩阵不可逆，模型不能估计 |
| `NO_VARIATION_IN_Y` | 因变量无变异 |
| `TOO_FEW_ROWS` | 行数不足以估计 |

#### WARNING（模型可跑，但核心解释受影响）

| Issue | 条件 |
|---|---|
| `TREATMENT_PROXY_CORRELATION` | abs(r) ≥ 0.7，或 abs(r) ≥ 0.9 加注 redundancy |
| `QUASI_SEPARATION` | 模型不稳定但不一定完全失败 |
| `RARE_EVENT_WARNING` | 见下方 EPP 分档表 |
| `OVERDISPERSION_DETECTED` | 影响 Poisson/count model 选择 |
| `AUTOCORRELATION_DETECTED` | Durbin-Watson 显著偏离 2 |
| `HETEROSKEDASTICITY_DETECTED` | 未用 robust SE 时 |
| `REPORT_RENDER_FAILED_RESULTS_AVAILABLE` | HTML/PDF 坏了但 model_results 还在 |
| `MODEL_RESULTS_AVAILABLE_REPORT_NOT_FOUND` | 可展示 fallback summary |
| `EXPOSURE_VARIABLE_DETECTED_BUT_NOT_USED` | 检测到 exposure 候选但 MVP 未支持 offset |
| `VARIABLE_DROPPED`（核心变量） | 用户指定的 treatment/main variable 被 drop |
| `VARIABLE_DROPPED`（大量变量） | 模型结构因 drop 明显改变 |
| `HIGH_VIF` | VIF > 10 |
| Cook's distance max D ≥ 0.5 |
| Cook's distance max D ≥ 1.0（高亮） |
| Cook's distance 极少样本且高影响点主导（模型不可估计时升 BLOCKER） |

#### CAUTION（模型可用，解释需谨慎）

| Issue | 条件 |
|---|---|
| `TREATMENT_PROXY_CORRELATION` | 0.5 ≤ abs(r) < 0.7 |
| `CATEGORICAL_CANDIDATE` | 系统不确定，需用户确认 |
| `BINARY_CORRELATION` | abs(r) < 0.8 |
| `VARIABLE_DROPPED`（普通控制变量） | 因共线性被 drop |
| `HETEROSKEDASTICITY_DETECTED` | 已用 robust SE 时 |
| `RESIDUAL_NON_NORMALITY` | Jarque-Bera p < 0.05 |
| `HIGH_LEVERAGE_POINTS` | 非极端情况 |
| `HIGH_VIF` | 5–10 |
| `VARIABLE_ROLE_ID_AS_PREDICTOR` | ID 变量被用作 predictor |
| `CATEGORICAL_CANDIDATE`（低置信度） | `needs_user_confirmation: true` |
| Cook's distance max D < 0.5（部分 obs > 4/n） |

#### INFO（System Notes）

| Issue | 说明 |
|---|---|
| `CATEGORICAL_AUTO_DUMMY_CODED` | 系统已自动编码 |
| `COERCED_X_DTYPE` | 非数值列自动转换 |
| `PANEL_POOLED_MODEL` | panel 数据但用了 pooled 模型 |
| `SUSPICIOUS_DTYPE` | datetime 列低唯一值 |

#### RARE_EVENT_WARNING — events-per-predictor（EPP）分档

| 条件 | Severity | 说明 |
|---|---|---|
| event rate < 5%，但 EPP ≥ 10 | WARNING | 事件少但每个 predictor 有足够事件支撑 |
| EPP 5–10 | WARNING | 提示 estimates may be unstable |
| EPP < 5 | WARNING | 强提示，建议 penalized / Firth logistic |
| positive 或 negative class 数量 = 0 | BLOCKER | 无法估计 logistic 模型 |
| perfect separation | BLOCKER | 系数不可正常解释 |

不分 CAUTION——rare event 只要触发就至少是 WARNING，因为会影响模型可靠性。

#### 条件升级规则

- `VARIABLE_DROPPED`：普通控制变量 CAUTION → 核心变量 WARNING → 全部核心 drop BLOCKER
- `BINARY_CORRELATION`：abs(r) ≥ 0.8 升 WARNING
- `TREATMENT_PROXY_CORRELATION`：abs(r) < 0.5 不触发
- `REPORT_RENDER_FAILED`：拆为 `_RESULTS_AVAILABLE`（WARNING）和 `_NO_RESULTS`（BLOCKER）
- Cook's distance：max D 决定 severity，4/n screening 只是阈值

### 3.3 UI 显示

```
Critical Errors（BLOCKER）  → 红色，报告顶部
Warnings（WARNING）         → 橙色
Cautions（CAUTION）         → 黄色
System Notes（INFO）        → 灰色，底部
```

## 4. 通用 Issue 数据结构

所有 issue 统一使用以下结构：

```python
@dataclass(frozen=True)
class GuardrailIssue:
    severity: Severity
    code: str
    message: str
    evidence: Mapping[str, Any] = field(default_factory=dict)
    issue_id: str = ""            # 唯一标识，供 coefficient table 和 UI 引用
    affected_stage: str = ""      # estimation / diagnostics / interpretation / report
    variables: list[str] = field(default_factory=list)
    metric: str = ""              # pearson_r / vif / cooks_d / overdispersion_ratio
    value: float | None = None
    threshold: float | None = None
    template_key: str = ""        # 模板文案 key
    template_params: dict[str, Any] = field(default_factory=dict)
    recommended_action_key: str = ""
    is_user_action_required: bool = False
```

Issue 通过 `to_dict()` 序列化时，以上字段全部写入。

## 5. Template Registry — 微文案映射系统

`template_key` 不映射到裸 dict 或 Jinja2 碎片文件，而是映射到一个结构化 **template registry**。

### 5.1 设计选择：Python registry（方案 A）

| 方案 | 决定 |
|---|---|
| A. Python dict registry | **采用** |
| B. 每 key 一个 .j2 文件 | 不采用——文件碎片化、grep 不友好、测试 fixture 复杂 |
| C. 混合 dict + Jinja2 | 不采用——同一 key 走哪条路径需额外判断，增加 report generator 复杂度 |

### 5.2 文件结构

```
workbench/
  narrative/
    __init__.py
    templates.py      # TEMPLATES registry
    render.py         # render_template() + 参数校验
```

### 5.4 render.py

```python
def render_template(template_key: str, params: dict) -> str:
    if template_key not in TEMPLATES:
        raise KeyError(f"Unknown template_key: {template_key}")

    spec = TEMPLATES[template_key]
    missing = set(spec.get("required_params", [])) - set(params)

    if missing:
        raise ValueError(
            f"Missing template params for {template_key}: {sorted(missing)}"
        )

    return spec["text"].format(**params)
```

### 5.5 测试

- known `template_key` + 完整 params → 渲染成功
- unknown `template_key` → `KeyError`
- missing `required_params` → `ValueError`，错误信息列出缺失参数名
- 所有注册的 template 的 `required_params` 都是 `text` 的子集（防止 typo 引起的 forever-missing）

### 5.6 长期演进预留

- V1.3.0：所有微文案走 Python registry
- V1.3.x：报告大段结构仍用 `report.html.j2`（Jinja2），微文案继续走 registry
- 未来：AI 模式下，`narrative_contract` 约束 + template registry 作为 AI prompt 的 few-shot 示例

文件位置：`runs/{run_id}/diagnostic_summary.json`

### 6.1 `run_status` — 全局状态

```json

  "report_render_status": "success",

  "has_warnings": true,
  "model_results_available": true,
  "report_available": true,
  "safe_to_generate_report": true

```

前端和报告生成器可直接读取，无需从 issue list 推断。

### 6.2 `model_identity` — 模型身份

```json
{
  "model_family": "ols_robust",
  "model_label": "OLS with robust standard errors",
  "y_variable": "continuous_score_y",
  "x_variables": ["x1_budget", "x2_exposure", "..."],
```

### 6.3.1 变量角色判定逻辑

角色判定采用 **名称规则 + 数据特征双重判断**，不允许只看列名或只看数据。

#### 角色命名关键词映射

```python
VARIABLE_ROLE_PATTERNS = {
    "treatment": ["treatment", "treated", "intervention", "policy", "program", "assigned", "did", "post"],
    "proxy": ["proxy", "index", "score", "intensity", "interaction"],
    "categorical": ["region", "state", "city", "sector", "industry", "category", "type", "code", "group", "class", "level", "tier", "rank"],
    "exposure": ["exposure", "offset", "duration", "months", "time_at_risk", "population"],
    "id": ["id", "case_id", "user_id", "firm_id", "unit_id", "gvkey", "cusip", "permno"],
    "time": ["date", "time", "year", "month", "week", "quarter", "day"],
}
```

#### Treatment role

| 条件 | 判定 |
|---|---|
| name hint + data is binary/small-finite-group | `confirmed_by_rules`, confidence ≥ 0.85 |
| name hint only, data not binary | `candidate`, confidence ~0.55–0.65 |
| data binary but no name hint | `candidate`, confidence ~0.5（需要 AI 或用户确认） |

**原则：** commercial_use、fleet_vehicle 这类二值变量即使数据是 binary，没有 name hint 就不能自动当 treatment。

#### Proxy role

| 条件 | 判定 |
|---|---|
| name hint + continuous/score-like | `candidate`, confidence ~0.7 |
| name hint + no specific data signal | `candidate`, confidence ~0.5 |
| 与 confirmed treatment 的 abs(r) ≥ 0.7 | 追加 proxy candidate，触发 `TREATMENT_PROXY_CORRELATION` WARNING |
| 与 confirmed treatment 的 abs(r) 0.5–0.7 | 追加 proxy candidate，触发 `TREATMENT_PROXY_CORRELATION` CAUTION |

**原则：** proxy 判定必须结合与 treatment 的相关性。不能只看名字。

#### Categorical role

| 条件 | 判定 |
|---|---|
| dtype string/category | `confirmed_by_rules`, confidence ≥ 0.95 |
| name hint + unique 3–20 + numeric | `confirmed_by_rules`, confidence ≥ 0.85 |
| numeric + unique 3–20 + not binary + no name hint | `candidate`, confidence ~0.5–0.6 |
| numeric + unique 2 (binary 0/1) | `rejected`（视为 binary，不视为 categorical） |

**规则：** `confirmed` → auto dummy-code + `CATEGORICAL_AUTO_DUMMY_CODED` INFO。`candidate` → `CATEGORICAL_CANDIDATE` CAUTION + 不自动编码。

#### Exposure / offset role

| 条件 | 判定 |
|---|---|
| name hint + positive numeric + y is count | `candidate`, confidence ≥ 0.85 |
| name hint + positive numeric + y is not count | `candidate`, confidence ~0.55（可能是普通 X） |
| name hint only, data not positive | `candidate`, confidence ~0.4 |

**规则：** exposure role 带 `context_required: "count_model"`。如果当前不是 count model，不触发 exposure 处理。如果 MVP 不支持 offset，触发 `EXPOSURE_VARIABLE_DETECTED_BUT_NOT_USED` WARNING。

#### ID role

| 条件 | 判定 |
|---|---|
| name hint + unique ratio > 0.95 | `confirmed_by_rules`, confidence ≥ 0.85 |
| name hint + unique ratio 0.5–0.95 | `candidate`, confidence ~0.6 |

**规则：** confirmed ID 默认不作为 predictor。如果用户把 ID 放进 X，触发 `VARIABLE_ROLE_ID_AS_PREDICTOR` CAUTION。

#### Time role

| 条件 | 判定 |
|---|---|
| parseable date/datetime dtype | `confirmed_by_rules`, confidence ≥ 0.9 |
| name hint + values show ordered temporal pattern | `candidate`, confidence ~0.7 |

### 6.3.2 关键原则

1. **角色判定 ≠ 建模处理。** `candidate` 不自动编码，`confirmed` 才自动处理。
2. **角色判定必须进入 diagnostics。** 低置信度 candidate 通过 `CATEGORICAL_CANDIDATE` 等 CAUTION issue 提示用户。
3. **角色判定保留完整 evidence。** 不输出 `"possible_treatment": ["x8"]`，而是输出 name_hints + data_hints + unique_count。
4. **角色判定影响 warning 触发。** treatment-proxy 高相关只有在一方被识别为 treatment-like 时才触发 treatment interpretation risk，普通变量之间高相关只是 multicollinearity。

### 6.4 `diagnostics` — 按 severity 分组的 issue 列表

```json
{
  "blockers": [...],
  "warnings": [
    {
      "issue_id": "diag_001",
      "code": "TREATMENT_PROXY_CORRELATION",
      "severity": "WARNING",
      "affected_stage": "interpretation",
      "variables": ["x8_treatment", "x10_interaction_proxy"],
      "metric": "pearson_r",
      "value": 0.791,
      "threshold": 0.7,
      "detail": {"vif_treatment": 4.4, "vif_proxy": 5.7},
      "template_key": "treatment_proxy_high",
      "template_params": {"r": "0.791", "treatment": "x8_treatment", "proxy": "x10_interaction_proxy"},
      "recommended_action_key": "interpret_jointly",
      "is_user_action_required": false
    }
  ],
  "cautions": [...],
  "info": [...]
}
```

每个 issue 必须包含 `issue_id`，供 `coefficients_summary.rows[*].linked_issues` 交叉引用。

### 6.5 `coefficients_summary` — 系数摘要

```json
{
  "interpretation_mode": "associational",
  "rows": [
    {
      "variable": "x8_treatment",
      "display_name": "x8_treatment",
      "estimate": 0.123,
      "std_error": 0.05,
      "p_value": 0.04,
      "significance_label": "significant_5pct",
      "interpretation_guide": "warn_joint",
      "linked_issues": ["diag_001"],
      "template_key": "coef_binary_association_warn_joint"
    }
  ],
  "full_table_ref": "model_results/ols_1.json"
}
```

`interpretation_guide` 取值：`"standard"` / `"warn_joint"` / `"reference_only"` / `"categorical_coef"` / `"do_not_interpret_independently"`。

`linked_issues` 将系数与 diagnostic 关联，报告生成时可为系数附加具体警告。

### 6.6 `model_quality` — 模型质量指标（可变）

```json
{
  "metrics": {
    "r_squared": 0.42,
    "f_statistic": 12.3,
    "f_p_value": 0.001,
    "aic": 1234.5,
    "bic": 1280.1
  },
  "primary_metric_keys": ["r_squared", "aic", "bic"],
  "metric_notes": []
}
```

不同模型类型可放不同 metrics，`primary_metric_keys` 指示报告应突出哪些指标。Logit 可能用 pseudo_r2 替代 r_squared，Poisson 可能用 deviance 和 overdispersion_ratio。

### 6.7 `narrative_contract` — 报告叙述契约

```json
{
  "summary": "OLS model with categorical auto-encoding and treatment-proxy correlation detected.",
  "constraints": {
    "causal_language_allowed": false,
    "allowed_effect_language": "association_only",
    "must_not_claim_policy_effect": true,
    "must_not_interpret_treatment_independently": true,
    "must_acknowledge_treatment_proxy_correlation": true,
    "must_note_categorical_encoded": true,
    "must_not_hide_blockers": true,
    "must_not_change_severity": true,
    "must_not_add_uncomputed_statistics": true
  },
  "required_mentions": [
    "treatment-proxy correlation",
    "categorical auto-encoding"
  ],
  "forbidden_claims": [
    "causal effect of treatment",
    "one-hot encoding required"
  ]
}
```

`narrative_contract` 是规则模板和未来 AI 都必须遵守的契约。它会作为 report 生成或 AI prompt 的硬约束输入。取名不包含 `ai_` 前缀——V1.3.0 用规则模板，V1.3.x 可平滑切换到 AI。

## 7. 报告五段式结构

报告 HTML 改为五段式：

```
1. Facts               — 客观信息，不解释。Model / y / X / N / categorical / dataset kind
2. Data Diagnostics    — 数据结构问题。Categorical 处理、missing rate、exposure 检测
3. Model Diagnostics   — 模型可靠性。Heteroskedasticity、autocorrelation、VIF、Cook's distance
4. Coefficient Interpretation — 每个系数的标准化解释模板
5. Causal Caution      — 默认加注 associational_not_causal
```

### 7.1 系数解释模板

所有系数解释遵循统一模板：

> Holding other selected regressors constant, [variable] is associated with [estimate] change in [y]. This association is [significant / not significant] at [level].

禁止使用：

- "X causes Y"
- "X improves Y"
- "treatment leads to Y"
- "the effect of X"

### 7.2 Causal Caution 模板

**普通模型（OLS/Logit/Poisson）：**

> These estimates are associations, not necessarily causal effects. Statistical significance does not imply causality.

**存在 treatment-like 变量时附加：**

> Because this model includes a treatment-like variable, causal interpretation requires additional design assumptions such as random assignment, parallel trends, valid controls, or an explicit identification strategy. The treatment coefficient should not be interpreted as a standalone causal effect.

### 7.3 Cook's distance 语言

不写：

> 34 observations exceed threshold

改写为：

> 34 observations exceed the conservative screening threshold (4/n = 0.0057). However, no single observation dominates the model (max Cook's D = 0.0172, well below 0.5). This is not a model failure — it is a standard screening check and is generally expected with moderate sample sizes.

## 8. 报告模板 severity 四区

`report.html.j2` 现有三区（Errors / Warnings / Diagnostics）扩展为四区：

```jinja2
{% set blockers = report.warnings | selectattr("severity", "equalto", "BLOCKER") | list %}
{% set warnings = report.warnings | selectattr("severity", "equalto", "WARNING") | list %}
{% set cautions = report.warnings | selectattr("severity", "equalto", "CAUTION") | list %}
{% set infos = report.warnings | selectattr("severity", "equalto", "INFO") | list %}
```

四区显示：

- **Critical Errors**（红，有 blockers 时报告顶部显著警告）
- **Warnings**（橙）
- **Cautions**（黄）
- **System Notes**（灰）

每个 issue 卡片内容：message + 可选 `recommended_action` + 相关变量列表 + metric value。

## 9. diagnostic_summary.json 与 errors.json 的关系

### 9.1 架构决策

`diagnostic_summary.json` 是 report 和 downstream consumer 的**主契约**。`errors.json` 保留但降级为 **legacy compatibility artifact**，不再作为主判断来源。

```
internal diagnostics state（内存中统一的 issue 列表）
        ↓
        ├── diagnostic_summary.json   ← 主 artifact，report generator 的唯一输入
        └── errors.json               ← legacy projection，向后兼容旧前端/旧测试
```

**核心原则：同一个 internal state 输出到两个文件，不存在文件之间的转换。** 避免 `errors.json → diagnostic_summary.json` 或反向转换导致信息丢失或 severity 漂移。

### 9.2 errors.json 降级处理

errors.json 保留现有格式以保证向后兼容，但添加标记字段：

```json
{
  "schema_version": "legacy",
  "run_id": "abc123",
  "issues": [...],
  "superseded_by": "diagnostic_summary.json"
}
```

新代码不应继续往 errors.json 里加复杂解析逻辑。旧测试和旧前端读取 errors.json 不受影响。

### 9.3 故障时也写 diagnostic_summary.json

即使模型失败，也应输出最小版 diagnostic_summary.json：

```json
{
  "schema_version": "1.0",
  "run_id": "abc123",
  "run_status": {
    "model_fit_status": "failed",
    "model_results_available": false,
    "report_available": false,
    "safe_to_generate_report": false
  },
  "model_identity": {},
  "preprocessing": {},
  "diagnostics": {
    "blockers": [
      {
        "code": "MODEL_FIT_FAILED",
        "severity": "BLOCKER",
        "message": "Model estimation failed."
      }
    ],
    "warnings": [],
    "cautions": [],
    "info": []
  }
}
```

前端和 report generator 始终读 diagnostic_summary.json，不需要在失败时回退到 errors.json。

## 10. 报告渲染管线

### 10.1 架构

`diagnostic_summary.json` 是 canonical input，但 HTML 模板不直接消费它。中间加一层 **ReportViewModel** adapter。

```
orchestrator.py
  ↓
fit model / run diagnostics
  ↓
internal issue registry
  ↓
diagnostic_summary.json          ← 持久化 artifact
  ↓
build_report_view_model()        ← Adapter：将 schema 转为展示层对象
  ↓
template registry renders text   ← 微文案从 template_key 映射
  ↓
report.html.j2                   ← 只做展示，不含复杂逻辑
```

### 10.2 代码结构

```python
# orchestrator.py 中的调用
diagnostic_summary = build_diagnostic_summary(
    issue_dicts, model_results, categorical_vars, routing, ...
)
write_json(diagnostic_summary, run_root / "diagnostic_summary.json")
write_json(_legacy_errors(diagnostic_summary), run_root / "errors.json")

view_model = build_report_view_model(diagnostic_summary, run_root)
render_html_report(view_model, run_root)
```

### 10.3 ReportViewModel 结构

```python
def build_report_view_model(summary: dict, run_root: Path) -> dict:
    return {
        "title": summary["model_identity"]["model_label"],
        "facts": _build_facts_view(summary),
        "critical_errors": [
            {"text": render_template(i["template_key"], i["template_params"])}
            for i in summary["diagnostics"]["blockers"]
        ],
        "warnings": [
            {"text": render_template(i["template_key"], i["template_params"])}
            for i in summary["diagnostics"]["warnings"]
        ],
        "cautions": [
            {"text": render_template(i["template_key"], i["template_params"])}
            for i in summary["diagnostics"]["cautions"]
        ],
        "system_notes": [
            {"text": render_template(i["template_key"], i["template_params"])}
            for i in summary["diagnostics"]["info"]
        ],
        "coefficient_interpretations": _render_coefficients(summary),
        "causal_caution": _render_causal_caution(summary),
        "descriptive_stats": _load_descriptive_stats(run_root),
        "statistical_tests": _load_statistical_tests(run_root),
        "model_diagnostics": _load_model_diagnostics(run_root),
        "model_quality": summary.get("model_quality"),
    }
```

### 10.4 关键原则

- **HTML 模板不直接读 diagnostic_summary。** 模板只迭代 `warnings`、`cautions` 等预渲染好的 list。复杂度在 Python 中。
- **template registry 在 adapter 层调用。** `render_template()` 在 `build_report_view_model` 内部完成，不是模板在调用。
- **无 diagnostic_summary 时不回退到旧 report dict。** 如果 diagnostic_summary 不存在，renderer 显示错误页，不从旧 dict 组装。
- **旧 report dict 废弃。** `facts` / `claims` / `warnings` 原始拼装逻辑逐步移除，统一从 diagnostic_summary 派生。
