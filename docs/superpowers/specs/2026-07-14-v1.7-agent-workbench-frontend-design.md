# v1.7 Agent Workbench Frontend Design

## Goal

Give Workbench a first-class, operable Agent surface without creating a second
product or bypassing lineage truth: a Codex-inspired composer below the Graph,
an `Agent` page in the existing bottom panel, durable session history, visible
context budget, and model selection synchronized with LLM Settings.

## Confirmed product shape

- The Graph remains the primary analysis surface and the source of selected
  node/active-head context.
- A composer appears only in the Graph view, aligned to the center Graph
  column width. It is translucent, rounded on all four corners, and has a
  restrained shadow so it reads as an elevated command surface.
- The composer exposes: prompt input, context-length ring, active model
  selector, scope indicator, submit state, and an accessible error/status line.
- The bottom panel adds an `Agent` tab before `Logs` and `AI activity`.
  The panel owns the full conversation, session status, scope, context
  details, proposal/operation notices, and activity history.
- Composer and panel consume one shared `AgentSurfaceProvider`; submitting in
  either place updates the same session and transcript.
- Model choices come from the active provider in the existing LLM Settings.
  Choosing a model persists through the existing provider update API; there is
  no second model configuration store.

## Codex-inspired principles, adapted to Workbench

The reference is [openai/codex](https://github.com/openai/codex): keep the
composer close to the working surface, show bounded model context, preserve
observable agent status, and keep approval/operation state explicit. Workbench
does not copy Codex's terminal runtime or introduce a free-form agent network.
Its existing Global Main Agent / Chain Agent split, typed tools, proposal
confirmation, and backend-owned lineage remain authoritative.

## Architecture

### Frontend

`AgentSurfaceProvider` is mounted inside the existing `WorkbenchShell`, after
`ForestContext`, `LineageBridge`, and `WorkbenchStateProvider` are available.
It derives a bounded advisory packet for the selected node from the existing
operation-context resolver. The packet is for read-only Agent context only;
the frontend never constructs an executable mutation payload.

`AgentComposer` is rendered at the bottom of `GraphView` after the canvas. It
uses the provider's send method and is not a second chat implementation.
`AgentPanel` is registered in `BottomPanelRegistry` and renders the same
provider state. URL state adds `agent` to the panel enum while keeping `logs`
as the default for backward-compatible URLs.

### Backend

Add `backend/workbench/http/agent_routes.py` with a small HTTP seam over the
existing Agent Harness:

- `POST /agent/sessions` creates a project-scoped Main or Chain session,
  persists a bounded read-only context entry, and returns the active model.
- `GET /agent/sessions/{session_id}` returns metadata and durable message
  history.
- `POST /agent/sessions/{session_id}/turns` runs one bounded AgentCore turn
  through the existing provider-neutral adapter and returns the assistant
  result plus status.
- `GET /agent/sessions/{session_id}/events` replays durable events after a
  sequence number.

The route validates project-root scope, session IDs, question length, and
serialized context size. It returns structured Workbench API errors. This
first HTTP slice is advisory/read-only; mutations remain behind the existing
typed proposal and confirmation executor seam.

### Existing smoke fixes

- Ask AI and report generation must surface successful results and activity
  records in the same mounted UI state that initiated the request.
- Draft save/validate must surface request failures and lifecycle state; a
  locally dirty control must not silently remain dirty after a successful
  backend patch.
- Rerun confirmation must expose structured 409/422 failures and preserve the
  accepted context fields in the request body.
- Vite's default proxy target must match the documented backend port 8000.

## Context and safety

- Context ring displays estimated input tokens, configured model capacity, and
  percentage; unknown capacity is shown explicitly rather than as zero.
- Server caps serialized advisory context at 24,000 characters and prompt
  input at 4,000 characters for this slice.
- Agent responses are rendered as advisory text. No model text is interpreted
  as an operation. Any future mutation must arrive as a typed proposal and
  pass the existing context revalidation/confirmation path.
- Session and event logs are append-only project-local artifacts and are
  reloadable after the browser refreshes.

## Acceptance criteria

1. Graph route shows the composer with accessible prompt, model, context ring,
   and submit controls; Graph tests verify layout and keyboard submit.
2. Bottom panel has an Agent tab; composer and panel show the same transcript.
3. A submitted prompt creates/reuses a durable session, displays the answer,
   and survives a reload through the session GET endpoint.
4. Provider/model changes in LLM Settings are reflected in the composer; a
   composer model change uses the existing provider update seam.
5. Failed AI, draft, and rerun calls display actionable errors; no request
   remains indefinitely disabled without a status.
6. Existing focused tests remain green, quick gate passes, and full gate is
   rerun before this implementation stage is called complete.

## 2026-07-14 usability revision (approved)

The original first-class Agent surface is retained, with the following
interaction corrections:

- The Graph composer is the only Agent input surface. The bottom `Agent` tab
  is terminal-only and must not render a second textarea, model selector, or
  context control.
- The bottom panel prioritizes the durable transcript. Pending proposals are
  rendered in a bounded action rail that is visible only when confirmation is
  required; session status and errors stay in the terminal header/status line.
- Assistant messages use the existing deterministic Markdown renderer so
  headings, emphasis, lists, and code are readable instead of exposing raw
  `##`/`**` markers. Tool entries remain compact typed status lines.
- The composer context ring is an actual control with a popover. The ring has
  fixed equal dimensions and an inner surface so it remains circular in both
  themes and at responsive widths. Unknown capacity is explicit.
- `Home`/`Workbench` and the theme control share one compact navigation row;
  the visible `Local Econometrics Workbench` heading is removed from the
  application chrome.
- LLM Settings is the source of truth for provider, API key, model mapping,
  default model, and model refresh. The Agent selector consumes the same
  provider records and persists changes through the existing provider API.
  DeepSeek Flash/Pro are exposed through the provider's verified model records
  and labels, never as an unpersisted frontend-only choice.
