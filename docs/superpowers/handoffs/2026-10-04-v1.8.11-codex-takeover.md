## 6. 硬规则（必须遵守）

**正确性**
1. 统计数字只由确定性代码产生。不适用的方法明确拒绝并给出带代码的错误，**不静默降级、不静默换方法**（例如不得静默把 α 固定为 1，不得把 z 当 t 用）。
2. 每个新数字都有 Stata 或 R 对照；比较最终报告的量（统计量、自由度、p 值），不只比中间量。R 的 `glm` 标准误取自上一轮迭代，需要时从最优点再算一次。
3. 一个引擎替换了方差（聚类、抽样设计等），所有读推断信息的地方（结果包、推断核心、诊断、Agent、界面）都要读替换后的那份。
4. 在 Agent 规划器里拒绝的组合，在流水线（HTTP、CLI、Agent 三个入口）里也要拒绝。
5. 一个默认值要在每个入口（界面、HTTP、Agent、Notebook、草稿）按模型族解析；某个入口里写死的默认值会悄悄覆盖模型族自己的声明（第 2 步刚修过这类问题）。

**架构**
6. 能力按性质声明、可组合，不写死流程。共享代码里**不写模型族名字字面量来分支**（`tests/test_family_literal_ratchet.py` 会检查）；后估计对哪些族开放由 `postestimation/registry.py` 的 `VALIDATED` 与 `admission.py` 推导。
7. 新能力和新选项必须登记进能力目录，Agent 能用自然语言调用（可达性守卫测试覆盖）。
8. 新模型族准入五项：声明、对照、结果信封、台账分类、真机评测用例（`backend/workbench/admission.py`）。

**流程**
9. 开发线：只能用 `scripts/devline_control.py`（`append` / `verify` / `retrospective` / `rescope-context`），**不得手工编辑 `.agent/devlines/**`**。重要的失败、缺口、审查结论、gate、状态变化要记事件。事件 JSON 必须带 `event_id`、`incident_id`（UUID）、`schema_version: 1`、`type`、`stage`（只能是 design / implementation / review / gate / integration / release）、`subtype`、`timestamp`、`cause`、`cause_status`、`impact`、`lesson`、`lesson_key`、`preventability`、`resolution`、`evidence`（`kind`、`observed_at`、`ref`、`sha256`）、`links`；状态变化另加 `state_from` / `state_to`（当前状态 `STEP_0_COMPLETED`，之后用 `STEP_<n>_COMPLETED`、`GATE_PASSED`、`RELEASED`）。事件文件放在仓库内临时路径（如 `.agent/tmp/e.json`），append 后删除。参照 `.agent/devlines/v1-8-10/events.jsonl` 的写法。
10. 每完成一个交付就提交；不留跨天未提交的改动。
11. **不 push、不 merge 到 main、不打 tag、不建 GitHub Release，除非用户在对话中明确同意。** 绝不自动删除 worktree、分支、tag、stash 或缓存。
