# AI-native 定位：对标 SPSS/Stata，但不止于模仿

> 类别：`roadmap/` — 长期产品方向，**长活文档**，就地更新，不归档。
> 2026-08-04 立，由 v1.8.7 起手时的产品定位讨论固化而来。
> 本文件**不定义任何版本的范围**。范围的唯一权威始终是该版本自己的设计文档。

---

## 0. 一句话

> Workbench 要覆盖 SPSS/Stata 被真正使用的那部分能力，但在 LLM/Agent 有明确优势的地方
> **超过**它们，而不是模仿它们。前提是：数值的准确性与执行的安全性是地基，
> 地基不因为「我们是 AI native」而松动——恰恰相反，正因为 AI 深度参与，它必须更硬。

---

## 1. 支点：AI 的优势在「提问」，不在「回答」

这是本文件所有判断的来源，也是评估任何「要不要让 AI 做这件事」的第一把尺子。

| | 例子 | 问错的代价 | 价值 |
|---|---|---|---|
| **让 AI 回答** | 「这个系数是多少」 | 一篇论文的结论是错的 | 无（确定性引擎更快更准） |
| **让 AI 提问** | 「这 20 列是不是量表」<br>「这个模型的前提你检验过吗」<br>「换成聚类标准误结论还成立吗」 | 用户说一句「不用」 | 极高 |

**不对称性**：提问的错误代价接近零，回答的错误代价接近无穷。

因此：凡是要把 LLM 放进某个位置，先问一句——**它在这里是提问者还是回答者？**
是回答者，就要重新设计，直到它变回提问者。

这条尺子的一个直接推论：**Agent 的产物应当是 typed proposal 与证据，而不是结论与数字。**

## 2. 四层定位

### 第 0 层 · 数值正确性 —— 不可超越，只能追平并证明

系数、标准误、p 值、置信区间、设计自由度必须由确定性引擎计算。
**LLM 在这一层一寸都不能碰。**

而且这里要求比 SPSS/Stata 更严格：它们靠数十年声誉背书，我们没有，
只能靠逐位对照的证据。每项能力必须按三选一如实标注验证等级：

```
对 X 逐位验证  /  仅内部一致性测试  /  未对外部实现验证
```

用同一个执行引擎复核**不算**外部验证（用 statsmodels 核对 statsmodels 算出的结果，
等于自己批自己的卷子）。

> 反面教材：v1.8.6 的 `frequency_weight` 被执行成分析权重语义，加权 run 的每一个
> p 值和置信区间都是错的。**所有测试全绿。** 它不是被测试发现的，是被独立实现发现的。

### 第 1 层 · 认知负担 —— AI 明确胜出

SPSS/Stata 最大的门槛从来不是「跑不出来」，是**不知道该跑什么**。
Stata 上千条命令，SPSS 上百个菜单项，选择本身就是专家知识，而它们不提供这份知识。

属于这一层的：

- 从研究问题 + 数据形状 → 备选方法及其代价（不是替你选，是把选项和代价摊开）
- 元数据补全（测量级别、变量角色、结构声明）
- 前提自动检验并用人话解释后果
- 把「N 次手工操作」压缩成「1 次确认」

**这一层是护城河的主体。**

### 第 2 层 · 记忆与可追溯 —— 架构已经赢了，且不靠 LLM

Graph + lineage 对 do-file 是降维打击：跑了 40 个模型，SPSS/Stata 用户靠自己起文件名，
Workbench 有一张可回溯、可 fork、可对比的有向图。

**这一层的胜出与 LLM 无关**，是既有资产。不要把它算进「AI 带来的优势」里，
也不要为了显得 AI native 而把它重做成 LLM 驱动。

### 第 3 层 · 结论纪律 —— 最值钱，也最容易搞砸

过度解释检测、稳健性提议、「你这个结论在什么条件下会翻」。
SPSS/Stata 完全不管这一段——它们输出数字，从数字到论文里那句话，全靠人。

**但必须是 AI 提出质疑，不是 AI 下结论**（回到 §1 的尺子）：

- ✅ 「要不要也看看聚类标准误」「这个结论依赖 X 假设，是否检验过」
- ❌ 「因此 X 导致 Y」「模型 A 优于模型 B」

这条线一旦模糊，第 0 层所有的严谨都白费。

## 3. 永久红线

不因为版本、需求或「AI native」而松动：

- **AI 不产出正式数字。** 统计量一律来自确定性引擎。
- **AI 不改结果语义。** 系数、标准误、result identity 的含义不由 LLM 决定。
- **AI 不绕过确认。** 改数据、改图、产出正式结论必须走
  `typed → validate → confirm → execute → verify → lineage`。
- **AI 不生成自己的证据。** proposal 中的证据字段必须由后端确定性抽取，
  agent 只能**引用**，不能**生成**。否则 LLM 会编造出看起来很有道理的理由。
- **fail-closed 优于静默降级。** 做不到就明确拒绝并说明缺什么，
  不要给一个「能跑但对不上」的结果。

> 三条系统不变量（roadmap 既有，任何版本不得违反）：
> 没有类型的内容可以解释、不能执行；没有验证的实现可以实验、不能产出正式数字；
> 没有 lineage 的结果可以预览、不能成为 Workbench 结论。

## 4. 依赖关系：为什么地基必须先修

**第 1 层与第 3 层全部架在第 0 层之上。**

如果 svy 的方差估计本身是错的，一个「聪明地建议你用 svy」的 agent
**比没有这个 agent 更糟**——它会自信地把用户导向一个错误答案，
而且因为建议听起来很专业，用户更不会去怀疑。

所以排期原则是：**每开一块第 1/3 层能力，它所依赖的第 0 层必须已经有外部 oracle 证据。**
不允许「先做聪明的建议，正确性以后补」。

---

## 5. 「几乎全部功能」怎么落地

Stata 官方命令上千条，其中大半在目标场景里从未被使用。
逐条对标既不可能也不划算。分层框架给出更实际的排法：

- **第 0 层只需要覆盖真正被用的那部分**——回归、方差分析、抽样设计、面板/DID、
  有序/多项/计数、生存分析——把它们做到**可证明地对**；长尾按真实需求补。
- **第 1、3 层才是别人抄不走的东西。**

> 追平是入场券，超越才是护城河。入场券不必买最贵的那张。

## 6. 模式参考：「AI 备料 + 人确认」

v1.8.7 的测量级别声明是这个模式的第一个实例，后续第 1 层能力应照它扩：

```
后端确定性抽取证据
    → agent 扫描、归类、拟一份批量 proposal（证据只引用不生成）
    → 拿不准的老实标为存疑，不塞进提议凑数
    → 用户看证据，一次确认
    → typed execute → child 节点 + lineage
```

要点：

1. **成本压缩是 agent 的主要价值。** 一份 50 列的问卷，让用户手标 50 次，
   结果是没人标——功能等于不存在。压成 1 次确认才有人用。
2. **证据必须可核。** 摊开给用户看的是后端抽出来的原文（值标签、取值范围、缺失率），
   不是「AI 认为」。
3. **存疑要老实说。** 宁可少提议几列，不可为了显得聪明而把没把握的塞进去。
4. **按钮永远是人按的。**

## 6A. 架构约束：可组合，而不是可枚举

> 2026-08-04 用户定：**按模块化做，实现最大扩展性；不写死公式与死流程，
> 要能像编程那样自由组合；充分考虑 Agent 接入适配性。**
> 终极愿景：自然语言调用 Agent 实现 Workbench 全部能力，
> 并能在可控环境下自主写算法/模型，**验证通过后应用**。

### 6A.1 判据：正交组合 vs 枚举矩阵

每当出现「A 种能力 × B 种配置」时，默认答案是**正交组合**，不是 A×B 的支持表。

> **反模式**：手写一张「哪个模型族支持哪种设计」的矩阵。
> 后果是加一个估计量要改配置层，扩展性归零。

> **正模式**：把 A 与 B 拆成独立对象，**组合合法性由可推导的性质决定**。
> 加 A 不碰 B。

v1.8.7 的 `Design × Estimator × Variance` 是第一个按此约束落地的实例，
其 A1-14「正交性证明」验收（临时注册的合成估计量跑通完整路径而不改设计层）
是这条约束的可执行检验形式，后续同类设计应照此立验收。

### 6A.2 Agent 适配的三条硬要求

1. **能力可发现** —— agent 必须能从能力投影推导出「什么能组合」，
   不得要求 agent 硬编码支持列表。
2. **失败可推理** —— 非法组合返回 **typed 失败**：机器可判定的 reason code
   + 缺失前提清单。一句自由文本不算，agent 无法据此换路。
3. **契约即接入点** —— 新能力通过声明接入（`PackDeclaration` / `ModelFamilyContract`
   这类），而非修改中心文件。既有 pack loader 已具备完整注册面的快照回滚
   （失败的声明不得留下 handler / stage / action / capability），这是为
   第三方与自研代码准备的正确形状，不要绕过它另建通路。

### 6A.3 「自主写算法，验证通过后应用」的依赖链

这条愿景当前尚未开放，原因有**两条，性质不同，不要混写**：

**① 策略限制（用户所定，未来再放开）**

`V1.8.3-CAPABILITY-EXT` 中「运行时禁止任意安装」是**用户设定的策略边界**，
不是技术不能。它按用户意愿在未来单独立项时重新裁定，
本文件不代其决定放开条件。

**② 技术前置（已在 BACKLOG 记录）**

```
自研/扩展能力从 experimental 晋升 verified
    ⛔ 被 ARTIFACT-SCHEMA-REGISTRY 阻塞
       原因：只知道「它产出一个 table」不足以信任外部 Adapter 的产物
```

①放开后②仍然成立：即使允许自主写算法，产物 schema 不可协商时，
它也只能停在 experimental。两条都清了，这条愿景才完整成立。

验证判据 BACKLOG 已定，三档，不得放宽：

| 情形 | 判据 |
|---|---|
| 有 oracle | 逐元素对照 |
| 无 oracle 但有可推导性质 | 性质 / 模拟回收检验 |
| 两者皆无 | **只能停在 experimental，永不升 verified** |

因此依赖顺序是：

```
Artifact payload schema 声明与协商
  → 自研能力的产物可被理解
  → 三档验证判据可执行
  → experimental → verified 的晋升通道成立
  → 「验证通过后应用」才是一句有意义的话
```

**在此之前，沙箱里写出来的东西可以实验，不能产出正式数字**
（这正是三条系统不变量的第二条）。

各版本应做的是：**保证自己的扩展点是这条链的正确形状**
（如 v1.8.7 的 `(data, weights) -> params` 估计量契约，
使自研估计量能自动继承设计方差与 oracle 工装），而不是提前实现整条链。

## 7. 已识别、待单独立项的方向

### 7.1 重复横截面的两阶段设计（由 v1.8.7 讨论析出）

「时间序列 + 抽样设计」不组合——抽样设计描述从**有限总体**抽单位，
时间序列是随机过程的**单条实现**，不存在被分层 PSU 抽样过的「时间点总体」。

但相邻的真需求存在，且 SPSS/Stata 也做不好：

```
重复横截面（CPS 月度、CGSS 各期）
  → 每期算设计基础的估计值（带正确的设计方差与 degf）
  → 再把这串估计值当时间序列建模（含估计误差的传播）
```

这是**两阶段架构**，不是给 ARMA 配 strata/PSU。关键难点在第二阶段要正确传播
第一阶段的抽样误差，而不是把估计值当作无误差观测。单独立项。

### 7.2 判断某能力能否加抽样设计的通用判据

> **这个估计量是不是数据的确定性函数？**

是 → 重复权重就能给它设计方差，且能对 R `survey::withReplicates` 逐位对照
（重复权重不需要估计量光滑，也不需要推导影响函数——它把整个估计量重跑一遍）。

**不要用「R `survey` 里有没有对应的 `svy*` 函数」作判据。** 这条判据在 v1.8.7
设计讨论中被实测推翻两次，按它会误排除分位数回归、IV/2SLS、面板 FE 与 DID
——而这四类实测全部可做且可验证。
