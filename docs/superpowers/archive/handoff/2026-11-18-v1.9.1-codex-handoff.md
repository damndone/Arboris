## 开始前先做三件事

1. `git log --oneline -5`，确认 HEAD 就是交接提交或它之后的提交；工作树必须干净。
2. 运行 `.venv/bin/python scripts/handoff_check.py check docs/superpowers/handoffs/2026-11-18-v1.9.1-codex-tasks.json --partial`，
   应输出 6 个 `open` 任务和 `0 problem(s)`。
3. 读完下面的“规则”一节再动手。

## 规则（校验脚本会逐条检查）

| 规则 | 怎么查 |
|---|---|
| 一次做一个任务，按 C1 → C6 的顺序；C1 发现的失败只记录，不在 C1 里修 | 每个提交只能改它所属任务的 `allowed_paths` |
| 提交标题写任务号，例如 `fix(tests): isolate AR fixture (C6)` | 标题没有 `(Cn)` 的提交判失败 |
| 只改清单 JSON 里的 `progress`；任务定义一个字都不改 | 和首次提交的版本逐字段比较 |
| 改了已有测试的任何一行（删、改断言），要在 `progress.Cn.test_changes` 写路径和原因；能不改就只新增测试 | 提交里删除了测试行而没有声明，判失败 |
| 证据日志一律用 `handoff_check.py log` 跑，不要 `cmd \| tail`：管道返回的是 tail 的退出码，曾因此把失败的测试当成通过提交 | 日志里记录命令自己的退出码、当时的提交和工作树是否干净；之后再改代码，日志作废要重跑 |
| 犯的每个错都写成 lint 规则或回归测试：`scripts/lint_rules.py`（后端）、`frontend/eslint.config.js` 的 `RESTRICTED_IMPORTS`（前端跨层导入，ESLint `no-restricted-imports`），不写进 `AGENTS.md` | `AGENTS.md` 在禁止路径里 |
| 做不了就把任务标为 `blocked` 并写明原因，然后做下一个；不扩大范围、不换做法凑通过 | `blocked` 不算完成，会在最终输出里列出来 |
| 交接期间 Claude 若在同一分支提交，标题带 `(outside-handoff)`；这类提交会列在输出里，碰到任何任务的允许路径即判失败 | 两个人不改同一个文件 |
| 每做完一个任务运行一次 `check --partial`；全部做完运行 `check`（不带 `--partial`），**把输出原样贴给用户** | 最终输出就是验收结果 |

**不许做**：真实模型调用、评委、留出集、M5、性能门计时；push、merge、tag、发版；`pip install`、`npm install`；
修改受保护路径（`contracts/model`、`econometrics`、冻结的评测文件）；删除证据、数据或 worktree；
修改 `scripts/handoff_check.py`、它的测试或本页。遇到需要这些的情况，停下来问用户。

## 记录进度

`progress` 的格式（每个任务一项）：

```json
"progress": {
  "C1": {"status": "done", "commits": ["<sha>"], "notes": "full gate 跑了 41 分钟"},
  "C6": {"status": "blocked", "blocked_reason": "broken_event_sink 30 次里挂 2 次，根因在 events.py，不在允许路径内",
         "test_changes": [{"path": "tests/test_cli_agent.py", "reason": "原断言依赖调度顺序"}]}
}
```

`status` 取 `open`、`in_progress`、`blocked`、`done`。改 `progress` 的提交标题写 `(handoff)` 或任务号。

证据日志：

```bash
.venv/bin/python scripts/handoff_check.py log docs/superpowers/handoffs/2026-11-18-v1.9.1-codex-tasks.json C1 backend-full -- sh -c 'PYTHONPATH=backend:scripts .venv/bin/python -m pytest tests -q -p no:cacheprovider'
```

日志名必须是清单里 `done_when` 的 `name`；`suggested_command` 是建议命令，`must_match` / `must_not_match` 是判据。
日志写在 `local/handoff/2026-11-18-v1.9.1-codex/`（不进 Git）。

devline 事件（C2、C3 需要）：照常用 `scripts/devline_control.py append`，`links` 里加一项
`handoff:2026-11-18-v1.9.1-codex:C2`（换成对应任务号）。

## 各任务做法

### C1（P0）把当前候选完整验一遍，只记录不修

按清单依次跑八个日志（`frontend-eslint` 跑 `eslint . --max-warnings 0`）。`host-gate` 必须在宿主终端独占运行（嵌套沙箱会假报 containment 失败）：先停掉预览服务，
确认没有别的 pytest、vitest 或 gate 在跑。全量后端约 16 分钟，gate 更久。
结果写进 `docs/superpowers/evaluations/2026-11-17-v1.9.1-candidate-verification.md`：每个日志一行（通过数、失败数、耗时、日志路径）。
有失败就写清失败的测试名和第一行错误，**不在 C1 里修**：八个日志全部通过 C1 才能标 `done`；
有失败就标 `blocked`、写明失败项，继续做 C2，失败项交给用户决定由谁修。

### C2（P1）把已记录的错误写成 lint 规则

每条规则：在 `RULES` 登记，`origin` 写清来自哪次缺陷；在 `tests/test_lint_rules.py` 加一个用例，证明它能抓住原来那段代码。
报错信息要写“该怎么改”（改走哪个公共接口），照 `restricted-imports` 的写法。

1. `monkeypatch-stub-signature`：`tests/` 里 `monkeypatch.setattr(<workbench 模块>, "<函数名>", <lambda 或本地函数>)`，
   替身的位置参数个数和被替换函数对不上时报错。来源：`9516c643` 把 `native_math._pair_ranks(matrix, ...)` 改成 `(a, b, ...)`，
   `tests/test_default_path_speedups.py` 的替身还是旧签名，统计阶段逐位一致的守卫抛 TypeError，而那组测试不在 Codex 跑的标准组里。
   当前树上若查出别的违例，修掉；改已有测试行要在 `test_changes` 写原因。
2. `private-cross-package-imports`：跨顶层包导入下划线名字（如 `http` 导入 `repository.run_repository._read_manifest`），
   以当前树为基线存进 `scripts/lint_baselines/private_imports.json`（2026-11-17 实测 547 处），只拦新增；
   报错写“在 <模块> 导出一个公共名字再导入它”。基线只能减不能增。
3. `agents-md-pinned`：把 `AGENTS.md` 的 SHA-256 固定在规则里；文件一变就报错，信息写
   “教训写成 lint 规则或测试；AGENTS.md 的改动需要用户批准并更新固定值”。来源：用户 2026-11-17 的要求。
4. 回放守卫（回归测试，不是 lint）：`scripts/agent_eval_run.py --replay-round <轮次>` 遇到该轮 `run.py`
   设置了项目拒绝规则、而命令行没加 `--project-deny-policy` 时，拒绝运行并说明要加这个参数。
   测试放 `tests/test_agent_eval_replay_deny_policy.py`。来源：`e83e9c7b`（2026-11-10）开发轮回放在第一次拒绝处就分叉，结论作废。

完成后跑全量后端（日志 `backend-full`），记一条 devline 事件。
