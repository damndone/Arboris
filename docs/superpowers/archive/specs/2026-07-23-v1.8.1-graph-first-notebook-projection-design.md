# Workbench v1.8.1：Graph-first Notebook 投影与证据门控推荐

状态：双重设计审查完成；implementation plan 已锁定，等待执行方式确认。

日期：2026-07-23

适用工作区：`.worktrees/integration-v1.8.1`

## 1. 目标

Workbench Notebook 是 Graph 的叙事视图，不是第二套执行系统。Notebook 应该把一条分析演化线讲成：

```text
用户目标
→ 数据检查
→ Agent 推荐路径
→ 用户选择
→ Draft / Graph branch
→ Run / Artifact
→ 诊断
→ 备选方案
→ Compare
→ 结论
```

每个阶段都引用既有事实对象：`Dataset`、`Node`、`Draft`、`Proposal`、`Run`、`Artifact`、`Diagnostic`、`Compare`。

本设计同时解决两个当前缺口：

1. 当前 Notebook 默认创建没有 `active_head_run_id` 的独立 Notebook/RunFamily，因此 Context Compiler 看不到正在分析的 Graph 和数据。
2. 当前 planner 以固定 ETS / ARMA-GARCH 列表和固定文字 rationale 生成候选，首推没有真实数据证据，也没有近似候选的“不强排”语义。

## 2. 不变量

### 2.1 Graph 与执行对象是事实源

Notebook 不拥有一套独立的模型参数、执行状态、结果或 active head。

- Notebook 的叙事内容是对 Graph、Draft、Run、Artifact、Diagnostic、Compare 的读取投影。
- 选择 Option 只会 materialize 一个已有系统认可的 `PipelineDraft` / Graph branch；不会在 Notebook 内另存一份可执行参数。
- 正式执行只能通过现有 Draft / Run 路径发生。
- Notebook reload 后必须能够仅凭既有对象重建叙事，不依赖浏览器内存状态。

未 materialize 的 Option 与用户 decision 是 Graph 尚不存在的意图事实，因此仍由
append-only Notebook proposal log 作为其规范记录。它们不得被误称为执行事实；一旦
materialize，Draft / Graph / Run 立即成为可执行事实的唯一来源。

### 2.2 Option 是未 materialize 的 typed branch proposal

未选择方案不是自然语言备注，也不是预先创建的空 Graph 分支。它是一个引用当前上下文的结构化 proposal，至少包含：

```text
option_id
option_revision
title
typed_proposal
assumptions
expected_artifacts
risk_level
source_context_hash
freshness_dependency_fingerprint
evidence_refs
comparative_claims
recommendation_decision_id
recommendation_status
lifecycle_status
```

Option 不能绕过 proposal schema、capability registry、freshness gate 或 Artifact Contract。

现有 `NotebookOptionRevision@1.0` 是严格键集契约，不能向其中静默塞入这些字段。
本设计新增 `NotebookOptionRevision@1.1` 与独立的 `RecommendationDecision@1.0`：新写入
只产生 1.1；读取 1.0 时保留其历史内容，但标为 `legacy_unverified` 叙事，不能显示为
`recommended`，也不能直接 materialize，必须对当前 Graph context 重新验证并写出 1.1
revision。前端和服务端必须显式支持这两个版本，拒绝未知版本。

### 2.3 raw data 只能通过有界检查进入 Agent 上下文

完整 raw data 永远不直接塞入模型上下文。Workbench 提供受控的 Data Inspection 能力，对真实 raw data 执行有界检查并生成可追溯证据：

- 数据规模、字段类型、缺失率、唯一性、重复观测；
- 时间索引、频率、连续性、间隔异常；
- 分布、异常值、趋势、季节性或其他已注册诊断；
- 有明确行数上限的样本片段；
- 已存在的 Graph diagnostics、Artifact 摘要和执行状态。

每项证据都必须包含来源引用、检查协议版本、结果 hash、预算和遗漏信息。数据过大时必须显式报告 omission；关键证据被截断时，推荐状态只能是 `insufficient_evidence`，不能继续输出可执行的首推。

### 2.4 首推必须由证据门控

Agent 可以提出候选、选择检查和解释结果，但不能仅凭惯例或自然语言把某方案标成首推。

只有经过 Recommendation Validator，且满足本设计第 6 节的条件，Option 才能获得 `recommendation_status=recommended`。

如果候选方案近似、证据不足或比较协议不能证明差异，系统必须允许没有首推。

## 3. 目标架构

### 3.1 Graph-bound Notebook（含 pre-run Dataset 投影）

当项目已经存在 Graph head 时，Notebook 路由解析当前 focused head，并创建或打开绑定该
run family 的 Notebook。它不能再默认创建一个没有来源的独立分析线。

pre-run 也不是例外：上传已进入 content-addressed upload store 的 Dataset 可以先创建
`origin=notebook` 的 persisted RunFamily，并作为不可变 Dataset source 绑定 Notebook。它
没有 Run / active head，但用户选择后必须 materialize **现有的 genesis PipelineDraft**；该
Draft graph 就是第一个可执行事实，而不是 Notebook 内的第二份模型状态。

规则如下：

```text
有 focused Graph head → 绑定该 run 所属的 persisted RunFamily + run source
无 Graph head、有已验证 upload → 创建/打开 notebook family + dataset source
无 Graph head、无 Dataset → 只能显示 data-preparation，不得产生 Option
旧的无来源 Notebook → 不静默 rebind；创建带 source 的新 projection 并保留旧记录
```

RunFamily 绑定继续遵守 v1.8.1 的不可变语义。旧 Notebook 不会被悄悄改绑；迁移通过新 Notebook 引用旧 Notebook 的 supersession 关系完成。

Workbench 初始界面的自动入口使用 `default-projection:<run_family_id>` 作为稳定
projection key，并由服务端原子 ensure，避免 React 重挂或多个浏览器标签创建多个默认
Notebook。Notebook 必须持久化严格二选一的 `projection_source`：`run`（`run_id`）或
`dataset`（`upload_sha256`、`filename`、可选 sheet metadata）。这个唯一性只适用于默认
入口；用户显式创建的其他叙事 Notebook 仍可属于同一 family。URL 中显式指定的 notebook
必须先验证 family 与 source 相符，不能因当前 focused run 或上传文件不同而静默改绑。

“当前 head”不是服务端扫描后猜出的全局最新 Run：它是调用方传入并经同 family 校验的
`focused_run_id`。当该值不同于 projection 已绑定的 run source 时，响应将它作为
`current_family_head_run_id` 比较点，显示此事实并使依赖旧 head 的 options stale；不会把
Notebook 的 source 静默改成外部 Run。active head 的推进仍只由现有 Draft / Run 路径的
成功 Artifact Contract 驱动。

### 3.2 Projection source

Notebook response 必须携带投影来源：

```text
run_family_id
projection_source = run | dataset
active_head_run_id?                 ← 仅 run source
focused_run_id?                     ← 调用方当前比较点
current_family_head_run_id?         ← 同 family，绝不由“最新目录”推断
dataset_ref?                        ← 仅 dataset source；sha + filename + sheet metadata
graph_ref / graph_hash
source_manifest
projection_generation
```

Notebook narrative 中的事实段落由这些来源对象生成。只有用户输入、Agent proposal、用户 decision 等尚未 materialize 为 Graph 对象的内容，才作为 proposal/decision 记录出现，并明确标注其非执行事实身份。

### 3.3 Context Compiler 与 Evidence Compiler

推荐上下文分两层：

1. `NotebookPlanningContextV1`：Graph/Run/Artifact/Diagnostic 的有界确定性投影，或在
   pre-run 时为已验证 Dataset source 的有界 profile 投影。
2. `DataEvidencePackV1`：针对推荐所需的 raw-data inspection 结果。

Context Compiler 负责“Agent 看到了哪些事实”；Evidence Compiler/Inspection Registry 负责“Workbench 对真实数据做了哪些检查”。两者都输出 content hash，并写入 Trace 的证据引用。

Agent 不直接读取任意路径、不直接运行未注册代码、不在上下文中接收完整 raw data。Agent 发出的检查请求必须匹配已注册的 typed inspection capability，并经过预算和风险策略校验。

样本片段还必须经过项目既有的数据暴露策略：默认不返回直接标识符列和原始自由文本；
若一个推荐所需的证据不能在该策略与预算内安全提供，结果是 `insufficient_evidence`，
而不是扩大上下文或绕过数据边界。

## 4. 推荐流程

### 4.1 第一阶段：确定性可行性检查

Workbench 先根据真实数据、Graph 和 capability contract 对候选进行硬门控：

- 数据结构是否满足候选模型的输入契约；
- 时间索引和分析单位是否满足模型前置条件；
- blocking diagnostic 是否使候选不可用；
- capability 是否已注册、可执行并能满足 Artifact Contract；
- proposal 的 target、precondition、family 和 context hash 是否一致。

违反硬条件的候选可以进入 `blocked`，但不能成为首推。

### 4.2 第二阶段：Agent 请求受控检查

Agent 接收有界 Context Packet 后，可以提出 typed inspection plan。每个检查请求包含：

```text
inspection_id
capability_id
target_ref
arguments
budget
why_needed
```

Workbench 执行检查，产生：

```text
evidence_id
source_refs
protocol_version
observations
metrics
warnings
omissions
result_hash
```

检查结果写入 content-addressed evidence store，并与本次 context manifest 关联。Agent 只能引用已经存在的 `evidence_id`。

Inspection 与 recommendation probe 是只读、受预算限制的证据计算：它们不得创建
`PipelineDraft`、正式 Run、正式 Artifact，也不得改变 Graph 或 active head。Probe
结果只能作为 Evidence Pack 的不可执行输入；正式数值仍须走 Draft → Run → Artifact
Contract 路径。

Evidence Pack 与 RecommendationDecision 都是 append-only、content-addressed 的项目审计
记录；它们与 Option 一样记录“当时为什么这样建议”，但不保存第二份可执行模型参数。

### 4.3 第三阶段：候选生成与比较

Notebook 规划复用现有 OpenAI-compatible provider 配置与 Agent context boundary，但使用
专用 `NotebookPlanningAgent` adapter 和严格的 typed submit envelope；普通侧边聊天文字、
Markdown 表格或通用 `propose_operation` 成功消息都不是 Notebook option batch。Provider
只能提交 inspection plan 或 option batch，服务端仍是 context、evidence、schema 与
recommendation decision 的权威。provider 不可用时 fail closed，不回退到固定模型列表。

Agent 根据用户目标、Graph context、Data Evidence Pack 和已注册能力生成最多三个 typed options。每个 option 必须说明：

- 当前数据观察到的事实；
- 事实如何支持或削弱该方案；
- 方案的假设和风险；
- 相比每个其他候选的差异；
- 预期 Artifact；
- 需要在正式执行前满足的条件。

Agent 可以提出 `comparative_claims`，但不能自行填入未经 Workbench 计算的数值。所有比较数字必须来自 evidence refs。

## 5. 证据等级

### 5.1 Hard evidence

硬证据来自可验证的契约或直接数据条件，例如：

- 时间索引不满足某模型要求；
- 某模型需要的字段类型不成立；
- blocking diagnostic 已明确否定某种设定；
- 某 capability 无法产出 required Artifact。

硬证据可以直接淘汰候选。若它使某个方案成为唯一可行方案，逻辑判断本身可以形成首推。

### 5.2 Empirical evidence

若多个候选都可行，则调用该 capability 注册的 recommendation protocol，使用相同数据和相同验证边界进行受控比较。协议可包含：

- rolling-origin / holdout 预测误差；
- 残差和稳定性诊断；
- 收敛和数值条件；
- 模型复杂度与额外假设；
- Artifact 完整性和执行风险。

不同模型家族不得默认共享一个未经验证的总分。比较维度、方向、阈值和 tie policy 必须由模型 capability 或分析 contract 声明。
每个 protocol 还必须声明可比较候选 cohort；不存在共同 cohort 的候选只能得到
`insufficient_evidence`，不能把不可比指标换算成伪精确总分。

### 5.3 Heuristic evidence

领域惯例、简洁性、可解释性等可以作为解释和 tie-breaker，但不能单独把近似候选提升为压倒性首推。

## 6. Recommendation Validator

Recommendation Validator 对一个 option batch 生成唯一的
`RecommendationDecisionV1`，而不是让每张 option 卡片独立声称自己是首推：

```text
recommendation_decision_id
batch_id
generation_context_hash
freshness_dependency_fingerprint
evidence_pack_hashes
comparison_protocol_refs
candidate_option_ids
outcome = recommended | tied | insufficient_evidence
recommended_option_id (only for recommended)
reason_refs
```

Option 只保存对该 decision 的引用和自己的派生展示状态。一个 batch 最多有一个
`recommended_option_id`；`tied` 和 `insufficient_evidence` 都没有它。

Decision 的 immutable revision 与相关 Evidence Pack 由 Notebook store 在 option log 之外
持久化并按 `batch_id` 索引；这不是另一套 Graph，而是未 materialize 提案的审计事实。
新的 option revision、revalidation 或 protocol 变化必须创建新的 decision，不得就地修改
既有 recommendation outcome。

### 6.1 recommended

一个 batch 只有同时满足以下条件，才能把其中一个 option 标记 `recommended`：

1. typed proposal 已通过 schema、capability、family 和 freshness 校验；
2. 所有关键前置条件都有有效 evidence ref；
3. 没有 blocking diagnostic；
4. `comparative_claims` 覆盖其他候选，且每条关键差异都能解析到证据；
5. 注册的 recommendation protocol 判断差异超过该协议的推荐门槛，或者其他候选已被硬证据阻塞；
6. 所有证据仍与当前 `freshness_dependency_fingerprint` 一致。

### 6.2 tied / insufficient_evidence

以下任何情况都不能强排首推：

- 预测和诊断结果处于 tie margin 内；
- 关键证据缺失或被预算截断；
- 候选间没有声明可比的 recommendation protocol；
- Agent 的解释没有覆盖为什么胜过其他候选；
- provider 或 inspection 执行失败，且没有可验证替代证据。

系统返回 `tied` 或 `insufficient_evidence`，保留所有结构化候选，并要求用户选择或继续检查。

### 6.3 rank 语义

现有 `rank` 只能作为展示顺序，不能独立表示首推。新增
`recommendation_decision_id`、`recommendation_status` 和 `recommendation_rank`：

```text
recommended + recommendation_rank=1 → UI 显示“首推”
tied / insufficient_evidence        → UI 显示“候选 / 近似 / 证据不足”
blocked                              → UI 显示“不可用”，不可确认执行
```

禁止通过“列表第一个”或“rank=1”绕过 Recommendation Validator。

## 7. Materialize 与 Graph 回流

### 7.1 选择 Option

用户选择只记录决策事实，并重新验证当前 option revision。它不会直接执行。

### 7.2 Materialize Draft

确认后，系统把 immutable typed proposal 转成现有 `PipelineDraft`，并写入幂等的
`OptionMaterialization`。run source 只能走现有 `/pipeline-drafts/from-node`、patch、
validate 的 rerun-child 路径；dataset source 只能走现有 `/pipeline-drafts/genesis`、node
patch、genesis validate 路径。两条路都只把 lifecycle 从 `selected` 推进到 `materialized`，
不启动运行。Materialization 附带：

```text
source_option_id
source_option_revision
source_context_hash
source_evidence_hashes
base_graph_head
run_family_id
source_run_id? / source_model_node_id? / source_op_node_id?
source_node_hash? / source_forest_node_key? / source_context_fingerprint?
dataset_upload_sha256?
```

Draft 是后续编辑和执行的权威对象。若用户修改了 Draft，必须产生新的 Draft revision
或新的 typed proposal 关系，不能静默修改原 Option。Option 后续变 stale 时，只禁止
由它再 materialize 新 Draft；已 materialize Draft 继续受现有 draft hash / validation
gate 管理，不能被 Notebook 的旧 freshness verdict 放行。

只有用户从 Draft UI 或等价的 Draft execute API 明确执行后，lifecycle 才能进入
`executing`。执行记录必须以 `OptionExecution@1.1` 同时钉住 Option revision、
Materialization id、Draft id/hash 和实际 run id；执行失败或 Artifact Contract 失败回到
`materialized`，保留 Draft 供检查或修改，不回退为一个看似从未落地的 selected proposal。

### 7.3 执行与回流

这是 Graph-first 的后续闭环目标，不属于本设计首个 implementation slice。首个切片只
materialize Draft，并让用户使用既有 Draft UI 的 validate/execute 路径；它不新增一条
Notebook 执行器，也不把 Compare 接入 Notebook。

执行沿现有 Draft → Run → Artifact Contract 路径进行。成功后：

- Run 继承 Notebook 的 RunFamily；
- Graph index 写入新的节点和 lineage；
- Artifact Contract 验证结果；
- active head 按现有规则推进；
- Notebook 重新读取 Graph / Run / Artifact / Diagnostic 形成结果叙事；
- deferred options 仍保留，并根据新的 freshness fingerprint 重新显示 fresh 或 stale。

Notebook 不自行写入执行结果，也不维护第三套 active head。

## 8. 生命周期与 stale

Option 的生命周期仍包括：

```text
proposed → selected → materialized → executing → executed
proposed → deferred
deferred → selected
proposed / deferred → rejected
```

`stale` 是 freshness 轴，不是用户决策生命周期。以下变化必须触发重新验证：

- active Graph head 或其 lineage 变化；
- dataset profile、变量定义或数据来源变化；
- analysis contract 或 user focus 变化；
- capability / vocabulary / recommendation protocol 版本变化；
- evidence source hash 变化。

`generation_context_hash` 记录 Agent 实际看到的完整上下文；`freshness_dependency_fingerprint` 只记录会使 proposal 失效的上游依赖。两者不能合并。

## 9. 失败语义

- 没有 Graph head：允许显示数据准备/Genesis 状态，但不得输出可执行首推。
- raw data 超出预算：继续执行不依赖被截断部分的检查；关键证据缺失则返回 `insufficient_evidence`。
- Agent provider 不可用：返回明确的 planning failure，不使用硬编码 ETS/ARMA-GARCH fallback 冒充推荐。
- typed inspection 失败：保留失败证据和原因，不把失败当成“没有问题”。
- Option stale：禁止 confirm/materialize，要求 revalidate。
- Option 与 Graph family 不一致：拒绝并返回 `RUN_FAMILY_MISMATCH`。
- Artifact Contract 失败：Run 可以被记录为执行事实，但不得推进 Notebook 的可信结果叙事或 active head。

## 10. 测试与验收

### 10.1 后端契约

- 使用真实持久化 run 目录构造 fixture，禁止手写一个看似完整但脱离真实 artifact 的上下文。
- Notebook 创建于已有 active head 时，Context Packet 必须包含非空的 run、Graph、dataset profile 和 source manifest 引用。
- Context Packet 不能包含完整 raw data；必须断言预算、omissions 和 evidence hash 的具体值。
- 硬门控能拒绝不满足输入契约的候选。
- 近似候选得到 `tied`，不产生 `recommendation_rank=1`。
- 关键证据被截断得到 `insufficient_evidence`。
- 没有 provider 时不会调用旧的硬编码 planner。
- 一个 batch 不能同时出现两个 `recommended`，也不能在 `tied` / `insufficient_evidence`
  decision 下出现 `recommendation_rank=1`。
- recommendation probe 不能写入 Run、Artifact、Graph 或 active head。
- 每一条 comparative claim 都能解析到具体 evidence ref。
- 选中 Option 后产生带 provenance 的 PipelineDraft；未选择方案仍可读取。
- Graph head 改变后旧 Option 读时变 stale，confirm 被拒绝。
- 执行完成后 Notebook reload 从 Graph / Run / Artifact 重建叙事，浏览器内状态丢失不会丢结果。

### 10.2 前端与浏览器

验收以下状态：

- Graph-bound Notebook loading / ready；
- 无 active head 的 data-preparation 状态；
- evidence 检查中、完成、部分遗漏、失败；
- recommended、tied、insufficient_evidence、blocked；
- 选择、materialize Draft、编辑 Draft、取消；
- deferred Option 保留；
- stale Option 禁止执行；
- 已 materialize Draft 在既有 Graph Draft Registry 中可见并可编辑；
- 选中文本动作生成 proposal 或 Agent side-chat draft，并引用正确的 Graph/Option source ref。

Run / Artifact / Diagnostic / Compare 的 Notebook 自动回流是上述 7.3 的后续闭环，
不作为本 implementation plan 的完成条件。

### 10.3 Gate

- golden 数值保持 0-drift；

## 11. 范围与明确不做

本设计不引入：

- 完整 raw-data embedding；
- 向量 RAG 或跨项目语义检索；
- 任意 Agent 生成代码的正式执行；
- 自动安装依赖；
- 强化学习、reward 或评测标签；
- 未注册模型之间的万能总分；
- Notebook 独立执行引擎或第二套 Graph。

首个实现切片应优先完成：Graph-bound Notebook、真实 Context Projection、Data Evidence Pack、Recommendation Validator、Option → Draft materialize，以及 deferred/stale 的完整保留语义。
