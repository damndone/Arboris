# Econometrics Workbench v1.7 Agent Harness 设计

**日期：** 2026-07-13
**状态：** 已获用户确认，待用户审阅修订稿
**基线：** v1.6.12.1 / 510ff5a
**目标分支：** workbench-v1.7

## 1. 设计结论

v1.7 不是“给 Ask AI 增加一个 rerun 按钮”，也不是只做一个模型修复 Agent。它建立一个通用的 Workbench Agent Harness：

- 一个项目有一个 Global Main Agent；
- 一条分析 chain 有一个 Chain Agent；
- Main Agent 通过结构化 command 管理 Chain Agent；
- 每个 Agent 都运行在明确的 context scope 内；
- AI 可以观察和提出操作，但写操作必须经过 Workbench 的 typed operation、用户确认和执行校验；
- 图节点分叉和 Agent 消息分叉必须同时创建对话分支与谱系 fork 子节点；
- Operation Registry、Proposal、Session、Operation Record 和 Verifier 从第一版起使用通用契约；
- model.rerun 是第一个可执行 operation，数据清洗、节点创建、图连接和报告生成以后通过同一 Registry 接入。

产品目标是让 researcher、咨询公司和商业分析团队可以用自然语言完成可审查的统计分析工作，同时保留谱系、分叉、回滚、比较和报告生成能力。

## 2. 当前基础和本版缺口

### 2.1 已有基础

当前 Workbench 已经具备：

- OpenAI-compatible LLM provider 和 DeepSeek 配置；
- /llm/chat 的节点上下文问答和报告生成；
- 只读 Ask AI context packet；
- 基于 OperationContract 的模型节点可编辑 schema；
- op_overrides、manual patch、context 校验和不可变 child run rerun；
- run family / forest / active head 谱系结构；
- 节点比较和参数、指标、诊断、上游路径 diff；
- typed AI activity，但当前只包含 Ask AI 和报告记录，并存储在前端 localStorage。

### 2.2 本版缺口

v1.7 需要补上：

1. 有状态、可暂停、可恢复的 Agent Session；
2. Main Agent 到 Chain Agent 的层级调度协议；
3. 通用 Tool Registry 和 Operation Registry；
4. 结构化 Proposal、Confirmation 和执行前 precondition 校验；
5. 后端权威的 Agent context 和持久化记录；
6. fork 对话和 fork 谱系的一致映射；
7. 确定性的 run 验证和 diff 记录；
8. 基于 allowlist、scope 和资源限制的 Workbench sandbox；
9. 全局 Agent、chain Agent 和 operation 的可见 UI。

## 3. 术语和身份模型

~~~
run_id
  一次具体 pipeline 执行结果和快照。

run_family_id
  一组拥有共同祖先、可相互比较的相关分析路径。

chain_id
  一条具体的分析分支，由一个 Chain Agent 负责，拥有一个 active head。

agent_session_id
  一个可恢复的 append-only Agent message tree；Main Agent 和 Chain Agent 都是使用该
  SessionRepository 的 AgentCore 实例。

fork_id
  对话分支和谱系分支的共同身份。

operation_id
  Registry 中的通用操作标识，例如 model.rerun、graph.fork。
~~~

一个 run_family_id 可以包含多条 chain；一条 chain 可以关联多个历史 run，但只有一个当前 active head。分叉产生新的 chain 和新的 Chain Agent，原 chain 不被覆盖。

### 3.1 身份持久化和旧数据映射

现有 run 的 `rerun_of` 仍然是不可变 pipeline lineage 的事实来源；v1.7 不回写旧的
`graph.json`，也不把 `chain_id` 的推断偷偷写入旧 run。Agent 管理的身份由项目级
metadata 显式保存：

~~~
workbench/
├── chains/{chain_id}.json
├── agent-sessions/{session_id}.jsonl
└── ...
~~~

`chains/{chain_id}.json` 是 chain 的权威记录，至少包含：

~~~json
{
  "chain_id": "chain_b",
  "run_family_id": "family_run_001",
  "parent_chain_id": "chain_a",
  "source_run_id": "run_001",
  "source_node_ref": "model_ols",
  "fork_id": "fork_001",
  "active_head_run_id": "run_002",
  "status": "active",
  "schema_version": "chain.v1"
}
~~~

新建 run 时，`run_inputs.json` 增加可选的 `workbench_context` 块，保存
`chain_id`、`run_family_id`、`fork_id`、`agent_session_id` 和触发它的
`operation_id`。这些字段必须与 chain record 交叉校验；`rerun_of` 仍按现有规则保存。

没有 `workbench_context` 的 v1.6 及更早 run 视为 unmanaged legacy lineage：继续由现有
family scanner 读取，只读展示，不强行补写 chain。用户从 legacy run 发起第一条 Agent
任务时，沿 `rerun_of` 向上走到最早可达的 root run，并使用
`legacy-family:{root_run_id}` 作为确定性的 legacy family anchor；从此产生的新 run 才
进入 managed chain。这样旧数据可以被 Agent 观察和作为分叉起点，
但不会因为迁移而改变原有谱系事实。

## 4. 架构方案

### 4.1 方案比较

| 方案 | 特点 | 主要问题 |
|---|---|---|
| 单 Agent + 动态切换 context | 实现简单 | 全局和链上下文容易污染，难以支持独立分支 Agent |
| Global Main Agent + Chain Agent | scope 清晰，适合谱系和分叉，主 Agent 可汇总 | 需要 Session、command 和事件协议 |
| 多 Agent 自由协作网络 | 扩展性最大 | 权限、成本、可解释性和状态一致性都难以控制 |

本版采用第二种。它保留未来增加更多 Agent 类型的空间，但不引入自由协商网络。

### 4.2 组件

~~~
AgentCore
├── SessionRepository
├── ContextBuilder
├── AgentLoop
├── ModelAdapter
├── ToolRuntime
├── AgentEventStream
└── ControlQueue

WorkbenchOrchestrator
├── MainAgent / ChainAgent roles
├── ToolRegistry
├── OperationRegistry
├── PolicyEngine
├── Proposal / ConfirmationGate
├── WorkbenchExecutor
├── Verifier
└── OperationRecordStore
~~~

AgentCore 是 provider-agnostic、Workbench-agnostic 的通用 Agent 引擎；WorkbenchOrchestrator
负责把它绑定到 project、chain、Graph、run、typed operation 和 proposal。Main Agent 和
Chain Agent 不是两套 Runtime，也不是 AgentCore 的两个实现，而是同一 AgentCore 在不同
role/scope 下的编排实例：

~~~
role: main
scope: project / run_family collection

role: chain
scope: one chain_id + active head + inherited prefix
~~~

不要求 Main Agent 和 Chain Agent 使用不同模型或不同进程。第一版可以在后端使用同一个
DeepSeek provider 和独立的 SessionRepository；进程级隔离只在未来开放任意代码执行时增加。
AgentCore 不知道 `model.rerun`、Graph fork、run diff 或用户确认；WorkbenchOrchestrator
通过 typed tool、custom AgentMessage 和 event hook 接入这些能力。

### 4.3 AgentCore 和 ModelAdapter 契约

AgentCore 只依赖 stream-first 的 provider adapter，不直接依赖某个 provider 的响应格式：

~~~python
stream(
    *,
    messages,
    tools,
    response_schema,
    model_config,
    request_id,
) -> AsyncIterator[ModelStreamEvent]
~~~

`ModelStreamEvent` 至少包含以下归一化事件：

~~~json
{
  "type": "text_delta | tool_call_start | tool_call_delta | done | error",
  "request_id": "req_001",
  "delta": "可选的文本或工具参数增量",
  "tool_call": {
    "tool_call_id": "call_001",
    "tool_id": "inspect_node_context",
    "arguments": {}
  },
  "finish_reason": "tool_calls",
  "provider_request_id": "...",
  "usage": {"input_tokens": 0, "output_tokens": 0},
  "error": null
}
~~~

Provider adapter 可以使用原生 tool call，也可以使用严格的 JSON envelope 模式，但必须在
adapter 内完成归一化和 schema 校验。AgentLoop 只消费归一化事件，不猜测非 JSON 文本中的
工具意图。AgentCore 将完整 assistant message 和 tool call 聚合后写入 SessionRepository；
流式 delta 只进入 AgentEventStream，不成为另一份上下文事实。

响应无法解析、工具参数不符合 schema、超出最大 step 或 provider 报错时，AgentCore 产生
错误/aborted message entry，session 进入 `failed`/`blocked`，不调用 Workbench Executor。

v1.7 的 DeepSeek adapter 先复用现有 messages/config 发送路径；如果当前 provider 只能
返回一次性文本，就将其适配为单个 `text_delta` 加一个 `done` 事件。现有 `/llm/chat`
只读问答契约保持兼容，不把 Agent tool call 混入旧 endpoint。以后增加 OpenAI-compatible
provider 时只需实现同一 stream adapter 契约。

## 5. Context 设计

### 5.1 Global Main Agent context

Main Agent 的 context 包含：

- project identity；
- 用户总体目标；
- run family 和 chain 摘要；
- 各 chain 的 active head、状态、风险和最近 operation；
- 全局策略、预算和权限；
- 跨链比较任务；
- 子 Agent 的公开事件和摘要。

Main Agent 默认不加载完整数据集、完整 artifact 或所有 chain 的全文上下文。需要详细信息时，通过 command 要求对应 Chain Agent 返回受限摘要。

### 5.2 Chain Agent context

Chain Agent 的 context 包含：

- chain_id 和 run_family_id；
- 当前 active head；
- fork 点以及继承的 prefix snapshot；
- 上游谱系节点和 artifact 引用；
- 当前节点参数、OperationContract 和诊断；
- 本 chain 的 operation 历史；
- 当前用户任务和相关对话摘要。

Chain Agent 默认不能访问 sibling chain 的详细 context。Main Agent 可以通过显式 command 请求跨链摘要，或者向 Chain Agent 授予有限的只读引用。

### 5.3 后端是事实来源

前端发送 project、chain、node 等引用，不把前端生成的 packet 当作写操作依据。后端负责：

1. 解析真实 run manifest、graph 和 artifact；
2. 生成受限的模型上下文；
3. 生成并保存 context fingerprint；
4. 在用户确认后重新验证 context；
5. 使用同一份后端引用调用 Executor。

现有 Ask AI packet 可以继续用于只读问答和 UI context preview，但不能直接授权 Agent 写操作。

### 5.4 ContextBuilder、compaction 和 custom AgentMessage

SessionRepository 保存完整的 Agent message tree；ContextBuilder 在每次 turn 开始时，从
当前 `leaf_entry_id` 沿 parent path 读取上下文，并按以下顺序生成本轮模型输入：

~~~
SessionTreeEntry[]
→ load branch path
→ transform_context()
→ compaction / branch summary
→ inject Workbench context
→ omit oversized artifact
→ convert_to_llm()
→ LLM Message[]
~~~

Agent message 与 LLM message 不是同一种类型。Session 可以保存 Workbench 专属的 typed
message，例如：

~~~
workbench_context
diagnostic_evidence
operation_proposal
operation_confirmation
operation_result
graph_fork
diff_summary
main_to_chain_command
chain_to_main_result
~~~

这些 custom AgentMessage 可以在 UI、分支和审计中保留；`convert_to_llm()` 决定哪些消息
以结构化摘要进入模型，哪些只作为 UI/审计记录保留。前端不得自行拼接一份可执行 context。

Compaction 不删除历史 entry，而是追加一个 typed `compaction` entry，记录 summary、
`first_kept_entry_id`、tokens_before、details 和生成方式。跨分支切换时可以追加
`branch_summary` entry；旧分支和原始消息仍然可通过 parent path 恢复。context fingerprint
计算在最终 `convert_to_llm()` 输出和相关 Workbench references 之上，确认时重新计算。

## 6. Agent Session 和层级调度

### 6.1 Main Agent 状态

~~~
queued
→ routing
→ coordinating
→ waiting_child
→ waiting_user
→ completed
~~~

终止或阻断状态：

~~~
failed / cancelled / blocked / stale / recoverable_failed
~~~

### 6.2 Chain Agent 状态

~~~
queued
→ inspecting
→ proposing
→ needs_confirmation
→ executing
→ verifying
→ completed
~~~

### 6.3 Main → Chain command

Main Agent 不通过自然语言复制上下文，而是发送结构化 command：

~~~json
{
  "command_id": "cmd_001",
  "dispatch_seq": 12,
  "child_agent_id": "agent_chain_a",
  "chain_id": "chain_a",
  "objective": "检查当前 OLS 模型的诊断问题",
  "allowed_operations": ["inspect", "propose", "model.rerun"],
  "budget": {"max_steps": 8, "timeout_s": 300},
  "context_fingerprint": "..."
}
~~~

Main Agent 可以发送：

~~~
spawn / inspect / request_more_evidence / pause / resume / cancel / revise_objective
~~~

`dispatch_seq` 由 Main Agent 针对目标 chain 单调分配，用于确定执行顺序；`command_id`
只负责幂等身份。一个 command 可以产生多个 event，但不能重复执行同一个 mutation。

子 Agent 通过 typed event 返回：

~~~
started / tool_started / tool_completed / evidence_found
proposal_ready / needs_confirmation / executing / verifying
completed / failed / stale / blocked
~~~

Main Agent 的 command 不是用户对写操作的确认。任何改变谱系、run 或数据的 operation
execution 仍然需要用户确认，除非未来用户显式授予有 scope 和期限的一次性授权；用于
恢复和审计的 session、event、proposal、operation record 状态写入不属于 Workbench
mutation。

### 6.4 SessionRepository 和 AgentEventStream

SessionRepository 是 Agent 上下文和分支的唯一事实来源。v1.7 使用项目级 JSONL
repository，并保留 memory repository 作为契约测试实现；未来可以替换为 SQLite、PostgreSQL
或云端 repository。每条 SessionTreeEntry 只追加、不覆盖：

~~~json
{
  "entry_id": "entry_003",
  "parent_ref": {"session_id": "agent_chain_a", "entry_id": "entry_002"},
  "entry_type": "message | custom_message | compaction | branch_summary | state_change",
  "session_id": "agent_chain_b",
  "payload": {},
  "created_at": "2026-07-13T12:00:00Z",
  "schema_version": "agent.session_entry.v1"
}
~~~

Session metadata 保存 `session_id`、`chain_id`、`role`、`root_entry_id`、
`leaf_entry_id` 和当前状态。更新 leaf 或切换分支只改变 metadata pointer，不复制 ancestor
entries；`get_branch(leaf_entry_id)` 沿 `parent_ref` 跨 session 返回从 root 到 leaf 的确定性
路径。新 session 的 root entry 可以引用父 session 的 entry，但父引用必须 immutable。

AgentEventStream 是运行时观察接口，不是上下文存储。它向 UI 和 orchestrator 发出：

~~~
agent_start / turn_start / message_start / message_update / message_end
tool_execution_start / tool_execution_update / tool_execution_end
turn_end / save_point / agent_end / error / aborted / queue_update
~~~

事件 envelope 使用 `event_id`、`session_id`、`command_id`、`seq`、`event_type`、`payload`
和 `created_at`。事件可以写入 `workbench/agent-events/` 供断线 UI 使用，并通过
`after_seq` 游标重放；但 AI 上下文、分支和恢复事实必须从 SessionRepository 读取。
同一 event 或 command 重复投递必须幂等。

AgentCore 在 `message_end`、`turn_end` 和 `save_point` 执行 SessionRepository 写入；
`message_update` 和 tool progress 默认只走 AgentEventStream。进程重启后先恢复 session
metadata 和最后完整 entry，再根据 event cursor 刷新 UI；对 `executing`/`verifying` 状态
查询 run 和 operation record，不能用 event stream 直接伪造完成状态。

### 6.5 调度顺序和并发边界

同一 `chain_id` 同时最多有一个改变 run、graph 或 data 的 active mutation；只读 inspection
可以并行，但必须继承同一个 context fingerprint。Main Agent 对同一 chain 的 command
按 `dispatch_seq` 串行化并按 `command_id` 去重；不同 chain 可以并行。

Chain 正在 `executing` 或 `verifying` 时，新的写 command 进入 `queued`，不能直接改写
active head。用户取消只取消尚未执行的 command；已提交给现有 rerun 的任务只能进入
`cancelling`/`cancelled`，不能伪造为成功。每个 mutation 使用
`operation_id + proposal_id + proposal_revision + active_head_run_id` 作为幂等键。

### 6.6 AgentCore 控制接口

每个 AgentCore session 同时只有一个 active loop；busy session 的新 prompt 返回
`busy`，用户必须使用明确的控制接口：

~~~
abort       中止当前 provider stream 和可取消的 tool，追加 aborted/error entry
continue    从最后一个合法 user 或 toolResult entry 继续，不复制 assistant error
steer       当前 tool batch 完成后，将新 user message 注入下一 turn
follow_up   当前 agent_end 后排队一个新的 user message
~~~

`steer` 和 `follow_up` 的队列状态通过 `queue_update` 事件展示，并在对应 message entry
追加时成为 SessionRepository 的事实。已有的 Main→Chain `pause`、`resume`、`cancel` 是
orchestrator command：`pause` 不等于隐式 abort，必须返回当前 AgentCore phase；`cancel`
只能取消尚未提交的 Workbench mutation，不能把已经产生的 run 标记为未执行。

## 7. Tool Registry 和 Operation Registry

### 7.1 Tool Registry

第一版向模型暴露的工具以只读观察为主：

~~~
inspect_node_context
inspect_operation_contract
inspect_diagnostics
inspect_result_summary
inspect_artifact_preview
inspect_data_profile
~~~

每个工具都必须声明：

~~~
tool_id
version
input_schema
output_schema
scope_requirements
max_output_budget
side_effect = none
~~~

不暴露任意 shell、Python、文件写入或网络请求工具。

ToolRegistry 和 PolicyEngine 由 WorkbenchOrchestrator 持有；AgentCore 只接收已经声明
schema、scope 和执行模式的 AgentTool descriptor，并通过 ToolRuntime 调用，不直接发现
或注册 Workbench operation。

### 7.2 Operation Registry

所有可执行 Workbench 操作使用统一定义：

~~~
OperationDefinition
├── operation_id
├── version
├── target_types
├── input_schema
├── effect_level
├── scope_requirements
├── validate()
├── preview()
├── execute()
├── verify()
└── summarize()
~~~

第一版注册：

~~~
model.rerun
~~~

后续注册：

~~~
graph.fork
graph.create_node
graph.connect_nodes
data.clean
data.type_override
report.generate
~~~

Registry 应复用现有 capabilities 和 OperationContract，成为后端唯一权威。前端和 prompt 不重复维护第二套字段定义。

AI 可以读取 OperationContract 并提出运行时参数修改，但不能运行时改写 Workbench 的代码 schema。新增参数或新的模型类型必须先注册新的 OperationDefinition、schema 和 executor。

### 7.3 现有契约的适配规则

v1.7 不再造一套平行的模型字段校验。现有 `OperationContract` 继续负责节点能力和字段
合法性；`OperationDefinition` 负责 Agent-facing 的 operation identity、proposal、执行
和验证生命周期。两者通过后端 adapter 连接：

~~~
model.rerun OperationDefinition
  → resolve_operation_contract()
  → validate_overrides()
  → 现有 /runs/{run_id}/rerun 请求模型
  → child run
~~~

Registry 不直接调用 HTTP endpoint，而是调用 request-independent executor；HTTP rerun
route 和 Agent executor 共享同一个底层 submit path。现有 rerun 的
`owner_run_id`、`op_node_id`、`node_hash`、`forest_node_key`、`active_head_run_id` 等
context target 字段必须全部保留，新增的 chain/session/operation 引用作为附加 provenance
写入，不替换旧校验。

## 8. Proposal、确认和执行

### 8.1 通用 Proposal

~~~json
{
  "proposal_id": "proposal_001",
  "operation_id": "model.rerun",
  "operation_version": "v1",
  "target": {
    "chain_id": "chain_a",
    "run_id": "run_001",
    "node_ref": "model_ols"
  },
  "preconditions": {
    "context_fingerprint": "...",
    "active_head_run_id": "run_001"
  },
  "changes": {
    "covariance": {"old": "nonrobust", "new": "HC3"}
  },
  "evidence_refs": ["diagnostic:heteroskedasticity"],
  "expected_effect": ["标准误可能变化，系数预计不变"],
  "risks": ["HC3 在小样本中可能导致标准误偏大"]
}
~~~

### 8.2 执行顺序

~~~
只读工具
→ Proposal
→ schema 校验
→ 用户确认
→ context / active head 再校验
→ Operation Executor
→ 新 run / 新 chain
→ 等待完成
→ Verifier 计算 diff
→ append-only Operation Record
~~~

用户可以取消 Proposal，也可以在确认前编辑 Proposal 的允许字段。用户确认绑定 proposal fingerprint，不能只绑定一个模糊的“确认”动作。

### 8.3 Proposal revision 和确认边界

Proposal 初次生成后不可变。用户编辑允许字段时创建新的 `proposal_revision`，重新执行
schema 校验并计算新的 fingerprint；旧 revision 保留为审计历史。用户确认必须绑定
`proposal_id + proposal_revision + fingerprint`，并且 proposal 的 operation、target、
scope 和 preconditions 不能由普通字段编辑改变。需要改变这些内容时必须生成新的 proposal。

确认前允许持久化 session、message、proposal、event 和 audit metadata；这些是审计和
恢复记录，不是 Workbench mutation。确认前不得创建 child run、改变 graph/active head、
改变数据或调用 Operation Executor。

确认到执行之间必须重新读取 active head、node hash、OperationContract 和 context
fingerprint。任何变化都产生 `stale`，原 proposal 不得自动改写或自动重试。

在 v1.7 中，确认后的 `model.rerun` 固定是 branch operation：它从 source chain 的
stable head 创建新的 child chain、Chain Agent 和 child run。只读 inspection、比较和
摘要继续留在当前 chain；未来若需要在同一 chain 内追加 mutation，必须另行注册明确的
operation policy，不能隐含改变本规则。

## 9. Fork 设计

### 9.1 ForkContext

~~~json
{
  "fork_id": "fork_001",
  "source_chain_id": "chain_a",
  "source_node_ref": "model_ols",
  "source_session_id": "agent_chain_a",
  "source_session_entry_id": "entry_042",
  "inherited_context_fingerprint": "...",
  "child_chain_id": "chain_b",
  "child_agent_id": "agent_chain_b",
  "child_session_id": "agent_chain_b",
  "graph_fork_node_id": "fork_node_001"
}
~~~

### 9.2 两种入口

图节点分叉：

~~~
选择图节点 → Fork
→ 创建 graph fork 子节点
→ 创建 child chain
→ 创建 Chain Agent
→ 打开新 Agent 对话
~~~

Agent 消息分叉：

~~~
选择 Agent 消息 → New branch
→ 从消息绑定的 chain/node/context 解析 ForkContext
→ 创建 graph fork 子节点
→ 创建 child chain
→ 创建 Chain Agent
→ 创建指向 source_session_entry_id 的 child session leaf
→ 通过 parent path 继承该消息之前的对话和谱系 prefix
~~~

如果消息来自 Global Main Agent 且同时涉及多条 chain，用户必须先选择目标 chain。没有唯一目标 chain 时不得创建 graph fork。

### 9.3 Graph fork 节点

Graph fork 节点是真实的结构化谱系节点，但不是统计结果节点。它表示分支上下文，不伪造数据或模型结果。

~~~
planning → ready → active → archived
~~~

所有后续操作都追加在 fork 节点之后。父链和继承的上游节点保持不可变；数据和 artifact 通过 content-addressed reference 共享，不复制原始数据。

### 9.4 Fork projection、rollback 和消息继承

fork record 是 `workbench/forks/{fork_id}.json` 的权威记录。`graph_fork_node_id` 使用
`fork:{fork_id}` 命名，不占用 pipeline `node_hash`，没有 stage output、artifact 或统计
结果。它在 serve-time forest projection 中作为 structural node 展示，连接
`source_node_ref → fork:{fork_id} → child_chain_id`；底层 pipeline `graph.json` 保持
字节不变，legacy `/graph` 不认识 fork metadata 时继续返回原有 graph。

从 Agent 消息分叉时，不复制 immutable message prefix，而是在 SessionRepository 中创建
新的 branch pointer：child session 的 root entry 保存
`parent_ref={source_session_id, source_session_entry_id}` 作为 inherited parent，child leaf
之后再追加新的 user message。`context_snapshot_ref` 指向分叉时的
ContextBuilder 输入快照。未确认 proposal 只能作为 child session 的 draft custom message
追加，不能自动执行。Global Main Agent 消息若没有唯一 `target_chain_id`，必须先让用户选择
chain。

对话和消息至少保存以下字段：

~~~
session_id
entry_id / parent_ref
role: user | main_agent | chain_agent | tool
target_chain_id
node_ref
context_snapshot_ref / context_fingerprint
proposal_ref
fork_id
created_at
~~~

消息的 context snapshot 是 immutable reference；不能在消息分叉后用当前 active head
覆盖历史上下文。旧 localStorage Ask AI 记录如果没有这些身份，只能作为不可分叉的兼容
展示记录，不能伪造 parent entry。

Rollback 不是删除或覆盖旧 chain，而是从用户选择的历史 stable node 创建新的 fork、child
chain 和 Chain Agent，并将新 chain 设为 active。旧 chain、旧 run、旧 operation record
全部保留；rollback 本身也生成一个 typed operation record。

### 10.1 权威存储

│   └── {session_id}.jsonl

AI Activity 是这些后端记录的前端投影。现有 localStorage 记录可以作为兼容缓存，但不能作为 Agent 执行事实来源。

### 10.3 写入原子性和恢复对账

一次 mutation 的持久化顺序固定为：

~~~
command/proposal event
→ confirmation event
→ operation record: pending
→ submit child run（run_inputs 写入 operation/chain provenance）
→ child run created event
→ child run terminal event
→ deterministic verification
→ operation record: completed/failed
→ chain active head projection
~~~

每一步都可由 `operation_id` 重放。重启对账规则：child run 存在而 record 缺失时补建
`recovering` record；record 存在而 child run 不存在时标记 `failed` 并保留错误证据；
验证完成但 active head 未更新时重新投影，而不重新执行 pipeline。`workbench/` metadata
必须从现有 runs/graph scanner 的输入目录排除。

### 10.4 Actor 和审计来源

Operation Record 还必须保存：

~~~
actor_type: user | main_agent | chain_agent | system
actor_id
command_id
message_id
provider / model
policy_decision
confirmation_actor / confirmation_at
tool_call_refs
source_run_id / target_run_id
~~~

v1.7 仍是单用户本地项目，但这些字段先进入 repository interface，未来接入咨询公司
协作数据库或 RBAC 时不需要重写 operation 语义。

~~~

用户

→ 确认 Proposal

→ 校验 context 和 active head

## 12. 错误和安全边界

| 情况 | 行为 |
|---|---|
| context fingerprint 过期 | 状态变为 stale，停止执行，要求重新检查并生成 Proposal |
| OperationContract 不允许字段或值 | 状态变为 blocked，不创建 run |
| DeepSeek 返回格式错误 | 记录模型响应错误，不尝试猜测或执行 |
| 用户拒绝 Proposal | 记录 declined，父链不变 |
| rerun 失败 | 保留 child session、失败 run 和错误证据，不自动尝试其他方案 |
| fork 目标正在运行 | 只允许从最近稳定 snapshot 分叉，不能继承 in-flight 状态 |
| 重复确认或重复 command | 使用 proposal fingerprint、request id 和 operation idempotency 去重 |
| 同一 chain 存在并发写 command | 进入 queue 或返回 conflict，不改变 active head |
| 进程在执行期间崩溃 | 通过 session event、run manifest 和 operation record 对账恢复，不盲目重跑 |
| 子 Agent 访问 sibling chain | PolicyEngine 拒绝，记录 scope violation |
| artifact / data 超过预算 | 返回摘要和显式 omission，不静默扩大上下文 |
| provider 错误 | 脱敏错误并保留可恢复 session 状态 |

第一版 sandbox 由 tool allowlist、project scope、chain scope、输出预算、超时和并发限制构成。任意代码执行不是 v1.7 第一条 workflow 的能力；未来开放时必须增加进程或容器级 sandbox。

每次 tool 或 operation 访问都经过 PolicyEngine，生成可审计的：

~~~json
{
  "allowed": true,
  "actor_type": "chain_agent",
  "project_scope": "project_001",
  "chain_scope": "chain_a",
  "operation_id": "model.rerun",
  "reason": "allowlisted_and_in_scope",
  "budget_remaining": {"steps": 4, "timeout_s": 180}
}
~~~

拒绝结果不只返回给模型，也写入 event 和 Operation Record；policy decision 不能由模型
自行覆盖。

## 17. v1.7.1 Agent 可靠性加固增补

v1.7.1 不把 Agent 扩展成通用研究 Agent 平台。本增补只把现有单 Chain Agent
的上下文边界、证据披露、loop 终止和恢复行为写成可测试的契约。

### 17.1 短期上下文契约

- Session tree 是短期记忆的唯一持久化来源；事件流只负责观察和 replay，不作为模型事实来源。
- 当前 HTTP context packet 和问题长度继续受 `MAX_CONTEXT_CHARS`、`MAX_QUESTION_CHARS` 限制。
- 本版禁止隐式截断。超出预算必须返回结构化错误，不能静默删除旧消息、tool call 或 tool result。
- `compaction` 只能作为新的 typed session entry 追加，必须带 summary、覆盖范围和 `tokens_before`；原始 session entry 不删除。
- tool call 与对应 tool result 必须作为完整块保留，不能在块中间截断。
- 自动 token-aware compaction、branch summary 生成和 provider token 计费统计列为后续设计，不在本版冒险实现。

### 17.2 渐进式披露层级

Agent 通过 scoped read-only tools 逐级取得证据，不在初始 context packet 中塞入完整 artifact：

```text
Level 0  项目/任务摘要
Level 1  run、node、active-head 摘要
Level 2  schema、诊断、结果摘要
Level 3  受限详细证据
Level 4  operation contract
Level 5  proposal 与确认信息
```

每层必须有输出预算；被省略的 section 必须显式标记；生成 proposal 前必须重新取得必要
contract 和 active-head 证据。摘要不能替代后端 canonical state，也不能成为 mutation 的
安全依据。

### 17.3 Prompt protocol 版本

当前 role/protocol 通过 typed `custom_message` 注入，版本为 `agent/v1`。系统提示文本只
负责指导模型：工具证据、proposal 边界、拒绝不支持操作和风险说明。后端 registry、scope、
active-head、proposal lifecycle 和 confirmation 才是强制安全边界。

以后若拆出 versioned prompt bundle，必须同时绑定 role、protocol version、allowed tools、
allowed operations、输出要求和预算；不得让 prompt 文本单独授予权限。

### 17.4 Loop 与失败恢复

- 每个 session 同时只能有一个 active loop。
- `max_steps` 和 timeout 继续是硬上限；本版增加连续相同 tool call 的最小护栏。
- 相同 `tool_id + canonical arguments` 连续达到默认上限后，Agent 必须以
  `repeated_tool_call_limit` 进入 `blocked` 终态，并发布可见 `loop_guard` 事件；不得无限重试。
- tool result、provider error、timeout、abort 和 terminal assistant error 都必须写入 session
  与 event stream，reload 后可读到相同终态。
- 不在本版实现 token/cost budget、并行 tool call、自动退避、语义规划或 Main→Chain 全生产闭环。

### 17.5 v1.7.1 验收矩阵

- fake/local provider：schema inspection、diagnostics inspection、proposal-only、unsupported
  request refusal、provider/tool failure、session reload/replay。
- real API：只做手工、只读的 DeepSeek smoke；不作为自动 gate，不写入 key，不自动确认 mutation。
- browser smoke：必须让前端和 Agent session 使用同一个 backend、project root 和 session URL；
  仅脚本直接调用 backend 不算浏览器呈现。
