# V1.3.2: Foundation Refactor — Design Spec

Date: 2026-05-12

## 1. Goal

V1.3.2 is a pure-refactor release that pays down three pieces of technical debt identified during V1.3.1 review. None of these introduce new user-facing behavior; all of them clean up code that V1.4's lineage graph work will heavily touch. Doing them now in isolation (rather than folded into V1.4) keeps each change small, low-risk, and easy to three-level-review.

The primary engineering outcomes are:

1. `backend/workbench/diagnostic_preview.py` is split into four focused submodules so future feature work touches one file at a time instead of a 594-line catch-all.
2. The frontend has a runtime contract validator (`validateDiagnosticPreview`) that catches malformed API responses at the boundary, instead of letting them propagate into rendering code where TypeScript types provide no protection.
3. Backend `C()` / patsy term parsing is consolidated into a single module, with the frontend consuming pre-parsed `display_term` / `reference_level` / `source_id` fields rather than re-parsing.

V1.3.2 is **strictly additive and refactor-only**. No P0 user-facing behavior changes. The full V1.3.1 test suite (480 tests) must continue to pass without modification; new tests are added only to cover the new boundaries.

## 2. Scope

### 2.1 P0 Must Have

1. Split `backend/workbench/diagnostic_preview.py` into a package:
   - `backend/workbench/diagnostic_preview/__init__.py` — re-exports the existing public surface so `api.py`, `orchestrator.py`, and all tests continue to import from `workbench.diagnostic_preview` unchanged.
   - `backend/workbench/diagnostic_preview/artifact_manifest.py` — manifest assembly, availability flags, report gating contract.
   - `backend/workbench/diagnostic_preview/coefficient_risk.py` — risk aggregation by original variable, dummy term grouping, reference-level handling.
   - `backend/workbench/diagnostic_preview/guidance.py` — recommended actions, interpretation restrictions, primary-reasons formatting.
   - `backend/workbench/diagnostic_preview/contract_validation.py` — canonical-field validation, contract fallback, legacy/malformed preview detection.
2. Every existing import site of `workbench.diagnostic_preview` continues to work without modification.
3. New frontend `frontend/src/lineage/contractValidator.ts` (utility lives under a generic name, not lineage-specific):
   - Actually placed at `frontend/src/contract/validateDiagnosticPreview.ts`.
   - Exports `validateDiagnosticPreview(raw: unknown): ValidationResult` where `ValidationResult` is `{ valid: true, data: DiagnosticSummaryPreview } | { valid: false, errors: ValidationError[] }`.
   - Validates: required canonical fields present, severity enum values valid, trust counts numeric and non-negative, primary reasons array shape, model identity present.
   - Returns structured errors with field path and reason; does not throw.
4. `runResult.tsx` calls `validateDiagnosticPreview` on the API response before rendering. On `valid=false`, render a clear error state and log the structured errors; do not attempt partial rendering.
5. Unified term parser in `backend/workbench/term_parser.py`:
   - Single source of truth for parsing patsy / statsmodels term names (`C(region)`, `C(region)[T.north]`, `np.log(income)`, interaction terms `var1:var2`, etc.).
   - Public API: `parse_term(raw: str) -> ParsedTerm` where `ParsedTerm` carries `display_term`, `source_id`, `reference_level` (when applicable), `is_dummy`, `is_interaction`, `transformation_op` (e.g. "log", "C", `None`).
   - `diagnostic_preview/coefficient_risk.py` and `orchestrator.py` import from this module. Existing per-call-site parsing logic is deleted.
   - Frontend types in `frontend/src/api.ts` add `display_term`, `reference_level`, `source_id` as required fields on coefficient risk entries; the frontend never re-derives these.
6. Test coverage for the new boundaries:
   - Unit tests for `term_parser.parse_term` covering at least: plain term, `C(var)` dummy, `C(var)[T.level]` reference-level, `np.log(var)`, `np.log(var + 1)`, interaction `var1:var2`, interaction with dummy, polynomial / spline terms (graceful unknown-form handling).
   - Unit tests for each `diagnostic_preview/*.py` submodule (carry over from existing tests where possible; add focused tests for any internal helper now exposed at submodule boundary).
   - Unit tests for `validateDiagnosticPreview` covering: valid payload, missing required field, wrong type, malformed enum, legacy/preview-only payload.
   - Snapshot test on `runResult.tsx` for the validation-failure error state.
7. Full V1.3.1 test suite (480 tests) passes unchanged.

### 2.2 P1 Should Have

2. Add a `# regenerated by V1.3.2 refactor` comment header to each new submodule for git-archaeology context.

### 2.3 Non-Goals

1. **No new statistical methods.**
2. **No new API endpoints.** The API contract is unchanged; only the implementation modules underneath move.
3. **No new UI features.** The only frontend behavior change is showing an error state when the API response is malformed, which today either silently renders garbage or crashes.
4. **No graph / lineage work.** That is V1.4.
5. **No Trust Console deepening / Secondary model UI / Report top trust summary / i18n.** Those are V1.4.x or later.

## 3. Architecture

### 3.1 `diagnostic_preview` package layout

Existing file becomes a package. The split follows function-cohesion boundaries already visible in the current file:

```
backend/workbench/diagnostic_preview/
├── __init__.py              # public API re-exports — DO NOT add logic here
├── artifact_manifest.py     # ~120 lines
├── coefficient_risk.py      # ~200 lines
├── guidance.py              # ~140 lines
└── contract_validation.py   # ~130 lines
```

`__init__.py` re-exports exactly the symbols `api.py`, `orchestrator.py`, and tests currently consume from `workbench.diagnostic_preview`. No call-site changes outside the package itself.

Helpers used by multiple submodules go into a private `_shared.py` within the package, not the public surface.

### 3.2 `term_parser.py`

```python
@dataclass(frozen=True)
class ParsedTerm:
    raw: str                          # original term string
    display_term: str                 # user-facing label, e.g. "log(income)" or "region (=north)"
    source_id: str                    # canonical variable id, e.g. "income" or "region"
    reference_level: str | None       # for dummy terms only
    is_dummy: bool
    is_interaction: bool
    transformation_op: str | None     # "log", "sqrt", "C", "poly", None
    components: list[str]             # for interactions: ["var1", "var2"]; else [source_id]

def parse_term(raw: str) -> ParsedTerm: ...
```

Parser is intentionally restrictive: it recognizes patsy / statsmodels term forms used by the current orchestrator. Unknown forms return a `ParsedTerm` with `raw == display_term == source_id` and `transformation_op=None` — never raises.

All previous duplicate parsing sites (in `coefficient_risk`, in `orchestrator.py`, in any inline logic) are replaced by `parse_term(...)`.

### 3.3 Frontend contract validator

```typescript
// frontend/src/contract/validateDiagnosticPreview.ts
import type { DiagnosticSummaryPreview } from "../api";

export type ValidationError = {
  path: string;        // e.g. "trust.counts.warning"
  reason: string;      // human-readable
  expected: string;    // e.g. "non-negative number"
  actual: string;      // e.g. "string"
};

export type ValidationResult =
  | { valid: true; data: DiagnosticSummaryPreview }
  | { valid: false; errors: ValidationError[] };

export function validateDiagnosticPreview(raw: unknown): ValidationResult;
```

The validator is hand-written (not a runtime type library dependency) to keep the bundle small and the validation rules explicit. It validates the canonical V1.3.1 fields and flags anything missing or shape-mismatched.

`runResult.tsx` integration point: where the component currently consumes `runDetail.diagnostic_summary_preview` directly, it now runs through `validateDiagnosticPreview` first. If invalid, the Trust Summary / Coefficient Risk / Recommended Actions sections render a single "Invalid diagnostic data — see browser console for details" panel, and the validation errors are logged.

## 4. Key Design Decisions and Rationale

### 4.1 Why split now, not in V1.4

V1.4's lineage graph work will repeatedly edit code in `diagnostic_preview.py` (trust state per node reuses the existing trust model; auto_chosen flag will share validation logic with contract validation). Splitting first means each V1.4 edit lands in a focused submodule rather than a 600-line file. Splitting *during* V1.4 risks merge conflicts and obscured diffs. Splitting *after* V1.4 means doing the refactor with V1.4's additions already merged in, which is harder.

The split itself is mechanical and low-risk. Doing it as its own version makes the three-level review cheap and the rollback story clean.

### 4.2 Why the term parser is its own module, not a `diagnostic_preview` submodule

Term parsing is used by both `diagnostic_preview` (for risk aggregation) and `orchestrator.py` (for node labeling, and in V1.4 for graph node display). It does not belong to either consumer. A separate module avoids circular imports and makes the parser independently testable.

### 4.3 Why hand-written frontend validator instead of `zod` / `io-ts` / etc.

The frontend bundle is currently small. Adding a runtime validation library for one validator is an unfavorable trade. The hand-written validator is ~80–120 lines, explicit about every rule, and trivially extensible when V1.4 adds graph fields.

### 4.4 Why the CI line-count check is P1, not P0

P0 keeps V1.3.2 small. The CI guard is nice to have but not load-bearing; if it slips it can land in V1.3.3 or alongside V1.4.

## 5. Testing Strategy

1. **Pre-refactor snapshot**: before any move, capture the current V1.3.1 test output (480 tests pass). After every refactor step, re-run the full suite and confirm zero new failures.
2. **Module-by-module move**: do the four `diagnostic_preview` submodule extractions as four separate commits within the V1.3.2 branch, each with a passing test run. This isolates any regression to one commit.
3. **Term parser tests** are written *first* using the existing parsing behavior as the oracle (the new parser must reproduce current outputs). Only after these pass do the duplicate sites get replaced.
4. **Frontend validator tests** are unit tests on the validator itself plus a snapshot on `runResult.tsx` showing the error state with mocked invalid input.
5. **Three-level review** per project convention (Implementer → Test/QA → Reviewer) before commit. Reviewer specifically confirms: no behavior change visible to users, public import paths unchanged, test count goes up (new tests added) and existing test count stays at ≥480.

## 7. Success Criteria

V1.3.2 is complete when:

1. `backend/workbench/diagnostic_preview.py` is gone; the package at `backend/workbench/diagnostic_preview/` provides identical public API and all import sites work unchanged.
2. `backend/workbench/term_parser.py` exists; no other backend file contains patsy-term parsing logic.
3. `frontend/src/contract/validateDiagnosticPreview.ts` exists and is called in `runResult.tsx`.
4. Full V1.3.1 test suite (480 tests) still passes.
5. New tests for the term parser, the frontend validator, and the four `diagnostic_preview` submodules all pass.
6. A run on the existing fixture dataset produces byte-identical user-visible output (Run detail, Report) compared to V1.3.1, modulo timestamps.
7. Three-level review passes; commit pushed to the V1.3.2 branch.
