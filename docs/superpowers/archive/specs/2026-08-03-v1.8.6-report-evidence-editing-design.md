# Workbench v1.8.6 Report Evidence、期刊标准与安全编辑设计

> 状态：设计草案，已获得用户方向性批准，等待本文档审核后进入实施规划。
>
> 本文件只定义 Report 页、报告证据协议、论文式写作质量闸门和安全编辑边界；不改写
> `2026-08-03-v1.8.6-full-scope-expansion-design.md` 或预测研究基础设计。

## 0. 决策摘要

Workbench 的计算结果和报告文字必须是两层对象：

```text
Run / Graph / Artifact / Evidence Packet（不可变事实）
                         ↓
              Report Draft / Revision（可编辑叙述）
```

用户可以润色、重排和补充报告文字，但不能修改 Workbench 已计算的数据、模型、诊断、图表
或任何证据值。编辑后的报告是新的 report revision，不是对 Run 的修改。

Report 页仍然是唯一的报告工作台，不新增独立的 Run 导出页或数据导出页。它承担：

1. 查看只读证据报告；
2. 选择哪些证据进入 AI 报告上下文；
3. 生成符合 `journal_full_v1` 的论文式报告；
4. 编辑报告叙述并保存修订版；
5. 用户主动导出报告或结果表。

数据节点的清洗/变换后数据导出仍属于现有数据节点详情抽屉中的上下文操作，不混入报告
正文，也不创建新的页面。

## 1. 当前实现与本设计要修正的问题

### 1.1 三种报告含义必须分开

| 入口 | 当前含义 | 本设计后的产品名称/边界 |
|---|---|---|
| 普通 Run | 确定性地生成 HTML；当前代码仍自动生成 PDF/XLSX | 保留 HTML、JSON、模型结果和诊断 artifact；PDF/XLSX 改为用户主动操作 |
| Report 页 `Generate report` | 把事实表、图表和 lineage 发给 LLM，生成受引用约束的文字 | `Paper report`，使用可验证的期刊式章节合同 |
| Agent `report.compose` | 收集 workflow steps、artifact 和事件，生成确定性证据集合 | `Assemble workflow evidence`，不是论文写作，不伪装成 LLM 报告 |

Report 页当前使用 `workbench-report/v1` packet，LLM 只能引用 fact table 中的数字；现有
约束只有 Title、Data、Methods、Results、Limitations，缺少最低篇幅、研究问题覆盖、诊断
覆盖和结果解释闸门。本设计补足这些约束。

### 1.2 当前 checkbox 的真实职责

Report 页的 checkbox 是事实级的“是否允许 AI 引用”开关，不是模型配置，也不是结果编辑器。

事实来源分为可注册的 provider：

- lineage/node provider：节点参数、指标、系数、标准误、p 值和决策；
- figure provider：真实图表 artifact 的有界数值摘要；
- time-series provider：变换、缺失策略、ARMA/variance 选择、参数、诊断和预测指标；
- post-estimation provider：联合 F、White test、驻点等声明过的后估计结果；
- future capability providers：新模型族、预测研究、统计工具箱等只需注册 provider，
  不应继续在 `ReportView` 中增加散落的模型专用分支。

取消事实只改变 LLM 输入，不改变 Run。完整事实快照、被排除的 fact IDs 和上下文指纹仍然
保存，用于审计和复现。

## 2. 设计原则

### 2.1 结果不可变

以下对象只允许由 Run/Artifact 生产端写入，Report 页只能读取：

- 原始数据、清洗数据、变换数据和行集合；
- 模型参数、系数、标准误、p 值、置信区间、样本量和预测值；
- 诊断结果、统计检验结果、权重语义和 SplitPlan；
- 图表的真实数据源和 artifact 内容；
- Graph node、Run、artifact、hash 和 lineage。

报告编辑 API 不得接受这些字段的更新操作。报告服务端也必须拒绝带有结果覆盖字段的
revision payload，而不是依赖前端隐藏输入框。

### 2.2 证据和叙述分离

Evidence Packet 是唯一数字来源；报告正文是引用这些证据的叙述层。LLM 不能创造数字，
用户编辑也不能把新数字伪装成 Workbench 结果。

### 2.3 能力通过注册扩展

新增模型或分析能力必须提供：

1. capability manifest；
2. typed evidence provider；
3. 适用的 report module；
4. validation level 和 limitations；
5. consumer contract（Report/Table/Agent/Compare 中至少声明支持或明确不支持）。

核心 Report 页面只消费统一协议，不为每个模型族复制一套页面逻辑。

### 2.4 缺证据时显式缺失

没有执行、没有保存或没有验证的诊断必须显示为 `not performed`、`not available` 或
`internal-only`，不能由 LLM 用常识补齐。

### 2.5 质量优先于字数

最低字数只是兜底，不能通过重复空话达标。报告必须先通过章节、证据、解释、限制和引用
覆盖闸门；证据很少时应诚实缩短并标记 `insufficient_evidence`，不能为了满足字数编造结果。

## 3. 统一 Evidence Packet

### 3.1 顶层结构

新增或演进的 packet 使用版本化 envelope，旧 `c1`、`c2` 引用格式在兼容期继续可读：

```json
{
  "packet_schema": "workbench.report.evidence",
  "schema_version": 1,
  "packet_id": "content-addressed-or-run-scoped-id",
  "source_run_id": "run-id",
  "scope": {"node_keys": [], "node_count": 0},
  "context_fingerprints": [],
  "capabilities": [],
  "sections": [],
  "figures": [],
  "limitations": [],
  "reproducibility": {
    "artifact_ids": [],
    "fact_snapshot_hash": "sha256:..."
  }
}
```

每个 `capability` 至少包括：

```json
{
  "capability_id": "model.survival_cox",
  "provider_id": "evidence.survival_cox.v1",
  "availability": "available",
  "validation_level": "external_oracle | internal_only | unverified",
  "report_modules": ["survival"],
  "limitations": []
}
```

每个 fact 至少包括：

```json
{
  "id": "c12",
  "kind": "estimate | diagnostic | sample | decision | metadata",
  "label": "Hazard ratio for age",
  "field": "coef:age",
  "value": 1.08,
  "unit": null,
  "node_key": "model:cox",
  "artifact_ids": ["model_results"],
  "claim_types": ["associational"],
  "validation_level": "external_oracle",
  "qualifiers": []
}
```

`field` 和机器 ID 供审计使用，`label`、`kind`、`unit`、`qualifiers` 供用户和报告使用。
新增 provider 必须保留原始字段路径，不能只提供一个不可追溯的自然语言值。

### 3.2 Provider 注册协议

逻辑接口如下，具体实现可按当前前后端边界拆分：

```text
EvidenceProvider {
  provider_id: string
  schema_version: positive integer
  capability_ids: string[]
  applies(context): Applicability
  collect(context): EvidenceSection
  limits: EvidenceBudget
}
```

协议要求：

- `collect` 是确定性的，只读 Run/Artifact；
- 默认输出有界标量、摘要表和 artifact 引用，不输出无界原始数据；
- 未适用时返回 `not_applicable`，缺失 artifact 时返回 `unavailable` 及原因；
- 不得在 provider 内重新拟合模型或修改 Run；
- 每个事实都绑定 node、artifact 或 context fingerprint；
- provider 自己声明最大事实数，不能由 Report 页面写死“某种模型最多 80 个事实”；
- 未知 provider 不得静默丢弃，必须保留 capability manifest 和缺失说明。

这样未来增加 panel、Tobit、Bayesian、matching 或新的时间序列模型时，只需要增加对应
provider 和 report module；主页面仍按协议渲染。

## 4. `journal_full_v1` 报告标准

### 4.1 默认报告形态

Report 页默认使用 `journal_full_v1`。短摘要或管理层简报可以作为未来显式 profile，不能
通过缩短默认 prompt 偷换标准。

默认最低结构：

- 至少 10 个可见报告 block：标题、摘要和至少 8 个正文/证据 block；
- Abstract 至少覆盖 5 个要素：问题、数据、方法、主要结果、限制；
- Data、Methods、Results、Diagnostics、Limitations 必须各有实质段落；
- 当可用证据不少于 2 个主要发现时，Results 至少拆成两个有标题的小节；
- 只要存在真实 regression/table/figure artifact，就必须在报告中说明或引用它；
- 每个主要发现必须同时有：claim、evidence、interpretation、limitation/implication；
- 每个数字、参数、比较、样本量、p 值、区间端点和模型选择都必须有 fact citation；
- 不能用空泛句子填充字数。结构闸门失败时报告状态为 `needs_revision`。

语言长度只作为底线提醒：中文正文少于约 1,200 个非空白字符、英文正文少于约 700 个
英文词时，默认提示篇幅不足；如果证据不足，允许生成更短报告，但必须标记
`insufficient_evidence` 并列出缺少什么。

### 4.2 必需章节

| 章节 | 必须回答的问题 | 证据要求 |
|---|---|---|
| Title | 研究对象、问题和方法是什么 | 不得只使用默认标题 |
| Abstract | 研究问题、数据、方法、发现、限制是什么 | 至少一个主要结果引用 |
| Research question and scope | 分析单位、样本范围、时间范围、estimand 是什么 | scope、sample、结构事实 |
| Data and sample | 数据来源、样本量、筛选、缺失、最终样本是什么 | 行数、样本和 lineage facts |
| Variables and transformations | 因变量、自变量、参考组、派生/重编码和变换是什么 | params、recipe、labels、data-operation facts |
| Methods | 模型形式、估计方法、权重、标准误和假设是什么 | model params、decisions、contract facts |
| Results | 主要方向、量级、不确定性和含义是什么 | estimates、intervals、tests、tables |
| Diagnostics and robustness | 哪些假设和稳健性检查完成、失败或未执行 | diagnostic facts、warnings、validation level |
| Limitations | 哪些限制会改变解释 | run-specific warnings 和 capability limitations |
| Conclusion | 最终能说什么，不能说什么，下一步是什么 | 只能复述有证据的结论 |
| Reproducibility metadata | 如何定位本次结果 | run/node/artifact/hash，默认作为元数据保存 |

### 4.3 模型族 report module

模型族模块只负责增加该模型所需的章节内容，不改变通用章节：

- OLS/GLM：系数尺度、协方差、链接函数、拟合和残差诊断；
- binary：概率、优势比、边际效应和参考类别；
- count：exposure/offset、IRR、过度离散和零膨胀限制；
- ordinal/multinomial：类别、参考组、概率、优势比/相对风险比及比例优势限制；
- survival：事件、删失、时间尺度、risk set、hazard ratio、Kaplan–Meier、log-rank、
  Schoenfeld 和 external oracle 状态；
- quantile：分位点、区间、bootstrap、跨分位数比较和内部验证状态；
- prediction：SplitPlan、development/final holdout、baseline、负对照、泄漏检查和指标；
- time series：变换、缺失策略、模型选择、残差诊断、预测窗口、coverage 和 exceptions；
- weights：frequency、analysis、sampling 的语义、执行状态和不支持原因。

### 4.4 Claim 合同

报告内部的主要陈述应能归类为：

```text
descriptive | associational | causal | predictive | diagnostic | methodological
```

每个 claim 至少绑定：

- fact IDs；
- artifact IDs；
- source run/node；
- validation level；
- qualifiers/limitations；
- 是否允许使用因果措辞。

默认所有回归系数使用“条件相关/关联”语言。只有存在明确设计和对应证据时，才能使用
因果语言；不能仅凭 p 值、系数方向或模型拟合优度声称因果关系或模型优越性。

## 5. 确定性报告质量闸门与 LLM 合同

LLM prompt 只负责写作风格和语言；以下规则必须由确定性 validator 检查：

1. 必需章节、章节顺序和最低 block 数；
2. 每个 supplied figure 恰好一次，且 artifact ID 真实存在；
3. 每个数字/参数/决定都有合法 citation；
4. 引用的 fact 属于本次 packet，未被用户排除；
5. 未出现 fact table 之外的新数字；
6. 结果段覆盖适用的 capability modules；
7. 诊断和限制没有被遗漏或用泛化语句替代；
8. 因果、优越性、预测能力等高风险措辞符合 claim type；
9. 外部 oracle、internal-only、unverified 状态原样保留；
10. 报告引用的 run、artifact、fact snapshot 与当前 revision 一致。

报告状态至少有：

```text
draft → evidence_ready → generated → needs_revision → exportable
                              ↘ stale
```

`needs_revision` 和 `stale` 不得被静默导出为正式报告。

## 6. 安全自定义编辑

### 6.1 单一 Report 页布局

同一页面内提供两个模式：

1. Evidence：只读事实、表格、图表和 provenance；
2. Paper：生成后的论文稿、编辑器、证据插入器、revision history 和导出动作。

不增加新的 Report/Run/Data 页面。

### 6.2 可编辑对象

允许编辑：

- 标题、摘要、正文、章节标题和章节顺序；
- 图表 caption 和解释段落；
- 用户自己的定性作者备注；
- 事实排除选择（只影响本报告 revision 的 AI context）。

不允许编辑：

- 任意事实的 `value`、unit、field、source 或 validation level；
- 数据行、清洗/变换结果和 Graph lineage；
- 模型参数、系数、p 值、置信区间、预测值、样本量和诊断结果；
- 图表 underlying data、artifact 内容和 Run 状态。

### 6.3 结构化文档模型

持久化的报告正文使用可版本化 block，而不是把一整段 HTML 当作事实：

```json
{
  "report_revision_id": "...",
  "source_run_id": "...",
  "evidence_packet_id": "...",
  "fact_snapshot_hash": "sha256:...",
  "blocks": [
    {"id": "b1", "type": "heading", "text": "Results"},
    {"id": "b2", "type": "paragraph", "text": "...", "cite_ids": ["c12"]},
    {"id": "b3", "type": "figure", "artifact_id": "figure_1"},
    {"id": "b4", "type": "author_note", "text": "...", "verified": false}
  ]
}
```

Markdown/HTML/PDF/Word/LaTeX 都从同一结构化 revision 渲染，避免不同导出格式产生第二套
事实来源。

### 6.4 编辑校验

- 数字从 evidence picker 插入时自动生成 citation chip；
- 用户手写但无法匹配 fact 的数字，允许暂存为草稿，但正式导出时阻止；
- 无法验证的定性作者备注必须有显式标记，不得渲染成 Workbench 结果；
- citation chip 只能指向当前 evidence packet 的事实；
- 保存 revision 时重新计算文档 hash、citation coverage 和 stale 状态；
- Run 或 evidence packet 变化后，旧 revision 标记为 `stale`，不得静默重绑新结果；
- “恢复自动生成稿”只恢复正文，不删除原始 Run 或历史 revision。

### 6.5 Revision 与原始结果的隔离

保存报告只创建新的 report artifact/record，至少包含：

- `source_run_id`；
- `fact_snapshot_hash`；
- `artifact_ids`；
- `excluded_fact_ids`；
- `base_generated_revision_id`；
- `editor_revision`；
- `validation_status`。

任何 report API 请求若携带 `dataset`、`model_results`、`diagnostics`、`artifact_payload`、
`lineage` 等结果覆盖字段，必须 fail-closed。

## 7. Checkbox 与证据面板重设计

当前一行一个机器字段的表格改为“报告证据”面板：

- 默认折叠为按 provider/capability 分组的条目；
- 每组显示“已选/总数”和全选/全不选；
- 默认全部选中；取消操作命名为“从本报告中排除”；
- 主行显示人类可读 `label`、来源节点和简短值；
- `id`、raw `field`、artifact、hash 和完整值进入“证据详情”抽屉；
- 保留 node 跳转和 excluded disclosure；
- 使用紧凑、统一的 checkbox/toggle 尺寸，不让浏览器默认控件撑大整行；
- 事实值没有输入框、textarea 或 contenteditable；
- report generation 请求只发送 selected facts，revision 仍保存完整 snapshot。

建议的默认分组：

```text
数据与样本
模型与估计
统计检验
诊断与稳健性
预测研究
时间序列
图表
血缘与可复现性
```

新 provider 可以声明自己的 group，但必须提供 fallback group，不能让新能力以“无标签长表”
出现在页面底部。

## 8. 导出边界

- Run 完成时默认只保留 HTML、JSON、模型结果和诊断 artifact；
- PDF 只能由 Report 页用户主动点击“导出报告”生成；
- XLSX 默认不生成；
- Report 页提供明确的“导出结果表”动作，用户选择后才生成结果表 XLSX；
- 清洗/变换后的数据从对应数据节点详情抽屉导出；
- 报告导出和结果表导出必须引用当前 report revision/evidence snapshot，不能重新计算模型；
- 导出的正式报告必须通过相同的 citation、figure、stale 和 numeric-coverage validator。

## 9. Agent 边界

`report.compose` 的显示名称改为“汇总工作流证据”或等价名称，输出：

- workflow steps；
- artifact IDs；
- exploration log；
- 有界事实和 warnings；
- evidence packet reference。

它不生成论文正文、不修改结果，也不绕过 Report 页的 `journal_full_v1` validator。
如果未来支持 Agent 直接生成论文稿，必须复用本文件定义的 Evidence Packet、ReportStandard
和 ReportRevision，不得单独创建一套 Agent 报告格式。

## 10. 可验收标准

### 10.1 不可变结果

- 编辑标题、正文、章节顺序和作者备注后，Run、数据、model result、diagnostic、figure
  artifact、Graph lineage 的内容 hash 完全不变；
- report revision 能反查唯一的 source run 和 evidence snapshot；
- 修改 report revision 不会改变任何 run artifact 的 mtime、payload 或 registry entry。

### 10.2 证据正确性

- 取消事实后，该事实不进入 LLM 请求，但完整 snapshot 和 excluded disclosure 保留；
- 报告不能引用已排除、未知或另一 Run 的 fact；
- 新 provider 能在不修改主 Report 组件的情况下显示事实、限制和 validation level；
- unknown/unavailable provider 显示缺失原因而不是静默消失。

### 10.3 论文标准

- 缺少必需章节、引用、图表或模型族模块时生成状态不是 `exportable`；
- fact table 之外的数字、区间、p 值、样本量和模型选择会被拒绝或标记为未验证；
- 适用能力必须出现在对应章节，未执行诊断必须明确写出；
- causal/causal-adjacent、model superiority 和 predictive claims 通过专门措辞测试；
- 中文和英文都不能靠重复句子满足最低长度而绕过 evidence coverage。

### 10.4 可扩展性

- 新增模型族至少只需新增 capability manifest、evidence provider、report module 和测试；
- 既有模型族的 report output、fact IDs 兼容策略和历史 revision 可继续读取；
- Report 页面没有按模型族无限增长的条件分支；
- provider budget、section contract、validation level 和 report profile 都是版本化的。

## 11. 明确不在本轮实现

- 不允许用户修改 Workbench 结果或直接编辑 fact value；
- 不建设新的 Run/Data/Export 页面；
- 不把自由代码、用户上传的任意数字或外部论文数字自动纳入 Workbench evidence；
- 不承诺任何模型族自动获得 external oracle 验证；
- 不把 `report.compose` 改造成隐藏的 Agent 自主写作/执行入口；
- 不在本轮实现模型数量扩展，只为后续模型预留统一协议和注册点。
