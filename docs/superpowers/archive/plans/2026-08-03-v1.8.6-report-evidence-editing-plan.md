# Report Evidence and Safe Editing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Upgrade the single Report page into an extensible, evidence-bound, journal-style report workspace with safe narrative editing and explicit exports, without mutating any Run result.

**Architecture:** Keep Run/Graph/Artifact data immutable and add a versioned report-quality boundary above the existing fact-table contract. The frontend will use provider-prefix grouping and a small document/revision layer; the backend will validate report packets, persist immutable revisions, reject result-overwrite fields, and expose explicit result-table export. Existing model-specific result producers remain untouched.

**Tech Stack:** Python 3, FastAPI/Pydantic, pytest, React/TypeScript, Vitest, existing Markdown/report exporters, filesystem artifact registry, formal `scripts/devline_control.py`.

### Step 3: Implement the document model and server boundary

Use a versioned TypeScript model:

```typescript
export interface ReportDocumentV1 {
  schema_version: "workbench.report.document/v1";
  blocks: ReportBlock[];
}

export interface ReportRevisionFields {
  source_report_id?: string;
  evidence_packet_id?: string;
  fact_snapshot_hash: string;
  editor_revision: number;
  validation_status: "draft" | "needs_revision" | "exportable" | "stale";
  document?: ReportDocumentV1;
}
```

Keep Markdown as the editable text surface for this first slice, but parse it into blocks before persistence so future block editors and renderers have a stable seam. Add `sha256` canonicalization for facts, figures, scope, and excluded IDs. Set Pydantic `extra="forbid"` on the revision request and explicitly reject result-like keys in nested document data.

### Step 4: Add the Report page edit flow

When a generated report is open, render an `Edit report` action. Edit mode must provide:

- a textarea labelled `Report editor` containing the current Markdown;
- `Save revision`, `Cancel`, and `Reset to generated draft` actions;
- a visible `Draft / needs revision / exportable / stale` status;
- a read-only evidence summary and no fact-value input;
- saved revisions in the existing per-run history list.

Saving creates a new record ID, leaves the parent report untouched, sends the full fact snapshot plus excluded IDs, and updates the current view only after the server/local persistence succeeds. If the active Run changes, the draft is marked stale rather than rebound.
