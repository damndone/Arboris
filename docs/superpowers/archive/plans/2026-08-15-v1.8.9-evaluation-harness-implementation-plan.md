**Goal:** 先完成并关闭与 feature 实现分离的 Evaluation Harness 实现线，再用 E1/E2/E3 独立 formal run lines 对 Integration 生成的 exact candidate commits 产出不可变、可追溯的 evidence manifests 和 sidecar admissions。

**Architecture:** Evaluation 在独立 worktree 中维护自己的 runner、fixtures、tests 和 evidence manifests，不修改产品代码、feature tests、golden 或容差。Runner 读取一个明确、干净、只读的 candidate worktree 和 exact SHA，使用冻结输入与独立 expected facts 验证该 candidate；任何 central contract/registry/wiring 变化都要求新的 evaluation id。

**Tech Stack:** pytest、FastAPI TestClient、Vitest、TypeScript、subprocess fixed-command runner、JSON evidence manifests、canonical SHA-256、formal devline control。

- [ ] **Step 2: implement candidate identity checks**

Runner 接受 `--candidate-worktree`、`--candidate-sha`、`--suite` 和 `--output-dir`。它通过固定参数数组调用 `git -C <path> status --porcelain`、`git -C <path> rev-parse HEAD` 和预声明 test commands；拒绝 dirty、SHA mismatch、路径不是 worktree、suite 不在 enum 或 output 已存在。不得接受 command string、shell expansion 或任意 environment override。

Candidate evaluation 必须在 Work Order 冻结的 candidate checkout 执行：backend cwd=`$V189_CANDIDATE_WORKTREE/backend`，interpreter=`$V189_CANDIDATE_WORKTREE/.venv/bin/python`，`PYTHONPATH=$V189_CANDIDATE_WORKTREE/backend`，tests/runner/product source 均解析到 candidate；frontend cwd=`$V189_CANDIDATE_WORKTREE/frontend`，使用 candidate 的 package lock、Vitest/TypeScript config 和 source。Harness self-test 与 candidate evaluation 是两类不同命令。测试必须记录并断言 imported `workbench.__file__`、frontend source root、interpreter 和 `git HEAD` 全部属于 candidate；expected sealed facts 来自 evaluator-only store。

- [ ] **Step 3: implement append-only manifest**

每次 run 产生新 `evaluation_id`，至少保存 evaluated commit、wave/contract/catalog digest、fixture digests、commands、environment/runtime、case totals、pass/fail/not_verified、failure refs、browser/provider mode 和 started/finished time。manifest 不保存 secrets、raw user data 或 provider raw prompts。

- [ ] **Step 4: run tests and mutation**

临时允许 dirty candidate 和覆盖已有 manifest；测试必须失败后恢复。
