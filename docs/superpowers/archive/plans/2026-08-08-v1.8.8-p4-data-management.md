# P4 Data Management Implementation Plan

> **For agentic workers:** Follow this plan task-by-task. Every new assertion must be red for the intended reason before production implementation, then green. Keep mutation failures and formal-line evidence in the handoff.

**Goal:** Close the P4 data-management natural-language gap by registering and executing typed transformation steps through the P0–P3 declaration seam, while preserving real dataset identity, fail-closed validation, graph provenance, and the existing model lifecycle.

**Architecture:** `WORKFLOW_STEP_SPEC_CONTRACTS` remains the only source of workflow-step operation identities and their capability metadata. Each data transformation gets its own declaration and `OperationDefinition`; the five feature recipes share one declaration because their persisted contract is already one typed `FeatureRecipeV1`. The four user-facing transforms and the shared feature-recipe definition are natural-language enabled; the atomic operations are composable through `operation.multi_step` while their inputs remain declaration-owned. All data-producing declarations set `produces_dataset=True`, `consumes_input_frame=True`, and `replayable_by_recipe=False`, so P0 forces every downstream consumer to name the persisted `source` binding. A single trusted runtime dispatcher reads the declaration’s operation identity, resolves the injected frame and lineage once, calls the existing preview/apply data services, and publishes the standard `produced_dataset` binding. `list_project_datasets` is a chain-scoped read-only provider tool backed by graph nodes, artifact-index records, and the existing dtype-preserving frame reader. No frontend or top-level orchestrator operation table is added.

**Tech Stack:** Python 3, pandas, dataclasses, JSON Schema, FastAPI provider tools, `OperationRegistry`, `WORKFLOW_STEP_SPEC_CONTRACTS`, `WorkflowExecutor`, `GraphStore`, existing data-operation/FeatureRecipe services, pytest, and the repository’s host full-gate commands.

## Data-operation contracts

The workflow `spec` carries operation-specific fields directly so the projected
`proposal_schema` can require the fields that distinguish one operation from
another. The runtime converts those fields into the existing typed service
specifications; the workflow target supplies the primary source identity and a
P0 `source` commitment supplies an upstream-produced source.

- `data.merge`: required `secondary_run_id`, `secondary_node_id`,
  `secondary_artifact_id`, and `keys`; `how` is `left`, `right`, `inner`, or
  `outer`; optional `indicator` is a boolean true or a non-empty output-column
  name; growth policy fields retain the existing bounded contract.
- `data.append`: the same secondary identity fields; `schema_policy` is
  `exact` or `union`; row growth is explicitly bounded by the existing policy.
- `data.reshape`: `direction` is `wide_to_long` or `long_to_wide`; the
  direction-specific id/value/index fields are closed and semantically required
  for the selected direction.
- `data.subset`: required output `columns`; optional `filters` is a list of
  `{column, op, value?}` with only `eq`, `ne`, `gt`, `ge`, `lt`, `le`, `in`,
  `not_in`, `between`, `is_missing`, and `not_missing`; legacy `equals`,
  `row_indices`, `row_index_range`, and `row_range` remain explicitly supported.
- `data.feature_recipe`: required `recipe_id`, inner recipe `operation_id`
  (`interaction`, `log`, `ratio`, `recode`, or `derived_variable`), `inputs`,
  `output`, and `parameters`; fit/policy fields reuse the typed FeatureRecipe
  contract and reject silent behavior.
- `data.dedupe`: `columns` and `keep` (`first` or `last`).
- `data.rename`: non-empty `mapping` from existing names to distinct new names;
  old-name absence and collisions fail closed.
- `data.aggregate`: `group_by` and non-empty
  `aggregations: [{column, func, output}]`; `func` is one of `sum`, `mean`,
  `median`, `min`, `max`, `count`, or `std`.
- `data.fill_missing`: non-empty `strategies: [{column, strategy, value?}]`;
  strategy is `drop_rows`, `constant`, `mean`, `median`, or `mode`, and only
  `constant` may carry `value`.
- `data.tsset`: `time_column`, closed `frequency`, and optional
  `panel_id_column`; it validates time values and duplicate time/panel keys,
  then performs the declared stable time ordering without adding `data.sort`.
- `data.lag`: non-empty `columns`, positive integer `lags`, and optional
  non-negative integer `difference`; outputs use deterministic
  `<column>_lag<lag>` names and fail on output collisions.

All nested objects reject unknown fields. Runtime validation repeats the domain
checks before reading or writing data, so a workflow cannot compile a permissive
shape and wait until confirmation to discover that it was never executable.
