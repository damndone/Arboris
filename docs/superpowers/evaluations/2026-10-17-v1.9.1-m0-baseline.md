### 1.3 对设计的直接含义

1. F1–F3 合起来说明：**"执行结果回到模型"是本版第一优先**。没有它，两种模式都无从谈起。
2. F4、F5、F7、F8 是工具人机接口问题，占被拒和多余步数的大部分。修法：
   - 补丁扁平化，错误信息附正确示例；
   - 上下文里放项目地图（runs、节点、模型），并给出"当前对象"的确切 id；
   - 重跑允许改回归元；
   - 全精度数值按引用读取。
3. F6 来自两个 Agent 身份：合并为一个，能力相同，只是焦点不同。
4. 没有完整分析的历史任务，说明评测集必须从头建，不能只用回放。

## 3. 评测集（M0.3，2026-10-18）

### 3.1 开发集：21 个已知真值情境 × 3 种问法 = 63 个任务（`dgps.py`、`tasks.py`）

**21 个情境**：
- 横截面：异方差、遗漏变量；
- IV：有效、弱工具，并带一个违反排除限制的候选工具；
- 面板固定效应；DID：2×2、交错且效应异质（这里 TWFE 有偏：试跑 1.68，真值 2.57）；
- 时间序列：伪回归、协整、GARCH；
- 过度离散计数、二元结局、按班级随机的实验、重复测量、依赖结局的缺失；
- 高杠杆点、生存分析、分位数异质、近似共线；
- 脏数据（-99、"n/a"、重复行）、分层抽样均值。

**每个情境声明**：
- 真值和容差；
- 适用的模型族；
- 必做的检查（`a|b` 表示两个操作 id 等价）；
- 已知陷阱。

**数据生成过程已验证会产生设计的偏差**：
- IV 中 OLS 为 0.149，真值 0.10；
- 高杠杆点使全样本斜率为 −0.24，去掉后 0.99；
- 完整个案斜率 0.56，真值 0.70；
- 遗漏能力时 0.087，加控制后 0.059。

**3 种问法，都不点名方法**：
- `open`（中文，只给研究问题）；
- `specific`（英文，说明交付物要包含什么）；
- `goal`（中文，从最终产物反推）。

### 3.4 运行与评分

**模拟用户**是确定性的，不用模型：
- 有提案就全部确认；
- 否则发固定的"请继续……完成后回复「分析完成」"；
- 最多 8 次。

"用户操作次数"= 确认次数 + 催促次数。

**提问方式按 v1.9.0 界面的默认**：
- 链会话聚焦导入后的模型节点；
- `execution_policy = proposal_only`。

这一点所有版本都相同。

**基线运行环境**：
- 基线运行时间长，而模型运行会在需要时才导入产品代码。为不受开发影响，基线在固定于 tag `v1.9.0` 的独立检出里运行（`.worktrees/eval-v190-baseline`，devline 事件 `baseline_runs_from_pristine_checkout`）；
- 该检出 `backend/`、`frontend/` 无改动，每轮在 `run_meta.json` 记录产品树哈希。

**评分**：
- 确定性部分：
  - 磁盘上的模型及其设定；
  - 台账里 Agent 执行的操作；
  - 是否有合格模型恢复了真值；
  - 检查覆盖率；
  - 产品自带的数字核对（`numeric_grounding.check`）对用户实际看到的回复；
  - 录制的 usage。
- 评委部分：五个维度各 1–5 分（`judge.py`），评委看得到真值，Agent 看不到。
- 评委校准：我先盲评一部分任务，计算我和评委的一致性（κ），再请用户抽查。

**pass^3**：每个情境取 `open` 问法共 21 个任务，各跑 3 次，3 次都恢复真值且标记完成，才算该任务通过。

**试跑**（v1.9.0，`cs_hetero.open`）：
- 8 次用户操作，168 s，16 次模型调用；
- prompt 86 万 token，缓存命中 90.8 %；
- 恢复了真值，评委 4.2 / 5。

### 3.5 基线期间发现并修复的产品缺陷

**缺陷**：
- Agent 工作流里的 `iv.gmm` 和 `iv.weak_instruments` 不加截距。数据里没有常数列时（几乎总是这样），第一阶段和 GMM 都过原点估计。
- 基线任务 `iv_valid.goal` 里，偏 F 报为 6223.5，正确值是 170.6（statsmodels 重算，有截距 / 无截距两种分别对上）。
- `iv_weak.goal` 因此把真实第一阶段 F 约为 4 的工具说成"很强"。

**修复**：commit `89357e5f`，经用户 2026-10-18 同意，在基线运行期间修复。
- 适配器默认加截距，`intercept: false` 可关；绑定列里已有常数列时不重复加。
- 新测试 `tests/test_iv_workflow_intercept_oracle.py` 走注册操作的消费路径，与 Stata 18 对照：
  - 偏 F、残差自由度、HC0 稳健 Wald F 一致到 1e-9；
  - 2SLS 与两步 GMM 系数和 `ivregress` 一致，并另与闭式两步 GMM 一致。
- devline 事件：`iv_workflow_adapter_omits_intercept`（FAILURE）、`iv_workflow_intercept_fixed`。

**对比较的影响**：基线（v1.9.0）在 IV 任务上带着这个缺陷运行，v1.9.1 的 IV 任务改进有一部分来自修复本身，而不是 Agent。所以 IV 情境（`iv_valid`、`iv_weak`、复现挑战里的 AJR 与 AK91）在所有比较中**单列报告**，总体指标同时给出含 IV 与不含 IV 两个版本。

| **产品合同摩擦** | `ts_garch.goal/specific` | ARMA-GARCH 规格嵌套很深：`INVALID_ORDER: unknown variance field p, q`、`missing … validation`、`TIME_PARSE_FAILED`，共失败 5 次 | M3-13 |
| **产品合同摩擦** | `survival` ×3 | `survival.rmst` 要求必须显式给 τ，没有按随访上限取默认值；`tabulate` 不支持 `group_by` | M3-13 |

| **Agent 判断** | `lmm_repeated.goal`、`count_overdispersed.goal` | 只看了描述统计和导入时那个 OLS，就宣布"分析完成" | 完成前自检（M3-10） |

| **已修复的产品缺陷** | `iv_weak.goal` 等 | IV 截距缺陷（§3.5） | 已修，IV 单列 |

结论：
- 剩下的失败约一半是**产品合同与能力**问题（Agent 想做对的事，但工具不让、或报错不说清楚），另一半是 **Agent 判断**（不做、过早结束、过度请示）。
- 两类都在 v1.9.1 范围内，分别对应 M3-13（工具人机接口）和 M3-10（剧本与完成前自检）。
- 剩下的失败里，评分器的问题已修完；凡是新暴露的评分器问题，都会先修再计。

### 4.2 token 去哪了（63 个 r1 任务、813 次调用）

单次请求平均 30.5 万字符：

| 部分 | 占比 | 每次调用平均 |
|---|---:|---:|
| 历史中的工具结果 | 51.5 % | 15.7 万字符 |
| 系统消息（协议里内联了操作目录） | 29.7 % | 9.1 万字符 |
| 工具 schema | 14.9 % | 4.5 万字符 |
| Agent 与用户的文字 | 4.0 % | 1.2 万字符 |

工具结果里最大的是 `inspect_operation_contract`：每次返回约 **17.2 万字符**（等于把操作目录再发一遍），一共被调用 68 次。它一旦进入历史，后面每一轮都会重发。这一项就占工具结果字符的 90 % 以上。

改法（M3-13）：
- 合同按需返回单个操作，不再整本返回；
- 常驻的操作目录只留索引；
- 工具结果按引用存放，历史里只留摘要。

按上表估算，每次调用可减到原来的约三分之一。

### 4.4 评分器的改动记录与冻结

## 6. 评委与校准（第 1 轮，2026-10-18）

两个评委都用用户自己的订阅，不花 DeepSeek 的钱：Codex 评了全部 67 个任务（63 个开发集 + 4 个 BLADE），Grok 评了 20 个用作交叉校准，0 次失败。日志在 `local/agent-eval/judging-baseline.log`。

| 一致性（20 个共同任务，每个任务 5 个维度） | 二次加权 κ | 完全一致 | 相差 ≤ 1 分 | 均分 |
|---|---:|---:|---:|---|
| Codex vs Grok | **0.83** | 0.67 | 0.99 | 3.23 vs 3.47 |
| Claude 盲评 vs Grok | 0.47 | 0.47 | 0.85 | 3.97 vs 3.47 |
| Claude 盲评 vs Codex | 0.33 | 0.39 | 0.72 | 3.97 vs 3.23 |

**解读**：
- 两个来自不同厂商的评委高度一致。
- 我（Claude，也是开发者）的盲评系统性偏宽，平均高 0.5–0.7 分，主要偏在"可追溯性"（4.4 vs 2.65–2.95）和"结论"上。
- 看了分歧最大的任务，评委抓到的问题大多是真实的，我在盲评时漏看了：
  - GARCH 实际只用了 1250 个训练样本，报告里写成"全样本 1500"；
  - 违例次数报成 19，按 233/250 算应为 17（整数小于 1000，产品的数字核对按规则不检查）；
  - "64% 的关联来自企业间差异"这个分解没有依据。
- 因此我的盲评**不能当人工校准用**，只作为第三个评委之一；人工校准需要用户抽查。

**评分材料的缺口**：有一部分"不可追溯"是评委冤枉的。
- 33 份材料里的分析结果被截到 1500 字符；
- 导入时那个模型、R² 等拟合统计没有放进材料；
- Agent 在对话中实际收到的工具结果（例如解释限制）也没有放进去。

已修正：材料改为包含全部模型（导入模型单独标出）及其拟合统计、每个分析结果最多 4000 字符，以及 Agent 收到的工具结果（剔除操作目录，总长不超过 3 万字符）。修正后材料中位数约 4.5 万字符。**修正后需要重评**，是否重评等用户批准。

**第 1 轮基线**（Codex，63 个开发集任务）：均分 2.85。各维度：方法 3.75、诊断 2.68、稳健性 2.44、结论 3.00、可追溯性 2.38（最后这项受上面的材料缺口影响，偏低）。

**由此得到、与 v1.9.1 直接相关的两条发现**：
1. 产品的数字核对不检查小于 1000 的整数，可报告里的计数、样本量、违例次数正是最常写错的地方。M3-13 要把计数类数字纳入核对：只要能在结果里找到对应的计数，就核对。
2. 结论里没有依据的说法（这里是一个"分解"）只有评委看得出来。这正是 M3-12 独立复核子 Agent 要做的事。
