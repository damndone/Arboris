### 1.3 对设计的直接含义

1. F1–F3 合起来说明：**"执行结果回到模型"是本版第一优先**。没有它，两种模式都无从谈起。
2. F4、F5、F7、F8 是工具人机接口问题，占被拒和多余步数的大部分。修法：
   - 补丁扁平化，错误信息附正确示例；
   - 上下文里放项目地图（runs、节点、模型），并给出"当前对象"的确切 id；
   - 重跑允许改回归元；
   - 全精度数值按引用读取。
3. F6 来自两个 Agent 身份：合并为一个，能力相同，只是焦点不同。
4. 没有完整分析的历史任务，说明评测集必须从头建，不能只用回放。

缓存（DeepSeek 在流式最后一块返回 `prompt_cache_hit_tokens`，试跑实测）：
- 同一会话内，第二次调用起命中 29,824 / 30,016，约 99%；
- 每个新会话的第一次调用命中为 0。原因是会话专属内容（节点上下文）排在协议之前，跨会话的公共前缀断在第一条消息。

**录制工具自身的一个问题**：第一版录制在转发响应时保留了 `content-encoding` 头，客户端二次解压失败，适配器就把成功的请求重发了 3 次。已修复，修复前的试跑记录全部作废、重跑。这说明录制工具本身也要像产品代码一样验证。

**试跑一项完整任务**（`cs_hetero.open`，v1.9.0）：
- 模拟用户共 8 次操作：4 次确认、4 次"请继续"；
- 用时 168 s，16 次模型调用，prompt 861,377 token（缓存命中 90.8%），completion 21,632 token；
- 恢复了真值：对数工资上教育系数 0.0834，CI [0.0755, 0.0913]，覆盖 0.08；
- 评委评分 4.2/5：没做 RESET 和 VIF，扣在诊断。

对设计的含义：
1. 操作目录改为按需加载：常驻的只是名字加一句话，完整合同经 `inspect_operation_contract` 读取。每次调用估计可减约 1.5 万 token。
2. 常驻内容按"跨会话不变 → 项目不变 → 会话专属"排序，使跨会话的前缀也能命中缓存。
3. 一项完整分析在 v1.9.0 上可以做出来，但每一步都要人推。这正是两种执行模式要解决的问题。

## 3. 评测集（M0.3，2026-10-18）

代码在 `scripts/agent_eval/` 与 `scripts/agent_eval_run.py`、`scripts/agent_eval_grade.py`。数据和运行记录在 `local/`，不入 Git。

### 3.1 开发集：21 个已知真值情境 × 3 种问法 = 63 个任务（`dgps.py`、`tasks.py`）

**21 个情境**：
- 横截面：异方差、遗漏变量；
- IV：有效、弱工具，并带一个违反排除限制的候选工具；
- 面板固定效应；DID：2×2、交错且效应异质（这里 TWFE 有偏：试跑 1.68，真值 2.57）；
- 时间序列：伪回归、协整、GARCH；
- 过度离散计数、二元结局、按班级随机的实验、重复测量、依赖结局的缺失；
- 高杠杆点、生存分析、分位数异质、近似共线；
- 脏数据（-99、"n/a"、重复行）、分层抽样均值。

**每个情境声明**：
- 真值和容差；
- 适用的模型族；
- 必做的检查（`a|b` 表示两个操作 id 等价）；
- 已知陷阱。

**数据生成过程已验证会产生设计的偏差**：
- IV 中 OLS 为 0.149，真值 0.10；
- 高杠杆点使全样本斜率为 −0.24，去掉后 0.99；
- 完整个案斜率 0.56，真值 0.70；
- 遗漏能力时 0.087，加控制后 0.059。

**3 种问法，都不点名方法**：
- `open`（中文，只给研究问题）；
- `specific`（英文，说明交付物要包含什么）；
- `goal`（中文，从最终产物反推）。

### 3.4 运行与评分

**模拟用户**是确定性的，不用模型：
- 有提案就全部确认；
- 否则发固定的"请继续……完成后回复「分析完成」"；
- 最多 8 次。

"用户操作次数"= 确认次数 + 催促次数。

**提问方式按 v1.9.0 界面的默认**：
- 链会话聚焦导入后的模型节点；
- `execution_policy = proposal_only`。

这一点所有版本都相同。

**基线运行环境**：
- 基线运行时间长，而模型运行会在需要时才导入产品代码。为不受开发影响，基线在固定于 tag `v1.9.0` 的独立检出里运行（`.worktrees/eval-v190-baseline`，devline 事件 `baseline_runs_from_pristine_checkout`）；
- 该检出 `backend/`、`frontend/` 无改动，每轮在 `run_meta.json` 记录产品树哈希。

**评分**：
- 确定性部分：
  - 磁盘上的模型及其设定；
  - 台账里 Agent 执行的操作；
  - 是否有合格模型恢复了真值；
  - 检查覆盖率；
  - 产品自带的数字核对（`numeric_grounding.check`）对用户实际看到的回复；
  - 录制的 usage。
- 评委部分：五个维度各 1–5 分（`judge.py`），评委看得到真值，Agent 看不到。
- 评委校准：我先盲评一部分任务，计算我和评委的一致性（κ），再请用户抽查。

**pass^3**：每个情境取 `open` 问法共 21 个任务，各跑 3 次，3 次都恢复真值且标记完成，才算该任务通过。

**试跑**（v1.9.0，`cs_hetero.open`）：
- 8 次用户操作，168 s，16 次模型调用；
- prompt 86 万 token，缓存命中 90.8 %；
- 恢复了真值，评委 4.2 / 5。
