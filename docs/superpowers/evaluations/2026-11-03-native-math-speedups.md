## 1. 剖析（改动前）

详见 `PROFILE.md`。方法：每 2 ms 对所有线程采样调用栈。cProfile 在统计阶段的双线程下归因失真，
比如它把 2.6 s 记到 pandas `.loc`，采样只有 0.55 s。

- **导入 + OLS 5.85 s：** 统计检验 2.41 s（core 线程 2.38 s 是关键路径，advanced 线程 1.40 s 与它并行），
  估计 1.47 s（OLS 合同 0.84 s，其中指纹 0.6 s；拟合本身很小），清洗 0.49 s，诊断 0.36 s，读入 0.35 s，报告 0.28 s。
- **core 线程：** 秩相关 1.08 s（Kendall 原生计数 0.52 s，6 对串行；Spearman 原生求秩 0.33 s，同一列在 3 对里各排一次），
  Kruskal 0.38 s，MWU 0.29 s，Pearson 0.23 s，ANOVA 0.18 s，Welch 0.18 s（把 100 万个值转成 Python list，逐个 `float()`，再用内置 `sum()`）。
- **summarize detail 3.18 s：** `_stata_percentile` 每算一个分位数，就把整列转成 Python list 重新 `sorted()` 一遍：3 列 × 9 个分位数 = 27 次 100 万元素排序。
- **其他族：** IV 8.35 s 里 diagnostics 5.5 s（linearmodels `IVData` 用 `list(range(n))` 建 pandas 索引 2.3 s）；
  DID diagnostics 2.4 s、Cox 估计 3.8 s、Panel 估计 1.6 s，都在 linearmodels/statsmodels 内部；
  wide 的统计阶段在该750行输入累计7.1 s（Tukey积分累计2.6 s，已是C++多线程）；必须同时考虑列对数、组数和调用次数，不能称固定启动开销。
- **perf_1m 的 14 项：** 只有 summarize detail（3.18 s）、export dta（4.01 s，pyreadstat 自己逐行循环）、
  export csv（1.60 s，pandas）超过 1 s，其余都在 0.6 s 以内。

## 2. 改了什么

| 改动 | 为什么逐位相同 | 证明 |
|---|---|---|
| **分位数每列只排一次**（NumPy；有负零时用稳定排序） | 稳定排序和 `sorted()` 用同一个 `<`，相等的值保持输入顺序，所以 ±0 的次序也相同；NaN 和非数值类型仍走原来的排序 | 13 个分位数 × 11 种列类型（含 ±0、Int64/Float64 可空、uint64、bool、float32、NaN），最多 10 万行，与原实现比较 |
| **Rust `arboris_python_sum`**：逐位复刻 CPython 3.12+ 的 Neumaier 求和；用在 `_GroupSummary`，Welch 直接传 float64 数组 | 同样的运算、同样的顺序；加载时与内置 `sum()` 自检，不一致就退回 Python | 7 种分布（大指数跨度、正负抵消、±0、inf/NaN、溢出）、最多 25 万行；另有 936 个特殊情况的原始比对 |
| **Spearman 每列只求一次秩**，缓存到这一轮结束 | 内核按列独立求秩，整数列精确提升，所以同一列和谁配对，秩都一样；按原来的 Fortran 布局拼回 | 整个统计阶段（12 万行双线程、2000 行串行）与原路径比较 |
| **Kendall 计数放到一个后台线程**（10 万行以上），结果按原顺序放回 | 每次调用完全相同，只是换了线程；失败和取消照常传到调用方 | 同上；另测失败、取消、小表保持串行 |

`native/kernels` 的 ABI 从 1 升到 2。旧构建会报 “ABI mismatch”，这是加载器的既定行为，不会静默变慢；
合并后每个 worktree 要重跑一次 `native/kernels/build.py`。

**机械检查：** `tests/test_default_path_speedups.py`（差分测试和回归测试），
`tests/test_python_float_loops_guard.py`（静态检查：不许再出现 `sum(map(float, …))`，只有内核自检和回退处例外）。
用变异测试确认差分测试有效：求和结果差 1 ulp、分位数改用不稳定排序、缓存里两个秩对调，都会让测试失败。

### 关于内存

整条 OLS 流程的峰值 RSS 中位数高了 4–9%，但这个指标本身噪声很大：同一份基线代码的 10 次运行在 1249–1896 MiB 之间。
每 5 ms 采一次 RSS（`profile/rss_timeline.py`）显示，峰值出现在统计阶段之后的估计、诊断、报告阶段，这些代码没有改；
统计阶段自身的峰值基线 1359/1239 MiB、改后 1260/1310 MiB，看不出差别。只调用统计阶段的 A/B 能隔离改动的代码，
两轮分别是 +1.4% 和 +3.2%，在 1.05 倍预算内（来源：缓存的秩约 32 MB，以及后台 Kendall 的一份输入快照）。
没有做 tracemalloc 内存专项；perf_1m 的正式 `--ab` 门在有别的测试运行时会拒绝启动，这次机器一直不空闲。

## 4. 试过但没用、或没做的

- **wide 第一版慢了 4.5%（8.175 → 8.542 s，噪声 1.6%）。** 750 行时每次 Kendall 主要是 Python 代码，持有 GIL，
  放到后台线程只增加了线程切换。现在只在 10 万行以上（统计阶段本来就开双线程的门槛）才用后台线程；复跑 7.960 → 7.716 s。
  已加回归测试。
- **wide 本身没变快。** 该输入统计阶段累计约7 s：Tukey 二重积分 2.6 s（已是 C++ 多线程；被积函数是 SciPy 编译出来的，
  Rust 要逐位复现必须重现 clang 的 FMA 合并，做不到）、Shapiro 0.71 s、Kruskal 1.05 s（一半是 pandas 每次切分）、Fisher 0.51 s。
- **分位数排序用 Rust。** NumPy 排序本来就是原生代码（100 万个浮点 26 ms），Rust 最多再省几十毫秒，不值得多一个原生依赖。
- **Kendall 计数用 Rust 重写。** 现有 C++ 已是 O(n log n)，每对约 87 ms；放到后台线程以后它已不在关键路径上，重写省不了墙钟时间。
- **规范 JSON 指纹直接从数组编码。** 剩余收益约 0.3 s，要在 Rust 里逐位复现 Python `repr` 的最短浮点格式，相邻代码在受保护的 `contracts/model` 里。没做。
- **秩矩阵的内存布局。** 原以为缓存的秩按 C 顺序拼回会改变 `np.corrcoef`；变异测试显示这里不会。仍按 Fortran 布局拼回，和原调用保持同一形状。
- **新编译的 dylib 第一次加载要 0.37 s**（macOS 对新二进制的一次性检查），之后 0.3 ms，自检 21 ms。不是重复成本。
