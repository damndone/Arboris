# 原生引擎决策：先测瓶颈，再选语言（2026-11-01）

基准：`scripts/perf_engine_baseline.py`（`local/perf-evidence/engine-baseline-20261101/report.json`）和 `scripts/perf_native_engine.py`（`local/perf-evidence/native-engine-ab-20261101/report.json`）。机器：M4 Pro，12 核，24 GB，Python 3.14.6，NumPy 走 Accelerate。

## 五个判断，分别对照数据

| 判断 | 测量 | 结论 |
|---|---|---|
| 依赖和部署包臃肿 | site-packages 585 MB：pyarrow 122、scipy 93、pandas 66、statsmodels 51、sklearn 44 | **成立**。纯 Python 无法再明显减小 |
| 冷启动慢 | `workbench.api` 1.48 秒、261 MB；`workbench.orchestrator` 0.67 秒、187 MB；Python 本身 0.02 秒 | **成立，但不是一次分析的主因**：占 8 秒分析的不足 10%。对 CLI 和批量任务才关键 |
| 数据处理和调度开销大 | OLS 剖析 9.41 秒中，线性代数只有 0.12 秒；其余是 pandas、作图、统计、合同构建 | **成立，而且比预想严重** |
| 解释执行、对象、序列化开销 | 100 万行上有数百万次逐元素循环；IV 有 800 万次 `deepcopy`；Cox 的 `_json_safe` 调用 185 万次 | **成立** |
| 长期需要更好的架构 | 同一次拟合，原生进程快 13–18 倍，内存降到 1/3–1/6 | **成立**，但见下面的边界 |

**没有想到的一点：** 真正的数学运算（LAPACK、已有的 C++ 模块）已经很快，重写它们回报很小。Mann-Whitney 看起来是热点，单次其实只有 0.09 秒，所以没有重写。时间花在数学之外。

## 语言选择：Rust，纯标准库

- **为什么不继续用 C++：** 现有 C++ 模块是 Python 扩展，依赖 Python ABI 和 SciPy 的 capsule，留在进程内加速没问题，不能脱离 Python。独立引擎需要一个不靠 Python 的单文件程序。
- **为什么是 Rust：** 内存安全，并行不易出数据竞争，工具链本机已有，产物是单个文件。
- **不用第三方 crate：** 不增加依赖，也不需要审批。线性代数是自写的 Householder QR，不依赖 BLAS，所以结果不随机器上的数学库变化。
- **现有 C++ 模块不动：** 它们成熟、逐位相同，重写没有收益。

## 原型：`native/engine`（`arboris-engine`）

支持 OLS（经典、HC0、HC1）、2SLS（稳健）、双向固定效应（实体聚类）。读 CSV，输出一个 JSON；缺失单元格的行会被删除并计数；共线、非数值列等无法识别的情况报错退出（退出码 2），不猜结果。

### 同一计算的 A/B

相同的固定输入（带 SHA），全新进程，5 次基线校准加 5 对交替运行，只做读取和这一次拟合。

| 场景（100 万行） | Python 库 | Rust 引擎 | 提速 | 内存（Python → Rust） | 时间噪声 |
|---|---:|---:|---:|---:|---|
| OLS + HC1 | 0.863 秒 | 0.064 秒 | **13 倍** | 610 → 210 MiB | 1.2% / 1.6% |
| 2SLS 稳健 | 1.494 秒 | 0.109 秒 | **14 倍** | 1041 → 275 MiB | 0.9% / 3.7% |
| 双向固定效应 | 2.078 秒 | 0.116 秒 | **18 倍** | 1424 → 224 MiB | 2.1% / 3.8% |

冷启动：引擎约 1 毫秒内（`time` 显示 0.00 秒），Python 加这些库 0.68 秒。程序大小 0.42 MB，对比 585 MB 的依赖。

### 数值核对

- **产品录制结果（100 万行，`scripts/compare_native_engine.py`）：** 系数和标准误最大相对差 8.75e-13，置信区间 1.09e-11，R² 1.38e-13。`hours` 的 p 值显示差 1.9e-6，是因为产品记录保留 5 位小数（0.19578）；引擎的 0.19577962679620 与 SciPy 的 0.19577962679620 差 6e-15。其余 p 值在极端尾部。
- **statsmodels（5 种规模，30 到 20 万行，3 种协方差）：** 系数、标准误、t、p、区间、R² 差异都在 2e-13 以内。
- **linearmodels：** 2SLS 和双向效应在 1e-10 容差内相同。**p 值只有一处例外**：linearmodels 用 `1 − CDF`，极端尾部丢精度，直接得 0；引擎给出 2.09e-49，这里用 SciPy 的 `norm.sf` 对照。
- **可复现：** 1、2、7 个线程的结果逐字节相同（测试保证）。
- 测试：`tests/test_native_engine.py`，12 项。

### 边界

- **不是默认路径，也不是逐位相同：** 差异在 1e-13 量级，但项目规则要求默认路径系数逐位相同，所以它没有接入。
- **覆盖面小：** 3 个模型；没有公式、分类变量展开、权重、Parquet；没有诊断、证据链、报告。
- **13–18 倍只针对拟合本身：** 产品一次 OLS 要 7.84 秒，其中拟合约占两成。只替换拟合，整体大约只能快一成多。
- **只在这台 Mac 上跑过。** 不依赖 BLAS，原则上可移植，但还没验证。

## 路线

1. **把 Python 留作编排，分层迁移。** 引擎以进程和 JSON（之后是 C ABI）为边界，Python 调用；不做一次性重写。
2. **先处理占时间的阶段，而不是数学：** 统计、诊断、作图的原始数据准备，以及合同构建中把 100 万行转成 Python 字符串的部分。
3. **让默认路径可以接纳原生结果：** 这是一个产品决定。要么放宽为“差异 < 1e-10 且有证据”，要么让原生引擎只用于批量和 CLI 这样新开的路径。
4. **用单独进程跑长任务：** 引擎不加载 Python，可以并行上百个规格，批量研究最适合先用。

## 这一轮顺带查清的问题

IV 的主要开销在 `linearmodels` 内部：`IVData` 把行标签转成 Python 列表并深拷贝（2.5 秒 + 1.5 秒，带剖析器）。默认路径不能打补丁改第三方库，所以这是把 IV 迁到原生引擎最直接的理由。

## 用户决定（2026-11-02）

保持逐位规则。`native/engine` 的 OLS/2SLS/固定效应与默认路径约差 1e-13，所以不接入默认路径。默认路径只接受逐位相同的原生代码，例如 `native/kernels`：它按 NumPy 的运算顺序计算，加载时与 NumPy 比对，不一致就让回 Python。
