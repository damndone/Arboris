Reviewer: Claude, at the user's request. Scope: `54814fa2`, `9516c643`, `0c513596`, `a2484eb8`,

### 1. Focused questions now get a forced completion recovery (54814fa2) — should be measured before it ships

`delivery._computed_question_request` gives a question-scope answer with a computed result and no
completion contract the bounded recovery (`recovery_scope: question`). It was validated on the
five binary_logit positions, where it removes the goal.r1 nudge.

Replaying QRData round 7 (55 focused questions) at `fa70e117`: **50 of 55 tasks now receive a
completion recovery; before the change, none did.** Each recovery is at least two more model
requests (an `update_plan` call, then the answer again). The median QRData task used 4 requests,
so this is roughly +50% requests on the product's most common kind of question, to save a
contract the person did not ask for. The earlier rule ("a focused question with no contract stays
quiet") was deliberate, and its test was edited in this commit.

The QRData harness stops at FINAL ANSWER, so its score will not show this; real conversations will.

Suggested: limit the recovery to requests that ask for a deliverable (the goal.r1 wording), or
bind the computed result on the server without a model round trip. Either needs the user's
decision, since it changes what "complete" means for a plain question.

Decided and fixed on 2026-11-14 (the user's "you decide"): the recovery stays, limited to requests
that ask for the work to be finished (`task_requirements.FINISH_REQUEST`: "请完成", "做完", "finish
this", "complete the …"). The goal.r1 wording matches; a plain question stays quiet. QRData round 7
replay afterwards: 0 of 55 tasks receive a completion recovery (50 before), tool results unchanged.
The wording rule is a heuristic of the same kind as `FULL_ANALYSIS`; binding on the server with no
model round trip remains the better long-term design and is not done here.

### 2. No step carries its contract in the prompt any more (fa70e117) — an unmeasured trade

All inline signatures and the four reference step specifications were removed (vocabulary
53,028 → 24,763 characters, about 7,000 fewer prompt tokens per request). The reference steps
were inlined on 2026-10-23 because they were the most fetched contracts (model.genesis 116,
report.compose 97, statistical.explore 75 of 228 reads), and signatures were added after the
refusal audit (13 of 29 refusals were guessed field names). `statistical.explore` and
`model.genesis` are 60% of all recorded step uses.

In recorded rounds, 65% of QRData tasks and 80% of the binary_logit positions wrote at least one
step, with 0.44 and 1.40 contract reads per task. With nothing inline, each of those tasks needs
at least one contract read before its first step. For a 4-request task that is one more request
for about 28,000 fewer prompt tokens: fewer tokens, more requests, and the refusal rate is
unknown. The commit says plainly that this was not measured live; this review agrees and
adds that the short-task case is the one most likely to get worse.

Suggested: keep the reference steps (or at least statistical.explore and model.genesis) inline
until a live batch compares both variants on short and long tasks.

Decided and fixed on 2026-11-14, by measurement on the 55 recorded QRData tasks (36 wrote a step):

| In the prompt | Tasks needing a contract read first | Vocabulary size |
|---|---|---|
| nothing (fa70e117) | 36 | 24,763 |
| statistical.explore reference only | 23 | about 26,300 |
| 43 field signatures + statistical.explore reference (now) | 5 | 35,775 |
| the above + model.genesis, report.compose, data.subset references | 0 | about 46,000 |

The 42 measured signatures plus data.subset (8.8 KB) and the statistical.explore reference (1.5 KB)
are back: about 2,700 prompt tokens per request, keeping about 60% of the saving. model.genesis
(6.7 KB) stays on demand; a task that fits a model reads it once. Not measured live.

### 3. Request admission halves the usable Ask turn on the NVIDIA route (fa70e117) — works as designed, margin is thin

A request is not sent when the turn's remaining time is less than the provider's configured wait.
NVIDIA's is 300 s; turn budgets are 600 s (Ask), 1,200 s (Auto) and 300 s (no mode). So an Ask
turn sends nothing after its 300th budget-second, although the median NVIDIA request took about
20 s of budget time in the last batch. In that batch no request would have been refused; the
latest one started about 262 budget-seconds into its turn. A turn that is refused ends
`blocked` and needs the person to continue, which is a nudge under the M0.5 definition.

With no execution mode (direct API use; the UI always sends one) the budget equals the wait, so
the first request is refused once any time has elapsed. The tests cover the 60 s case and exact
equality, not this configuration.

Suggested: admit on an observed bound (for example the slowest completed request this turn, or a
percentile) rather than the full configured wait, or raise the no-mode budget above the largest
configured wait. A decision for the user: it trades a wasted request against an early stop.

Decided and fixed on 2026-11-14: every admission check point stays; what a request must fit is now
the slowest request completed in this turn, never more than the configured wait. A turn with nothing
observed (the first request, and a turn resumed after a restart) keeps the configured wait. The
test for this change is a recorded turn: after requests of 183, 103 and 105 s, 209 s remained, and the
fourth request (161 s) was refused although it fit; now it is sent and the fifth (48 s left) is not.
A request slower than anything seen in its turn can still be cut by the turn timeout, as before
fa70e117. Left as designed: with no execution mode on a 300 s wait the turn budget equals the wait
and the stop message asks for a configuration change; the UI always sends a mode.
