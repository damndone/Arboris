## 1. 现状（修改前）

- **真实运行**（第七轮 55 个 QRData 任务的事件时间戳，`diagnostics/recorded-round7-gaps.txt`）：每步非模型开销中位
  **57.6 ms**，p90 72 ms，最大 85 ms；目标 ≤ 300 ms **已满足**。其中发送前组装 6.5 ms，收完到落盘 21.5 ms，步间（工具执行+持久化）32.4 ms。
- **离线完整回放**（新工具 `scripts/perf_agent_turn_replay.py`：真实 headless Agent、真实工具与审批，用录好的 provider tape，禁止联网）
  把轮次启动和收尾也算进每步，所以数字比事件间隔大：每步中位 65–133 ms，仍低于 300 ms。
- 开销随会话变长而增长。剖析（`diagnostics/spans-*`）显示主要是设计问题，不是语言问题：
  1. 会话日志每追加一条就**整文件读出再重写**（真实会话最大 19 MB）：38 步任务里占非模型时间约 19%；
  2. headless 入口只为确认会话存在就生成整份公开会话视图；轮末又重复生成一次消息列表：约 15%；
  3. 记录展示类读取每次解析全部负载，包括占日志 47% 字节的 `turn_state` 检查点；
  4. 每轮构建约 5 次 `OperationRegistry`（约 6–12%）。
- JSON 编解码与哈希已由 CPython 的 C 实现完成；没有 CPU 密集的内核值得搬到 Rust。所以**没有做 Rust 改写**（按“只改写剖析显示重要的部分”）。

## 2. 改动

| 改动 | 说明 |
|---|---|
| 会话日志原地追加 | 非空日志用 `O_APPEND` 式写一行 + fsync；空日志仍走原替换路径（权限 0600 不变）。读取方忽略未写完的末行；下次追加删掉残行（或给完整但无换行的末行补换行）。已提交的条目仍然恰好是完整行，WAL 意图、元数据顺序不变。 |
| 只按需解析负载 | `_messages`、`_context_fingerprint`、`find_binding`、`ensure_standing_message`、`_last_person_text`、`_tell_agent_finished_outcomes` 只读某几类条目，改用已有的 `payload_entry_types`。 |
| 去掉重复投影 | `require_agent_session` 只做原来的检查和报错；轮末复用刚生成的消息列表。 |
| 每轮一个注册表 | 协议文本与 orchestrator 共用同一个 `OperationRegistry`。 |

顺带发现并修复两个缺陷，各配了机械检查：

- **协议文本随进程哈希种子变化**：`p7_pack_registry.py` 遍历 frozenset，每个新进程的步骤词表顺序都不同，跨会话的提示缓存前缀因此失效。现已排序；`tests/test_agent_prompt_hash_seed_stability.py` 用三个种子比对。
- **会话日志用 `str.splitlines()` 切行**：U+2028/U+2029/U+0085 在 JSON 里不转义，消息里出现一个就会让整个会话读不出来。会话日志已改为按 `\n` 切；`tests/test_jsonl_line_splitting_guard.py`（AST 规则）禁止新增这种写法，并列出现存的 21 处读取器。

## 3. 前后对比（交替 A/B）

做法：每次运行都是新进程，导入 `git archive` 导出的源码树（脚本会核对模块来源）。每个任务先做 5 次基线标定，再做 5 对严格交替的 before/after。
机器上同时有其他会话的进程（load1 中位 3.6，最高 6.6，记录在每条运行里）。标定离散度用 MAD/中位数衡量为 0.3–2.2%（极差为 3.5–7.1%）。

| 任务（步/轮） | 每步非模型中位 ms：前 → 后（5 次范围） | 每轮非模型合计 s：前 → 后 | 成对比值中位（合计） | RSS MiB |
|---|---|---|---|---|
| qrdata.403（17/9） | 132.9 (129–134) → **84.0** (80–94) | 1.901 → **1.479** | 0.778 | 417 → 418 |
| qrdata.381（38/12） | 64.8 (62–77) → **45.7** (43–47) | 3.292 → **2.514** | 0.722 | 566 → 563 |
| qrdata.106（9/5） | 76.9 (73–85) → **66.9** (64–73) | 0.651 → **0.573** | 0.881 | 349 → 348 |

合并所有步：p90 为 192→160 ms（403）、169→130 ms（381）、132→127 ms（106）。五对中每一对都是 after 更快。

口径说明：回放时流式响应会瞬间到达，逐块处理被算作非模型时间；真实运行里这部分与等待模型重叠，所以回放数字偏保守。

## 4. 等价性

在 403、106 上，旧码（只加排序修复，因为该修复有意改变顺序）与新码比较：规范化 ID 和时间戳后，会话日志、每个发给模型的请求体、最终回答完全一致。新码与新码之间也为 0 差异。
在 381 上，仅数字核对提示里的“最接近的结果值”不同。原因是数字核对把随机十六进制提案指纹里的数字（`27600adca2…` → 2760）当成证据，这是逐次运行随机的，不是本次改动引起的（见 §5）。
测试：会话、日志索引、追加、恢复相关测试全部通过。接近全量的一次运行结果为 10,980 通过、14 失败；已查明的失败来自环境：worktree 缺 `.venv` 链接（已用 `link-shared-deps.sh` 补上，p7 矩阵测试随后通过）和缺 `local/perf-inputs`。
`test_real_1m_statistics_http_cancel_drains_before_terminal_artifacts` 在未改动的 `33f60afb` 上同样失败。**补链接后的全量重跑尚未完成。**

## 2026-11-04：真实持久化与重启读取修复

U+2028/U+2029/U+0085均由现有writer原样写入合法JSON字符串；旧reader却当作行边界。用真实PlanStore保存/重开、prepared提案幂等复用、事件重放和带校验链的provider录制复现15项失败；修复后相关82项通过。共享reader保留LF/CRLF/CR、合法无终止末行及原损坏尾行规则，prepared admission和recording的唯一键、checksum、序号与完成门未放宽。没有改写任何旧项目或tape。

独立审查发现首版回放修复会拒绝旧裸CR分隔，并由`json.loads(bytes)`意外接受UTF16/32；新增实际签名录制的5红/1绿复现，改为严格UTF8解码、仅ASCII CR/LF归一化后，相关66项通过。此前集中标准2809pass/0fail/3skip、36warnings（172.61s）；最后仅复查回放delta，没有把这两个调用拼成一次整版全绿。证据在`local/test-evidence/agent-unicode-jsonl-20261104/`及`local/test-evidence/native-review-batch-20261104/standard.log`。未重跑性能、真实Provider、全量或M5；旧回放性能仍为有干扰的观测，不因本次功能回归升级。
