## Implemented

- Host authority is admitted only from a deployment-owned pathname Unix endpoint or a supervisor-passed FD. Missing external configuration fails closed with `HOST_AUTHORITY_REQUIRED`.
- The deployment configuration is loaded from a secured external file. Its endpoint path, device, inode, peer UID/PID, scope/session binding, and handshake secret are checked.
- The endpoint must be an external process. OS peer credentials, exact pathname, non-symlink path components, secure parent ownership/mode, socket ownership, device, and inode are verified. Endpoint replacement invalidates an existing handle.
- The handshake binds the challenge, endpoint identity, owner PID, session, and deployment secret. Caller-selected scope, peer, fake handshake, arbitrary private ticket, socketpair, same-process fake endpoint, and wrong identity values fail closed.
- `HostAuthorityServerV1` is retained only as a compatibility symbol; its public constructor cannot create authority. A raw caller-created socket cannot be converted into a host handle.
- Authority config, host handles, scope bindings, capability receipts, and capability selections reject copy/deepcopy/pickle/JSON reconstruction, `object.__new__` forgery, malformed proofs, and forked-process reuse.
- Exact admission registries prevent equal-looking or reconstructed proof objects from being accepted by scope and capability consumers.
- Existing effect, risk, port, natural-language, replay, cross-process reservation, and root FD/inode constraints remain covered by the focused suite.
