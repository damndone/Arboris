# Workbench v1.8.4 — Agent Model Composition

v1.8.4 把已有的服务端 OLS 项词表接进 Notebook Agent 生命周期：用户可以用
自然语言要求一个带**声明式分类项**和**声明式多项式项**的模型，审阅生成的
typed workflow，确认后执行，并把完成结果作为有界证据读回。

同时新增三个服务端定义的 post-estimation 结果操作，用于通用地解释这类模型，
并把它们的结果投影到 Run、Table、Agent 与 Report 四个消费面。

这不是允许 Agent 写公式、跑任意代码或读原始数据的开关。所有 workflow 仍然是
typed、服务端校验，并受既有 Proposal/Risk 确认生命周期约束。

## 本版本交付

- **声明式模型项。** `categorical` 与 `polynomials` 进入已发布的 workflow
  词表。分类列展开为指示变量并显式丢弃参照类；多项式次数限制在 2–4。
  校验器与执行器共用 `model_terms.py` 一个来源，二者不可能对同一份 spec
  给出不同解释。非法选择器 fail-closed，不做静默降级。
- **派生列复用。** 当数据集中已存在预先算好的指示列或幂列时，只有在证明它
  与本次请求的项**逐值相同（含缺失值掩码相同）**之后才复用，并保持原列不被
  改写；仅仅同名的列仍然被拒绝。此前这类数据集会在拟合前直接失败。
- **三个 post-estimation 结果操作。** `model.joint_f_test`（对声明的项组做
  联合检验）、`model.quadratic_stationary_point`（声明二次项的驻点，并报告
  该点是否落在观测范围内）、`model.white_test`（怀特异方差检验，辅助回归
  在拟合前丢弃共线交叉项）。三者都从已完成的模型分支推导，带 artifact
  provenance，校验各自的语义前置条件，并拒绝不受支持的请求。
- **post-estimation 结果的四面投影。** 同一份结果现在出现在 Run detail、
  Table 视图、Agent 操作面板，以及 Report 的可引用事实表中；此前它们只存在
  于产物文件里，用户在任何界面上都读不到。
- **分支协方差保真。** 分支 refit 现在按声明的估计量（unadjusted / robust
  HC1 / clustered）实际重拟合，并把该估计量写进分支 spec。此前 refit 会读回
  未调整的原始拟合，导致同一个 workflow 里的 robust 分支与 unadjusted 分支
  实际同构，且 post-estimation 统计量在与 provenance 不符的协方差下计算。
- **Notebook 规划预算可见。** 规划路由强制并发布 180 秒预算，界面按该预算
  显示已用时间，超时后显式标记 overdue。计时锚定在**这次规划尝试**上，
  组件重挂不会把计数清零。
- **规划被拒时给出下一步。** 当提议的 run-source 不在 active head 血缘内，
  规划器不再只返回拒绝：存在合格目标时给出确切的 rerun 前置条件，不存在时
  引导到 `model.genesis`。
- **Action 模式措辞。** Action 模式只产出一份按用户规格准备的 Draft，界面
  不再称其为 "Recommended"——那会声称一个 Agent 并未被要求做出的比较判断。
- **面板模型进入 Notebook 主路径。** `panel_ols` 的 entity/time 维度现在会随
  typed option 正确 materialize；缺失、错类型或不属于数据集的维度一律拒绝，
  不会静默退化为普通 OLS。
- **导航与失败状态忠实呈现。** 用户从 workflow 导航到其产出 run 时保留 Agent
  transcript；被输入护栏拦截的运行明确显示为 blocked，而不伪装成旧 lineage。

## 明确不宣称

- **计时器跨重挂的行为只有确定性测试证据**，没有真机复现。真机复现需要在
  一次真实规划调用进行中触发组件重挂，本版本未刻意构造。
- `notebook_load_not_found`（FMS incident `15b227d6`）**未复现也未修复**。
  已以 legacy persisted Notebook fixture 走加载和编译路径，仍不能复现，因此既不能
  声称已修，也不能声称不存在。
- `chain_agent_proposal_upstream_error`（FMS incident `ddcc9408`）仍保持 open：
  产品已验证将 upstream provider failure 与 tool-protocol failure 分开、fail-closed
  且有用户可见文案；但原 DeepSeek V4 Pro 的上游错误没有在本次重试中获得可归因的
  provider 复现证据。
- 下列能力不计为 v1.8.4 remediation：predictor-residual planner guidance
  (`64ec6d96`)、Global model-figure reader (`8ff5b466`)、covariance protocol
  boundary (`2c20a717`)、bounded workflow answer path (`33c552d6`) 与
  `depends_on` correction (`11a22915`) 已核实由 baseline `6607c2d` 提供；
  proposal-ready (`9aac0586`) 的“额外 provider turn 导致 max-steps”诊断未复现。
  这只是对历史关闭证据的订正，不是新增产品能力。协方差项是经测试的 model-input
  protocol boundary，不能被表述成对未来所有概率模型输出的绝对保证。
- full gate 的证据来自**宿主终端**（见「验证证据」）。任何在 agent 沙箱内产出的
  gate 数字都不可作为发布证据：`sandbox_apply` 会因嵌套被拒而制造出与产品无关的
  失败。**不得**通过 skip、xfail 或弱化 sandbox 让它「变绿」。
- 本版本不引入任意公式、代码执行、原始数据浏览、自动执行，也不使用与具体
  数据集或习题绑定的列名。
