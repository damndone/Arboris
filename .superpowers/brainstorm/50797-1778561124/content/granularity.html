节点粒度怎么定？

同一个 run，三种粒度的样子。这决定 AI 注释挂在哪、图大不大、visualization 怎么写。

A

粗粒度：阶段级（5-15 节点 / run）

节点 = 数据集快照（原始 / 清洗后 / 变换后 / 模型输出）。变量在节点 payload 里，不单独成节点。

优点

  • 简单
  • 易实现
  • 视觉清爽

缺点

  • 看不到变量级链路（你明确想要的）
  • AI 注释没法精确到列
B

细粒度：变量级（数十~数百节点 / run）

节点 = 单个变量/列在某个阶段的状态。能直接画出 income → log_income → 模型A 的 β 系数。

优点

  • 正是你描述的 Obsidian 风格
  • AI 能精确注释到"这一列"
  • 系数表能反查血缘

缺点

  • 大数据集变量多时图很乱
  • 需要折叠/分组机制
C

多分辨率：默认阶段级，可下钻到变量级

底层数据模型是变量级（B），但 UI 默认折叠成阶段视图（A），用户点节点能展开看里面的变量血缘。

优点

  • 同时有"看全局"和"看细节"
  • 对大数据集友好
  • 架构更通用，未来加 sub-graph 容易

缺点

  • 实现成本最高
  • UI 折叠/展开交互要细想
  • 底层仍是变量级，存储更大

我的倾向

C（多分辨率）。理由：(1) 你原话提到"元数据-清洗-处理"链路（阶段级）和"自变量因变量关系"（变量级）两种视图，C 同时满足；(2) 底层用 B 的数据模型保证扩展性，UI 用 A 的清爽默认；(3) AI 注释挂在变量节点上才有价值——AI 评论"income 这一列需要 winsorize"远比"清洗阶段需要注意"具体；(4) 折叠/分组机制是必要技能，迟早要做，趁切片打好。

顾虑：实现成本最高。如果 V1.4 时间预算紧，可以先实现 B 的数据模型 + A 的 UI（即"折叠永远开着"），把"展开"作为 V1.4.x 或 V1.5 的增量。
