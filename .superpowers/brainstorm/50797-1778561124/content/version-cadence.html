三种版本节奏

同样的目标，三种切片方式。横轴 = 时间，方块 = 一个版本。

A

直接 V1.4（当前文档的方案）

一次到位，把图模型 + 存储 + API + 前端 + 顺手重构全塞进 V1.4。

优点

  • 到目标最快（理论上）
  • 只做一次 review

缺点

  • 任一模块出问题整体延期
  • 违反你们既有的小步节奏
  • 三审压力大
B

V1.3.x 全面深化，再做 V1.4

先把 V1.3 系列所有"应该深化"的点都做完（Trust Console / Report 顶部 trust / secondary model / i18n registry），再开始图谱。

优点

  • 每步都小
  • V1.3 系列彻底收尾
  • V1.4 时基础非常干净

缺点

  • 到图谱时间最长（~6-8 周）
  • 部分 V1.3.x polish 之后还会被 V1.4 再改
  • 容易"分析瘫痪"
C

混合：V1.3.2 只做基础重构 → V1.4 纯新功能

V1.3.2 把 V1.4 必会触碰的重构（diagnostic_preview 拆分 + frontend contract validator + 统一 term parser）单独做完，纯重构无新行为。V1.4 然后只做图谱，scope 干净。Trust Console / report polish / secondary model UI 等留作 V1.4.x 或 V1.5 后续。

优点

  • V1.3.2 风险最低（纯重构）
  • V1.4 scope 干净，三审压力小
  • 到图谱时间合理（~3-4 周）
  • 不强迫一次性深化所有 polish

缺点

  • 多一个 review 周期（V1.3.2）
  • Trust Console polish 还要等

我现在的倾向

C（混合）。理由：

  • 你的疑虑是对的——A 跨度确实太大，单点风险集中
  • 但 B 把所有 V1.3.x polish 都做完是过度——其中 Trust Console / Secondary model UI 等会被 V1.4 的图谱重新塑形（变量节点能直接挂 risk badge / 二级模型成为一个分支），现在 polish 一遍 V1.4 时还要再调
  • C 把"V1.4 必会碰且纯重构"的部分（diagnostic_preview 拆分、contract validator、term parser）抽出来做 V1.3.2，scope 极小风险极低
  • V1.4 之后再做 polish（Trust Console / Report top summary）就能直接基于图谱节点设计，效果更好

V1.3.2 具体范围：(1) 拆 diagnostic_preview 为 4 子模块；(2) 新增 frontend `validateDiagnosticPreview()` runtime validator；(3) 统一后端 patsy/statsmodels term parser，前端只消费 `display_term` / `reference_level` / `source_id`。三项都是纯重构 + 测试，不引入新功能。
