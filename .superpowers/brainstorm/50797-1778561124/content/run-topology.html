分叉怎么组织：Run 内部分支 vs 多个 Run

这决定 API、存储、process tracker 形态，以及未来 AI 能否在一个视图里对比分支。

A

每个分叉 = 新 Run（parent 指针 + fork_node）

从 log_income 分叉就生成 run_43，记录 parent=run_42, fork_at=log_income。Run 模型几乎不动。

优点

  • 现有 run 模型几乎不改
  • 每个 run 单结果语义清晰
  • API 兼容性好

缺点

  • 分叉多了 run 列表爆炸
  • 对比分支要并排打开两个 run
  • AI 跨分支分析要多次查询
B

一个 Run 内部树状分支（Run 模型升级为图）

run_42 内部就是一棵分支树。所有分叉、回滚的中间产物都在同一个 run 里。Run 列表数量保持稳定。

优点

  • 所有分支一图见
  • 分叉成本低（共享上游）
  • AI 对比分支天然
  • process tracker = 分支图

缺点

  • Run 模型大改
  • API 需要"分支地址"概念
  • 现有 run-detail UI 要重做
C

混合：内部轻量分支 + "提升为新 Run" 按钮

默认像 B，run 内部支持快速试错分支。当某个分支证明有价值，可以"promote"成独立 run（变成 A 的形态），便于分享、归档、报告。

优点

  • 试错便宜（B 的好处）
  • 正式产出干净（A 的好处）
  • 未来"分享/导出"清晰

缺点

  • 两个概念要学：分支 vs run
  • 实现成本最高
  • promote 语义要细想

我的倾向

B，但分阶段实现：

  • V1.4：实现 B 的数据模型（run 内部支持分支树）+ 简单 UI（先只允许"线性 + 一次回滚 + 一次分叉"，不做无限嵌套分支）
  • V1.5+：放开任意分叉、增加分支命名、增加跨分支 diff 视图
  • 更晚：如果 promote 需求真的出现，再加 C 的语义（不预先做）

为什么不选 A：你明确想要"流程 tracker 自己查看 + 回滚历史"。如果分叉 = 新 run，回滚就要在 run 列表里跳，体验割裂。AI 对比分支也要多次跨 run 查询，未来重做的概率极高。

为什么不选 C：promote 在没有真实场景需求前是过度设计。等用户真的喊"我想分享某个分支"再加。
